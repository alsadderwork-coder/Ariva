# Testing strategy

How Ariva is tested, from pure formula tests to field validation, and how to run each layer locally and in CI. One entry point runs the gates: `node scripts/verify.mjs <scope>`, which writes per-step results to `.verify/last.json`.

## 2. Unit tests

- Every formula in `docs/domain/formulas.md` lives as a pure function in Ariva.Core (or the Python worker for v1 forecasting) with its listed test cases, for example F8: 29 queuing, 6 desks, cycle 1.5 minutes gives a nowcast of 7.5 minutes; F17: 10 breaches, 2 excluded, 1 held, allowance 6, rate 350 gives a penalty of 350.
- Floating-point rule: never call a ceiling on a floating ratio directly (`(24 - 0.3) / (4.25 - 0.3)` evaluates to 5.999999999999999); use `Math.Ceiling(Math.Round(x, 9))` or `decimal`, and compare in tests with a tolerance of 1e-9.
- Geometry gets property tests (line crossing, F4): touch-and-return is not a crossing; a sample pair outside the segment is not a crossing.
- Naming, as in the existing tests: `Method_Should_Result_When_Condition`.
- A test that fails only under load is not a flake (ARV-156): find the race or the bound and fix it; never retry, skip or widen a timeout to hide it. In-process hosts (`ArivaHosts`) hold each host's start until `WebApplicationFactory` listens for it (`GatedHostLifetime`), so a host that refuses its configuration always fails with its own exception, never with a disposed service provider. A regular expression's timeout is wall-clock time, so a rule that must not refuse a valid value on a loaded machine is `RegexOptions.NonBacktracking` without a timeout (CWE-1333 in `docs/security/cwe-controls.md`).
- A test fixture removes what it writes (ARV-164): a folder from `Directory.CreateTempSubdirectory` or the temporary folder goes with the test or the host that made it (`ArivaHosts` deletes each host's key folder when it is disposed, the MQTT tests' certificate folders go with their host, the Data Protection tests' certificate folders with the test), because a run of the unit suite starts hundreds of hosts and the leftovers filled the disk under the integration suite. A test that needs an outside service checks it first, once and bounded, and fails naming it: the AppHost model tests ping the Docker daemon (10 s) instead of waiting for the container runtime for ever, and each test that builds the model has a 2 minute timeout for a runtime the ping cannot check (an ssh:// DOCKER_HOST). A test that measures a bound measures only what the bound covers: warm a query's first translation and the first connection before a stall, as a host that has served a request has, then clear the pool so the stalled call opens its connection through the stall (`DatabaseStallTests`). The unit gate and CI's unit step run the test executable itself (Microsoft Testing Platform, in process; CI since ARV-164a), because under `dotnet test` the VSTest adapter reads the runner's messages from standard output, which the Pact verifier's native report and display names with raw control characters can break, and drops a line it cannot read without a failure, so a failing test could pass unnoticed. A count guard then checks the run against the cases the executable lists (`node scripts/test-count-guard.mjs --dll <test dll> --trx <file>`, ARV-164a, in the unit gate and CI; the comparison in `scripts/test-counts.mjs`): the TRX must be whole (its summary and end there, its stated total its number of results), and method by method it must hold at least as many results as the listing has cases, since a theory whose rows are not enumerated at discovery is listed once and runs as many rows (7,212 cases listed against 7,869 results on 2026-10-25); a method with fewer results fails the gate, so does a result for a method the listing does not name. Such a theory's rows are held by its project's row file since ARV-251 (the next point). What it still cannot see: a loss hidden by another method's extra rows when two tests share the name before their parenthesis, which only a display name of its own could make (`TheoryRowsTests` refuses one), and a theory listed once and left out of its row file whose every run, from its first, lost all but one of its rows. The integration suite runs the same way since ARV-164b (section 3).
- A theory whose data xUnit cannot serialize (a delegate, an entity, a settings object) is listed once and runs all its rows under that one case, so the count guard holds it to the rows its project's row file gives it (ARV-251): `theory-rows.json` beside the project file (`Ariva.UnitTests`, `Ariva.IntegrationTests`), copied beside the test executable, names each such theory with its number of rows. A run with fewer results than the file says (a row lost while another ran), with more (a row added without the file), an entry for a theory listed by its rows (its data made serializable), any method that ran more rows than it was listed with and has no entry, and on a whole run an entry for a method not listed (renamed or removed) all fail the guard. Each project's `TheoryRowsTests` (one source, `Ariva.UnitTests/Setup/TheoryRows.cs`, linked into the integration project) keeps the file current from the theories' own `InlineData`, `MemberData` and `ClassData` and refuses a method named twice and a test or data row under a display name of its own, so a change to a theory's rows fails that project's run until its entry is changed with it. A theory with serializable data needs no entry: xUnit lists its rows one by one.

Run:

```bash
node scripts/verify.mjs unit
# or the executable itself (the counts of dotnet test are not reliable, ARV-164), then the guard
dotnet Platform/Backplane/Ariva.UnitTests/bin/Debug/net10.0/Ariva.UnitTests.dll --report-xunit-trx --report-xunit-trx-filename unit-tests.trx --results-directory .verify
node scripts/test-count-guard.mjs --dll Platform/Backplane/Ariva.UnitTests/bin/Debug/net10.0/Ariva.UnitTests.dll --trx .verify/unit-tests.trx
```

### Mutation testing (Stryker.NET)

Agents write many tests; mutation testing checks that they would catch a real fault. Stryker.NET changes the engine code one small fault at a time (a `<` for a `<=`, a `+` for a `-`, a removed statement) and runs the unit tests that exercise it; a mutant the tests do not notice "survives".

- Scope (`Platform/Backplane/Ariva.UnitTests/stryker-config.json`): in Ariva.Core, `Queueing/QueueStateEngine.cs`, `QueueBins.cs`, `ZoneProcessor.cs`, `WaitStatistics.cs` (realised wait attribution), `Nowcast.cs`, `Border/EgateCoupling.cs`, `Flights/ArrivalWave.cs`, since ARV-104e the F18 comparison engine `Validation/Comparison/*.cs` and, since ARV-150, the availability rule `Availability/AvailabilityRule.cs`, and, since ARV-149, the desk state engine `Desks/DeskStateEngine.cs` with its state rule `Desks/DeskState.cs` (F10, the transaction rhythm's rows 5a to 5f among them) and the lane contexts `Desks/DeskRhythm.cs`, since ARV-149a with the desk engine's snapshot checks `Desks/DeskStateEngine.Snapshot.cs`; Stryker records which unit tests cover each mutant and runs only those against it. Other snapshot persistence and guard clauses are left out. A story that adds an engine can run Stryker on its own files only: from `Platform/Backplane/Ariva.UnitTests`, `dotnet tool run dotnet-stryker -- --mutate "**/Validation/Comparison/*.cs" --output <folder>` (the command line's `--mutate` replaces the configuration's list; everything else, thresholds included, comes from `stryker-config.json`).
- Thresholds: the run fails below 70 percent of mutants killed; 80 is the target. Surviving mutants are triaged in `backlog/progress.md`: a missing test is added, an equivalent mutant (a change no input can observe) is recorded as such.
- When: weekly (Saturday night) and on demand (Actions, mutation, Run workflow); the HTML and JSON reports are the `mutation-report` artifact. Locally: `node scripts/verify.mjs mutation` (one to three hours, mostly the queue engine; the report goes to `.verify/stryker`). It runs in its own worktree of the current commit (uncommitted changes are not mutated) under its own lock, because Stryker replaces Ariva.Core in the unit tests' output while it runs; builds and story gates may use the main checkout meanwhile. `verify.mjs` turns the test platform's telemetry off: refused by a network proxy, it made Stryker's initial test run take 80 minutes instead of about 15 (2026-10-09).
- Runner: Stryker's Microsoft Testing Platform runner (`test-runner: mtp`; the unit test executable has `UseMicrosoftTestingPlatformRunner`, while `dotnet test` still runs through VSTest). Under VSTest Stryker could neither activate mutants nor capture coverage in the xUnit v3 test process, so every mutant "survived". The AMAN pact tests skip themselves in a Stryker run: the Pact FFI aborts Stryker's test server, and they test no engine. Stryker's results come over the platform's protocol, not standard output, so it cannot drop a line as `dotnet test` can; still, the mutation run fails when Stryker reports fewer tests found than the worktree's unit test build lists (`mutation-run.mjs --tests`, ARV-164a), since its mutants would then be measured against part of the suite (it found all 7,212 on 2026-10-25).
- Tool: `dotnet-stryker` is pinned in its own manifest, `Platform/Backplane/Ariva.UnitTests/.config/dotnet-tools.json` (restore it from that folder). With SDK 10.0.4xx, restoring it from the same manifest as `aspire.cli` fails ("not contained in the package"), which failed every job that restores the root tools, the E2E run's smtp4dev included.
- Compile errors and safe mode: when a mutant does not compile and Stryker cannot tell which one it was, it removes every mutant of the method and counts them as compile errors (its safe mode, "Safe Mode! Stryker will remove all mutations in ..."), so the method is not measured and the score does not show the gap. The first checkpoint (2026-10-08) found 14 methods in safe mode; ARV-069a restructured them. The rule for the engines: **no `out` variable or pattern variable declared inside a condition.** `if (code is null || !_desks.TryGetValue(code, out var desk))`, `if (x is not { } v || ...)` and `while (list.First is { } first && ...)` become a declaration in its own statement (`Desk desk = null;` before the condition, `var v = x; if (v is null ...)`, `HasValue` and `Value`, or a `for` loop over a local), because a mutant that short-circuits the condition leaves the variable unassigned (CS0165). Two other shapes did the same: a concatenation of interpolated strings passed to `string.Create` (CS1620; pass one interpolated string) and a nested `HashCode.Combine` (CS0411; use typed locals).
- Gate: `verify.mjs mutation` (and the checkpoint's mutation step) runs Stryker through `scripts/mutation-run.mjs`, which prints Stryker's output, keeps it in `.verify/mutation.log` and fails the step when any method is in safe mode, no final score was printed (even when Stryker exits zero) or Stryker found fewer tests than the unit tests list (`--tests`). `node scripts/mutation-run.mjs --check <log> [--tests <dll>]` checks an earlier log; `--self-test` proves the check.

## 3. Integration tests (Testcontainers)

Containers: `timescale/timescaledb-ha` (PostgreSQL 17 with TimescaleDB), Kafka, Redis. Shared fixtures (container lifetime, connection strings, script runner) live in `Ariva.IntegrationTests/Setup`; every Kafka container is built with `KafkaContainers.Builder()`, whose start command replaces Testcontainers.Kafka's (that one can execute its start script while the copy still holds it open, "Text file busy", ARV-156). Typical tests: the Timescale script runner applies all scripts and records them; a checksum change stops startup; COPY writers and upserts are idempotent by (zone, bin start, revision); a consumer replays after a rebalance without double counting.

Failure injection (ARV-072): `Faults/FaultsFixture` starts PostgreSQL, Redis and Kafka on their own Docker network behind one Toxiproxy (`ghcr.io/shopify/toxiproxy:2.12.0`, pinned by digest like the suite's other images, ARV-096; a machine that cannot pull ghcr.io's blobs, such as the cloud agent sessions, sets `ARIVA_TOXIPROXY_TAG_ONLY=true` to take a local build of the same release by its tag, which the fixture refuses where `GITHUB_ACTIONS` or `TF_BUILD` is true, `ToxiproxyImageTests`; Testcontainers' own Ryuk image is still taken by its tag, ARV-214), driven through its HTTP API with an Apizr client; Kafka advertises the proxy's address, so broker connections after bootstrap go through it too. Tests cut a dependency off (proxy disabled), stall it (Toxiproxy's `timeout` toxic, nothing comes back) and restore it while the code under test keeps running. The checks are the indicators operators and screens rely on: readiness, 503 with Retry-After (`DependencyOutage`), the publication time that turns screens and boards stale, and the stored rows (outbox, sensing archive). Each wait polls for the condition the test asserts, never for a fixed time or a status that may not come (during a broker outage MassTransit reports the bus `Degraded`, not `Unhealthy`, so `/health/readiness` keeps answering 200), and the broker test's waits share one budget inside the fact's timeout, so a step that is too slow fails with its name and the time each earlier step took (ARV-156). About four minutes; they run with the rest of the integration suite.

Backup and restore (ARV-126): `Operations/BackupRestoreTests` starts two TimescaleDB servers as the chart starts one (`Operations/ChartDatabase`: the chart's image, initdb arguments and init script, uid 1000, read-only root filesystem) and runs `scripts/ops/ariva-db.sh` in them with the container's exec (an argument array, as an operator runs it in the pod). It backs up a seeded deployment, checks the dump and its plain SQL for every secret, restores it into the other server, runs the migration job and starts Ariva.Api.Main and Ariva.Api.Integration on the restored database as a cluster runs them (`Operations/DeployedHost`: k8s-dev, the runtime login, the schema check on, the Data Protection certificate from PEM files; Kafka and Redis off). The steps are in wiki 04 section 10.6. `Ariva.UnitTests/Operations/OpsScriptTests` keeps the script in step with the code (the compacted topics, the roles the scripts create) and free of shell strings, and `node scripts/ops/ariva-ops.mjs --self-test` checks the operator wrapper in the `security` scope: its validation and argument arrays, and the signed path end to end with stand-ins for kubectl and age and the real ssh-keygen (every refusal before any kubectl step, only the verified private copy decrypted). The restore test also plants what a forged dump could leave and checks that `ariva-db.sh check` fails on it. Since ARV-262 it also holds the pins `check` compares with (`ARIVA_SCHEMA`, `ARIVA_EXTENSION_MEMBERS`, `ARIVA_SYSTEM_FUNCTIONS`) equal to `ariva-db.sh schema` on the source right after its migration, and its message holds the lines to pin; a new script moves `ARIVA_SCHEMA_AT` and the list (`OpsScriptTests` fails until it does), and a new database image moves the members and system functions digests.

TimescaleDB extension update (ARV-236): `Operations/ExtensionUpdateTests` starts one server as the chart does, puts both extensions back to the newest older versions the image can update from (as a database created under the previous image has them; built with the new image's own install scripts, not a volume of the previous image), and runs the migration job on them. `ariva-db.sh check` then fails on the old versions. Before any statement as the superuser, `update-extensions` refuses a function the migration login planted under a system function's name and a session of the runtime login, changing nothing. With only another login's session holding the old library, the update moves both extensions, keeps every hypertable, chunk, row and TimescaleDB job, and that session is closed at its next statement (FATAL) while a new one works; `check` passes, a second run changes nothing, and an option is refused. It reads the versions from the image, so it holds for the next TimescaleDB line too. `OpsScriptTests` holds the four statements the superuser may run (the restore's two TimescaleDB steps and the two updates), each in a session of its own with no value in it.

Runner (ARV-164b): the integration gate and CI run the test executable itself (`UseMicrosoftTestingPlatformRunner`, in process) and then the count guard of section 2 (`scripts/test-count-guard.mjs`), as for the unit suite: under `dotnet test` the hosts' console logs share the xUnit runner's message stream, from which the VSTest adapter drops a line it cannot read, so a case could be left out of a run unnoticed. The story gate's `--integration` filter keeps dotnet test's form, `FullyQualifiedName~A|FullyQualifiedName~B` and nothing else, and runs as `--filter-method *A* --filter-method *B*` (a method whose fully qualified name holds A or B), with the guard listing the same selection.

Run (needs Docker):

```bash
node scripts/verify.mjs integration
# or the executable itself, then the guard (a filter goes to both)
dotnet Platform/Backplane/Ariva.IntegrationTests/bin/Debug/net10.0/Ariva.IntegrationTests.dll --report-xunit-trx --report-xunit-trx-filename integration-tests.trx --results-directory .verify --filter-method "*CsvImports*"
node scripts/test-count-guard.mjs --dll Platform/Backplane/Ariva.IntegrationTests/bin/Debug/net10.0/Ariva.IntegrationTests.dll --trx .verify/integration-tests.trx -- --filter-method "*CsvImports*"
```

## 4. API end-to-end and functional tests

`Platform/Testing/Ariva.E2E` will hold Playwright tests for both the APIs and the web app, against a running stack with the simulator. Coverage required by the design: the integration token exchange, TOTP replay rejection, scope and site enforcement, idempotency, every Integration API endpoint, and the security behaviour tests in `tests/security` (oversized body returns 413, deep JSON returns 400, injection payloads never return 500, script payloads never execute, CSV formula injection neutralised, refresh-token reuse revokes the family, the session id changes at sign-in, critical endpoints return 401 without a token and 403 without recent MFA).

Run:

```bash
node scripts/verify.mjs e2e
```

The suites never run against a deployed environment (TC-56, answered as Proposed by ARV-128): they write, attack and load, so `playwright.config.ts` refuses to load when a target is not on this machine (`localhost`, `127.0.0.0/8`, `[::1]`). A deployed environment, at go-live and after each release, gets the read-only release smoke suite: the specs in `tests/smoke`, run with `npm run test:smoke` (`playwright.smoke.config.ts`, no host started, every address and credential from `ARIVA_SMOKE_*` variables; wiki 04 section 8.1). Each smoke test declares `@read`, `@write`, `@attack` or `@load`; against a non-local target only `@read` tests may exist (anything else stops the run before a test starts), the smoke client and the browser send reads and the session calls only, traces, screenshots and videos are off, and the run fails when a credential reaches its report or output. Never run the suites with a port-forward or tunnel open on the hosts' ports (51001 to 51005, 51011, 51020): global setup checks, before it writes anything, that every host answers as a vm-local host of this run (a CORS preflight from the vm-local web origin, this run's simulator key) and stops otherwise (`tests/support/local-hosts.ts`). Never point the database, Redis or Kafka of an E2E run (`Database__*`, `ARIVA_E2E_*` or the hosts' connection settings) at a tunnel or port-forward to a deployed store either: the hosts the run starts are genuinely vm-local, so the check above passes, and they would run SchemaUpdate and seed the development accounts (known passwords) into whatever store they reach. Since ARV-180 a deployed database records its environment (the migration job writes it), and a vm-local host refuses one that names another before it migrates or seeds anything (wiki 04, `Database:AllowSchemaUpdate`); a database whose last migration predates ARV-180 has no record yet, so the rule stands. Redis and Kafka have no such record. A local database that a cluster's migration job once recorded (a restored copy of a deployed one, say) stops every vm-local host the same way: drop it and let the hosts create it again (the E2E run's own database is reset at every run), or, only when it is certainly a local database, set its record back with the migration login (`UPDATE public.database_environment SET environment = 'vm-local'`). A vm-local Ariva.Api.Main reads its database at start (the check) whenever it migrates or seeds, the demo topology included: without a database, start it with `Seed__DemoTopology=false` as well as `Database__AllowSchemaUpdate=false` (the E2E configuration does so when `ARIVA_E2E_SCHEMA_UPDATE` is not set). The same specs are the `smoke` project of every ordinary E2E run, against the local stack (global setup provisions the smoke site `E2SM`, a test device and a display); `tests/api/smoke-guard.spec.ts` proves the guard with probe files and `tests/api/smoke-config.spec.ts` runs the deployed config against the local stack.

Against Ariva.AppHost (ARV-066): `node scripts/e2e-apphost.mjs [playwright arguments]` runs the same suite against hosts the AppHost starts, configured exactly as Playwright would start them (the config writes each host's variables when `ARIVA_E2E_WRITE_HOST_ENV` names a file; the AppHost applies them with `AppHost:HostEnvironmentFile`), on throwaway containers. It is for local runs and agents; CI keeps compose. The integration tests use an existing PostgreSQL instead of their own container when `ARIVA_IT_POSTGRES` holds a superuser connection string (they recreate only their `ariva_it` and `it_*` databases there).

Load run (ARV-071): `tests/api/load.spec.ts` provisions a site of its own (a published queue zone, 41 canonical sensors, the displays, one screen sign-in per five screens, since the hub holds at most 8 connections per session) and runs `Platform/Testing/Ariva.LoadTests` (built with the backend) with the credentials in its environment. Every E2E run does the smoke size (40 screens, 10 displays, 15 seconds at 0.2 pushes a second per sensor, the device limit lowered to 120 a minute for the flood); `ARIVA_LOAD_MODE=full npx playwright test tests/api/load.spec.ts` does the lab measurement (150 screens, 50 displays, 120 seconds at 1 push a second, the production device limit). The harness writes `.verify/load/<mode>/load-report.json` and `.md` (p50, p95, p99, throughput, CPU and memory per host from /proc) and exits 1 on any failed request, a limit that did not answer 413 or 429 with Retry-After, a screen that could not join or was dropped, under 95 percent of snapshots delivered, or a display board that did not answer 200. The harness is our own rather than NBomber, whose licence is paid for organisational use (decision log). `functional/live-under-load.spec.ts` watches the live screen in a browser while 40 other hub connections share the zone and snapshots arrive five times a second.

Pilot hall run (ARV-124a): `tests/load/pilot-load.spec.ts`, its own Playwright project (`--project=pilot-load` with `ARIVA_E2E_PILOT_LOAD=1`, which starts Ariva.Api.Stream and creates new topics with 6 partitions as production does), or `node scripts/verify.mjs pilot-load` on fresh services. The spec builds the pilot site through the admin API (an arrivals hall with an immigration checkpoint, five queue zones with lanes and lines, 20 desks and 6 e-gates mapped to AMAN's codes, 100 calibrated T3 sensors and a flood device, 10 displays, 10 screen sessions) and lets AUH-TA's 84 seeded sensors play their evening beside it; the harness in `ARIVA_LOAD_MODE=pilot` then produces AMAN's feed to Kafka, holds 50 screens on every zone and polls 10 boards while the hall's 30 sensors push for 5 minutes (people who keep their track ids while they walk from the entry line to the exit line), all 100 for a minute (15,000 positions a second, with a flooding device and bodies over 256 KB), and the 30 again until Stream's lag, read from the broker every 2 seconds, is back to its steady value. It gives two verdicts: problems (any 5xx or transport error, a connection reset included, a push without exactly one outcome, an accepted push with events Ingest refused, a limit that did not answer 413 with `Connection: close` or 429 with Retry-After, a 429 for a measured device, a screen that could not join or got no snapshot of a zone from Stream, a board that did not answer 200), exit 1; and capacity (Stream stopped during the run, or its queue engine or archive did not catch up after the burst), exit 2. The flooding device must get exactly its limit accepted and every other push refused with 429 and Retry-After (`FloodRule` proves its table before each run); a connection reset is a problem there too. ARV-124a's runs saw a few, and one on a measured device: Ingest's 413 to an oversized push closed its connection without saying so, and the next push on that connection from the harness's shared pool was reset; since ARV-233 that 413 carries `Connection: close`. The spec's first test judges the problems and what the pipeline stored; its second, Stream's capacity and that it counted at least 98 percent of the crossings Ingest accepted on every zone, passes since ARV-230 (with ARV-232's connection bounds). Before reading the counts the spec waits until every zone's stored watermark is past the run's end (at most 5 minutes; Stream applies an event once the watermark, 90 seconds of lateness behind a clock up to a 60-second push interval behind, passes it, and stores a zone's minutes with its state). The harness sends a person's exit only once Ingest accepted that walk's entry: its walks run on the wall clock, so about everyone is already inside when the run starts, and an exit whose entry Ariva never received pairs by FIFO with someone another sensor holds (F5), whose own exit then counts as a duplicate (wiki 05). The spec then reads the stream state of every zone (`state_bytes`), the desk feed state, the outbox, the archive's rows, Redis and every staffing run's duration from Cronz's log, and attaches `pilot-report.md` and `pilot-measurements.json` (in `.verify/load/pilot`) for wiki 05's sizing notes.

Visual regression (ARV-075): `tests/visual/screens.spec.ts` compares 20 screenshots (sign-in, live operations, immigration and a validation campaign in English and Arabic, light and dark; the passenger display, bilingual, light and dark; since ARV-140 the split display, Arabic first on a landscape screen and English first on a portrait one, in one colour scheme since the board keeps its own palette) with the baselines in `tests/visual/__screenshots__`. Only one browser renders them: the official Playwright image pinned by digest in `scripts/visual-browser.mjs` (the same in CI and on a developer machine), reached as a Playwright server on 127.0.0.1:3123, while the tests and the hosts run as usual; Ariva.Web bundles its fonts (DM Sans, Noto Sans Arabic), so the image only supplies fallbacks. Run it on its own and before the other suites, on a fresh database (the demo seed): `node scripts/verify.mjs visual` (Docker needed), or `node scripts/visual-browser.mjs start` and `ARIVA_E2E_VISUAL_WS=ws://127.0.0.1:3123/ npx playwright test --project=visual`. The story gate runs it, before its E2E specs, whenever the change touches Ariva.Web, the visual suite, its support code or browser script, the E2E configuration or the Playwright pin (ARV-188, docs/harness/test-cadence.md); every `verify.mjs` visual step first runs `node scripts/visual-browser.mjs ensure`, which reuses the pinned image or pulls it and fails with the reason when Docker is not running or the pull is refused. The live values are planted (fixed snapshots for every DMO queue zone, and since ARV-120 one final health bin per queue zone and an occupied minute of the arrivals visitors' overflow band, as Ariva.Api.Stream writes them), the publication times in the zones table and the bin times of the data-quality panels are replaced by one fixed text (their digits change the widths around them), and what follows the clock or AMAN's feed (times, the arrival wave, the wait chart, alerts, desk states, desks and e-gates) is masked. A pixel counts as changed at a colour distance of 0.01, and a screen fails above 0.05 percent of its pixels: a five-unit change of the primary colour fails. The run removes what it planted. In CI the visual step runs first in the E2E job; a failure uploads `visual-diffs` (expected, actual and diff images) and the rest of the suite still runs. To accept a deliberate change, run the `ci` workflow by hand with `update-visual-baselines` ticked, download the `visual-baselines` artifact, review it and commit it, or run `node scripts/verify.mjs visual --update` locally (the same image gives the same pixels). When @playwright/test is upgraded, pin the matching image digest and regenerate.

Secrets in reports and artifacts (ARV-152, CWE-532): Playwright uses an expect's custom message as the step title even when the assertion passes, and the HTML report keeps every step title (a `fill` step's title holds the typed value, a request context's call or a navigation keeps its URL with the query as the step's subtitle, a relative navigation its fragment too, and the report keeps the source lines around each step as its snippet). A spec therefore never passes an answer's body or a secret as an expect message, a step title, an annotation, an attachment or console output: it checks a status with `expectStatus(answer, status, message?)` or `expectStatusIn(answer, statuses, message?)` from `tests/support/expect-status.ts`, which add the answer to the message only when the status is wrong, redacted (`scripts/secret-shapes.mjs`); it types a password, a TOTP code, a recovery code or a key with `fillSecret(field, value)` from `tests/support/web-auth.ts` (as `fillSignIn` does), which sets the value in the page so the step's title is "Evaluate" (an error context still lists input values: the artifact check is the backstop); it sends a token or a key in a query only through `call` (Node's fetch, no step); it navigates to a display with its key in the fragment of an absolute address only (`${webUrl}/display?...#key=...`), since Playwright keeps a relative address whole; it builds a made-up token or key at run time, never on a source line; and it asserts a value that may be a secret, such as an import's preview token, as a boolean (`expect(previewToken === null).toBe(true)`, `(token is null).Should().BeTrue()`, `expect(/shape/.test(token)).toBe(true)`), since a failing `toBeNull`, `toMatch`, `not.toContain`, `Should().Be()`, `Should().BeNull()`, `Should().NotContain()` or `Should().HaveCount()` prints the value it got and the one it expected (ARV-155 for the import tests, ARV-249 for every unit, integration and E2E test: `string.Equals(a, b, StringComparison.Ordinal).Should().BeTrue()`, `secret.Length.Should().Be(43)`, `text.Contains(secret, StringComparison.Ordinal).Should().BeFalse()`, `expect(text.includes(secret)).toBe(false)`). Three checks hold the rule: `node Platform/Testing/Ariva.E2E/scripts/expect-messages.mjs` (with `--self-test`) fails on a spec that puts an answer's body, a secret-named member or variable, or a variable holding either (one step removed included) where the report keeps it or where a failing matcher prints it (an expect's subject or its matcher's argument, ARV-249), types a secret with `fill` or `type`, puts a credential into a request URL's query or a relative navigation's fragment, or holds a secret's shape on a source line, in the security step of `verify.mjs` and in CI's security gate; `node scripts/security/secret-assertions.mjs` (with `--self-test`, ARV-249) fails on a C# assertion whose subject or argument is a secret by its name or by a read that yields one (a secret JSON member, a secret header, the Authorization header), with the same reach (a secret under another name, or a container asserted by shape, is held by review); and `node Platform/Testing/Ariva.E2E/scripts/artifact-secrets.mjs` (with `--self-test`) scans the report, the zip it embeds, the test output, its trace zips and error contexts (and in CI the run's log and the hosts' logs) for device and display credentials, integration client secrets, JWTs, bearer values, TOTP seeds and codes, recovery codes and temporary passwords by shape, and the run's own account passwords and TOTP seeds and its other secrets (the simulator, mock AMAN, ACRIS and Cronz keys and the validation reader's password, derived from the run's seed and given to the run) by exact value, after every Playwright run `verify.mjs` starts and in CI and the ZAP workflow before any report, test output or summary is uploaded, published or quoted (CI fails instead). CI masks the account seed and every value derived from it in its log and keeps no traces, since a trace records every header and typed value. Details in [test cadence](../docs/harness/test-cadence.md).

Alert emails (ARV-040): the run starts smtp4dev from the pinned local tool (`.config/dotnet-tools.json`, `dotnet tool restore`) on 127.0.0.1 (SMTP 25251, web API 5081, `ARIVA_E2E_SMTP_PORT` and `ARIVA_E2E_SMTP4DEV_URL` to change them), so neither a developer machine nor CI pulls an image; `alert-emails.spec.ts` reads what arrived through its API. The integration tests use a small SMTP server in the test process (`Setup/SmtpSink.cs`) that can refuse a recipient or drop the connection.

## 5. Replay and golden scenario tests

The reference scenario is the prototype's seeded day at the fictional DMO airport, whose topology and zone profile v12 the demo seed creates in dev and demo (ARV-019; layout in the [Administration guide](11-Administration-Guide.md)): seed 9303, simulated from 17:40 in the prototype, with scripted events:

| Time | Event | Expected behaviour |
|---|---|---|
| 18:05 | A visitor-heavy arrival wave | The arrivals Visitors nowcast passes 15 minutes and rule R-001 fires |
| 18:20 to 18:30 | Sensor S-17 over the arrivals hall offline | The Visitors zone is `Degraded`, the wait shows a band, a device alarm appears |
| 19:10 | Handler B's check-in island C after a shift change leaves 5 of 12 counters open | SLA breach for consecutive 15-minute bins, provisional first, final once the queue clears |

Same seed, same output: golden-file tests lock the behaviour so that changes to the engine show up as reviewed diffs. Created objects use their own sub-seeded random streams so they do not disturb the scripted events.

The engine is ported to C# in `Ariva.Simulation.Api/Scenarios/Engine` (ARV-027) and must reproduce the prototype bit for bit. `node scripts/simulation/reference-golden.mjs` runs `sim.js` for six cases and writes SHA-256 fingerprints of every output family (schedule, roster, the run, servers, expected and day-ahead runs, alerts, bins, states, the Monte Carlo forecast, recommendations, waits, servers at a minute, demand and hall curves) to `Ariva.UnitTests/Simulation/reference-golden.json`. `ScenarioParityTests` checks the port against every fingerprint, `ReferenceScenarioTests` checks the three scripted events above, and `ScenarioEndpointTests` checks the simulator's operator keys and endpoints. The sensor emulator (ARV-028) is checked by `SensorTrafficTests` (every push of every sensor maps through Ingest's own canonical and Xovis mappers, names only published lines and zones, and conserves passengers), `SensorEmulatorTests` (the demo clock, pause, speed, jump, failures) and the E2E `sensor-emulator.spec.ts` (a 10-minute run at speed 60 against the running Ingest, accepted equal to expected). `node scripts/verify.mjs unit` also fails when the golden file no longer matches `sim.js`.

The golden replay (ARV-036) locks the stream's behaviour on the same evening: `GoldenReplayTests` runs the sensor emulator's pushes of S-15, S-17 and S-50 from 17:00 to 20:30 through Ingest's own ingest, puts them in the archive's form and replays them through `ZoneReplay`. The replay must show the Visitors nowcast passing 15 minutes at 18:05, S-17 out from 18:20 to 18:30 (the start of the minute its 18:31 push covers, ARV-148) with the Visitors zone degraded and only its 18:15 bin marked (the 18:30 bin is judged), and island C's 19:00, 19:15 and 19:30 bins above 15 minutes; its output hash must equal `Ariva.UnitTests/Replay/replay-golden.json`, run after run and after a fresh ingest; and its export must fail verification when any line is changed, dropped, added or moved. `GoldenReplayArchiveTests` writes the same evening to the archive in TimescaleDB (pseudonymous tracks, health reports), replays it with the command's runner under the demo seed's profile version 12 and must reach the same output hash. A change to the engine that changes the hash is reviewed as a diff of the outputs, and the golden value is updated only with the human's approval (`/replay`).

Alert evaluation (ARV-038) is tested on the same evening: `AlertEvaluatorTests` judges the replayed Visitors minutes with R-001 and must raise at 18:05, the minute the prototype raises it, both as one fold (backtest) and one minute at a time with the state stored as JSON between minutes (live), with the same transitions; on random series the two must also agree for every sustain and clear setting. `AlertEvaluationTests` writes the evening's stream outputs to TimescaleDB, ticks the live evaluation once a minute from 17:00 to 20:35 with the demo airport's R-001 to R-005, and requires every rule's backtest to list exactly the alerts the live evaluation stored.

## 6. Accuracy validation

Field validation is not a software test but uses the same metrics (F18): count accuracy per 15-minute bin per line at least 95 percent, realised-wait error within the larger of 1 minute or 10 percent, bias within 5 percent, track completion at least 90 percent, desk-state agreement at least 95 percent, nowcast median error within 2 minutes for waits under 20 minutes. Protocol in [Commissioning and calibration](07-Commissioning-and-Calibration.md).

## 10. Definition of done for a story

A story is done when its acceptance criteria pass, `node scripts/verify.mjs story` passes (which includes `security`), the tests for every control it touches pass, and the security reviewer has signed off its checklist (see `../docs/security/cwe-controls.md`). The full suite runs at the next checkpoint ([test cadence](../docs/harness/test-cadence.md)); a checkpoint failure is fixed before the next story starts.
