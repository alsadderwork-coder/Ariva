# Operations runbook

For Dalil support, site IT and the local partner. It lists what to watch, which alarms Ariva raises about itself, and step-by-step procedures for the incidents that matter. The guiding rule: degrade and flag, never guess silently. A failure must leave affected numbers marked `Degraded` or `Unknown` and screens honest, not frozen.

Status: metric names, dashboards and system alarms are built in Phase 0 epic Skeleton and platform and Phase 1 epic Hardening. Until then, use pod health, logs and the dependency tools shown below. Commands use `$NAMESPACE` for the deployment's namespace.

## 1. Monitoring stack

| Piece | What it does |
|---|---|
| Serilog | Structured JSON logs on the console of every API host; also to Loki (`Loki:Enabled`, `Loki:Uri`) and to the OTLP endpoint when telemetry is on, and to a JSON file when `LogFile:Path` is set (vm-local only, for the E2E run: a host elsewhere refuses to start with it, ARV-091). In k8s-prd both must be https, or the host does not start (ARV-082a), and one of them must receive the logs, with the deployment's log pseudonym key from its Secret, or the host does not start either (ARV-091a, section 4.17). Values are protected by level before any sink sees an event: credentials omitted (Authorization, Cookie, Set-Cookie, X-TOTP-Code, access_token and password-like values, bearer and basic credentials and JWTs inside text), staff email addresses masked, track ids and desk codes hashed. `Microsoft.AspNetCore.Hosting` and the security events' category stay at Warning in code (the hosting request line carries the SignalR access_token); raise other categories under `Serilog:MinimumLevel:Override`. | Resource attributes | `service.namespace=ariva`, `deployment.environment`, `k8s.cluster.name`, `service.version`, plus node, pod and namespace names |

For each one it gives the events, format, store, readers, retention and whether it can hold personal or border-only data. Its section 10 is the security event catalogue and the log protection levels; section 4.16 below says how to find the events.

### 1.1 Importing the alert rules and dashboards into SigNoz (ARV-125b)

The chart renders `ariva-monitoring-alerts` (one SigNoz alert rule per key, the thresholds already in them from `monitoring.alerts`) and `ariva-monitoring-dashboards` (two dashboards) in the release's namespace when `monitoring.enabled` is true (the default). It creates nothing in SigNoz itself: no Job, no SigNoz address or API key in the chart.

Every rule and dashboard reads its own release only, so one SigNoz can take several environments and clusters without mixing them. Each query of an Ariva metric is filtered on `deployment.environment`, which is `monitoring.environment`, or the release's `environment` when that is empty. The value must equal the hosts' `Application:Environment`, which the chart's appsettings set to `environment`. The `disk` and `ingressCertificateExpiry` rules read external metrics, so they are filtered on the release's namespaces instead. Rule and dashboard names end with the environment, for example "Ariva readiness failing (k8s-prd)", and each rule carries the label `environment`.

Import after each release that changes the rules or dashboards:

1. Create the notification channels in SigNoz (Settings, Alert Channels). Before the release, list their names in `monitoring.channels` in the site's values file; or leave it empty and choose each rule's channels after the import.
2. Use a SigNoz user kept for this import only, with the Editor role and nothing more. Signed in as that user, create an API key for this import (Settings, API Keys) with the shortest expiry SigNoz offers. Do not write the key to a file, to git or to shell history.
3. Import from a machine that reaches both the cluster and SigNoz. It needs bash, `jq` and curl 7.55 or later (for `-H @file`).
   - The key is read without echo and never written to disk.
   - curl reads the header from a process substitution, and `printf` is a bash builtin, so the key never appears on a command line: not in `ps`, and not in `/proc/<pid>/cmdline` on a shared host.

```bash
SIGNOZ_URL=https://signoz.example.internal          # the site's SigNoz
NAMESPACE=ariva                                     # the release's namespace
read -rs -p 'SigNoz API key: ' SIGNOZ_API_KEY; echo   # not echoed, not in history, not exported
for kind in alerts dashboards; do
  path=$([ "$kind" = alerts ] && echo rules || echo dashboards)
  kubectl -n "$NAMESPACE" get configmap "ariva-monitoring-$kind" -o json | jq -c '.data | to_entries[]' |
  while read -r entry; do
    echo "$entry" | jq -r .key
    echo "$entry" | jq -r .value | curl -sS -X POST "$SIGNOZ_URL/api/v2/$path" \
      -H @<(printf 'SIGNOZ-API-KEY: %s\n' "$SIGNOZ_API_KEY") \
      -H 'Content-Type: application/json' --data-binary @- -w '\n%{http_code}\n'
  done
done
unset SIGNOZ_API_KEY
```

4. Revoke the API key in SigNoz (Settings, API Keys) as soon as the import is done, and leave the import user without a key.

Each POST answers 201; any other code prints SigNoz's reason above it.

Importing again creates a second copy. Delete the rules (Alerts) and dashboards Ariva created before, or update a rule in place with `PUT /api/v2/rules/{id}`.

After an import, check three things:
- **Environment**: every `hostDown` rule firing at once means `deployment.environment` does not match the hosts. Compare `monitoring.environment` with `Application:Environment`.
- **External metrics**: a rule whose metric the site does not collect stays without data and never fires.
  - `disk` needs the collector's kubelet volume metrics (SigNoz k8s-infra).
  - `ingressCertificateExpiry` needs cert-manager's metrics scraped, under the label set in `monitoring.alerts.ingressCertificateExpiry.namespaceLabel`. That is `namespace` as cert-manager exports it, or `exported_namespace` when the scrape configuration adds a `namespace` label of its own.
- **SigNoz version**: another version may refuse these schemas. Test one rule first with `POST /api/v2/rules/test`.

Known gaps (ARV-179), and what covers each:

- Lag of the MassTransit consumer groups (the Stream archive groups, the AMAN feed groups and the domain event consumers) is not measured by Ariva: it comes from the broker (`kafka-consumer-groups.sh --describe --group <group>`) or the site collector's Kafka receiver (section 2, consumer lag). For the AMAN groups the AMAN feed alert fires when a site's feed age passes T_stale (ARV-257), with two caveats: it is off by default (`monitoring.alerts.amanFeedStale.enabled`; no shipped environment turns it on, a border deployment does in its own values), and the age is the site's feed whatever the transport (`rest`, `pull`, `kafka`), so a stalled Kafka group does not fire it while the site's records keep arriving over REST or pull. No shipped rule covers an archive or domain event group that is slow but running: `consumerUnconnected` and `busDegraded` catch only consumers that cannot connect or have stopped. Since ARV-254 a group held by one record (one that retries, stalls or whose dead letter waits) shows on `ariva.kafka.consumer_hold_seconds` and fires `consumerHeld` once the hold passes the longest the settings allow; a group slow over many records that each complete in time is still covered by neither.
- While the queue stream worker's reading is paused (a zone at its bound while its checkpoint fails, 4.5b), the high watermark it last fetched does not move, so `ariva.stream.consumer_lag` stays flat instead of growing. When the database is away its own alert covers that case (`databaseUnavailable`, from `ariva.health.status` for `database`). A checkpoint can also fail while the database answers (a statement timeout on a slow database, a lock wait, a zone's state above 64 MiB); since ARV-258 `ariva.stream.checkpoint_age_seconds` grows then and `streamCheckpointStale` fires (section 3.1), and the worker's Error log ("Queue stream checkpoint failed; retrying in N seconds") gives the reason.

Every alarm of section 3 has a rule since ARV-259e3.

What `zonesUnknown` (ARV-259e3) counts: the zones a Stream replica holds (one it has read a record of since it took the zone's partition) whose every device is out, while the zone still tracks a device. During a site-wide network or Kafka outage a held zone is ticked on by the host's clock while no record arrives (`Stream:IdleTickSeconds`, 15 s), so its devices go out after 180 seconds of silence and the zone counts during the outage.

What it does not see:
- a zone Stream does not hold: after a restart or a rebalance, while every device of the zone stays silent, the zone is not loaded until a record of it arrives, though its bins carry the spell from its snapshot (ARV-274 loads a partition's zones at assignment); its devices count toward `devicesOffline`'s share (above 0.2 by default, so one dark sensor may not raise it), and `zonesDegraded` counts it. Right after an upgrade, zones already dark are not counted until a record of them arrives;
- a zone with idle ticks off (`Stream:IdleTickSeconds` 0) whose devices all fall silent: it turns Unknown only once a record comes back, back-dated, and its spell opens and closes in that one step, so the gauge never counts it (its bins carry the spell);
- a device that keeps pushing while its counting fails: its readings are still a measurement (formulas F11: a flagged reading degrades, it never makes a zone Unknown), so the zone is never Unknown; `zonesDegraded`, the zone's health checks (4.2) and the devices rules see it;
- until devices declare the lines they cover (ARV-259e5), any live device keeps every line of its zone covered, so a zone with one live device that cannot see a line is not counted;
- a zone whose devices have all been silent for 24 hours (`DeviceForgetHours`): it tracks no device and is taken as out of use, so it stops counting and the page resolves although nothing was fixed; it stays Unknown on the screens and in its bins, and `zonesDegraded` (from the device registry) keeps counting it.

What it does page that may be expected:
- sensors switched off on a schedule (a hall closed overnight): their zones turn Unknown and page every night. Schedule a planned downtime for those hours in SigNoz, as for `displaysStale` (below), or turn the rule off;
- a zone retired from the published profile, or whose last sensor was moved or decommissioned: Stream keeps holding it until the replica restarts or loses its partition, and it pages until 24 hours after its devices were last heard (then it is taken as out of use). Roll the Stream deployment after retiring a zone or moving its last sensor, or silence the alert for that zone.

What `displaysStale` (ARV-259d) does not see: a player that stopped asking for its board (the kiosk off, its browser closed, the display network down) keeps its last board, then the neutral message or a blank screen, while the server judges the display by its zones only, because the board endpoint only reads and recording each request would add a write to it on every Main replica; check the players themselves from the display network (4.8). Nor does it model operating hours: it fires whenever a display is stale, so a site whose zones publish no snapshots while it is closed (its sensors off, or Stream stopped) and whose displays stay enabled raises it then. Where that is expected, schedule a planned downtime for the closed hours in SigNoz, raise `monitoring.alerts.displaysStale.minutes`, or turn the rule off.

Operational alerts for queues (for example R-001 "Nowcast above 15 min") are configured by users; see [Administration guide](11-Administration-Guide.md).

## 4. Procedures

Each procedure lists symptoms, the effect on numbers, checks and actions. Record every incident with times, so SLA evaluation can apply the right exclusions (sensor outages over 5 minutes in a bin are an allowed exclusion type in the reference contract).

### 4.1 Sensor offline

- **Symptoms**: device status `Offline`; rule R-003 "Sensor offline" fires; its zone turns `Degraded`; the floor plan shows a gap.
- **Degraded, not Offline** (ARV-259, `devicesDegraded`): the device is heard but reports itself not online (its own status report); its zone turns `Degraded` and `zonesDegraded` fires with it. An unstable clock offset does not mark a device Degraded: it flags the device's events `ClockUnreliable`, and `clockUnreliable` fires once that lasts its window (4.5, ARV-259a). Read the device's last status on the devices screen and its clock estimate in the device health answers (4.5), then the vendor's own health page; a device that stays Degraded is serviced as an offline one.
- **Effect**: bins for the zone flagged `Degraded`; the nowcast falls back to desk-event throughput and neighbouring sensors and is shown as a band. When the zone's last live sensor goes out, the zone has no measurement at all and is `Unknown` (formulas F11, ARV-259e1): its bins are stored `Unknown` from where that sensor's outage started until a sensor is live again (`SELECT start_utc, revision, quality FROM queue_bin WHERE zone_key = '<SITE>/<zone>' ORDER BY start_utc DESC LIMIT 8`); the live and immigration screens show it as Not measured, with no length or wait, and display boards their neutral message (ARV-259e2). Until devices declare the lines they cover (ARV-259e5) every sensor of a zone counts for all its lines, so a zone with another live sensor stays `Degraded`.
- **Checks**:
  1. Is it one sensor or a whole switch? Look at neighbouring devices on the same switch.
  2. Ping the device from the gateway's sensor interface; check the switch port and PoE status.
  3. Check Ingest logs for authentication or payload errors from that device: `kubectl -n "$NAMESPACE" logs deploy/api-ingest-deployment --since=30m`.
- **Actions**: raise a ticket to the local partner for power, cabling or hardware. If the device was replaced or moved, it goes back to `Commissioning` and must be re-calibrated.
- **Recovery**: health checks confirm the heartbeat; the device returns to `Online`. Stereo sensors that stored counts on board can backfill interval counts; tracks for the gap are lost and those bins stay `Degraded`.

The reference scenario rehearses this: sensor S-17 over the arrivals hall is offline from 18:20 to 18:30, and the Visitors zone shows a band.

### 4.2 Zone degraded or unknown

- **Symptoms**: zone flagged `Degraded` or `Unknown` without a sensor alarm; or the `zonesUnknown` rule fires for a site (ARV-259e3, critical: zones of the site have had no measurement for 5 minutes). On the live and immigration screens an `Unknown` zone reads Not measured (ARV-259e2; point at it for why) and is left out of the passengers waiting tile and the zones reporting count.
- **Likely causes**: a desk in `Unknown` state (all its signals stale); AMAN feed stale with last-known values in use; corrected clock drift; censored tracks above 5 percent of a bin's entries; conservation residual above tolerance; a line outside coverage after a profile change. `Unknown` bins (ARV-259e1): every device of the zone was out over them, so check section 4.1 for each device of the zone (`SELECT device_code, from_utc, to_utc, closed FROM zone_outage WHERE zone_key = '<SITE>/<zone>' ORDER BY from_utc DESC LIMIT 10`); after a site-wide network or Kafka outage every zone of the site shows the gap `Unknown`, which is expected.
- **Checks**: the zone's data-quality reason in the dashboard (once available) or Stream logs; the active profile version and its activation time; desk states for the lane; device clock offsets.
- **Actions**: fix the input (sensor, feed, mapping, clock). If a profile change caused it, publish a corrected version and recompute the affected period (the original revision is kept). When `zonesUnknown` fires: find the zones (the live screen's Not measured rows, or `ariva.stream.zones_unknown` by `site`) and treat each zone's devices as offline (4.1); several zones at once usually means a switch, the gateway or the site's network (4.1, check 1). The zone stays Unknown, by design, until one of its devices is live again; its bins over the gap stay `Unknown` and are not recomputed into numbers. Expected pages (sensors off on a schedule, a zone retired or its last sensor moved): section 3.1.

### 4.2a Queue zone name too long for its key (ARV-114c)

Every event of a queue zone is keyed by its zone key: the site code, a slash and the queue zone's name. Kafka keys and the outbox's `message_key` (script 0011) hold at most 200 characters, counted as PostgreSQL counts them (a character outside the basic plane counts once). Since ARV-114c the zone profile refuses a queue zone name whose key would be longer (at most 196 characters at a three-letter site, 182 at a 17-character one); service, staff and overflow zones share their queue zone's key, so only queue zone names are bound. A profile published before ARV-114c may still hold such a name. None of the seeded profiles does: the demo profile (DMO) has queue zone names of at most 5 characters, which a unit test keeps under the limit.

- **Symptoms**: the warning "Zone ... of ... is not assessed: its key is longer than 200 characters" from `Ariva.Infra.Services.Sensing.SvcDeviceHealth` (once per zone per Api.Main process) and the metric `ariva.zones.not_keyable` rising every sweep; the zone has no row in the device health overview; the stream's warning "Dropped ... overflow changes of zone ..." for the same zone (its `OverflowDetected` events are dropped, its band minutes are still written). Other zones and the device states are not affected: the sweep skips that zone and commits the rest.
- **Alerting**: such a zone is not counted in `ariva.zones.degraded_now`, so its lost health reporting is silent there. Alert on any increase of `ariva.zones.not_keyable` so the operator who can rename the zone hears of it.
- **Checks** (read only, safe on production):
  ```sql
  -- Queue zones of drafts and published versions whose key would not fit.
  SELECT p.site_code, p.status, p.version, z.name, length(p.site_code) + 1 + length(z.name) AS key_length
    FROM zone z JOIN zone_profile p ON p.id = z.profile_id
   WHERE z.kind = 'Queue' AND p.status IN ('Draft', 'Published') AND length(p.site_code) + 1 + length(z.name) > 200;
  -- Devices placed on such a zone.
  SELECT site_code, queue_zone_name, count(*) FROM device
   WHERE deleted_on IS NULL AND length(site_code) + 1 + length(queue_zone_name) > 200 GROUP BY site_code, queue_zone_name;
  ```
- **Actions**: create a draft of the site's profile (it copies the name, and its validation lists the zone with "A queue zone name at site ... is at most N characters"), rename the queue zone to fit, validate and publish (a second factor is needed). Then move each device of the zone to the renamed zone (Administration, Devices, or `PUT /api/v1/admin/devices/{id}/placement`): a move sends the device back to commissioning, so calibrate it again before it counts. Zone health, `ZoneHealthChanged` and `OverflowDetected` resume for the new key; recompute the affected period from the archive (4.10) if its overflow changes are needed.

### 4.2b Names and texts with control or invisible characters, and zone outlines (ARV-159, ARV-162)

Since ARV-159 site and topology names (sites, airports, terminals, levels, checkpoints, desks, zone profiles, zones, lines) may hold no control character and no invisible format character (a right-to-left override, a zero-width space, a tag character other than those of the England, Scotland and Wales flag emoji, which are taken whole since ARV-169), the rule display texts and the sensing path already applied. A name saved before is kept, but its record cannot be edited until it is renamed, and Ingest and the archive skip sensing data that carries it as a queue zone name. The other texts people read (device models, alert rule names and contacts, display names, labels and messages, notes, reasons, user display names and the names of integration clients, outbound endpoints, report schedules and validation campaigns) have followed the same rule per code point since ARV-158. Since ARV-162 a zone profile draft that copied a legacy zone or line name, or a zone outline that touches or crosses itself by ARV-161's rule (a vertex within 1 cm of an edge it does not end), cannot be published until it is fixed, and a site export answers 409 instead of giving a bundle its import would refuse.

- **Symptoms**: a zone profile draft whose validation lists "Zone ...: its name holds a control, invisible format or broken character (shown escaped); rename the zone.", the same for a line or the profile, or "its outline touches or crosses itself"; a site export answering 409 with "... which an import refuses ..."; the warnings "Sensing archive skipped ... batches and ... events out of bounds" or "Device health archive skipped ... reports out of bounds" from the Stream host, the metric `ariva.sensing.archive_skipped` rising; an edit of a topology record or a site answering 400 with "A name holds no control characters, invisible format characters or broken characters." although the name was not changed
- **Alerting**: a skipped item is acknowledged and never archived, dead-lettered or retried, so alert on any increase of `ariva.sensing.archive_skipped`
- **Checks** (read only, safe on production): run `./Ariva.Api.Main --check-stored-names` in an api-main pod, the way the break-glass command runs (Deployment Guide), or locally `dotnet run --project Platform/Backplane/Ariva.Api.Main -- --check-stored-names` with the hosts' settings. It reads the site, topology, zone profile, zone and line names and the devices' queue zone names, every other stored text listed above (each by its own rule: one line, line breaks allowed in notes, a person's name, an alert rule's list of zones, a display's labels and messages in their JSON), every zone outline and every floor plan file name, through the runtime login in a read-only transaction, and prints, escaped, each value that breaks its rule (place such as `zone.name`, `display.entries` or `zone.polygon`, site or `-`, id, state: `live`, `deleted`, `disabled`, the profile's `draft`, `published` or `retired`, or the alert's state; then the text, for an outline the zone's name, and for a personal text (a user's display name, an escalation contact, an alert or calibration note, a manual count or desk observation reason) only the offending code points and their positions, such as `U+202E at 6 (text not shown)`), then a summary. The output still names configuration (sites, zones, devices, rules): keep it to the operator's terminal and the pre-pilot record, and do not paste it into tickets, chat or CI logs. Exit code 0 when every value passes, 3 when some do not, 1 on failure. Not read: the archives, replay runs, audit entries, emails, alerts' copies of rule and zone names and validation campaigns' copies of zone, line and queue zone names, which are evidence nobody can rename, and validation result revisions, which only the results service reads; the email sender name is configuration, checked when a host starts.
- **Read only, by the session.** The check opens its connection with `default_transaction_read_only` on and runs one constant statement in a read-only transaction that it rolls back. The runtime login it uses could still write, so the guarantee comes from the session and the transaction, not from the login's privileges (security review of ARV-159).
- **Actions**: rename each listed record through Topology, Users and access (sites) or a new zone profile draft (zones and lines: a draft copies the stored name and outline as they are, so rename the zone, move its vertices, or remove the line and add it again there, then validate and publish); move the devices of a renamed queue zone to the new name; upload a listed floor plan again under a clean file name; change the other texts through their own screens. A note of a resolved alert and the reason of a manual count or desk observation cannot be changed: note them in the pre-pilot record. Run the check before a pilot starts and after importing data from another system.

### 4.3 Stale AODB feed

- **Symptoms**: stale-feed alarm; no flight messages while flights are due; the arrival-wave strip says it uses last estimates.
- **Alarm (ARV-041)**: every minute Integration judges each feed of each site: Stale when nothing came for longer than its cadence (`Flights:Feeds:DefaultStaleAfterMinutes`, 20, or per feed in `Flights:Feeds:StaleAfterMinutes`) while flights are due at the site (not cancelled or diverted, not yet on block or off block, expected from 120 minutes ago to 60 minutes ahead); Idle when silent with no flight due; Fresh otherwise. An SSIM import (`ssim`, cadence 0) is never stale. Going stale logs the warning "Flight feed {feed} of {site} is stale: nothing for n min while n flights are due" and counts `ariva.feeds.went_stale`; the gauge `ariva.feeds.stale` (meter `Ariva.Flights`) is the number stale now; recovery logs "is Fresh again" and counts `ariva.feeds.recovered`. Only a call with at least one item Ariva could check counts as a message: an empty batch, or one whose items are all refused, does not, so a feed that sends only refused data goes Stale (look for `ariva.flights.items` with outcome `refused`). In the database, `feed_freshness` shows each feed's last message, state, since when and the flights due at the last sweep.
- **Effect**: forecasts marked as built on stale inputs with widened bands; fall back to the schedule; the arrival-wave alert uses the last estimates and says so. Live measurement is unaffected.
- **Checks**: Integration logs for authentication failures (`401 invalid_client`, lockouts) or validation errors from the AODB client; the client's status in administration; network path from the AODB to the ingress; for outbound pulls, the `OutboundEndpoint` circuit breaker state and the remote API.
- **Actions**: contact airport IT; unlock the client after confirming the cause; if the AODB sent wrong data (for example a missing on-block), operators correct it or the next message does. Ad-hoc flights can be added manually while the feed is down (v1).
- **Recovery**: automatic when messages resume; messages are applied by their own timestamps.

### 4.4 AMAN feed stopped (border deployments)

- **Symptoms**: `amanFeedStale` for a site (its `site` label; ARV-257), or for no site when no Stream replica reports a feed age (Stream down, or its desk feed off); that site's desk states switch to sensor-derived; service rates frozen. `ariva.border.feed_age_seconds` for the site shows how long since AMAN was last heard.
- **Effect**: desk state from sensor zones; service rate from the last known values; affected bins flagged `Degraded`.
- **Checks**:
  1. Is AMAN publishing? Ask the AMAN operations team to check its outbox.
  2. Is Ariva consuming? `kafka-consumer-groups.sh --bootstrap-server <broker:port> --describe --group ariva-integration.aman-desk-intervals` (and `.aman-desk-sessions`, `.aman-egate-intervals`, `.aman-lane-demand`, one group per feed topic).
  3. ACLs on the `aman.feed.` prefix; unknown desk codes being parked (look for the data-quality alert).
  4. Does Ariva read the site? Stream logs "Desk feed of site <site> failed" (Error) when its desk feed cannot read the site, and "Desk feed" with its run timeout when a read is cut: the stored heartbeat then stays where it was and the age grows although AMAN may be publishing, so fix the read (the database, the site's desk feed state). An alert that names no site means no Stream replica lists the sites at all: Stream down, its desk feed off (`Border:DeskFeed:Enabled`), or the database out of its reach. When the desk feed comes back after such an outage, its first listing still shows the ages the stored heartbeats had, so a site can page once until its next read stores AMAN's latest record (one poll, 15 seconds by default): the site's desk states were indeed stale for that time, though AMAN itself may not have stopped.
- **Actions**: restore the AMAN side or the consumer; map any unknown desk or gate code in a new profile version.
- **Recovery**: automatic on resume; consumption is idempotent by `SourceEventId`.

### 4.5 Clock drift detected

- **Symptoms**: `clockUnreliable` fires (ARV-259a): devices heard within the heartbeat timeout whose clock is unreliable for the rule's window. The rule names no device: find them in the device health answers, `GET api/v1/admin/devices/health` (permission SearchDevice; each device's `clockState` and `clockOffsetMilliseconds`) or one device's `GET api/v1/admin/devices/{id}/health` (ViewDevice). The devices screen does not show the clock state yet.
- **Effect**: a clock off by more than 500 ms but stable is Corrected: its offset is subtracted from the events' times and they are flagged `Degraded`. An unstable one is Unreliable: its events are not corrected, they are flagged `ClockUnreliable` and the queue engine takes them as degraded input, so the zone's numbers are flagged and waits across its sensors' boundaries are not to be trusted. The clock does not change the device's state (formulas F19 as implemented): the rule, not the device state, says so.
- **Checks**: is the offset on one device (device NTP or PTP settings) or many (site time source, network path)? Check the site NTP server's own synchronisation and the servers' `chronyc tracking` or equivalent.
- **Actions**: fix the device or the time source; resynchronise. Avoid firmware or configuration changes during peaks.
- **Recovery**: offset back within 500 ms and stable: the clock state returns to Ok on the device's next pushes, and the rule resolves at its first evaluation that sees no such device (it fires only after a whole window of them).

### 4.5a Outbox backlog and dead letters (ARV-020)

The gauges `ariva.outbox.unsent` and `ariva.outbox.oldest_unsent_age` show the backlog without a query (section 2a). Outbox backlog, oldest unsent event and the last error (read only, safe on production):

```sql
SELECT count(*) AS unsent, min(created_on) AS oldest, max(attempts) AS most_attempts
  FROM outbox_message WHERE sent_on IS NULL;
SELECT topic, message_key, message_type, attempts, next_attempt_on, last_error
  FROM outbox_message WHERE sent_on IS NULL AND attempts > 0 ORDER BY seq LIMIT 20;
```

- A growing backlog with `last_error` naming the broker (timeouts, transport failure, queue full): Kafka is unreachable; the relay tries each key's first row again every 5 seconds (`Kafka:Outbox:BrokerRetrySeconds`) without counting an attempt (ARV-165), so `attempts` stays as it was and every key resumes within about 25 seconds of the broker's return. Since ARV-245 a relay that met the outage then runs no pass while the producer's probe says no broker answers (one Warning, below), and resumes when one answers. A row that fails for a reason of its own (a missing topic or permission) backs off 2 seconds doubling to 5 minutes per row and counts its attempts. Check the brokers, then the relay's logs (`Ariva.Infra.Messaging.Outbox.OutboxRelay`).
- `Broker: Unknown topic or partition` or `Local: Unknown topic` in `last_error` (ARV-177): the row's topic does not exist, usually because the topics job has not run (section 4.5). No Ariva client creates a missing topic, whatever the brokers' `auto.create.topics.enable`, so the first row for it fails after about 5 seconds and backs off as its own failure, and the topic is held until that backoff ends (each key's earliest unsent row shows it in `next_attempt_on`, the later rows of a key waiting behind it), so its rows fill at most one relay pass per hold (when it ends they are due together) and the other topics carry on; while the topic stays missing its oldest row tries it again at each hold's end, the hold growing with that row's backoff (since ARV-264 a row of a new key written meanwhile waits for the hold too; a relay that takes the lead during the hold tries the topic once with such a row). Ingest answers 503 to a push whose topic is missing, and the device sends it again. Run the topics job: the topic's rows resume when the hold ends, at most 5 minutes after the job ran, without a restart (a send once the topic exists goes at once). Before ARV-177 such a send waited the whole 30 second message timeout and read as the broker being away, which ended every relay pass at that row.
- `KafkaProduceTimeoutException` ("neither acknowledged nor refused ... within 45 seconds") or `TimeoutException` ("not sent within what was left of the relay pass's 60 seconds") in `last_error`: the relay stopped waiting for the broker's answer (ARV-166). Every produce ends within 45 seconds and a relay pass produces for at most 60 seconds (`Kafka:Outbox:PassSeconds`, 10 to 120, a host with another value does not start; ARV-264), so a pass always ends, commits and lets go of its leader lock and rows; the row is tried again after the 5 second broker retry (no attempt counted, ARV-165), its key waiting meanwhile, and the next pass sends it again. The relay logs each such row at Warning ("Outbox row ... not sent; key held back" with the exception), so during a broker outage expect one such line per pass that reaches a row due for its next attempt (since ARV-167 the relay waits for the host's producer, not for MassTransit's bus, so passes continue during an outage, and since ARV-245 only until a pass meets it and no broker answers the probe; each ends at its first failed row, which is due again 5 seconds later, so every key resumes within about 25 seconds of the broker's return, ARV-165). If the broker took the first copy after all, consumers drop the second as a duplicate. Nothing to do beyond the broker itself; a pass that never ends is no longer possible, so a relay that stops draining while Kafka is healthy is a bug to report. Since ARV-167 every host sends through one Kafka producer of its own that no failed or cancelled send takes down, so a failed send no longer takes the others with it: during an outage a row's `last_error` is the broker's own answer ("Local: Message timed out", after 30 seconds), and the 45 second `KafkaProduceTimeoutException` is a backstop that should not appear while the producer is healthy (report it if it does). "Local: Queue full" means the host's producer queue was full (below); the row is sent again like any other.
- "Outbox row ... has failed with the broker unavailable for N minutes without a break ..., the last time with <cause>: <what it means>" (Error, once per row, ARV-245), counted on `ariva.outbox.broker_streaks` by topic (rule `outboxBrokerStreak`): the row's sends have failed for `Kafka:Outbox:BrokerStreakMinutes` (15) while no attempt counted, so "stuck after N attempts" would never have fired. Since ARV-270 the Error names the last failure's cause and what it points at: `Local_MsgTimedOut`, "the topic's partition may have no leader" (below); `Local_QueueFull`, "this host's producer queue was full": the pod produced more than the brokers took, so look at the brokers' throughput and the pod's own sends (Ingest under a sensor flood) rather than a partition; `KafkaProduceTimeoutException`, "the producer did not report the send within its bound": the brokers slow or the pod's client stalled; `OutboxPassTimeoutException`, "the relay pass's bound cut the send before the client reported": the cause is not known, and on a dead-letter topic (`.dlq.v1`, whose sends get at most 5 seconds of a pass) the bound always comes before the client's 30 second message timeout, and with `Kafka:Outbox:PassSeconds` below 46 it can, so it can still be a partition without a leader: check the topic as for `Local_MsgTimedOut`; `Local_TimedOut` (no delivery report came, the producer's sweep), `Local_AllBrokersDown` or `Local_Transport`, "the brokers were not reached or did not take it": look at the brokers and this pod's connection to them. For `Local_MsgTimedOut`, when `kafkaUnavailable` is not firing the brokers answer, so it is usually one partition of that topic without a leader (or one broker out of reach of this pod): `kafka-topics.sh --describe --topic <topic>` and look for a partition whose leader is `none` or `-1`, then the brokers' logs. Since ARV-264 such a row (its send timed out in the client while the producer's probe says the brokers answer) holds only its topic: "Topic ... held back until ...: row ... timed out while the brokers answer" (Warning, in place of the row's "trying again in 5 s"), counted on `ariva.outbox.topic_holds` with `kind` `partition_unavailable`. For the hold (1 minute) the leading relay claims none of the topic's rows, a row written meanwhile included, and the other topics carry on. The relay cannot tell which partition a row goes to, so every row of that topic waits for as long as the partition has no leader, not only that partition's rows. When a hold ends the topic's oldest row tries it again: a pass then waits up to the client's 30 second message timeout on it (reported within about 40), about once every 90 seconds for each such topic. With two such topics the relay spends about two thirds of its time waiting on those tries, and with three or more nearly all of it (one broker out of this pod's reach can leave partitions of many topics without a leader), the other topics' rows going between the tries and each pass still producing for at most `Kafka:Outbox:PassSeconds` (its probe of the brokers adds at most 4 seconds). The oldest row's streak grows at each try, so this Error fires once the partition has been without a leader for the streak. So a growing `outboxBacklog` with `ariva.outbox.topic_holds` rising for one topic is that topic's partition, not the whole outbox; when the probe says no broker answers, the pass still ends at the row and the next passes wait for the brokers (`kafkaUnavailable`). A relay that takes the lead during a hold claims the rows there were only after it, and tries the topic once with a row written after the hold began, which holds it again. A dead letter's failure holds only its dead-letter topic (ARV-175, `kind` `dead_letter`), and a missing or refused topic holds itself (ARV-177, `kind` `topic_refused`). Outside a hold (the brokers not answering, or a `PassSeconds` below 46, which cuts the send before the client reports it; the relay warns at start) the row is tried again at every pass. It goes once the partition has a leader. Each relay keeps its own streaks in memory (a restart starts them afresh), so a row can be reported once by each relay that leads through its streak.
- "Outbox row ... not sent: this host's Kafka producer is unavailable (stopping, retired or failed); due again in N s, sent once the producer is ready" (Warning, ARV-269): the pod's own producer failed the send (a fatal client error, a message it purged at that error, a retired or disposed client), not the broker; the row counts no attempt, is due again after the broker retry and is sent once the producer is recreated, and it ends and stays out of the broker streak above (the broker never saw those sends), so a fatal error that lasts (for example a missing IdempotentWrite ACL) shows as these warnings and the producer's own fatal error logs, not as a partition without a leader. If it repeats, read the producer's fatal error in the same pod's log. "Kafka brokers do not answer" (below) can follow these warnings if the producer fails again just as the relay asks its probe before the next pass.
- "Kafka brokers do not answer: the outbox relay skips its passes until they do" (Warning, once) and "Kafka brokers answer again: the outbox relay resumes its passes" (Information, ARV-245): each relay that meets the outage (in turn, as the lead passes from one to another) holds one pass for up to the produce bound, then asks the producer's probe (the readiness check's, at most once a second, itself bounded at its 3 second timeout and a second more) before each pass and runs none while no broker answers, so a full outage no longer holds a pass, its transaction and its leader lock for up to the produce bound at every poll, and each such relay logs one Warning instead of one per pass. The backlog gauges still move (they are measured beside the passes) and `kafkaUnavailable` fires as before. Once a broker answers, the next pass runs and every key resumes within the broker retry (5 seconds). A streak keeps its start while passes are skipped, so a row still refused when they resume is reported at once if its streak has passed.
- `Unknown event type` in `last_error` with `attempts` 0: a pod of another build leads the relay (during a rolling deploy) or a rollback crossed an event rename. The row and the rows behind it with the same key wait without backoff and go as soon as a pod that knows the type leads; roll forward if it persists. Rows are never dropped. Since ARV-246 a leader whose whole batch is such rows waits its poll interval (`Kafka:Outbox:PollMilliseconds`, 500 ms) between passes instead of passing again at once, so the leader lock is free between its passes for the pods that know the type.
- `Outbox row ... stuck after N attempts` in the error log (from attempt 10): one key has been held back for a long time. Read its `last_error`; an event refused for size cannot happen (the commit that wrote it would have failed), so it is the broker, the topic (missing, or ACLs) or the principal.
- Dead letters: each one is counted on `ariva.kafka.dead_letters` by source topic, group and outcome (`sent`, `kept`, `failed`; section 2a). A consumer that fails after its retries writes the message to `<topic>.dlq.v1` (AMAN feed topics: `ariva.aman.feed.<contract>.v1.dlq.v1`) with the source partition, offset, key, consumer group and error, and moves on. Read them with any Kafka client from the beginning of the dead-letter topic; the body is base64 of the original value, cut at 512 KB (`bodyTruncated`, `bodyBytes`), in which case read the original from the source topic by partition and offset while its retention lasts. Replay to the source topic is an admin operation (target, audited; not yet built). Never delete a dead-letter topic: it is the record of what was not applied.
- "Dead-letter topic <topic> held back for 60 s after a failure that is not its letter's own; events and the other topics carry on" (Warning, ARV-175): a dead letter kept in the outbox could not be sent to that `.dlq.v1` topic (its broker or partition leader away, the send past its bound, or a refusal such as a missing ACL, which also shows in the row's `last_error`). For a minute no relay claims the topic's letters: each key's earliest unsent letter shows a `next_attempt_on` a minute ahead, the others waiting behind it, and since ARV-264 the leading relay claims none of the topic's letters, one kept meanwhile included. Events and the other dead-letter topics carry on. A relay pass spends at most 5 seconds on dead letters and sends its events first, so such a topic delays the events written meanwhile by at most 5 seconds once a minute, and once more on a relay that takes the lead for a letter kept after the hold began (at a host's stop). A dead-letter send cut short by the pass's own time (the events used it) holds nothing and is tried again after the broker retry. Since ARV-246 a dead letter whose send fails on its own pod's producer (a fatal client error, a message the producer purged at that error, or `Local_Destroy` when the replaced producer is retired) holds no topic: the failure is the producer's, not the topic's, so a hold would cure nothing. The pass ends as for an event, and the letter is tried again after the broker retry by whichever relay leads. At a pod's stop the relay's pass is cancelled and rolled back, so nothing is held. If the warning repeats, check the topic's partitions and leader (`kafka-topics.sh --describe --topic <topic>`) and its ACL.
- A dead letter the broker refuses ("Dead letter for <topic> partition <p> offset <o> not accepted (attempt N); retrying in ...") is tried again every 2 to 30 seconds, each attempt ending within 45 seconds, and holds its partition meanwhile (since ARV-253 every partition its consumer reads: an endpoint's consumer handles one record at a time, `Kafka:Consumers:ConsumersPerEndpoint` consumers to an endpoint, 1 by default; wiki 04). Since ARV-254 it is tried for a one minute window (its last attempt starting by the window's end), then kept in the outbox and the message completes ("Dead letter for <topic> partition <p> offset <o> refused for its whole send window; kept in the outbox, which sends it later"), so the hold is bounded (section 4.24); only when the outbox cannot take it either ("... could not be kept in the outbox either") is the broker tried for another window, and so on until one of the two takes it. When the host stops, the letter is kept in the outbox and the message completes (ARV-171; "Dead letter for <topic> partition <p> offset <o> not sent before messaging stopped; kept in the outbox, which sends it later"): it is an `outbox_message` row with `message_type` `ariva.dead-letter` for `<topic>.dlq.v1`, which the relay sends once the topic takes it, with the backoff and the `last_error` of any row (a missing dead-letter topic or ACL shows there, and the row waits until it is fixed; the provisioner creates every dead-letter topic). A stop that comes during a message's retries waits for them (at most three, 5 seconds apart by default) and then keeps the letter the same way. Only when the database is away as well does the loop end without anything durable (since ARV-175 a record whose key, headers or error text carry a NUL character or a lone surrogate is kept too: each is replaced with U+FFFD and the letter's `ariva-dead-letter-text-replaced` header names the parts; the original record is read from its topic by the letter's partition and offset) ("... not sent: messaging is stopping; the message is left unacknowledged and is delivered again after restart", after "could not be kept in the outbox either"): the next pod gets the message again and dead-letters it then, possibly twice if the broker took the interrupted attempt after all. Since ARV-253 nothing after such a message completes before the stop (each consumer handles one record at a time), so the group's committed offset stays at it; if after such a warning the group's committed offset on that partition (`kafka-consumer-groups.sh --describe --group <group>`) is ever past the logged offset with no dead letter for that offset on `<topic>.dlq.v1`, report it, then read the record from the source topic by partition and offset while its retention lasts and replay it (an admin operation, not yet built). Kept letters waiting: `SELECT topic, message_key, attempts, last_error FROM outbox_message WHERE message_type = 'ariva.dead-letter' AND sent_on IS NULL;`. A pod that will not stop while a dead letter is pending is not expected.

Kafka producer (ARV-167). Each host sends everything it writes to Kafka (events, the relay's rows, dead letters) through one producer of its own, created at start and kept until the host stops; its log category is `Ariva.Infra.Messaging.Kafka.KafkaProduce`.

- "Kafka producer error (Local_AllBrokersDown) ..." or a transport error at Warning: the brokers are unreachable; librdkafka reconnects by itself (at most 10 seconds apart). Nothing to do beyond the brokers.
- "Local: Queue full" in Ingest's "could not be stored" errors or in `last_error`: the producer's queue is full (32 MiB or 10,000 messages waiting for the broker, `KafkaClientConfig.QueueMaxKbytes` and `QueueMaxMessages`, sized so a pod stays within its memory limit during an outage). Devices get 503 at once and send again; the relay backs off. It clears by itself when the broker answers again; a full queue while the broker is healthy means the host produces faster than the cluster takes, so check broker load and disk.
- "Kafka producer fatal error (...)" at Critical: the client cannot send again (librdkafka raises this for an idempotence refusal, for example a principal without the IdempotentWrite ACL on the cluster). The host recreates its producer by itself, at most once per `Kafka:Producer:RecreateSeconds` (30) from the failed client's creation, and logs "Kafka producer recreated after a fatal error" at Critical; until then every send of that host fails at once (Ingest answers 503, events stay in the outbox, the relay waits). Both are counted on the `Ariva.Kafka` meter (`ariva.kafka.producer_fatal`, `kind` `fatal_error` or `recreated`). A cause that persists (the ACL) gives one fatal error and one recreation per interval, at most two Critical lines; fix the cause and the next recreation sends. No restart is needed; the host keeps serving everything else meanwhile.
- "Kafka producer ended N messages that had no delivery report after 90 s" at Error: librdkafka gave no report for messages it was handed (it reports every message within its 30 second timeout, so this is not expected; report it with the log). Their senders send them again (ARV-165).
- "Kafka endpoint ... was not stopped with the bus (its consumer was between restarts); stopping it now" at Warning when a pod stops: the pod stopped while a consumer was restarting after a broker error; MassTransit's stop skips such an endpoint, and the host now stops it itself so that no consumer of the stopping pod rejoins the group (ARV-165). Expected around broker outages; nothing to do. "... did not finish stopping within 5 s" means the consumer was held by an offset commit; it ends with the process.
- "Kafka producer stopped with N messages unacknowledged" at Warning when a pod stops: the 5 second flush at stop did not see those acknowledged (usually a broker outage at the time). Nothing is lost: the relay sends its rows again and devices send their pushes again; consumers drop duplicates.

Stop budget (ARV-165). A pod gets SIGTERM, then the kubelet kills it after its grace period. Every API pod's grace period is 60 seconds (`terminationGracePeriodSeconds` in the chart's values, passed to the host as `Hosting__GracePeriodSeconds`) and every host's shutdown timeout is 50 seconds (`Hosting:ShutdownSeconds`). Of those 50 seconds the message bus may wait 35 (the shutdown timeout less 15): a consumer with a message in its retries finishes them (at most `Kafka:Consumers:RetryCount` 3 times `RetryMaxMilliseconds` 5 seconds, 15 seconds, and up to a quarter more with MassTransit's jitter, 18.75 seconds, which the stop budget counts since ARV-268) and keeps its dead letter (at most 10 seconds), 28.75 seconds in all; then 5 seconds go to the endpoints the bus skipped, 5 to the producer's flush and 5 to the rest; the dispose and the exit have at least the last 5 seconds of the grace period. A host refuses to start (an error naming `Hosting:ShutdownSeconds`) when a change breaks this: a shutdown timeout that leaves the bus less than the retry schedule plus 10 seconds, or that does not end 5 seconds before the grace period. So raising `RetryCount` or `RetryMaxMilliseconds` may need a longer shutdown timeout, and a longer shutdown timeout a longer grace period (change `terminationGracePeriodSeconds` in the values; the chart passes it on). While the brokers are away and a consumer is held by an offset commit, the bus's stop ends at its 35 seconds and the pod exits within its grace period; nothing acknowledged is lost (an unfinished message is delivered again after the restart). At a stop MassTransit 8.5.11's Kafka consumer cancels a record still in hand when the bus's wait ends (the budget covers the retry schedule and the keep, not a consumer's own time per attempt, so a slow attempt at the stop, the database stalling at its 30 second command timeout, can outlast it; its Warning "Consumer stop canceled"), and never handles a record waiting behind one in hand when its endpoint begins to stop. Its checkpointer passes both as it passes a failed record, and commits the next completed record of the partition. Since ARV-253 each Kafka consumer handles one record at a time (one lane), so a partition's records complete in the order they were fetched and nothing after such a record has completed: the group's committed offset stays at it, and the next pod gets it again (found in ARV-177: with lanes by key, the record behind a 4 second one, on a clean stop, was consumed by neither host and the group's offset was past it). Since ARV-177a the attempt cancelled at the stop, which runs on while the host disposes its services, no longer keeps a dead letter when it fails (on `ObjectDisposedException` or its own error): a failure after the message's token was cancelled, or one from a disposed service while its endpoint stops, is the stop's, and the host logs "Message from <topic> partition <p> offset <o> failed after its endpoint began to stop past it; not dead-lettered, it is delivered again after restart (ARV-177a)" at Warning with the failure. Nothing to do: the next pod processes the record. Before ARV-177a such a failure on the message's last attempt kept a dead letter for the valid message, which the next pod processed as well, so a letter of an earlier stop whose error names `ObjectDisposedException` or a timeout may be such a duplicate. Neither its error nor its time tells it from a genuine dead letter (a message whose last attempt failed for its own reasons, a timeout among them, is still dead-lettered at a stop, and before ARV-253 a letter could be a record's only trace), so treat it as any dead letter: replay it, and the consumers' inbox drops it if the event was applied already. A message whose last attempt fails for its own reasons while its endpoint stops, before the stop wait ends, is still dead-lettered (kept in the outbox, ARV-171).

### 4.5b Queue stream worker (ARV-034)

Ariva.Api.Stream's queue engine worker (group `ariva-stream.queue-engine`) writes `queue_minute`, `queue_bin`, `line_minute` (per-line crossings per minute, ARV-113), `zone_health_bin` (the F18 health checks of each bin, ARV-114a), `overflow_minute` (each overflow band's occupancy per minute, ARV-115) with its `OverflowDetected` events in `outbox_message`, the zone snapshots (`stream_zone_state`) and its own positions (`stream_offset`) in one transaction per checkpoint. To check it is keeping up, compare `stream_offset.next_offset` with the end of each sensing topic partition and look at `stream_zone_state.updated_on`. A push a device sends again (it dropped the request, or Kafka delivered it twice) is applied once (ARV-168): the zone snapshot counts the resends it dropped (`state->'counters'->>'repeatedBatches'`) and the batches it had to forget early at its bound (`forgottenBatches`, 20,000 per zone and 1,000 per device; a resend of one of those would count again, so it should stay 0; a growing value means a device sends far more batches than a sensor should). T1 counters (interval counts, such as Xovis line logics) have each minute's exits counted in that minute since ARV-173; before it a push's exit line count landed a minute late (totals were right). Minutes and bins written before the upgrade keep the old placement until the period is recomputed from the archive (4.10), which gives a new revision; a replay of such a period names the new engine build and gives another output hash than one recorded before the upgrade.

- After a crash or a redeploy nothing needs doing: the worker restores each zone from its snapshot and replays the records after the saved positions, rewriting the same rows.
- State size: `SELECT zone_key, state_bytes, pg_column_size(state) AS stored_bytes, updated_on FROM stream_zone_state ORDER BY state_bytes DESC LIMIT 10;`. Every checkpoint (every 5 seconds) writes every zone's whole state, and a save above 64 MiB fails the checkpoint. A zone without track positions holds a few KB (AUH-TA's zones 4 to 18 KB, ARV-124a). Since ARV-230 a track's position samples are kept in a run (`state->'engine'->'runs'`: its anchor and one pending sample) instead of one buffered event each, so a hall zone with 6 T3 sensors holds a few hundred KB (208 to 269 KB in the pilot load run); before it, the zone held every position for its lateness, about 20 MB (82,440 positions), and five such zones made Stream run out of its pod's heap within minutes (`System.OutOfMemoryException` in `StreamStore.SaveStateAsync`, wiki 05). A zone above a few MB now means many tracks or a flooding device: the buffer holds at most 100,000 events and the runs 20,000 tracks (about 32 MB at worst); find the device by its track keys, or the `device` an anonymous event carries, in `state->'engine'->'buffer'`, and see section 4.22 for the refusals (ARV-231). A zone that starts afresh (its snapshot refused, as the log says, a new profile version, or go-live) knows nobody inside: for about one queue dwell time the exits of people already inside pair by FIFO with the earliest person another sensor holds, whose own exit then counts as a duplicate, so exits and waits are low until they have left (formulas F5; ARV-237). `state->'engine'->'buffer'` holds the waiting events, `state->'recentBatches'` the remembered batch keys (ARV-168; 316 KB at that zone).
- The positions in `stream_offset` are authoritative. Resetting the Kafka consumer group's offsets has no effect on a partition that has a saved position.
- To recompute a zone from scratch (for example after a geometry fix), stop the worker, delete the zone's `stream_zone_state` row and the group's `stream_offset` rows as the migration login, reset the group to the earliest offsets, and start it again. The topics keep 3 days; older periods come from the archive (4.10).
- A log line "the saved state of zone ... cannot be restored" means the snapshot failed its checks and the zone started afresh; recompute the affected period from the archive (4.10).
- `stream_partition_count` remembers every partition count the sensing topics have had, so a recompute still accepts records produced before partitions were added. Keep it when restoring or moving the database; a database restored from before a scale-out needs the earlier count inserted again (as the migration login) before it replays those records.
- Records of a zone that is not in its site's published profile, or beyond `Stream:MaxZones` zones on one instance, are counted and skipped (warning in the log); publish the profile or add instances, then recompute the period from the archive.
- Late events (ARV-148): a zone's watermark is its latest event time less the site's lateness (`Stream:LatenessSeconds`, per site under `Stream:Sites`; wiki 04). A bin with `late_events` above 0 on a site whose sensors are healthy means the lateness is shorter than the sensors' push interval plus their delay, or a device's clock runs behind: check the site's push interval against the sensors' configuration and the device clock estimates (F19) before raising the lateness. Upgrading to ARV-148: snapshots written before it (zone version 8) restore with the engine's clock at their latest held event, so the first minute after the upgrade closes up to a minute and a half later than usual; nothing needs doing.
- "Queue stream checkpoint failed" means the database refused the write; the worker keeps its outputs, retries every checkpoint interval and pauses reading while a zone is at its bound. Nothing is lost unless the instance itself stops, in which case its successor replays from the last checkpoint. `ariva.stream.checkpoint_age_seconds` (ARV-258) shows how long since the worker last wrote everything it owed, and `streamCheckpointStale` fires past its window. With "Queue stream checkpoint failed" in the log, read its reason (a statement or command timeout on a slow database, a lock wait, or a zone's state above 64 MiB from the state size query above); without it, the worker is held: a slow database (`pg_stat_activity` for the Stream host's sessions and who holds their locks), or a dead letter the broker will not take ("Dead letter ... not accepted", 4.5a). Fix that; the next checkpoint writes everything held.
- Dead letters of the sensing topics (`ariva.device.*.dlq.v1`) are records that are not a batch of the zone their key names. Investigate the producer (Ingest) before replaying them.
- Upgrading to ARV-036: Ingest keys device health reports by zone from then on. Upgrade Ingest before Stream if you can; reports Ingest published before (keyed by device id) are skipped by the queue worker and counted in a warning ("keyed by device id"), not dead-lettered. Add partitions to `ariva.device.health.v1` first if its count differs from the sensing topics'.
- Device outages (ARV-036): `zone_outage` lists, per zone, each device silent beyond 180 seconds or reporting itself offline, from the minute it was last heard in to the start of the minute its first push after it covers (the push interval before that push's receive time, ARV-148). A zone degraded on the live screens with no outage there is degraded by its inputs (skewed or unreliable clocks, F11). A device removed from a zone stops counting 24 hours after it was last heard.

A host that logs "Waiting for Kafka topics before connecting their consumers" is holding its start until Api.Main (or the platform team) has created the Ariva topics it consumes; after `Kafka:Consumers:StartWaitSeconds` (60) it starts anyway, and gives the consumers it connected at most 30 seconds more to be ready. It never waits for AMAN's feed topics (ARV-176). Start budget: the host's start holds its web server, so the 60 second topic wait, the 30 second ready wait and a 30 second margin must fit in the pod's startup allowance, 130 seconds, passed to the host as `Hosting__StartupAllowanceSeconds`. The allowance is the startup probe's worst case: the kubelet's probe ticks every `periodSeconds` (15) from before the container starts and skips the ticks within `initialDelaySeconds` (10), so the first counted tick can come at 10 seconds and the `failureThreshold`-th (9th) consecutive failure, which restarts the container, 8 periods later: 10 + 15 x (9 - 1) = 130 seconds at the earliest, 145 at the latest (a refused connection fails at once, so the probe's timeout adds nothing). The margin holds the bus's start (at most 15 seconds; a start that times out fails there, before the waits), a metadata request that overruns the topic wait (at most 12 seconds) and the process up to the bus (13 seconds left at the default 60 second topic wait, 3 at the largest accepted, 70). A host whose `StartWaitSeconds` would not fit refuses to start with a message naming both settings, rather than being restarted by its probe again and again. A consumed topic that does not exist does not stop the host's other consumers: the host logs "Kafka topic <topic>, consumed by <group>, does not exist; its consumer starts when the topic appears (checked every 10 s)" at Warning, reports it as 1 on the gauge `ariva.kafka.consumed_topic_missing` (meter `Ariva.Kafka`, tags `topic` and `group`; alert on any 1), looks for it every `Kafka:Consumers:TopicWatchSeconds` (10) and, when the topic is created, logs "Kafka topic <topic> now exists; its consumer <group> is starting" and consumes it from its earliest records, without a restart. While Kafka cannot be read the host logs "Kafka not reachable; the consumers of <topics> start once it is and their topics exist" once (and "Kafka reachable again" when it can), never "does not exist", and the gauge keeps the state it last read; a topic the host has never been able to read has no gauge value (the `kafka` readiness check, Degraded, is the outage's alert). A consumer whose topic exists but whose connect failed is logged as "Kafka consumer <group> of <topic> could not be connected; trying again in 10 s" and tried again at each check; the gauge reads 0 for it (the topic exists), and `ariva.kafka.consumer_unconnected` reads 1 for it until it connects (ARV-125a; alert on any 1 that lasts). Once every consumer is connected the host stops looking. A missing `aman.feed.*.v1` topic means AMAN has not created it (wiki 08 section 10 names the four that must exist before go-live); a missing `ariva.*` topic means the topics job did not run or failed (section 4.5, the deployment guide). Before ARV-176 one missing topic stopped the whole message bus of the host at its start, every consumer with it, while readiness answered 200.

### 4.5c Queue bins not finalised (ARV-259b)

`binsOverdue` fires when a site has queue bins whose latest revision has stayed Provisional for the whole window although they ended more than the censoring timeout (120 minutes) plus the longest lateness of any site ago. By then every entrant has left or been censored and every event is in, so the queue stream worker (4.5b) should have written them Final. The site's final results wait: reports, the SLA evaluation and staffing read Final bins.

- Which bins: `SELECT zone_key, start_utc, revision, profile_version, updated_on FROM (SELECT DISTINCT ON (zone_key, start_utc) * FROM queue_bin WHERE start_utc > now() - interval '24 hours' ORDER BY zone_key, start_utc, revision DESC) b WHERE status = 'Provisional' AND start_utc + make_interval(mins => length_minutes) < now() - interval '125 minutes' ORDER BY zone_key, start_utc;` (125 minutes: the 120 minute censoring timeout and the default 90 second lateness, rounded up; use a site's longer lateness if it has one). The sweep reads the same, with the bins of a zone that moved to a newer profile version and of a zone no longer in the site's published profile left out.
- Most zones of the site, the newest bins: the worker is not finalising. Read its consumer lag and checkpoint age (`ariva.stream.consumer_lag`, `ariva.stream.checkpoint_age_seconds`; 4.5b, 4.6) and its log. A Stream host running without Kafka (`Kafka:Enabled` false) runs the sweep but no worker.
- Zones whose sensors went quiet: an idle zone's clock moves on with the host's clock only while the worker is caught up and `Stream:IdleTickSeconds` is above 0 (15 by default); set to 0, a zone with no events keeps its last bins open until its next event.
- One zone, older bins: its snapshot was refused and it started afresh under the same profile version (the log line "the saved state of zone ... cannot be restored"). Its open bins are no longer held by any engine, and nothing writes a Final revision for them today: the recompute of a period is a Target procedure (4.10; the golden replay writes evidence, not bins). They stay counted, and the rule firing, until they leave the look-back, about 26 hours after their start at the defaults (24 hours plus the maturity delay). Silence the site's alert in SigNoz for that time (it then hides a real stall at that site too, so watch the worker's lag and checkpoint age meanwhile), or, while the period is within the topics' 3 days, recompute the zone from scratch by the offset reset of 4.5b, which writes its bins again from the start (the reset is the whole consumer group's: every zone on its partitions replays up to 3 days, and a bin becomes Final only where the replay rewrites its latest revision, usually revision 0).
- A zone that moved to a newer profile version starts afresh (4.5b) and leaves its open bins of the old version Provisional; the sweep does not count them once the zone has written a bin under the new version. A zone taken out of the published profile is not counted either. Their bins stay Provisional; nothing makes them Final today (4.10).
- The sweep itself: a sweep that keeps failing (the Error "Bin maturity sweep failed; retrying at the next interval", for example at the command timeout with a long look-back) reports nothing, so the rule cannot fire; read the log, and shorten `Stream:BinMaturityLookbackHours` if the read is too slow.
- Settings: `Stream:BinMaturitySweepSeconds` (60, from 10 to 3,600) and `Stream:BinMaturityLookbackHours` (24, from 1 to 168), checked at start (wiki 04). The sweep runs whenever `Stream:Enabled` is on; its read is bounded by the look-back and the database command timeout, and a sweep ends within a minute.

### 4.6 Kafka consumer lag growing

- **Symptoms**: lag alarm (the queue engine's own measure is `ariva.stream.consumer_lag`, per topic, section 2a); screens slow to update; nowcasts stale.
- **Checks**:
  1. `kafka-consumer-groups.sh --bootstrap-server <broker:port> --describe --group ariva-stream.queue-engine` (lag per partition; the queue engine commits after each checkpoint, every 5 seconds, so a few hundred to a few thousand records is normal at a busy site), and the archive's `ariva-stream.sensing-archive-tracks`, which writes every position to `sensing_event`. In ARV-124a's pilot run the queue engine fell behind first and the archive kept up (wiki 05): look at the zones' state size next (section 4.5b).
  2. Stream pods: `kubectl -n "$NAMESPACE" get pods -l app=api-stream` and `kubectl -n "$NAMESPACE" top pods -l app=api-stream` (CPU at the limit, restarts).
  3. Broker health and disk; under-replicated partitions.
  4. A single hot partition (one busy queue zone) versus all partitions.
- **Actions**: if CPU-bound, raise the HPA maximum or resources (`apiStreamHpaMax`, `apiStreamCpuLimit`), but replicas beyond the partition count do nothing; if a broker is down, restore it (three brokers, replication factor 3, minimum two in-sync replicas survive the loss of one).
- **Recovery**: lag drains; late events reopen bins as new revisions, which is expected.

If Kafka is unavailable entirely: Ingest keeps no buffer of its own and answers each push it cannot hand to Kafka 503 with Retry-After, at once when its producer's queue is full and otherwise within 45 seconds (its first produce fails by its delivery report within that bound, ARV-166 and ARV-167; the log says "Push from device ... could not be stored" with the broker's error or `KafkaProduceTimeoutException`), so the sensor or its gateway keeps the batch and sends it again (expect a run of 503s in Ingest's access log and these errors for the length of the outage); services keep unpublished events in the PostgreSQL outbox, and each relay pass during the outage ends at its first failed row (within the 30 second message timeout and 60 seconds, `Kafka:Outbox:PassSeconds`) and lets go of its leader lock, the row tried again 5 seconds later without an attempt counted (ARV-165); `kafka` in the readiness report turns Degraded within 3 seconds (ARV-165); a pod stopped during the outage stops within its shutdown timeout even while a consumer is held by an offset commit (ARV-165); screens switch to the neutral message after the staleness threshold. On recovery the relay drains the outbox, every key within about 25 seconds, and consumers resume from committed offsets.

### 4.7 Database disk filling

- **Symptoms**: disk alarm; slow queries; write errors in Stream logs.
- **Checks**:

```sql
SELECT pg_size_pretty(pg_database_size('ariva'));
SELECT hypertable_name, pg_size_pretty(hypertable_size(format('%I.%I', hypertable_schema, hypertable_name)::regclass))
  FROM timescaledb_information.hypertables;
SELECT job_id, hypertable_name, last_run_status, last_successful_finish, next_start, total_failures
  FROM timescaledb_information.job_stats;
```

- **Likely causes**: the retention or compression job failing (raw samples in `sensing_event` and `sensing_batch` must be dropped after the dispute window and compressed after one day; `SELECT * FROM timescaledb_information.job_stats` shows the last runs, and `policyJobsFailed` fires on them, section 4.8m); a dispute window (`migration.retention.rawSensingDays`, section 4.8m) set longer than the volume was sized for; WAL retained by a broken replica or backup archive.
- **Actions**: fix and re-run the failing job; expand the volume (volumes can grow, never shrink); check replication slots and WAL archiving. Never delete hypertable data by hand: only the retention policies may, and evidence for open disputes must be kept. A shorter period is a change of `migration.retention` agreed with the client and applied by the next release (section 4.8m).

### 4.8 Display board stale

- **Symptoms**: the `displaysStale` rule fires for a site (ARV-259d); a board shows the neutral message; operations report a blank or frozen board.
- **Effect**: by design, a board never freezes on an old number; it shows the neutral message when the latest nowcast is older than the staleness threshold. It also shows it, by design and without the rule firing, for a zone with no staffed desk and for a zone with no measurement (`Unknown`, every sensor of it out, ARV-259e2): for the latter, see section 4.1.
- **What the rule counts**: the enabled displays of the site that show a queue zone with no live snapshot, or one older than the display's stale threshold, by Api.Main's clock (section 2a). A fresh snapshot of a zone with no service or no measurement is not stale, so its display is not counted (ARV-259e2). It judges the zones, not the players: a player that stopped asking for its board is not counted, and a display counts even while nobody looks at it (operating hours are not modelled, section 3.1).
- **Checks**: is the zone's nowcast itself stale (4.1, 4.6) or are snapshots not published at all (4.8a: Stream writing, Redis reachable from Stream and Main)? Api.Main logs the Warning "Display stale sweep could not read the live snapshots" while Redis does not answer it, and then counts every display stale, including boards that cannot be refreshed but still show their last band until their own threshold passes. Does the display show a queue zone of the site's published profile? A zone taken out of it, or renamed, gets no new snapshot (Redis keeps the last one a day, ageing), and the display shows the neutral message for it until an administrator edits the display (Administration guide). For a board the rule does not count: from the display VLAN, can the player reach the display page and the read-only endpoint? Is the player's browser in kiosk mode and online?
- **Actions**: fix the upstream cause, the display's zones or the player's network; reload the kiosk page. Where displays stay enabled while the site is closed, see section 3.1 for the planned downtime.

### 4.8a Live dashboards not updating (ARV-035)

- **Symptoms**: dashboards connect but their queue figures stop changing; or the browser cannot connect to `/hubs/live`.
- **Checks**: is the stream itself writing (4.5b, `queue_minute` for the last minutes)? In Redis, does `ariva:live:zone:<site>/<zone>` change after each checkpoint, and does `ariva:live:relay` exist (one Main replica holds it, renewed every 5 seconds)? Do Api.Main and Api.Stream use the same `Redis:ConnectionString` and `InstanceName`? Does the ingress pass WebSocket upgrades on `/hubs` (a 400 or a connection closed at once)?
- **Log lines**: Stream logs "Live snapshots not published" when Redis refuses the write (the database checkpoint is not affected); Main logs "Live relay could not subscribe" or "Live relay lease not renewed" while Redis is unreachable and retries every 5 seconds.
- **Access**: a user who cannot join a zone gets `forbidden` (no `LiveQueue.View`, the zone's site is not among the user's sites, or the zone is not a queue zone of the site's published profile; a newly published zone is joinable within a minute), `too_many_zones` (more than 64 zones on one connection), `too_many_joins` (more than 120 joins a minute) or, on connecting, `too_many_connections` (more than 8 hub connections of one sign-in on one replica) or `hub_full` (the replica holds `Security:Hubs:MaxConnections` connections, every sign-in together; ARV-096b). A replica at its total answers a negotiate 429 with Retry-After and logs security event 9116 with policy `hub-connections`: the screen shows its live feed as disconnected and connects again when it next sets its zones or is reopened. Sustained 9116 `hub-connections` events mean the replicas hold more screens than the setting allows, or one account keeps opening sign-ins (there is no limit per account yet, ARV-229: the events and Main's join lines name the caller): add an api-main replica (connections spread over the replicas) or raise the setting (wiki 04; about 72 KB of buffers a connection), or disable the account.
- **Logs**: the hub's Ingress on the web host writes no access log and exports no OpenTelemetry spans by design (its URLs carry tokens), and every other host, api-main's included, answers `/hubs` 404 at the ingress (ARV-091): a client that cannot connect may be using the api-main host; connect through the web host. Use Main's logs: a join refusal names the connection id and, since ARV-091, the caller's `CallerUserId`, `CallerSessionId` and `CallerAddress` (section 4.16).
- **Actions**: restore Redis or fix the settings; the next checkpoint rewrites every zone's snapshot and clients receive it without reconnecting. Restart Main only if no replica holds the relay lease for more than a minute.

### 4.8b Alerts not raised or not clearing (ARV-038)

- **Symptoms**: a queue is clearly over a rule's threshold but no alert appears, or an alert stays open after the queue is back.
- **Checks**: is the rule enabled, and are its zones queue or overflow zones of the published profile? Is the stream writing the zone's minutes (`queue_minute` for the last minutes, 4.5b)? The evaluation only judges minutes the stream stored and that have ended. While the queue length is degraded (a sensor out, 4.1) a nowcast rule skips those minutes, so the sustain or clear count waits. Run the rule's backtest over the last hour: it is the same evaluation and shows whether, and when, it should have fired. In the database, `alert_rule_state` shows each target's counts and the last minute taken.
- **Log lines**: Stream logs "Alert evaluation: n raised, n cleared, n withdrawn, n failed" when a tick changes something, "Alert evaluation of rule {id} failed" with the error when one rule fails (the others go on; it is tried again next tick), and "Alert evaluation tick failed" when a whole tick fails.
- **Escalation**: an alert still Raised after its rule's escalation minutes is escalated at the next tick (audited as `Alert.Escalated` by `alert-evaluation`); if escalations are late, check that the Stream host is evaluating (the log line above) and that its clock is right.
- **Screens not told of alerts**: the screen must have joined the site's alerts (`JoinAlerts`), and its user must hold a role responsible for the alert; Main and Stream must share the Redis of 4.8a.
- **Known limits**: `OverflowOccupied` rules (since ARV-115) judge only zones whose overflow band has a commissioned sensor reporting occupancy (a band without one shows nothing, and is not counted as empty; a band whose sensor falls silent for more than 2 minutes becomes Unknown, an `OverflowDetected` with state Unknown, and the rule neither raises nor clears on it until the sensor reports again; check the band's sensor under Devices); predicted-nowcast rules read the arrival-wave projection (ARV-047) and have nothing to judge for a queue zone outside the arrivals hall or without a lane category the wave models (set the queue zone's lane in the zone profile; ARV-185). A new or re-enabled rule starts at the present (use the backtest for the past). After the Stream host was down for more than three hours (`Alerts:Evaluation:MaxCatchUpMinutes`), evaluation continues from the last three hours.
- **Open desks below recommendation rules (`DesksBelowPlan`, ARV-181b2)**: they judge the staffing job's stored minutes (`lane_staffing`, interval 0, written by Cronz once a minute; 4.8l), so no alert while Cronz is not computing the site, while a lane has no recommendation (its reason: no queue length, no throughput, no desks, a flight without passengers) or while its open count is unknown or degraded (the desk states, 4.1); the backtest over the last hour shows whether it should have fired. They are border data: only border shift supervisors and administrators see the rules and their alerts on any channel, so a duty manager who reports a missing alert is expected not to see it. Stream logs "Alert evaluation of site {Site} rule {Rule}: not evaluated, it fails the rule checks of its border metric" once per rule and values version (again when the rule is changed, and once after each restart of the Stream host; ARV-187, previously every tick) and writes one `AlertRule.NotEvaluated` audit entry with it (ARV-190: the site and rule code, the values version, the fixed reason and the number of alerts it withdrew, by the evaluation; the warning is logged once the tick's commit has succeeded, so a failed commit warns and audits again at the next tick, and the memory of a rule deleted or disabled since is dropped; like the warning, the entry comes once per values version in each Stream replica and again after a restart) for a stored rule on a border metric (`DesksBelowPlan` or, since ARV-187, `PredictedNowcast`) whose owner or escalation role is not a border role, or for `DesksBelowPlan` that fires below (one from before ARV-181b2 or ARV-187, or changed in the database); its open alerts are withdrawn (`RuleWithdrawn`) and it raises nothing: an administrator gives it a border owner or a supervisor deletes it (the release notes, wiki 18, list the SQL that finds such rules), and until then the site's configuration export answers 409; "its stored inputs exceed the rows one read takes" means a range beyond 100,000 lane minutes (it resumes when back within the bound).
- **Health-check rules (ARV-114b)**: `ConservationResidual`, `TrackCompletion` and `OccupancyOutOfRange` rules judge the zone's stored bins (`zone_health_bin`, the latest revision) and wait for each bin to settle: a residual rule until both boundaries of the bin were measured, an occupancy rule until the bin has ended, a completion rule until the bin is final (every track resolved, up to about 2 hours with long waits). An alert that appears late is therefore expected; one that never appears usually means the zone's sensors give no occupancy at a boundary (no residual) or do not track people (no completion), or the zone has no physical capacity in its profile (nothing to check). After 3 hours a bin still unsettled no longer holds its rule back. Such a rule watches queue zones only. A residual or occupancy alarm, or a bin marked `Degraded` for its track completion (below 90 percent, Proposed), calls for re-validation of the zone (wiki 15, section 8; formulas F18).
- **Actions**: fix the data source; an edit of the rule restarts its counts. Do not delete `alert_rule_state` rows by hand.

### 4.8c Alert emails not arriving (ARV-040)

- **Symptoms**: an alert was raised or escalated but its people got no email.
- **Checks**: is `Email:Enabled` on in the base settings, and does the rule notify by email (`notifyByEmail`)? Who is told: when raised, the people of the rule's owner role (every operational role for a rule without owner); when escalated, the people of the escalation role; each enabled, holding the role and the alert's site, with an email address that is one plain address. A rule that escalates to a named contact rather than a role sends no escalation email. In the database, `email_message` has one row per alert, kind and address: `Pending` (waiting or to be retried at `next_attempt_utc`), `Sent`, `Suppressed` (held back by the hourly limit per address, `Email:MaxPerRecipientPerHour`) or `Failed` (given up after `Email:MaxAttempts`). `reason` names the error type of the last failure, never the server's reply.
- **Held back at sending**: an email is sent only while its recipient is still an enabled account with that address, holding the alert's site and the role it was written for; otherwise the round marks it Suppressed ("The recipient no longer holds ..."). One Integration replica sends at a time; the others skip the round.
- **Log lines**: Integration logs "Email round: n sent, n to retry, n given up, n held back" when a round has any of those and "Email round failed" with the error when a whole round fails; the writing host logs "recipients skipped for an address that is not valid".
- **Actions**: fix the relay or its credentials; pending emails go out on the next rounds. Fix an address in the user's profile (Administration guide); emails already written keep the old address. Do not edit or delete `email_message` rows: the runtime role can change only how sending went (never the recipient, subject or body), Sent, Suppressed and Failed are final, and the rows are the record of who was told what.
- **Known limits**: delivery is at least once: if Integration stops between the relay accepting a message and the round's commit, that message is sent again. No digest or quiet hours yet; a burst over the per-minute limit waits for the next minutes.

### 4.8d Integration client locked out (ARV-042)

- **Symptoms**: an AODB or immigration system stops sending; its token exchanges answer 401 `invalid_client`.
- **Checks**: Integration logs "Integration token refused for {client}: {reason}" for each failure (wrong secret, wrong or reused TOTP code, address outside the allowed networks, disabled, locked, too many attempts in a minute) and "Integration client {client} locked until ..." when ten consecutive failures lock it (also the audit entry `IntegrationClient.LockedOut` and the counter `ariva.integration.lockouts`, meter `Ariva.Integration`). The client's view in administration shows `locked`; the failure count starts again at 0 when the lock is set, so a locked client with a count of 0 is normal. Common causes: the system's clock drifted (TOTP), the secret was rotated without the system being updated, a new source address, or a code used twice within one 30-second step.
- **What a lock does and does not do**: a lock stops new token exchanges only. Tokens the client already holds keep working until they expire (15 minutes), so a feed that is running does not stop at the moment of the lock; it stops when its token expires and the next exchange is refused. Exchanges from addresses outside the client's allowed networks are refused without counting, so a lockout always comes from inside those networks: either the integrator's own system or something on that network. Calls beyond 5 exchanges a minute for one client are refused without counting either.
- **Actions**: fix the cause with the integrator, then unlock the client (it also unlocks by itself after 15 minutes). Enabling a disabled client does not clear a lock; unlock it separately. Repeated lockouts with no cause on the integrator's side are an attack from inside the client's networks: narrow the allowed networks, disable the client (its tokens stop at once), rotate its secret and reset its seed. `integration_call` records every accepted or refused API call of the client with its payload's SHA-256 (the source address too), which shows where the failures came from; a call cut off while its body arrives is the exception (section 4.8e, ARV-229).

### 4.8e Integration batches and AIDX messages refused or replayed (ARV-043, ARV-044)

- **Symptoms**: an integrator reports 422 on a batch, or that a batch "did nothing", or that its feed went stale while it was sending; or a batch answered 503 with Retry-After, or 408 (ARV-096b).
- **Checks**: `integration_call` shows each call of the client (all but one cut off while its body arrives, below) with its status and payload SHA-256 (route `.../flights/batch`, `.../flights/events`, `.../allocations/batch`). A 422 means the integrator reused an `Idempotency-Key` for a different body, endpoint or site within 24 hours: their retry logic is generating keys per attempt group rather than per batch. A batch "doing nothing" is usually a replay (the answer carries `Idempotent-Replayed: true`) or items that were `unchanged` (nothing newer than what Ariva knows) or refused (each item's `errors`). `integration_idempotency` holds each key's claim and answer for 24 hours (read only for the runtime role apart from storing the answer once); Ariva.Api.Integration deletes expired keys every 10 minutes ("Deleted {Count} expired idempotency keys"). A feed is the client's own (`api-` and the client id without `ic_`), so the stale-feed alarm of runbook 4.3 names the client. A 429 is either the client's allowance (120 batches a minute per replica, `Retry-After` given; the call is in `integration_call`) or the replica's at-once limit (8 handled, 16 waiting; not in `integration_call`, since it is refused before authentication). Sustained 429s for one client mean its system sends tiny batches too often: ask for fuller batches; raise `Security:RateLimiting:IntegrationClient` only with a reason.
- **Actions**: tell the integrator to use one new key per new batch and the same key only when retrying that batch unchanged. For AIDX (route `.../aodb/aidx`), a 400 names only the line and position where the message broke Ariva's AIDX profile or was not well-formed (a DOCTYPE is always refused); ask the integrator for that message and compare it with wiki 08 section 8. Legs refused in a 200 answer are `Warning` elements with `Status="Refused"` and the reason; "exactly one airport of this site" means the site's airports (topology) do not include the leg's airport, or the AODB sends ICAO codes the airport record lacks. Never delete keys by hand to "unblock" a client: a deleted key lets a retry apply the batch again. If the sweep logs failures, the keys simply live longer; the table grows by one row per batch.

- **503 or 408 on a batch (ARV-096b)**: a batch's body must arrive within the host's default request timeout (`Security:RequestTimeouts:DefaultSeconds`, 120 s; an AIDX message the `transfer` timeout, 15 minutes), and over HTTP/1.x at 32 KB a second or more after 10 seconds (408 below that). Either means the integrator's link or sender stalled while sending; the batch was not applied (no item is applied before the body is whole) and is retried with the same `Idempotency-Key`. Such a call is not in `integration_call` (the call audit records a call once it has read its body; ARV-229): ask the integrator for the time and look for the 503 or 408 in the ingress access log. A 1 MB batch takes about 40 s at the slowest rate allowed.

### 4.8f Outbound endpoint failing (ARV-045)

- **Symptoms**: an ACRIS flight feed goes stale (runbook 4.3 names the feed `acris-` and the endpoint's code); the endpoint's view in administration shows a growing `consecutiveFailures` and its `lastStatus`.
- **Checks**: Integration logs "ACRIS pull from {endpoint} refused: {reason}" (warning) or "... failed". `lastStatus` says which: "Refused to connect: the address is outside the endpoint's allowed networks" (the partner moved or its DNS changed: confirm with the partner before widening the networks, and never to a broad range), "...link-local or metadata..." or "...loopback..." (the name now points at a forbidden address: treat as an attack until explained), "...redirect, which Ariva does not follow" (ask for the final URL), "The circuit to {endpoint} is open after N failures in a row" (it retries after the break), "The endpoint answered 401" (the key or credentials changed: replace the secret), "Not modified." (normal), "Pulled N flights: a applied, r refused" (refused flights touch none or both of the site's airports, or break the flight rules). "The endpoint's secret cannot be read with this key ring; set the secret again." (logged as an error "its secret cannot be unprotected") means the Data Protection key that protected the secret is gone (a ring restored from an older backup, or another environment's database): only that endpoint stops; set its secret again.
- **Actions**: fix the cause with the partner; change the connection or replace the secret (both critical actions); the next due pull uses it. Disable an endpoint that must stop at once. In k8s-prd an endpoint whose pulls time out on connect after it was registered or its networks changed needs its networks in `networkPolicies.outbound` and a release (ARV-085, section 4.15).

### 4.8g SSIM import refused or partial (ARV-046)

- **Symptoms**: a preview or import answers 400, 409 or 413, or the preview lists line errors.
- **Checks**: 400 "no flight leg records" means the file is not chapter 7 (or is another encoding); "The site has no airport" means the site has no terminal under an airport in the topology; 409 means the import is not what was previewed (the file was re-exported or edited, the horizon or site differs, another administrator sent it, the day changed, or the preview is older than two hours): preview again; 413 is a file over 20 MB (split it by carrier). Line errors give the line number and the field that broke (period, days, times, variations, frequency, length, characters). Legs of other airports are skipped, not errors. An import that reports many `unchanged` legs met legs a live feed has reported (`flight_leg.schedule_fallback = false`) or an earlier import that said the same: expected, since a schedule never changes a leg a live feed has reported. The audit entry `FlightSchedule.Imported` holds each import's SHA-256, outcome (`completed` or `failed`), units committed and counts; a failed import keeps the units it committed (500 legs each) and can be imported again, since repeated legs are `unchanged`.
- **Actions**: fix the file with the airline or the AODB team, preview again, import with the new preview token.

### 4.8h AMAN feed or immigration records refused or kept apart (ARV-048)

- **Symptoms**: the immigration endpoints answer items with `errors` or warnings, Integration logs "AMAN {contract} record refused" or "Border feed code {code} of site {site} has no AMAN desk code mapping" (the code hashed since ARV-091; the codes themselves: section 4.16), `ariva.border.feed.records{outcome="refused"}` or `ariva.border.feed.unmapped` rises, or records appear on `ariva.aman.feed.*.v1.dlq.v1`.
- **Checks**: a refusal names the rule: `intervalSeconds is 60`, `starts on a whole minute`, `at most 7 days ago and not later than Ariva's clock allows` (clock skew, or a simulator run faster than real time: `Border:Feed:AheadMinutes`), sums that do not add up, `small-cell suppression` (AMAN must fold categories under 3 into `Other`), lanes, a site other than the call's or one Ariva does not know. Dead letters are values that are not the contract (an unknown member, an enum that is not an exact member name, a time without an offset): check AMAN's contract version against `ContractVersion.Current`. An unmapped code is stored with no desk (`desk_id` null in `border_desk_*`, `border_egate_interval`): add the AMAN desk code mapping (Administration guide, desk code mappings); records received before the mapping keep no desk. `unchanged` means the record was already received (the same `sourceEventId` at the site, over either transport) or, for lane demand, a newer computation is known.
- **Actions**: map the code; ask AMAN to correct the contract or the suppression; never edit the tables (the runtime role cannot).

### 4.8i Desk states Unknown or e-gate minutes missing (ARV-049)

- **Symptoms**: AMAN desks show `Unknown` in `desk_minute` (`unknown_seconds` 60), `egate_minute` has no rows for a site, or Stream logs "Desk feed read failed".
- **Checks**: Stream's desk feed reads the records the immigration intake stored (4.8h first: no stored records, no desk states). AMAN desks turn `Unknown` two minutes after AMAN's last record of the site (the feed is their heartbeat); a desk AMAN never reports a session for is `Closed`. Only desks with an AMAN desk code mapping take part, keyed site/checkpoint/desk in the minute tables. `desk_feed_state` holds each site's read position and engine (`updated_on` moves every `Border:DeskFeed:PollSeconds` while Stream runs; a stale one means the worker stops or another replica holds the site's lock). Records more than 15 minutes late, or more than 5 minutes ahead of Stream's clock, are not applied (a simulator run faster than real time). A burst larger than `MaxRead` is read over several polls; a record whose intake transaction committed more than two minutes after it was stamped is not read (the overlap), and a record dated ahead of Stream's clock never extends the feed's heartbeat. Two desks whose checkpoints share a code on different levels share a key and are left out (logged): rename one checkpoint.
- **Staff and service zones (ARV-116)**: a desk whose staff or service zone (in the published profile, naming the desk) has reported takes part too, AMAN or not; the stream writes the readings to `desk_zone_reading` (kept 7 days) and the feed reads them every poll. A desk with zones and no AMAN code turns `Unknown` two minutes after its zones' last reading; an AMAN desk whose zones fall silent stays on AMAN's state, flagged `degraded`. A zone that never reported does not count (a zone drawn without a sensor over it). No readings for a desk: check that the zone names its desk in the published profile (and that the desk is not an e-gate), that the device covering it reports occupancy for that zone name, and `SELECT desk_code, source, max(reading_utc) FROM desk_zone_reading WHERE site_code = '<site>' GROUP BY 1, 2`.
- **Actions**: restore AMAN's feed or the mapping; restart Stream if `updated_on` is stale. Deleting a site's `desk_feed_state` row (migration role) restarts its desks from now (its AMAN feed age keeps the heartbeat each Stream pod knew, and after a pod's restart counts from its first listing of the site until AMAN is heard); never edit the minute tables.

### 4.8j AMAN pull failing (ARV-050)

- **Symptoms**: an `AmanFeed` outbound endpoint shows `consecutive_failures` rising, or its `last_status` reports refused or unreadable records; Integration logs "AMAN pull from {endpoint} failed".
- **Checks**: `AMAN answered 401.` is a refused exchange (client id, secret or TOTP seed wrong, or the host's clock more than 30 s off) or a refused call (the code on each call is wrong: the clock or the seed); "already requested in this TOTP step" means a retry within the step and clears itself; "not its feed envelope", "did not move forward" or "more than 1000 records" mean AMAN's answer is not the feed Ariva expects (check AMAN's version and the feed path); unreadable records are not the V1 contracts (4.8h); a refused or unreachable address is the SSRF control (4.8f, the endpoint's networks). The position per contract is in `aman_pull_cursor`.
- **Actions**: set the secret again (`PUT {id}/secret`), correct the connection, or ask AMAN to fix its feed. If AMAN restarted its sequence, a position beyond it finds nothing new: register a new endpoint (a new position) and disable the old one.

### 4.8k Availability ledger (ARV-118)

- **What runs**: Ariva.Api.Cronz's TickerQ function `AvailabilityLedger`, every minute at second 30. For each site with a published or retired zone profile it decides every minute whose end is at least `Availability:GraceSeconds` (120) past and writes one `availability_minute` row per site and minute (first decision stands). It reads Redis live snapshots and the database only. A site's ledger starts at the first whole minute at or after the first publication of its zone profile (ARV-150, `rule_version` 2): no minute before it is written, a new profile version does not restart it, and a site never published has no minutes; a site published before Cronz first ran for it starts at the latest decidable minute. A site Cronz sees while its first minute is still live stores that start at once, before its time zone is resolved, so a site skipped for an unknown time zone keeps it; its minutes are decided from the next run.
- **Symptoms**: a site's availability drops, or days show unobserved minutes; Cronz logs "Availability ledger of site {Site} failed" or "caught up {Minutes} minutes from the database alone", or warns once that a site's airport time zone "is not known on this host": that site is skipped (no minutes written, its cursor unmoved) until the airport's IANA zone resolves on the Cronz image (tzdata) or is corrected; the backlog is then filled, as `Unobserved` beyond the live window.
- **Checks**: the reasons say why: `SELECT state, reasons, count(*) FROM availability_minute WHERE site_code = '<site>' AND minute_utc > now() - INTERVAL '1 hour' GROUP BY 1, 2`. `StaleZone`: no fresh live snapshot (4.8a: Stream publishing, Redis reachable from Cronz); `MissingMinute`: Stream writes no `queue_minute` rows for a zone (4.5b); `StreamLag`: Stream behind real time (4.6); `NoPublishedZones`: the profile in force has no queue zone, or a `zone_profile.published_on` lies more than 60 s ahead of the Cronz clock: Cronz then warns once per site that "its first zone profile publication is stored more than 60 s ahead of this host's clock and is not trusted" (compare the hosts' clocks); `NotObservedLive`: minutes decided after Cronz was down. `availability_cursor` holds each site's catch-up position; minutes in their live window are written first, then the backlog at most `Availability:MaxMinutesPerRun` (1,440) per run. Each site's pass holds the advisory lock (50, hashtext(site)); a second replica skips a site held by another.
- **Actions**: fix the cause upstream; the ledger records what happened and is never edited (the runtime role cannot update or delete it). Minutes missed while Cronz was down are recorded as `Unobserved` once it runs again; they cannot be turned into available minutes later. A rule change for the KPI annex is a new rule version (`rule_version`) applied from its release, never a rewrite of past rows. Operating hours and maintenance windows are kept by administrators (wiki 11 section 2b) and must be recorded before they take effect.

### 4.8l Recommended open desks (ARV-181a)

- **What runs**: Ariva.Api.Cronz's TickerQ function `StaffingRecommendations`, every minute at second 45. For each site with an arrivals-hall lane (a queue zone with a lane category on a level with an Immigration checkpoint) it reads the lanes' last hour of queue and desk minutes, the arriving legs to 195 minutes ahead and AMAN's e-gate rejects, computes each lane's 13 intervals (formulas F16 pilot version) and inserts them once into `lane_staffing` under the site's advisory lock (class 51): the first computation of a minute stands, a second replica skips the site, and so does a second run on the same replica (TickerQ starts the next occurrence while a run is still going, and fires about one occurrence in ten twice; ADR-0020, measured by ARV-124a). Ariva.Api.Main's `GET api/v1/sites/{siteCode}/staffing-recommendation` answers each lane's latest minute, `Stale` when it is more than `Staffing:StaleMinutes` (3) old. A minute missed while Cronz was down stays empty: the arrival wave as it was then cannot be read back.
- **Symptoms**: lanes answer `Stale` (the job is not running, or every run of the site fails); Cronz logs "Staffing recommendation of site {Site} failed", or warns "Staffing recommendation of site {Site} refused: {Bound}" with a fixed text naming the bound (more arrivals-hall lanes than one run takes, more lane desks, queue minutes or desk minutes than one run reads; CWE-400): nothing is written for that site until it is back within the bound, never a part of it. A warning "Staffing recommendation of site {Site}: {Lanes} lanes refused: more desks in one lane than one run takes" means a lane matches more than 1,000 desks; "... lanes refused: a queue zone whose key is longer than a message key" means a queue zone's key (the site code, a slash and the zone name) exceeds 200 characters, which the zone profile editor refuses, so the profile was written outside it: rename the zone in a new profile version (until then it still counts in its lane's sharing, ARV-185). Either way that lane reads `Stale` and the site's other lanes are written. One site that fails does not stop the others: the job's warning counts the sites failed and refused and the lanes refused. A warning "Staffing recommendation (Cron): the run took {ElapsedMs} ms, its whole minute or more, so the next run started beside it" (written as well after the warning of a troubled run that took as long) means the job no longer fits its minute: the runs overlap, and a site the earlier run still holds is skipped by the next, so that site's minute stays empty; look at the number of sites and lanes in the line, then at the database (ARV-124a measured a run at pilot scale, wiki 05). Every run's duration is in TickerQ's own line at Information, "TickerQ Job completed: StaffingRecommendations (<id>) in <ms>ms - Success: True" (the same for every job).
- **Checks**: the reasons say why a lane has no number: `SELECT zone_key, lane_gap, gap, count(*) FROM lane_staffing WHERE minute_utc > now() - INTERVAL '10 minutes' GROUP BY 1, 2, 3`. `NoQueueLength`: no live queue minute in the last 3 minutes, a degraded length, or a length out of range (4.2, 4.5b); `NoThroughput`: the lane's exits and desk minutes give no measurement (a quiet hour, desk states Unknown, 4.8i) and no fallback is configured (`Staffing:Sites:<site>:FallbackCycleSeconds:<lane>`, wiki 07 section 5); `NoDesks`: no desk in service matches the lane; `FlightWithoutPassengers` and `BacklogUnknown`: an arriving leg has no passenger figure (an SSIM leg without AMAN's lane demand, an AODB leg without an estimate or seats; 4.3, 4.8g), and the rows after it follow; `ArrivalsTruncated`: more than 2,000 arriving legs in reach; `NoLaneDemand`: the lane takes no manual category of the wave (e-gates, a site's own lane code, or the shared lane `ALL` when every one of CIT, RES, VIS and CRW has a queue of its own at the site); `ArrivalsOutOfRange`: the wave gave the interval a number that is not plausible (not finite, negative, or above a million: check the leg's passenger figure, 4.8g), and the rows after it read `BacklogUnknown`. A lane reads `Stale` also when its stored minute does not hold together as the API reads it back (a row changed outside Ariva).
- **Actions**: fix the input upstream; the rows are never edited (the runtime role cannot update or delete them) and drop after `migration.retention.laneStaffingDays` (90 days by default, section 4.8m). Target, busy cap and fallback values are configuration (wiki 04 section 5); a host refuses to start with one out of bounds.

### 4.8m Data retention (ARV-111a)

- **What runs**: two things, both from the periods of `Database:Retention` (in the clusters the Helm values `migration.retention` of the environment; wiki 04 section 5; every table with its period: the [data inventory](../docs/privacy/data-inventory.md)).
  - The migration job (the Helm hook `database-migration`, before every release) sets each period after the scripts, with the migration login: the TimescaleDB retention policy of `sensing_event`, `sensing_batch` and `device_health_event` (raw sensing, the dispute window), `desk_zone_reading`, `lane_staffing` and `advertising_play` (the proof of play, ARV-144), and the relational periods in `retention_period`. It logs one line per table or data set: "Retention of {Name} stays {Days} days", or "Retention of {Name} set to {Days} days (was {Previous})" when it replaced a policy or a period. A period out of range stops the job with "Database:Retention:{Key} is a whole number of days from ... to ..." before anything changes. TimescaleDB's own background job (`policy_retention`, once a day) then drops whole chunks older than each period.
  - Ariva.Api.Cronz's TickerQ function `RelationalRetention`, daily at 03:15 UTC: for alert emails (`email_message`, never a Pending one), Integration API call records (`integration_call`) and report deliveries (`report_delivery`) it deletes the rows older than their period, oldest first, `Cronz:Retention:BatchSize` (5,000) rows per statement and transaction, at most `MaxBatchesPerRun` (100) batches per data set; the rest waits for the next run. It connects as the runtime login, which may not delete these rows itself: each batch is one call of the database function `ariva_retention_purge` (script 0054), which reads the period the migration job wrote. One replica runs it at a time (session advisory lock, class 52).
- **What it logs** (Cronz): per data set "Retention of {DataSet}: {Rows} rows older than {Days} days deleted in {Batches} batches" (Information; nothing older is Debug only); a warning when a run stopped at its batch limit ("... the most one run takes; the next run deletes the rest") or when a data set has no period ("Retention of {DataSet} skipped: no period is set; the migration job sets it"); an error with the exception when a data set failed ("Retention of {DataSet} failed after {Rows} rows in {Batches} batches; the next run tries again"), the other data sets going on; and a summary "Retention ({Type}): {Rows} rows deleted over {DataSets} data sets", a warning when a data set failed or had no period, or "another replica is running it; skipped". Logs name data sets, periods and counts only, never an address, a route or a recipient.
- **Checks**: the periods in force: `SELECT hypertable_name, config ->> 'drop_after' FROM timescaledb_information.jobs WHERE proc_name = 'policy_retention';` and `SELECT * FROM retention_period;`. TimescaleDB's runs: `SELECT job_id, hypertable_name, last_run_status, last_successful_finish, total_failures FROM timescaledb_information.job_stats;`. What the Cronz job still has to do: `SELECT count(*) FROM integration_call WHERE at_utc < now() - make_interval(days => (SELECT days FROM retention_period WHERE data_set = 'integration_call'));` (and the same for `email_message` by `created_utc`, `report_delivery` by `created_utc`). The job can be run at once from the TickerQ dashboard where it is enabled (`Cronz:Dashboard`, wiki 04 section 6.4); running it twice is harmless.
- **Alerts** (ARV-259c): `retentionFailed` reads the last Cronz run (`ariva.retention.problems`): `failed` names data sets whose purge failed (the Cronz log has the error), `unset` data sets without a period, `run` a run that failed as a whole (the database out of reach, its run timeout of an hour, or the periods unreadable; TickerQ's dashboard and the Cronz log have the exception). It is held a day and two hours after the run, so after a fix run the job from the dashboard to clear it; with more than one Cronz replica, another replica's older copy stays until it lapses, so restart the replica that reported it (a replica that restarted reports nothing until the next run). Neither rule fires while its job does not run at all (the retention job turned off or its schedule stopped, the check failing on every run): watch the Cronz log and TickerQ's dashboard for that. `policyJobsFailed` reads TimescaleDB's own jobs every 10 minutes (`ariva.retention.policy_jobs_failed`): find them with `SELECT j.job_id, j.proc_name, j.hypertable_name, s.last_run_status, s.last_successful_finish, s.total_failures FROM timescaledb_information.jobs j JOIN timescaledb_information.job_stats s USING (job_id) WHERE s.last_run_status = 'Failed';` and their errors in `timescaledb_information.job_errors` (read it as the migration login: it shows a job's errors to its owner only) or the database log. TimescaleDB retries a failed job on its own, less often after each failure (up to the job's schedule, a day for the retention policies); after a fix, `SELECT alter_job(<job_id>, next_start => now());` as the migration login (the job's owner) has the scheduler run it at once and record the run, which clears the rule at the next check. `CALL run_job(<job_id>);` runs it in your session without recording it in `job_stats`, so it does not clear the rule. A paused job (`timescaledb_information.jobs.scheduled` false; nothing in Ariva pauses one) counts by its last run; the pause itself is not seen.
- **Actions**: a missing period means the migration job has not run on this database since ARV-111a: run it (wiki 04 section 7.1). A run that keeps stopping at its batch limit is catching up a backlog (the first run after the period is set, or a shortened period): raise `MaxBatchesPerRun` for a while or let the daily runs finish it. A failing data set: read the error, fix it, the next run continues. To change a period, change `migration.retention` in the environment's values with the client's agreement (the dispute window is TC-62; the Proposed periods TC-66 to TC-68) and release; a shorter period drops older data at the next daily runs and cannot be undone. Never delete these rows or hypertable chunks by hand, and never give the runtime login DELETE on these tables.


### 4.9 Certificate expiry

- **Alarm**: `ariva.certificates.expires_in` (section 2a) counts down to the end of the Data Protection certificate in use (every host) and of Ingest's MQTT server certificate; it reads the certificate each pod loaded at start, so a renewed secret shows once the pods have restarted. The ingress certificate and device, partner and border-to-airport certificates are not in it: check them as below, or with the site collector or cert-manager. Neither are the pods' certificates in k8s-prd (`ariva-api-*-tls` and `ariva-web-tls`, ARV-082b): where cert-manager issues them, `ingressCertificateExpiry` covers them too, since it reads every cert-manager certificate of the namespace, but it reads the secret, not the certificate a pod serves. That matters for the web pods, whose nginx keeps the certificate it started with.
- **Checks**:

```bash
echo | openssl s_client -connect <host>:443 -servername <host> 2>/dev/null | openssl x509 -noout -enddate
kubectl -n "$NAMESPACE" get certificate    # where cert-manager issues it: the ingressCertificateExpiry alert reads these
# k8s-prd: what a pod serves against what its secret holds (web shown; api-main-service and the others likewise)
kubectl -n "$NAMESPACE" port-forward svc/web-service 8443:443 &
echo | openssl s_client -connect localhost:8443 -servername "web-service.$NAMESPACE.svc" 2>/dev/null | openssl x509 -noout -enddate
kubectl -n "$NAMESPACE" get secret ariva-web-tls -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -enddate
kill %1
```

Two different dates for the web pod mean the secret was renewed and the pods still serve the old certificate. Also check device client certificates (MQTT), outbound endpoint client certificates, the border-to-airport mutual TLS certificates, and integration partners' pinned CAs.

- **Actions**: renew through the customer's PKI; update the ingress certificate secret or the controller's default certificate; for device certificates, schedule rotation with the local partner outside peaks. Pod certificates (wiki 04 section 6.2): the API hosts serve a renewed `ariva-api-*-tls` by themselves within seconds of the kubelet updating the volume (each pod refuses new connections for up to about 5 seconds while it rebinds; the ingress retries on another pod, but api-cronz and api-integration have one pod each). The web pods take a renewed `ariva-web-tls` only when they restart: run `kubectl -n "$NAMESPACE" rollout restart deployment/web-deployment` after each renewal, or before the old certificate's end at the latest, since the ingress refuses an expired one and the web app's pages then fail with 502. A pod whose certificate the cluster CA in `ariva-cluster-ca` did not issue, or that does not name the pod's Service, fails the ingress's check (502 for that host); a CA secret the controller cannot read gives 503. After renewing an ingress certificate, run the TLS check (section 4.14).

### 4.10 Replaying a time range

Three kinds of replay exist; pick the right one.

| Need | Mechanism | Status |
|---|---|---|
| Recover after a crash, rebalance or Kafka outage | Automatic: consumers resume from committed offsets; idempotent upserts by (zone, bin start, revision) and event-id deduplication make replay safe | Built into the stream design |
| Recompute a disputed or misconfigured period | Recompute from raw samples in TimescaleDB (not from Kafka) under a named zone profile version; the result is a new revision and the original is kept | Target procedure, implemented in v1 epic SLA and penalty engine (recomputation and revision tooling) |
| Reproduce a day for tests or a demo | Ariva.Simulation.Api plays the reference scenario through the whole pipeline in real time (section 4.11); recorded customer feeds are not replayed yet | Built for the reference scenario (ARV-064); recorded feeds Target |
| Evidence for a period, or a regression check of an engine change | Golden replay of the archive (ARV-036): `Ariva.Api.Stream --replay`, below | Built |

Golden replay (ARV-036). Run the Stream image as a one-off job (or the host locally) with the runtime database login, as for the migration job:

```
dotnet Ariva.Api.Stream.dll --replay --replay-site=DMO --replay-zone=A-VIS --replay-zone=CI-C \
  --replay-from=2026-09-28T17:00:00Z --replay-to=2026-09-28T20:30:00Z --replay-profile-version=12 \
  --replay-output=/evidence/dmo-2026-09-28.jsonl
```

- Without `--replay-zone` every queue zone of the profile version is replayed; without `--replay-profile-version` the published one is used. Times are UTC and end in `Z`; a range is at most 31 days and a zone at most a million archived events and a million health reports (about 400 MB each in memory; split longer ranges, and give the job the Stream pod's memory). The archive keeps 90 days.
- The command prints the manifest (site, zones, range, profile version, engine version, settings hash), the hashes (`outputHead` is the stable output hash: the same archive, version and settings always give it), each zone's counters and the run's `rowHash`, and records the run in `replay_run`: the database sets the row's time and login and chains it to the run before, so a run cannot be backdated or slipped in later unnoticed. The export file is created new (never over an existing file or a link) with owner-only permissions; it holds one JSON line per archived record and per output row, each with its chain value. Hand it over with the printed `replayHash`, and keep the `rowHash` outside the database (in the evidence pack or the ticket) as the anchor.
- To check an export: `dotnet Ariva.Api.Stream.dll --verify-replay=/evidence/dmo-2026-09-28.jsonl`. Exit code 0 means every line is exactly as written, every chain value holds and the run is on record in `replay_run` (the output lists the recorded runs with their time, login and row hash); 3 means a line was changed, dropped, added, moved or given an extra property, the file is incomplete, or no such run was recorded (a recomputed chain shows here).
- What the chains prove, and what they do not: anyone who changes the export after the run is caught. The archive and `replay_run` are only as trustworthy as the runtime database login: whoever holds it can add archive rows or record runs (with the database's time, chained after the real ones). Keep that login to the Stream pods and the replay job, and compare a run's `rowHash` with the one kept outside.
- Expect the replay to equal what the stream wrote for the period except where records share a receive time (ordered by kind and id rather than Kafka offsets) and for tracks that cross UTC midnight (the archive's pseudonyms change daily); the zones start empty at `--replay-from`, so start an hour or two before the period of interest.

Do not reset consumer offsets by hand to "replay" a period until the procedure has been verified in Phase 0 epic Queue engine core; Kafka keeps track samples for only a few days, and raw samples in TimescaleDB are the source for anything older.

### 4.12 Host down or not ready (ARV-125b)

- **Symptoms**: `hostDown-<host>` (no health report from any pod of the host), `readinessFailing` (a readiness check Unhealthy, so readiness answers 503 and Kubernetes routes nothing to the pod) or `databaseUnavailable` (the `database` check Unhealthy).
- **Effect**: a host down stops its part of the system (Ingest: devices get no answer and keep their batches; Stream: no new minutes or alerts; Main: the screens and the administration). A pod not ready keeps running but gets no traffic. The database away makes every host's readiness fail together.
- **Checks**:
  1. `kubectl -n "$NAMESPACE" get pods -l app=api-<host>` and `kubectl -n "$NAMESPACE" describe pod <pod>`: restarts, `CrashLoopBackOff`, a failed startup probe, an image that cannot be pulled, a missing secret (in k8s-prd also the pod's `ariva-<service>-tls`, which keeps it in ContainerCreating).
  2. The host's log since the start: a setting refused at start names itself (`Hosting:ShutdownSeconds`, `Kafka:Consumers:StartWaitSeconds`, the schema version, and in k8s-prd `Kestrel:Endpoints`, `SslProtocols`, `ASPNETCORE_URLS` or `preferHostingUrls` when the pod would serve plain HTTP or weak TLS, ARV-082b, and `Security:ForwardedHeaders` when the trusted proxies are missing or unfit, ARV-085, section 4.15; the log collector, the pseudonym key and the log store's sender credentials, ARV-091a, section 4.17). A host that stops at start writes the refusal to its pod's own log (`kubectl -n "$NAMESPACE" logs <pod> --previous`), never to the log store.
  3. For the database: the TimescaleDB pod, its log and its volume (4.7), and `kubectl -n "$NAMESPACE" exec timescaledb-0 -- pg_isready`; for a database the site provides, its own monitoring.
  4. A host that runs but reports nothing: the OTLP endpoint (`otel.endpoint`) and the collector, since the rule cannot tell a silent host from a stopped one; in k8s-prd also the collector's peers in `networkPolicies.otlp` (section 4.15). A host whose logs are missing from Loki while it runs: `networkPolicies.loki` does not reach the address in `Loki:Uri` (production ships the documentation network `192.0.2.0/24` there), or Loki refuses the sender (section 4.17).
  5. In k8s-prd, a dependency that times out since a release: the NetworkPolicies' peers for it (section 4.15).
- **Actions**: fix the cause and let Kubernetes restart the pods; never set readiness aside. A Degraded check (Kafka, Redis, the message bus) does not make a host unready: it raises `kafkaUnavailable` or `busDegraded` (4.6).

### 4.13 Database or Kafka lost: restore and recovery (ARV-126)

The tooling is in `scripts/ops` (`ariva-ops.mjs` on an operator's machine, `ariva-db.sh` in the TimescaleDB pod); the procedure is wiki 04 section 10 and the Proposed recovery objectives are in its section 11.

- **Database lost or corrupted** (the TimescaleDB volume, an upgrade whose scripts cannot be rolled back, data deleted by mistake): restore the latest backup into an empty database (wiki 04 section 10.4), then run the migration job, restore the files, check the key ring against the certificate, start the hosts, run the release smoke suite, re-apply the security changes made since the backup (disabled accounts, removed roles, rotated credentials come back as they were) and, when Kafka survived, reset Ariva's consumer groups to the backup time.
- **Kafka lost** (topics gone, a new cluster): recreate the topics, scale api-stream to 0, run `node scripts/ops/ariva-ops.mjs after-kafka-loss --namespace "$NAMESPACE" --confirm-stream-stopped`, then start api-stream (wiki 04 section 10.5). `ariva.outbox.unsent` and `ariva.outbox.oldest_unsent_age` show the re-sent events until the relay has sent them; the outbox age alert can fire briefly.
- **The Data Protection certificate lost with no copy**: there is nothing to restore it from. An administrator resets every user's authenticator and every integration client's TOTP (they enrol again), outbound endpoints get their secrets again, everyone signs in again; then create a new certificate (wiki 04 section 6.2). Everything else is intact.
- Messages of `ariva-db.sh`: "is not empty" (a restore goes into an empty database only: give it a new volume); "refused: owned by ... not the migration login" (the dump is from another deployment, or its migration login has another name); "a key the hosts still need is wrapped under a certificate that was not given" (find the certificate in use at backup time, `DataProtection:Previous` during a rotation); "the restore did not finish" (fix the cause, then start again from a new volume). The wrapper's "the manifest's signature does not verify against ...: refused" (the manifest was altered, its signature is missing, or its signer is not in `allowed_signers`) and "has SHA-256 ..., not the expected ...: refused" (the file is not the one the signed manifest, or your own log, names) mean the backup set is not the one taken: do not restore it, and find out who could write to the backup store. Since ARV-183: "widens who may sign a restore" (a principal pattern or a `cert-authority` line in `allowed_signers`: list each signer by name with its own key; `--allow-signer-patterns` only if the file is meant so); "has lines a restore does not read" (a line that is not plain names, options, a key type and its key in printable ASCII, for example a byte order mark, a quoted name or a vertical tab: rewrite the line by hand, and find out who wrote it if you did not); "is a backup of the namespace ..., not ..." or "names no namespace" (the set is another deployment's, or from before ARV-183: check the printed namespace and time, then `--force-namespace` only if that is the set you mean). A `FAIL` line of `ariva-db.sh check` about functions, other functions, languages, extensions, plpgsql, system functions, event triggers, group members, held roles, logins, role settings, rules, replication, planted or settings after a restore means the database holds something no Ariva script creates: stop, do not start the hosts, and treat the dump as untrusted (what a server you provide carries on purpose passes when named: an extension with `--allow-extension`, a login with `--allow-login`, a setting with `--allow-setting`). On a running deployment the same lines mean someone with the migration login or the superuser changed the database: treat it as a possible compromise (section 4.13). "FAIL settings|the configuration files not read" follows a planted line: the superuser reads nothing until it is cleared. Since ARV-189: "FAIL runtime privileges" names each table or view whose grants to `ariva_runtime` differ from what the scripts leave (as "the scripts: ...; found: ..."); "FAIL views" a view of `public` the scripts do not create, or one reading something else; "FAIL internal privileges" a relation that grants it more than the rules allow ("(wider than ...)" for a chunk or other inheritance child wider than its parent, "(inherits ...)" for a child that is not one of TimescaleDB's chunks, "(more than SELECT)" for a continuous aggregate's table or view, "(reads ...)" for a view that grants what the role lacks on a relation it reads, a bare name for any grant on another relation outside `public`, "(sets values)" for a sequence, "(extension table)" or "(system table)" for one of TimescaleDB's or PostgreSQL's own); "FAIL runtime grants" a table or column granted to the runtime login (or another role holding `ariva_runtime`) rather than to the role, to the role with grant option, or to PUBLIC; "FAIL runtime role|may create objects" CREATE on a schema or the database for the role or a login of it; and "FAIL default privileges" a default privilege entry other than script 0001's two ("<role> in <schema> on <objects> gives ..."), which would widen the tables and views a later release creates: after a restore, treat the dump as untrusted as above; on a running deployment, someone with the migration login or the superuser changed a grant (section 4.13). "not compared" in restore's own check, after a restore of an older backup, is expected: run the migration job with `--migrate` and `check` again before starting the hosts (wiki 04 section 10.4, step 4); "FAIL runtime privileges|not compared" in a plain `check` means the database is behind the release's scripts: run the migration job, then check again. Since ARV-262: "FAIL schema" names each object of Ariva's that differs from a database the release's migration job migrated, "(differs)" for a relation's columns, constraints (or a disabled foreign key), indexes, triggers (or whether one is enabled), grants or a chunk that lacks its copy of a trigger, unique index or foreign key, a view's or continuous aggregate's definition, a function's definition, or a schema's or the database's grants, "(missing)" or "(not in the scripts)": after a restore, treat the dump as untrusted; on a running deployment, someone with the migration login or the superuser changed the schema (an index or grant a DBA added by hand fails it too: ship it as a script instead). To see each difference, run `node scripts/ops/ariva-ops.mjs schema --namespace <namespace> --full` on this database and on one this release's migration job migrated (a scratch namespace, wiki 04 section 10.6) and compare the two outputs line by line. "FAIL schema|not compared" behaves as the runtime privileges line does; "past the list" means the database ran newer scripts than this `ariva-db.sh` knows: run the one of the release that migrated it. "FAIL planted|function pg_catalog.... (created after initdb)" (or an operator) is an overload created in a system schema under a system or TimescaleDB name, which `update-extensions` refuses too: treat it as the other planted objects. "FAIL extension members" names an object added to TimescaleDB's extensions, missing from them or replaced in place ("changed", against template1's members of the same version); "has no members pinned here" means the image is not the one this release ships (use that release's `ariva-db.sh`, or move the image to it). "FAIL system functions|... differ from what this release pins" with "template1's are the same" means template1 changed as well, or the server is not the image this release ships. "FAIL settings|set outside the server's postgresql.conf" names each setting another file holds, with that file (`postgresql.auto.conf`, or a file an include line names): find out who, `ALTER SYSTEM RESET` what `postgresql.auto.conf` holds, take out an include line and the file it names, then restart the server; a DBA's own passes when named with `--allow-setting`, and the ok line names the file each allowed one comes from (a name allowed for one file showing up from another is a reason to look). These lines find what a careless forged dump leaves; they cannot prove a careful one absent (the superuser that ran it could have changed what `check` reads), so after a restore from a set whose origin is in doubt, the signed manifest decides, not a passing `check`. After a new TimescaleDB image (ARV-236, wiki 04 section 6.8): `check` failing on "extension versions ... run update-extensions" means the update has not run since the image changed (run it, with the deployments scaled to 0); "... it has no update from it): roll the image forward" (or `update-extensions` saying "has no update to") means the database image is older than the database's extension, as after a rollback of the database image past an update (roll the image forward; `update-extensions` refuses it too). `update-extensions` refusing with "Ariva's logins still have sessions" means a host is still connected (scale the deployments to 0 and wait for their pods to end); "refused before any statement as the superuser: function ..." or "operator ..." names an object outside the extensions under a system or TimescaleDB name, "extension ..." another extension, or "database setting ..." a setting made for every session of the database (`ALTER DATABASE ... SET`): treat it as a possible compromise of the migration login, find out who created it, remove it, then run the update again; "canceling statement due to lock timeout" means something held a lock for 30 seconds (nothing changed; run it again). TimescaleDB's own "cannot be updated after the old version has already been loaded" does not occur through the script (each update is its session's first statement); by hand it means a statement ran first in that session: start a new session with `psql -X`. After a restore of a backup taken before the last TimescaleDB bump, see wiki 04 section 10.4.
- Rehearse the restore at least before go-live and after every major release, in a scratch namespace (wiki 04 section 10.6).

### 4.14 TLS and header check of the hosts (ARV-084)

`scripts/ops/tls-check.mjs` (Node 22 only, no other dependency; `scripts/ops/README.md`) checks a site's hosts from outside and changes nothing. Per host it makes TLS handshakes, a `GET /` over HTTPS, one `POST` that announces a 1 GiB body and sends none (the ingress answers 413 before any pod sees it, which shows the headers of a response the ingress generates itself), a `GET /health/readiness` over HTTPS (ARV-085: the ingress must answer it 404, or 403 on a host with a source range, with the chart's headers) and a plain HTTP `GET /`. Every handshake verifies the host's certificate: a host whose certificate does not verify fails on that alone and is offered no weaker protocol, suite or HTTPS request. The dev release workflow runs it after each release (wiki 04 section 6.6). At a site, run it at go-live, after each release, after renewing an ingress certificate and after any change to the ingress controller or to what sits in front of it, from a machine that reaches the ingress:

```bash
kubectl -n "$NAMESPACE" get ingress -o json > ingresses.json   # read only
node scripts/ops/tls-check.mjs --ingresses ingresses.json
# hosts named by hand, with what they do with plain HTTP (refuse is the default), against the site's CA
node scripts/ops/tls-check.mjs --host api-ingest-ariva.example.com --host ariva.example.com=redirect --ca site-ca.pem
# split DNS, or before DNS exists: connect to a chosen address for a name
node scripts/ops/tls-check.mjs --host ariva.example.com=redirect --resolve ariva.example.com=10.20.0.15
```

- `--ingresses` checks the hosts of every Ingress that carries the chart's `ariva.dalil.tech/plain-http` annotation, with its mode; other Ingresses (an ACME solver) are left out, and Ingresses of one host that disagree are a usage error. `--host <name>[=refuse|redirect]` adds a host or overrides its mode.
- `--ca <PEM file>` verifies the certificates against that CA alone; without it, against Node's bundled Mozilla root store (the public CAs; leave `NODE_EXTRA_CA_CERTS` and `--use-system-ca` unset, or a site CA they add would let a site-PKI host pass as public). Hosts on the site's PKI and hosts on a public CA therefore need separate runs, with `--host`.
- `--port` (443), `--http-port` (80), `--timeout` (seconds, 10 by default, at most 120), `--summary <file>` (appends a Markdown table, as the workflow does to its summary).
- Exit code 0 when every host passes, 1 when one fails, 2 on a usage error. Each host prints `PASS` or `FAIL` with its notes (the TLS 1.2 and TLS 1.3 suites negotiated, certificate verified, plain HTTP refused or redirected) and one line per finding.
- Before it judges any host, the check proves that its own Node can offer TLS 1.0, TLS 1.1 and a TLS 1.2 suite without AEAD, against a local server; if not, it stops with "cannot offer ..., so it cannot prove a host refuses it" (run it with another Node 22 build or on another machine).

What each finding means:

| Finding | Meaning | Action |
|---|---|---|
| `accepts TLS 1.0`, `accepts TLS 1.1` | The controller allows old protocols: Ariva's controller values are not applied, or something in front of the controller ends TLS | Apply `ssl-protocols` from `Platform/Cloud/Ariva.K8s/Helm/ingress-nginx-values.yaml` (wiki 04 section 2); TLS must end at the controller |
| `accepts TLS 1.0, with a certificate that does not verify (<reason>)`, and the same for TLS 1.1 or a TLS 1.2 suite | The host answered the weak protocol or suite with a certificate other than its main one (whose own handshakes verified): something that serves those old handshakes with a second certificate, such as a default or fallback certificate. Answering counts as accepting | As the rows for the protocol or the suite; find what presents the second certificate (the controller's default certificate, a proxy in front) |
| `accepts the TLS 1.2 suite <name> (without AEAD)` or `(without ECDHE)`; `TLS 1.2 negotiates <name>, not one of the Mozilla intermediate suites` | The controller's `ssl-ciphers` is its default (which carries DHE and more) or another list | Apply `ssl-ciphers` from the controller values |
| `TLS 1.2 fails (...)`, `TLS 1.3 fails (...)` | The host does not take that version: a controller limited to one version, a proxy in front, a wrong address or no route | Apply `ssl-protocols: TLSv1.2 TLSv1.3`; check DNS or `--resolve`, and the route |
| `the certificate does not verify for <host> (<reason>)` | Expired (`CERT_HAS_EXPIRED`), for another name (`ERR_TLS_CERT_ALTNAME_INVALID`), or from a CA the check does not trust (for example `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, also given by a `tls.crt` without its intermediate CA). Every handshake verifies the certificate, so the host fails on this alone: no weaker protocol or suite and no HTTP request is offered to it, and its other findings appear only once the certificate verifies | Renew or reissue it (section 4.9; which CA, wiki 04 section 6.2); for the site's CA pass `--ca`; then run the check again for the rest |
| `GET / (<status>) has no Strict-Transport-Security`, `has more than one`, `max-age ..., under a year`, `without includeSubDomains`, `with preload` | The chart's headers are not in place: the controller refuses or ignores the chart's snippets (snippets not allowed, or a risk level below Critical), or another layer adds an HSTS header of its own | Apply the controller values; remove the other source (a proxy in front, which must not end TLS anyway) |
| `the ingress's 413 has no Strict-Transport-Security`, `lacks X-Content-Type-Options: nosniff`, `lacks a Content-Security-Policy with frame-ancestors 'none'` | Responses the ingress generates itself lack the chart's server-level headers: its `server-snippet` is not applied | Apply the controller values; read the controller's log for the Ingress |

| `GET / over HTTPS fails (...)`, `the body limit probe fails (...)`, `GET /health/readiness over HTTPS fails (...)` | The connection broke or timed out | The network or the controller; raise `--timeout` |

A run with findings after a release leaves the release applied (the check rolls nothing back): fix the cause and run the check again. Not checked: a 400 that nginx answers for an invalid Host header carries no HSTS (a known gap, wiki 13 section 6), and no cookie is read.

### 4.15 Network policies: opening a flow, a blocked connection, the probes (ARV-085)

In k8s-prd every Ariva pod denies all traffic but the firewall matrix's flows, and each flow's peers and ports come from the release's values (`networkPolicies`, `ingressController`; wiki 04 section 5, wiki 05 section Network policies). Changing a flow is a values change and a release, made by a person in a window: every apply restarts every pod (wiki 04 section 6.4).

Opening a flow for a new outbound endpoint (an AODB, an ACRIS API, AMAN's Integration API, an SMS gateway, a webhook):

1. Take the endpoint's networks from its `OutboundEndpoint` record (the allowed CIDRs the administrator registered, which its names must resolve into) and its port. The policy should allow the same networks, no wider: in k8s-prd the chart refuses a peer wider than /8 (IPv4) or /16 (IPv6).
2. Add an entry to `networkPolicies.outbound` in the site values file: a `name` (a DNS label, not used by another entry), `to` with one `ipBlock` per network, and `ports`, for example `- name: aodb`, `to: [{ ipBlock: { cidr: 10.20.30.0/24 } }]`, `ports: [443]`.
3. Preview with `helmfile diff` (or `helm diff upgrade`, read only): the only change should be a rule more in `api-integration-outbound-egress`, besides the pods' `rollme` annotation. Release it.
4. Check the endpoint's `lastStatus` in administration and the Integration log (section 4.8f).

The same applies to the other flows: the OTLP collector (`networkPolicies.otlp`; the chart refuses `otel.endpoint` without it), Loki (`loki`; the chart requires peers with `logging.collector` `loki`, but cannot check that they hold the Loki of `Loki:Uri`, so with the wrong peers the logs silently stay in the pods: wiki 04 section 8, check 10), the SMTP relay (`smtp`), the sensor networks for MQTT (`mqttSensors.from`), and kube-dns, the database, Kafka and Redis when they move. Release a moved database's or brokers' new peers before the release that points the hosts at them, since the migration and topics jobs (pre-upgrade hooks) run under the previous release's policies. A flow the chart does not know (a backup job, a metrics scraper) gets a NetworkPolicy of the site's own; policies add up.

A connection a NetworkPolicy blocks is usually dropped, not refused, so the caller sees a timeout rather than "connection refused":

- Integration: an outbound endpoint whose `lastStatus` reports a connect timeout right after it was registered or moved has no `networkPolicies.outbound` entry for its networks yet.
- A host after a release: a database connect timeout (its start or its readiness fails, section 4.12), a Kafka broker that cannot be reached (`kafka` Degraded, section 4.6) or Redis timing out after the peers changed point at `networkPolicies.database`, `kafka` or `redis`: compare their peers with the pods' labels and namespaces (`kubectl get pods -A --show-labels`, read only) and their ports with the ones the brokers advertise.
- Telemetry or logs missing since a release: `networkPolicies.otlp` or `loki`.
- Nothing reaches a pod through the ingress (502 or 504 from the controller): the `ingressController` selectors do not match the controller's pods (`kubectl -n ingress-nginx get pods --show-labels`, read only), or the controller runs on the host network, which needs a NetworkPolicy of the site's own.
- MQTT devices time out on connect: `networkPolicies.mqttSensors.from` lacks their network.

Where the CNI offers them, its own flow logs or policy verdicts show the drop and the policy (for example Cilium's `hubble observe --verdict DROPPED`). `kubectl -n "$NAMESPACE" get networkpolicy` and `kubectl -n "$NAMESPACE" describe networkpolicy <name>` (read only) show what the release rendered.

A host that refuses to start in k8s-prd with a `Security:ForwardedHeaders` message names its trusted proxies (`ingressController.podNetworks`): none given, 0.0.0.0/0 or ::/0, wider than an IPv4 /14 or an IPv6 /48, an entry that does not parse or has address bits after its prefix, or an IPv6 network that would trust IPv4 clients through the dual-stack mapped form (wiki 04 section 5). The messages never name the entry: compare the values with those rules.

The readiness check from inside the cluster: the probes answer only on the pods' own ports, and every Ingress answers `/health` and `/healthz` 404, by design. No other pod may connect to an Ariva pod in k8s-prd (only the ingress controller, on the serving port), so check readiness through a port-forward, which connects inside the pod's own network namespace and is not subject to the policies: `kubectl -n "$NAMESPACE" port-forward svc/api-main-service 8443:443`, then `curl -fsS --cacert cluster-ca.crt --resolve api-main-service:8443:127.0.0.1 https://api-main-service:8443/health/readiness` (wiki 04 section 8, check 2). The kubelet's own view is the READY column of `kubectl -n "$NAMESPACE" get pods` and the probe events of `kubectl -n "$NAMESPACE" describe pod <pod>`. The kubelet probes from the pod's node, which a NetworkPolicy cannot block; where a host firewall filters node traffic, probes failing on every pod at once after a release point at it (the site adds a NetworkPolicy for the nodes' addresses to 8443 and 3443). An external monitor that probed `/health` through the ingress gets 404 now: watch `ariva.health.status` instead (section 2a).

### 4.16 Security events, the trace id and the pseudonym key (ARV-091)

Every API host writes its refusals and account actions as security events: a name `SecurityEvent.<Name>` and an EventId that stays the same across releases (9101 to 9130; the Cronz dashboard's 9601 and 9602 have ids but no such name). A 401, 403 or 429 that no specific event recorded is still logged when its request ends, as `SecurityEvent.RequestRefused` (9129) with the status and a fixed reason: an ended session, a pending account, a service's own refusal, an integration client's own limit, the upload limit, and the sign-in's and the token refresh's refusals (the sign-in's `mfa_required` 401 among them, part of every two-step sign-in, and the refresh's 401 when a page loads after its session has ended: both routine). The [log inventory](../docs/security/log-inventory.md), section 10, lists each event with its fields, what it never contains and a proposed alert. No alert on them ships with the chart (the SigNoz rules of section 3.1 read metrics): set the proposed ones up in the site's log store or SIEM.

- **Finding them** (read only). In a JSON line the id is `Properties.EventId.Id` and the name `Properties.EventId.Name`; the request-level events (9114 to 9119, 9127 to 9129) also carry `CallerUserId` (or `CallerClientId`, `CallerDeviceId`, `CallerDisplayId`), `CallerAddress`, `Method`, `Endpoint` (the route pattern) and `Reason`, and 9129 its `Status`. In Loki, search the text, for example `{app="api-main"} |= "SecurityEvent.AuthorizationForbidden"`; in SigNoz, search the log body for `SecurityEvent.`. From the pods:

  ```bash
  # The security events of one host in the last hour: time, id, who, from where, where, status, why, trace.
  kubectl -n "$NAMESPACE" logs -l app=api-main --since=1h --max-log-requests=10 \
    | grep -F '"Name":"SecurityEvent.' \
    | jq -c '{t: .Timestamp, id: .Properties.EventId.Id, who: (.Properties.CallerUserId // .Properties.CallerClientId // .Properties.CallerDeviceId // .Properties.CallerDisplayId), from: .Properties.CallerAddress, at: .Properties.Endpoint, status: .Properties.Status, why: .Properties.Reason, trace: .TraceId}'
  # One kind only, for example the 403s:
  kubectl -n "$NAMESPACE" logs -l app=api-main --since=1h --max-log-requests=10 | grep -F '"Id":9114,'
  # The throttle's summaries: how many events of each kind were left out, and over how many seconds.
  kubectl -n "$NAMESPACE" logs -l app=api-main --since=1h --max-log-requests=10 | grep -F '"Id":9130,' \
    | jq -c '{t: .Timestamp, kind: .Properties.Kind, id: .Properties.KindEventId, left_out: .Properties.Count, seconds: .Properties.Seconds}'
  ```

  Replace `api-main` with `api-ingest`, `api-integration`, `api-cronz` or `api-stream` for the other hosts. `kubectl logs` reads what the kubelet still keeps (log inventory, section 2.2); older events are only in the site's log store.
- **Following one request (the trace id).** An error answer (ProblemDetails) carries `traceId`, `00-<trace id>-<span id>-01`: the 32 hex characters after `00-` are the trace id. Every line that request wrote, in each host it reached, has the same `TraceId` at the top level of its JSON line: `grep -F '"TraceId":"<trace id>"'` over the host's logs, or the trace id in SigNoz, which also shows the request's spans. Ask a user or an integrator who reports a refusal for the answer's `traceId` and its time.
- **Who and where.** A line a request writes names the client address (the client the ingress controller named, `Security:ForwardedHeaders`) and the caller by id: a user's account id and session id, an integration client's id, a device's or a display's id; never a name or an email address. These are the `Caller` fields: `CallerAddress`, and `CallerUserId` with `CallerSessionId`, or `CallerClientId`, `CallerDeviceId` or `CallerDisplayId`. `CallerUserId` says `anonymous` before the authorization decision, on endpoints that allow anonymous callers (sign-in, token refresh) and on every 429 of the rate limiter (it runs before authentication), and `unknown` for a principal with no id Ariva knows. A line that is about another account names that account in its own `UserId` (and `SessionId`): in an administrator's action, `UserId` is the account acted on and the `Caller` fields are the administrator. An administrator turns an account id into a person with `GET api/v1/admin/users/{id}`; a session id leads to the session's sign-in record (`user_session`).
- **Floods: the throttle, the summaries and the metric.** Per kind and host process, at most 60 request-level events are written a second, and at most 3 from one source (the identified caller, else the client address, an IPv6 address counted by its /64; the logged `CallerAddress` stays whole), so one source's flood does not hide another's events. The events left out are counted: every 10 seconds, and when the host stops, a `SecurityEvent.EventsSuppressed` line (9130) per kind gives `Count`, `Kind`, `KindEventId` and `Seconds`, and the metric `ariva.security.events` (section 2a) counts every event by kind and outcome (`written`, `suppressed`, `failed`). A 9130 means a flood (a scanner, a broken client, an attack on the sign-in): read the written events of that kind for its sources, and the metric for its size. A flood from 20 or more distinct sources (by /64 for IPv6) in one second on one pod fills the kind's 60 lines; the rest are only in the summary and the metric, which give their count but not their sources. A `failed` outcome means an event could not be written; the answer to the request was not changed.
- **Masked and hashed values.** A value shown as `[REDACTED]` where no credential is expected was one the enricher could not protect: it fails closed, and `ariva.security.log_protection_failures` (section 2a) counts it. Dictionary keys that mask or hash alike appear as `<protected key>~<n>` (`a***@x.com~2`). Staff email addresses appear as `a***@example.com` (first character and domain), and track ids and desk codes as `#` and 12 hex characters (for example Integration's "Border feed code #3f9a0c27b1e4 of site ... has no AMAN desk code mapping", section 4.8h). The codes to map are in the border feed tables, which keep them as received with `desk_id` null (read only): `SELECT desk_code, count(*) FROM border_desk_interval WHERE site_code = '<site>' AND desk_id IS NULL GROUP BY 1`. A dashboard, alert or SIEM rule that matched a whole email address or a desk code in a log line must match these forms, or the event's other fields, instead.
- **The pseudonym key** (`Logging:PseudonymKey`, wiki 04 section 5). Pseudonyms are keyed per UTC day (a day key derived from the master key), so a desk's pseudonym is the same all day and different the next day: never correlate across days. In k8s-prd every host takes the deployment's master key from its Secret (`logging.pseudonymKeySecret`, `ariva-log-pseudonym-key` by default; ARV-091a), so the pods and their restarts agree on a day's pseudonyms; a host there without the key does not start (section 4.17). Elsewhere, without the master key, each pod draws its own at start, so pseudonyms also differ between pods and after a restart. The master key is a secret: outside vm-local it is set only as the environment variable `Logging__PseudonymKey` from a Kubernetes Secret, base64 of 32 random bytes (wiki 04 section 6.2 creates it); never in the chart's values, an appsettings file or secret (they are mounted as files) or a ConfigMap. Rotating the key (wiki 04 section 6.2: a new key in the Secret, then a restart of the five API Deployments) changes the pseudonyms from then on: a desk's pseudonym written after the restart differs from the one written earlier that day, and lines already written keep theirs. While the restart rolls, the old and the new pods disagree for a few minutes. Never give the key to readers of the log store: with it, anyone can recompute any day's pseudonym of every desk code.

### 4.18 Upload malware scanning (ARV-092b, ARV-092c)

Ariva.Api.Main scans every upload with ClamAV (clamd, at `MalwareScan:Host` and `MalwareScan:Port`) before it parses, stores or imports it ([File handling guide](13a-File-Handling.md), section 4). A detection is refused and audited; outside vm-local, an upload the scanner gives no verdict on is refused, so no upload is taken while clamd does not answer. In the cluster each api-main pod runs its own clamd beside it, container `clamd`, on `127.0.0.1:3310`, with a `freshclam` container keeping its signatures current when the signature source is `public` or `mirror` ([Deployment guide](04-Deployment-Guide.md) section 6.7). A clamd that runs but stops answering is restarted by its liveness probe, and the pod stays in its Service meanwhile: only its uploads are refused. A clamd that cannot start at all (a damaged mounted signature set, signatures that outgrow its memory limit as they load) leaves its pod out of the Service, since Kubernetes counts a container that is not running as not ready: every new or rescheduled api-main pod then stays NotReady, and the whole host is down, not only its uploads. Every 10 minutes Ariva.Api.Main asks its clamd how old its signatures are (`ariva.uploads.scanner.signature_age`, `ariva.uploads.scanner.answered`, section 2a).

#### Signatures stale

Alert rule `scannerSignaturesStale` (ARV-092c): the signatures of a scanner beside api-main are older than `maxAgeHours` (48 by default). Uploads are still scanned, against old signatures. Find the pod (the rule groups by `service.name`; event 9133 names the age, the database version and its build time), then by the signature source:

- `public` or `mirror`: read freshclam's log, `kubectl -n "$NAMESPACE" logs <api-main pod> -c freshclam --since=24h`. A connection refused or timed out is the network: the mirror's peers in `networkPolicies.clamavMirror` (section 4.15), the site's proxy or firewall, DNS. A certificate error with a site mirror is its CA (`uploadScan.signatures.mirrorCaSecretName`). A 403 or 429 from ClamAV's public mirrors is their rate limit on the site's address: use a site mirror (wiki 04 section 6.7).
- `mounted`: the site's own update of the signature volume has stopped; nothing in Ariva downloads them.

Check what clamd has loaded: `kubectl -n "$NAMESPACE" exec <api-main pod> -c clamd -- clamdscan --config-file=/etc/clamav/clamd.conf --version` prints `ClamAV 1.4.6/<database version>/<build time>`. clamd takes changed signatures within 10 minutes (`SelfCheck`); a pod restarted with `public` or `mirror` starts from the image's bundled signatures and catches up when freshclam does.

#### Scanner not answering

Alert rule `scannerNotAnswering` (ARV-092c): a scanner beside api-main has not answered its signature check for 20 minutes, and its pod refuses every upload (503, security event 9132). The rest of the API on that pod keeps serving.

1. `kubectl -n "$NAMESPACE" get pod <api-main pod> -o jsonpath='{range .status.containerStatuses[*]}{.name} {.restartCount} {.state}{"\n"}{end}'`: a `clamd` that keeps restarting, or `OOMKilled` in its last state, means its memory limit is too small for the signatures (`uploadScan.clamd.resources`; about 1 GiB resident, wiki 04 section 6.7).
2. `kubectl -n "$NAMESPACE" logs <api-main pod> -c clamd --previous` shows why it stopped: a signature database it cannot load (`mounted`: a damaged or partly copied set), or a configuration error.
3. A clamd that runs but does not answer for about 20 seconds is reloading its signatures (`ConcurrentDatabaseReload no`); the rule waits 20 minutes for that reason.
4. A clamd that answers PING but no longer has a signature database: with `ConcurrentDatabaseReload no` a reload that fails (a changed file it cannot load) frees the old signatures first, so clamd keeps running without any, its VERSION answer has no database (`ariva.uploads.scanner.answered` 0, the host's Warning "did not answer its signature check (NoAnswer)") and every upload of that pod is refused until the files are fixed. Fix the signature files (freshclam's log, or the mounted set), then restart the pod: `kubectl -n "$NAMESPACE" delete pod <api-main pod>` (its Deployment starts another).
5. A pod NotReady whose `clamd` is in `CrashLoopBackOff` takes the host down with it (above): read `kubectl -n "$NAMESPACE" logs <api-main pod> -c clamd --previous`, then fix the signature set or raise `uploadScan.clamd.resources` and release.

### 4.20 Run timeouts of jobs, background loops and Kafka handlers (ARV-096e)

Every TickerQ job (Ariva.Api.Cronz) and every background loop of the hosts ends each run at its run timeout: alert evaluation 2 minutes; the device heartbeat and flight feed sweeps 1 minute; the desk feed 2 minutes; the idempotency sweep and the AMAN and ACRIS polls 5 minutes; the malware scanner's signature check 1 minute; the validation results freeze 65 minutes; the email round 10 minutes; the availability and staffing jobs 10 minutes, report deliveries and secret re-protection 30 minutes, retention an hour. Each attempt of a Kafka message ends at `Kafka:Consumers:HandlerTimeoutSeconds` (70 s). What a cut run committed stays and the next run starts as usual; the secret re-protection round is one transaction, so a cut one rewrites nothing. The email round and the report deliveries are cut only between messages: an email or report the relay took is recorded as sent, so a cut never sends one twice. The hub session sweep has no run timeout of its own (session code left as it is under the sign-in freeze).

### 4.22 Queue engine refusals (ARV-231)

Each zone's queue engine counts what it refuses or applies early, by kind, and Ariva.Api.Stream reports them once a checkpoint has written the zone's outputs: the counter `ariva.stream.queue_refused` (meter `Ariva.Stream`, tags `kind` and `site`) and a warning per zone and kind at most once a minute, "Zone {Zone}: the queue engine refused or applied early {Count} events of kind {Kind} since its last warning". The warning names the zone, the kind and the count, never an event's content. The SigNoz rule `queueRefused` (critical) fires on any `BufferFull` or `DeviceShareFull` in its 5-minute window (`monitoring.alerts.queueRefused`; its `kinds` are the counts below).

The live minutes a full buffer touched (events refused for it, or applied before their lateness was up) are marked `length_degraded` and `nowcast_degraded` in `queue_minute`, so screens, reports, staffing and alerts treat them as degraded.

| Kind | Meaning | Action |
|---|---|---|
| `BufferFull` | The zone's reorder buffer (100,000 events, `MaxBufferedEvents`) was full, or the tenth of it for events ahead of the clock was (each device holds at most its share of that tenth since ARV-239, so filling it takes several devices whose clocks run ahead; a sensor's samples a little ahead are coalesced in their runs and take few places); the event was refused, crossings included | Look at the zone's `state_bytes` and buffer (section 4.5b, the `stream_zone_state` query): which devices' events fill `state->'engine'->'buffer'` (an anonymous one carries its `device`, a tracked one's key starts with it) and the runs' pending samples in `state->'engine'->'runs'` (`pendingAhead` marks one ahead of the clock; its device is `pendingDevice` or the key's), and whether Stream is behind (section 4.6). A device sending far ahead of the clock shows as future times there (section 4.5) |
| `DeviceShareFull` | One device already held its share of the buffer (the bound over the devices sharing it: those holding events, the zone's devices heard recently, at least two; never below 10,000, `DeviceShareFloor`), and applying the events that were due freed none of its places, so its event was refused and the other devices of the zone keep being counted. Or, for an event ahead of the clock, the device already held its share of the tenth kept for those (the tenth over the same devices, never below 1,000, a tenth of `DeviceShareFloor`; ARV-239): that tenth is freed only as the watermark reaches its events, never by applying events early, so it is refused at once. A sensor within the clock tolerance refused so while another device floods unique tracks has found the runs of position samples used up (one pool a zone, `MaxSightingRuns`; ARV-240): its new tracks' samples then take a place each. Ten or more devices at the floor can still fill the buffer together (then `BufferFull`) | The named device floods the zone or sends far behind or ahead: check its rate and clock in the device registry (section 4.1, 4.5); a broken or hostile device is put in commissioning or disabled until fixed |
| `ForcedAdvances` | The buffer was full, or a device past its share, and the engine applied events that were already due to make room, before their full lateness: events of those minutes that arrive later are late | As for `BufferFull`; a few are harmless, a steady stream means the zone receives more than the buffer holds for its lateness, or a device floods it (its forced advances mark the zone's minutes degraded throughout the flood, though the other devices are counted) |
| `Late`, `Future`, `Invalid`, `UnknownGeometry` | Events behind the watermark (their minutes are recomputed, section 4.10), ahead of the clock beyond 5 minutes, with times or counts out of bounds, or naming a line or zone the profile does not have | A device's clock (section 4.5), its dialect mapping or the zone profile's lines |
| `Duplicates`, `Reverse`, `UnmatchedExits`, `NegativeWaits`, `TooManyDevices` | Pairing outcomes: a repeated entry or exit, an inward crossing of an exit line, an exit with nobody to pair (people inside when the zone started afresh, wiki 18), an exit before its entry, a zone with more devices than it tracks apart | Expected in small numbers; many of one kind points at the zone's lines or a device's geometry (wiki 06) |

### 4.23 A deployed database reached by a developer's process (ARV-180)

The migration job logs the error "The database recorded the environment vm-local and now records ...": before this release's migration, a vm-local process (a developer's host, an E2E run, the migration command run as vm-local) migrated this database, and may have run NHibernate SchemaUpdate on it and seeded the development accounts, whose passwords are known, and the demo topology. Since ARV-180 a vm-local process refuses a database that records another environment, so this means the database had no record yet (migrated before ARV-180) or was reached before its first migration with ARV-180.

1. Treat it as a security incident: find who ran it (the developer machines that could reach the database, the tunnels or port forwards open at the time).
2. Disable every account the seed created or reset, in user administration (Users and access), which revokes their sessions: `SELECT user_name, created_on, modified_on FROM "user" WHERE created_by = 'development-seed' OR modified_by = 'development-seed'` with a read-only login lists them. Check the audit trail for what those accounts did since.
3. Remove the demo topology if it was seeded and is not wanted (the fictional site `DMO` and the illustrative sites, their rows created by `demo-seed`, ARV-019 and ARV-139a), through the administration screens.
4. Compare the schema with a fresh migration of the same release (`pg_dump --schema-only` of both): SchemaUpdate adds columns and tables the scripts do not; report any difference to Dalil support.
5. The job has recorded the cluster's environment again, so from now on a vm-local process refuses this database.

### 4.24 A consumer held by one record (ARV-254)

`consumerHeld` fires, or `ariva.kafka.consumer_hold_seconds` stays high for a topic and group: a MassTransit topic endpoint has been handling one record for longer than the consumer settings allow (`ConsumerSettings.LongestHold`: its attempts at `Kafka:Consumers:HandlerTimeoutSeconds`, the retry waits and its dead letter; about 414 seconds at the defaults). Each endpoint's consumer handles one record at a time (ARV-253), so every partition it reads waits behind that record: the group's lag grows on them (`kafka-consumer-groups.sh --describe --group <group>`), and what the group feeds (the sensing archive, the AMAN feed's desk states, a domain event's consumers) falls behind. The gauge's `service.instance.id` names the pod.

1. Read that pod's log. The usual cause is "Dead letter for <topic> partition <p> offset <o> not accepted (attempt N)" repeating with "... could not be kept in the outbox either" once a minute: the broker refuses the dead letter (its `.dlq.v1` topic missing, a partition without a leader, a missing ACL) and the database is away as well. Fix either one: once the broker takes the letter, or the outbox does at the end of the next one minute window, the record completes and the gauge returns to 0. Check `kafkaUnavailable` and `databaseUnavailable`, then the topic (`kafka-topics.sh --describe --topic <topic>.dlq.v1`) and section 4.5a.
2. No dead-letter lines: either the hosts' `Kafka:Consumers` settings were raised past the rule (`RetryCount`, `HandlerTimeoutSeconds`, `RetryMaxMilliseconds`; raise `monitoring.alerts.consumerHeld.holdLimit` with them, wiki 04), or a handler does not honour its cancellation (every Ariva consumer passes its token to its reads and writes, so report it with the log).
3. A hold longer than the consumer's poll interval (`max.poll.interval.ms`, the longest hold and a minute: about 474 seconds at the defaults) takes the consumer out of its group; after the rebalance the records it had not committed are handled again, and the inbox drops those already applied, so nothing is applied twice and nothing is lost. Restarting the pod also ends a hold (at the stop the letter is kept in the outbox, or, with the database away, the record is left unacknowledged for the next consumer; section 4.5a), but the next consumer is held the same way until the cause is fixed.
4. The same poll interval is librdkafka's rebalance timeout: during a rebalance (a rolling update, a scale out, a pod lost) a consumer held with its fetched records waiting delays its whole group, every pod's consumers of it, for up to that long, so a rollout can pause that group's consumption for minutes while one record is held. A revoke also waits for the records already fetched for the partitions it takes away and commits them (ARV-255), so they are not handled twice. Expect it; it ends with the hold.
5. While a dead-letter topic cannot be reached, each held consumer keeps about one letter a minute in the outbox (`ariva.kafka.dead_letters` with `outcome` `kept`); they show on `outboxBacklog` and are sent once the topic takes them (section 4.5a).
