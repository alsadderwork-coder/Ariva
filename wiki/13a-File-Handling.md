# File handling

For administrators, Dalil engineers and the customer's security reviewers. This page lists every file Ariva takes from a person, upload by upload: who may send it, what it may be and how Ariva decides that, how large it may be and what it may unpack to, what Ariva does to it, where Ariva keeps it and under what name, how it is served back, how often it may be sent, what the audit trail keeps, and what happens to a malicious file. It answers OWASP ASVS 5.0 V5.1.1 ([ASVS mapping](../docs/security/asvs-l2.md), V5). The controls in brief are in the [Security guide](13-Security-Guide.md), section 4a; how to use each upload is in the [Administration guide](11-Administration-Guide.md) and, for SSIM, the [Integration guide](08-Integration-Guide.md) section 9.

Code paths below are under `Platform/Backplane/` unless they say otherwise.

|---|---|---|---|---|---|
| Floor plan (section 3.1) | `POST api/v1/admin/levels/{levelId}/floor-plan` | `FloorPlan.Create`: system administrators | PNG, JPEG, SVG | 20 MB | Yes: PNG and JPEG as uploaded, SVG rebuilt |
| SSIM schedule (section 3.2) | `POST api/v1/admin/sites/{siteCode}/flight-schedules/preview`, then `/import` | `FlightSchedule.Create`: system administrators | IATA SSIM chapter 7 text | 20 MB | No: only the flight legs it holds |
| Device list, CSV (section 3.3) | `POST api/v1/admin/sites/{siteCode}/device-imports/preview`, then `/commit` | `Device.Create` and a second factor in the last 15 minutes: border shift supervisors, terminal duty managers, system administrators | UTF-8 CSV | 1 MB | No: only the devices it registers |
| Desk code mappings, CSV (section 3.3) | `POST api/v1/admin/sites/{siteCode}/desk-code-mapping-imports/preview`, then `/commit` | `DeskCodeMapping.Create`: system administrators | UTF-8 CSV | 1 MB | No: only the mappings it creates |
| Site configuration bundle (section 3.4) | `POST api/v1/admin/sites/{siteCode}/configuration` | `SiteConfiguration.Transfer` and a second factor in the last 15 minutes: system administrators | Ariva bundle (JSON, format version 1) with floor plan files inside | 20 MB body | Only its floor plan files, as floor plans |
| Advertisement image (section 3.5) | `POST api/v1/admin/sites/{siteCode}/advertising/media` | `Advertising.Manage`, while the site's advertising policy allows advertising: terminal duty managers, system administrators | PNG, JPEG, WebP | 10 MB | Yes: decoded and written anew |

The roles are the default grants (`Ariva.Core/Security/RolePermissions.cs`); an administrator can change grants ([Administration guide](11-Administration-Guide.md) section 2). Every upload endpoint is also limited to the caller's sites (`[SiteScoped]`): another site, or a level of another site, answers 404 like one that does not exist. Floor plans, CSV imports and advertisements have screens in Ariva.Web; SSIM schedules and site configuration bundles are API only.

No other endpoint of any host takes a file. Sensor pushes (Ingest), Integration API batches and AIDX messages are messages, not files, with limits of their own ([Security guide](13-Security-Guide.md) section 2, rows CWE-120 and CWE-501; [Integration guide](08-Integration-Guide.md) section 5).

## 2. Rules for every upload

- **Typed by the bytes.** The file name and the declared `Content-Type` never decide what a file is. Each upload is read as the type it must be (sections 3.1 to 3.6), and the stored extension and the served type come from what the bytes turned out to be. The file pickers in Ariva.Web (`accept`) only help people choose; the server decides.
- **Names are text, never paths.** Nothing a caller sends becomes part of a path. Floor plans and advertisements keep the uploaded name as display text only: at most 200 characters (each accent or other combining mark counted as one), refused, never cleaned, when it holds a slash, a backslash, `..`, a colon, a control or invisible format character (a right-to-left override, for example) or a broken character (`FloorPlan.HasSafeFileNameCharacters` in `Ariva.Core/Domain/Entities/FloorPlan.cs`). SSIM and CSV imports never read the name. A NUL character in a file name or a form field answers 400 on every upload endpoint and is security event 9127 (`Ariva.Api.Common/Filters/NulCharacterGuard.cs`).
- **Stored under keys Ariva generates.** Files Ariva keeps go through `IFileStorage` (`Ariva.Infra/Storage/LocalDiskFileStorage.cs`): a local disk under `Storage:LocalRoot`, which the chart sets to `/app/data/files` on the persistent volume claim `ariva-files`, mounted by Ariva.Api.Main only (`Platform/Cloud/Ariva.K8s/Helm/Charts/platform/templates/file-storage.yaml`). The key is 32 hexadecimal characters of a new id, a dot and the extension of the detected type (`png`, `jpg`, `svg`, `webp`, `mp4` or `webm`), checked against that one pattern and resolved under the root, so no key reaches another folder. A file is written under a temporary name and moved into place, so a reader never sees half of it, and a file written for a request that is rolled back is deleted again. The volume is outside any web root and no host serves it as static files: a stored file is returned only by the endpoints named below, as data. Its database record keeps the type, the size, the SHA-256 of the stored bytes and, for floor plans and advertisements, the display name.
- **While a request arrives.** ASP.NET Core holds a multipart file in memory up to 64 KB and above that in a temporary file under the pod's `/tmp` (an `emptyDir`), deleted when the request ends. This is the framework's default: Ariva sets only the form's length, count and value limits (`Ariva.Api.Common/Extensions/RequestLimitsExtensions.cs`). The site configuration bundle, a JSON body, is held the same way (in memory up to 30 KB, then a temporary file under `/tmp`), since it is read whole before model binding (Arriving steadily, below).
- **Sizes, checked three times.** The ingress refuses a body above its `proxy-body-size` (21m on the api-main and web-api Ingresses in every values file), the endpoint above its `[RequestSizeLimit]` (for a multipart form also `[RequestFormLimits]`: the file plus 64 KB of form framing), and the service above the file limit, first on the declared length and again while it reads (`Ariva.Infra/Storage/UploadReader.cs` or the importers' own bounded reads), so a body longer than it declared is refused, not read whole. Too large answers 413.
- **One upload at a time.** Every upload endpoint, and the site configuration export, uses the `upload` concurrency policy (`Ariva.Api.Common/Extensions/RateLimitingExtensions.cs`): one at a time per host process, two waiting oldest first, the rest 429 with `Retry-After: 10` (security event 9116). The global per-address limit applies as well. Advertisements add a limit per person (section 3.5).
- **Arriving steadily (ARV-096).** Every upload endpoint reads its body itself before model binding (`Ariva.Api.Common/Filters/SteadyUploadAttribute.cs`; the advertisement upload through its own filter, which takes the same steps, section 3.5), so a slow sender cannot hold the one upload a host takes at a time for long: about 11 minutes at most over HTTP/1.x, the 15 minute `transfer` timeout on any protocol. Over HTTP/1.x the body must arrive at 32 KB a second or more once 10 seconds have passed, or it is cut off with 408 and the slot is free again: the largest, 20 MB, is in within about 11 minutes, a 1 MB CSV within about 32 s (HTTP/2 and HTTP/3 keep the connection's own rate). The read takes the request's token, which MVC's own readers do not, so the `transfer` request timeout (15 minutes) ends it on any protocol.
- **Fixed answers.** A refused file gets 400 (type or structure, or a form cut short), 413 (size) or 408 (a body arriving too slowly) with a fixed text that never repeats the file, its name or a value from it. These 400, 408 and 413 answers are not security events today; 401, 403 and 429 are ([Security guide](13-Security-Guide.md) section 6b).
- **Names and encoding on the way back (ARV-092).** A stored file goes back under a name Ariva builds, never the uploaded one: `Content-Disposition: inline; filename="{prefix}-{id}.{extension}"`, the prefix fixed by the endpoint (`floor-plan`, `advertisement`), the id the one the URL names (the level for a floor plan, the library item for an advertisement) and the extension that of the type read at upload, so the name is lower-case ASCII and needs no escaping or `filename*` (`Ariva.Api.Common/Security/StoredFileHeaders.cs`). `inline` because the screens and the display player show the file in place; a person who saves it gets that name. SVG, the one text type stored, goes out as `image/svg+xml; charset=utf-8`. The one file Ariva sends as an attachment is the daily report CSV (`GET api/v1/sites/{siteCode}/reports/daily.csv`): `attachment` with `filename=ariva-{SITE}-{yyyy-MM-dd}-{hours, alerts or devices}.csv` and `filename*=UTF-8''...`, as `text/csv; charset=utf-8` with a byte order mark (`Ariva.Api.Main/Controllers/OpsArea/Reports/ReportsController.cs`). The imports answer JSON only. Every text answer of the five API hosts names UTF-8: `SecurityHeadersMiddleware` adds `charset=utf-8` to any `text/*`, `application/xml`, `application/javascript` or `+xml` type that names none (the framework's plain-text status pages and the TickerQ dashboard included), leaving JSON, binary types and types that name a charset as they are; the web pod's nginx does the same for its page, `/healthz`, scripts, styles, JSON and SVG (`charset utf-8` and `charset_types` in `Platform/Frontplane/Ariva.Web/static/nginx/default.conf`).
- **Shown as text.** Names, rows and values from a file reach the screens through Svelte text interpolation only, never as markup (CWE-79).

## 3. Upload by upload

### 3.1 Floor plans (ARV-018)

| Question | Answer |
|---|---|
| Endpoint | `POST api/v1/admin/levels/{levelId}/floor-plan`, multipart field `file` with `metresPerPixel`, `originX` and `originY` (`Ariva.Api.Main/Controllers/AdminArea/Topology/FloorPlansController.cs`, `Ariva.Infra/Services/Topology/SvcFloorPlans.cs`). In Ariva.Web: Zones, Upload a floor plan |
| Who may upload | `FloorPlan.Create` (system administrators); not a critical action. The level must be live and in one of the caller's sites (404 otherwise) |
| Types, and how Ariva decides | `FloorPlanFiles.Inspect` (`Ariva.Infra/Storage/FloorPlanFiles.cs`): PNG by its signature with the `IHDR` chunk first; JPEG by its start marker and a start-of-frame segment; anything else must parse as XML whose root is an `svg` element in the SVG namespace. Anything else (HTML, PDF, GIF, a renamed file) answers 400 |
| Extensions | Stored as `png`, `jpg` or `svg`, from the detected type; the uploaded name's extension is ignored |
| Limits | Request 20 MB plus 64 KB; file 20 MB (`FloorPlan.MaxBytes`), on the declared length and again in the read. PNG and JPEG: at most 16,384 pixels a side and 134,217,728 pixels (128 megapixels), read from the header, so no viewer has to decode a pixel bomb. SVG: at most 25,000,000 characters, 200,000 elements (dropped ones counted) and 64 levels deep, and no DTD (`FloorPlanLimits`). Name: 200 characters |
| What Ariva does to it | PNG and JPEG are stored as uploaded, byte for byte, so any metadata in them (EXIF, text chunks, colour profiles) stays. SVG is parsed with DTDs prohibited and no resolver, then written anew through an allowlist: listed drawing elements and attributes only (script, style, `foreignObject`, `image`, `a`, animation, filters and every other namespace dropped with their content), `href` and `url()` only as references inside the file (`#id`), no CSS escapes, at-rules or image functions, comments and processing instructions dropped, CDATA written as escaped text |
| Where it is stored | `IFileStorage` under a generated key ending `.png`, `.jpg` or `.svg` (section 2). The `floor_plan` record holds the type, size, SHA-256 of the stored bytes, display name, pixel size and calibration. One live plan per level: an upload replaces the previous plan, whose record is soft deleted and whose file is deleted after the commit |
| How it is served | `GET api/v1/admin/levels/{levelId}/floor-plan/content` (`FloorPlan.View`: every role that reads topology, at its own sites): the stored type (`image/svg+xml; charset=utf-8` for SVG), `Content-Disposition: inline; filename="floor-plan-{levelId}.png"` (or `.jpg`, `.svg`: the type read at upload, never the uploaded name), `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, and the SHA-256 as the `ETag`. Ariva.Web fetches it with the user's token and draws it as an SVG `<image>` from an object URL, so no script in a plan ever runs. A site configuration export carries the stored bytes (section 3.4) |
| Rate limit | The `upload` policy (section 2) |
| Audit | `FloorPlan.Uploaded` with the level code and, before and after, the type, size, SHA-256, scale and origin; `FloorPlan.Calibrated` and `FloorPlan.Deleted`. A refused upload is not audited |
| A malicious file today | Refused when it is not one of the three types, is over a limit or does not parse; an SVG keeps no active content. A PNG or JPEG that passes is stored and served as uploaded without a malware scan, so a file crafted against an image decoder reaches the browsers that show the plan, inside the sandbox above |

### 3.2 SSIM schedules (ARV-046)

| Question | Answer |
|---|---|
| Endpoint | `POST api/v1/admin/sites/{siteCode}/flight-schedules/preview`, then `/import`: multipart field `file` with `horizonDays` (1 to 200, default 60) and, for the import, `previewToken` (`Ariva.Api.Main/Controllers/AdminArea/Flights/FlightSchedulesController.cs`, `Ariva.Infra/Services/Flights/SvcFlightSchedules.cs`, `Ariva.Infra/Flights/Ssim/SsimReader.cs`). API only |
| Who may upload | `FlightSchedule.Create` (system administrators); not a critical action |
| Types, and how Ariva decides | IATA SSIM chapter 7 text, decided by reading it: each line must be printable ASCII (a byte above 0x7E or a control character other than the CR before the LF makes that line an error), a record 2 must give the time mode U or L (otherwise that line is an error), and the file must hold at least one flight leg record (type 3), or it is refused as not an SSIM chapter 7 file. The name and the declared type are never read |
| Extensions | None checked |
| Limits | Request 20 MB plus 64 KB; file 20 MB (`SsimReader.MaxBytes`), on the declared length and again while streamed. Unpacked: at most 200,000 lines of at most 200 characters (a CR before the LF allowed), and at most 100,000 flight legs once the records of the site's airports are expanded over the horizon. At most 100 line errors are listed, with the total |
| What Ariva does to it | Reads it once as a stream and hashes it (SHA-256); expands each leg record of the site's airports into legs and checks each leg with the flight intake's own rules (`FlightRules`). The import applies the legs through the flight intake as the fallback feed `ssim`, in units of 500 |
| Where it is stored | Nowhere as a file. The legs go into the flight tables; the file's SHA-256 only into the preview token and the audit entry. The preview token (Data Protection) binds the SHA-256, the site, the horizon, the window and the user for two hours |
| How it is served | Never. The preview answers counts, at most 20 sample legs (flight key, direction, time, origin, destination) and the line errors by number with Ariva's reason, never a line's text |
| Rate limit | The `upload` policy |
| Audit | `FlightSchedule.Imported`, in a transaction of its own whether the import completed or failed: the SHA-256, horizon, window, outcome, units committed and counts. A preview, and an import refused before its token matched, are not audited |
| A malicious file today | Refused when over a limit or without leg records; a line that is not printable ASCII, does not parse or breaks the flight rules is a line error and is never applied. The file is never stored, executed or shown; only checked values reach the database. Not scanned for malware |

### 3.3 CSV imports: devices and desk code mappings (ARV-123a, ARV-123b)

| Question | Answer |
|---|---|
| Endpoint | `POST api/v1/admin/sites/{siteCode}/device-imports/preview`, then `/commit`, and `POST api/v1/admin/sites/{siteCode}/desk-code-mapping-imports/preview`, then `/commit`: multipart field `file` and, for a commit, `previewToken` (`Ariva.Api.Main/Controllers/AdminArea/Imports/`, `Ariva.Infra/Services/Sensing/SvcDeviceImports.cs`, `Ariva.Infra/Services/Topology/SvcDeskCodeMappingImports.cs`, `Ariva.Infra/Imports/CsvImportReader.cs`). In Ariva.Web: Devices, Import devices, and Topology, the desk code panel's Import mappings |
| Who may upload | Devices: `Device.Create` and a second factor in the last 15 minutes for both steps (border shift supervisors, terminal duty managers, system administrators). Desk code mappings: `DeskCodeMapping.Create` (system administrators), no second factor |
| Types, and how Ariva decides | UTF-8 text in RFC 4180 CSV, decided by reading it: invalid UTF-8, or a UTF-16 or UTF-32 byte order mark, refuses the file, and the header must name the import's columns exactly, each once. The server reads neither the name nor the declared type; the Ariva.Web dialog refuses a file that is not `.csv`, is empty or is over 1 MB before sending it, as a convenience only |
| Extensions | None checked by the server |
| Limits | Request 1 MB plus 64 KB; file 1 MB (`CsvImportLimits` in `Ariva.Core/Services/Imports/ISvcCsvImports.cs`), on the declared length and again while hashed (one byte beyond answers 413). Unpacked: 500 device rows or 10,000 mapping rows, cells of at most 200 characters (a field beyond 800 refuses the whole file), at most 100 refused cells listed with the total, and a token of at most 2,048 characters |
| What Ariva does to it | Reads it twice as a stream: hashed, then parsed with CsvHelper's low-level parser only (no record mapping or dynamic types). A text cell may not start with =, +, -, @, a tab or a carriage return (also after spaces), and no cell may hold a line break or another control character; a number is digits with an optional leading minus and decimal point. Each row then runs through the device registration (or the mapping service) as a dry run, rolled back |
| Where it is stored | Nowhere as a file. A commit creates the devices or mappings in one transaction, all or none. The preview token (Data Protection, one purpose per import) binds the file's SHA-256, the site and the user for 15 minutes |
| How it is served | Never. The preview answers the passing rows and each refused cell by row, column and fixed text, never the cell; a device commit answers each new credential once. Answers are `no-store` |
| Rate limit | The `upload` policy |
| Audit | `DeviceImport.Previewed`, `.Committed`, `.Refused` and `.Failed`, and the same for `DeskCodeMappingImport`: the kind, outcome, fixed reason, the file's SHA-256 and the counts, never a cell or a credential. Not audited: refusals before the service runs (no file, a file over 1 MB, a token of the wrong shape) |
| A malicious file today | Refused when it is not UTF-8 CSV with the import's header or is over a limit; a formula cell (CSV injection) or a control character is a refused cell, and only a file without refused cells can be committed. The file is never stored or executed. Not scanned for malware |

### 3.4 Site configuration bundles (ARV-122a, ARV-122b)

| Question | Answer |
|---|---|
| Endpoint | `POST api/v1/admin/sites/{siteCode}/configuration`, optional `?airportCode=`, with the export's `bundle` as the JSON body, not a multipart form (`Ariva.Api.Main/Controllers/AdminArea/Sites/SiteConfigurationController.cs`, `Ariva.Infra/Services/Topology/SvcSiteConfiguration.cs`, `Ariva.Core/Services/Topology/SiteConfigurationBundles.cs` and `SiteConfigurationParts.cs`). API only |
| Who may upload | `SiteConfiguration.Transfer` and a second factor in the last 15 minutes (system administrators), for the export too |
| Types, and how Ariva decides | One JSON document of format version 1: `formatVersion`, `sourceSite`, `exportedAtUtc`, `manifest` (each part's SHA-256) and `parts` (each part in base64). Known parts only: `topology`, `deskCodeMappings`, `zoneProfile`, `floorPlans`, `devices`, `alertRules` and `displays`, all required, and `floorPlanFile.1` to `floorPlanFile.N` without a gap. Each configuration part must be strict JSON of its kind (exact member names, every member present, no unknown or repeated member, numbers as numbers, no comments, at most 32 levels deep). Each floor plan file is typed by its bytes again with the floor plan rules (section 3.1), whatever the bundle says |
| Extensions | None; a floor plan file's stored extension comes from its bytes |
| Limits | Body 20 MB (`SiteConfigurationLimits` in `Ariva.Core/Services/Topology/ISvcSiteConfiguration.cs`; 413). Parts: at most 207 (the seven and one file per level). Decoded: a configuration part at most 8 MB and a file part at most 20 MB, each checked on its base64 length before it is decoded and again after (413). Records: 50 terminals, 200 levels, 1,000 checkpoints, 5,000 desks, 10,000 desk code mappings, one plan per level, the zone profile's 500 zones and 1,000 lines, 2,000 devices, 500 alert rules, 200 displays. A floor plan file inside is held to the floor plan's pixel and SVG limits. No archive or compressed format is taken |
| What Ariva does to it | Checks the envelope and the manifest first: every part's SHA-256 must match. That proves the bundle was not changed after export, not who made it. Every part is then checked as the endpoints check what an administrator types, and each floor plan file is typed, bounded and, for SVG, rebuilt as an upload is, its name checked as an upload's. The import goes into an empty site only, in one transaction, all or nothing |
| Where it is stored | The bundle is not kept. Its records are created with new ids; each floor plan file is stored under a new generated key (section 2) and deleted again if the import rolls back |
| How it is served | The import answers JSON: the bundle hash, the counts and notes, never a part (`no-store`). Imported plans are served as in section 3.1. The export (`GET` on the same route) is a JSON API answer (`no-store`), not a file download: it sends no `Content-Disposition`, the client names any file it saves, and the bundle in it carries the stored plan files |
| Rate limit | The `upload` policy, for the export too |
| Audit | `SiteConfiguration.Imported`, `.ImportRefused` (with the fixed reason) and `.ImportFailed`, a refusal or failure in a transaction of its own: the bundle hash once the manifest checked out, the format version, the claimed source site, the number of parts and the counts, never a part's content. `SiteConfiguration.Exported` and `.ExportRefused` for exports |
| A malicious file today | Refused by the envelope, manifest, size, strict JSON, entity and file checks before anything is written; an SVG plan is rebuilt again; a PNG or JPEG plan is stored as it arrives, as in section 3.1. Not scanned for malware |

### 3.5 Advertisement images (ARV-142a)

| Question | Answer |
|---|---|
| Endpoint | `POST api/v1/admin/sites/{siteCode}/advertising/media`, multipart field `file` with `advertiser`, `campaign`, `startsOn` and `endsOn` (`Ariva.Api.Main/Controllers/AdminArea/Advertising/AdvertisingMediaController.cs` and `AdvertisingUploadLimitAttribute.cs`, `Ariva.Infra/Services/Displays/SvcAdvertisingMedia.cs`, `Ariva.Infra/Storage/AdvertisingImages.cs`). In Ariva.Web: Passenger displays, the advertisement library |
| Who may upload | `Advertising.Manage` (terminal duty managers, system administrators), only while the site's advertising policy allows advertising (`[AdvertisingAllowed]`: 403 while it is off). Uploading is not a critical action; an item plays only after a second person approves it with a second factor |
| Types, and how Ariva decides | A file that does not start like a video container (section 3.6) is an image: PNG, JPEG or WebP by its signature. Managed code then reads its header (the size, an APNG's `acTL` chunk, a WebP's animation flag) before any native code sees the file, and the decoder (SkiaSharp) must report the same format, the same size and one frame. SVG, HTML, PDF, GIF, BMP, animated images and anything else answer 400 |
| Extensions | Stored as `png`, `jpg` or `webp`, from the detected type |
| Limits | Request: the larger of 10 MB and the video setting (section 3.6), plus 64 KB, set before the form is read, so a body declared larger answers 413 at once and one sent without a length is cut off at the limit; form values at most 1 KB and 16 of them; over HTTP/1.x a body arriving slower than 32 KB a second after 10 seconds is cut off with 408. File: 10 MB (`AdvertisingMedia.MaxImageBytes`). Unpacked: at most 3,840 pixels a side and 8,294,400 pixels (33 MB decoded), refused from the header; a JPEG with more than 64 scans is refused; the image written anew must fit 10 MB too. Name: 200 characters |
| What Ariva does to it | Decodes it and writes it anew in its own format, one decode at a time per process, with low encoder effort: turned upright from its EXIF orientation and converted to sRGB. No metadata (EXIF, XMP, comments, text chunks, colour profiles) and nothing after the image's end is carried over, so a polyglot's page or script is gone. The new pixels are still the uploader's and can be chosen to spell bytes, so the serving headers, not the re-encoding, are the control against content sniffing |
| Where it is stored | `IFileStorage` under a generated key ending `.png`, `.jpg` or `.webp` (section 2). The `advertising_media` record, a draft, holds the type, size, SHA-256, pixel size, display name and details; script 0058 matches the key's extension to the type. At most 500 items a site (409 beyond). Nothing is deleted: a retired item keeps its file |
| How it is served | `GET api/v1/admin/sites/{siteCode}/advertising/media/{id}/content` (the library preview: `Advertising.View` or `Advertising.Manage`) and, for display players, `GET api/v1/display/advertising/{id}?code=` (the display's own credential; only an approved item of its site that may play now), both with the same headers: the stored type, `Content-Disposition: inline; filename="advertisement-{id}.png"` (or `.jpg`, `.webp`: the type read at upload, never the uploaded name), `Content-Security-Policy: default-src 'none'; sandbox; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store` and `Cross-Origin-Resource-Policy: same-origin`. Ariva.Web and the display player show it from an object URL |
| Rate limit | The `upload` policy, and at most 30 upload attempts per person in 10 minutes per host process, images and videos together, refused files included (429 with `Retry-After: 60`, security event 9129; `Ariva.Infra/Services/Displays/AdvertisingUploadWindow.cs`) |
| Audit | `AdvertisingMedia.Uploaded`, and `.Changed`, `.Approved` and `.Retired`: the site, type, size, SHA-256, pixel size, advertiser, campaign, days, state and who uploaded, changed and approved it, never the file name. A refused upload is not audited |
| A malicious file today | Refused by the type, header, size and decoder checks; what passes is a new file made from its pixels, with nothing hidden in metadata or after the end. The decoder that reads the upload is native code (SkiaSharp, in Ariva.Api.Main only), reached after the managed header checks and one upload at a time. Not scanned for malware |

### 3.6 Advertisement videos (ARV-142b)

| Question | Answer |
|---|---|
| Endpoint | The image endpoint (section 3.5), with `Ariva.Infra/Storage/AdvertisingVideos.cs` and `Ariva.Infra/Services/Displays/AdvertisingVideoSettings.cs` |
| Who may upload | As images |
| Types, and how Ariva decides | A file that starts with an MP4 `ftyp` box or an EBML header is a video, checked by its container: an MP4 of a listed brand (QuickTime refused) with H.264 (`avc1` or `avc3`) and AAC or no sound, or a WebM with VP8, VP9 or AV1 and Opus, Vorbis or no sound; one picture track and at most one sound track. Refused: truncated, fragmented and live files, encrypted or compressed tracks, other tracks or codecs, and data after the last box or element ([Administration guide](11-Administration-Guide.md) section 9, Videos) |
| Extensions | Stored as `mp4` or `webm`, from the container; script 0059 matches the extension to the type |
| Limits | File: `Advertising:Videos:MaxMegabytes`, 20 MB by default (1 to 100). Length: `MaxSeconds`, 30 seconds by default (1 to 120), as the container states it; a track header or cluster that states a longer stream refuses the file. Request: as images. Unpacked: the container is read to at most 12 levels deep and 4,096 boxes or elements, nothing is allocated from a declared size and the media data is never walked; the picture is held to the image limits as the container states it. The ingresses take 21m: raise them with the setting ([Administration guide](11-Administration-Guide.md) section 9) |
| What Ariva does to it | Never decodes it. Metadata becomes zeroed padding of the same size, so the media does not move: MP4 `udta`, `meta`, `uuid` and free space, handler and compressor names and creation times; WebM tags, attachments, chapters, title, date, track names and `CRC-32`. Kept: WebM's `MuxingApp` and `WritingApp`, and the compressed media as uploaded |
| Where it is stored | As images, under a generated key ending `.mp4` or `.webm`, with its length |
| How it is served | As images, from the same two endpoints with the same headers, the file named `advertisement-{id}.mp4` or `.webm` |
| Rate limit | As images (the same 30 attempts) |
| Audit | As images, with the length (`durationMilliseconds`) |
| A malicious file today | Refused by the container checks; markup hidden in metadata or free space is zeroed and markup after the end is refused. The compressed media is stored as uploaded and never decoded on the server, so a file aimed at a decoder bug is a risk for the browsers that play it (the library preview, which loads a video only when someone asks, and the display players, after a second person's approval), each in its own sandbox. Not scanned for malware |

## 4. Malicious files

### Today

No upload is scanned for malware (ASVS V5.4.3 is a Gap). What stops a malicious file is the handling above: the type is decided by the bytes, every size and every unpacked bound is checked before the file is used, a file that does not have the structure of its type is refused with a fixed text, active content is removed (SVG rebuilt, advertisement images written anew, video metadata zeroed), nothing is ever executed on the server, and what is kept is served only as data with its own type, `nosniff` and a sandboxing content security policy. SSIM and CSV files are never kept: only checked values are imported.

What passes those checks unscanned:

- PNG and JPEG floor plans, uploaded or in a site configuration bundle, are stored and served as uploaded.
- Advertisement videos keep their compressed media as uploaded; browsers decode it.
- Advertisement images reach a native decoder on the server (after the managed header checks) before they are written anew.

When a stored file is suspected, find it by the SHA-256 in its audit entry ([Administration guide](11-Administration-Guide.md) section 10), then:

- Floor plan: delete it (`DELETE api/v1/admin/levels/{levelId}/floor-plan`, administrators) or upload a clean one; either removes the file from storage after the commit.
- Advertisement: retire it; it never plays again. Its file stays in storage and in the library preview, since nothing in the library is deleted, and no endpoint removes it.
- Then follow the incident steps of the [Security guide](13-Security-Guide.md), section 11.

### After ARV-092b and ARV-092c

Target procedure, not built yet: ARV-092b scans every upload in the hosts before Ariva stores or imports anything from it, with ClamAV (clamd, INSTREAM over TCP, with limits that cover the largest upload). A detection is refused with a fixed message and audited (who, what kind of upload, the signature name, never the file). A scanner that cannot answer refuses the upload outside vm-local (fail closed): no upload is taken while the scanner is down. docker-compose, the Aspire AppHost and the E2E run start a clamd, and the tests send the EICAR test file to every upload endpoint.

Target procedure, not built yet: ARV-092c runs clamd in the chart (pinned by digest, non-root, a read-only root with writable signature storage, resource limits) as a Service the upload hosts reach under a NetworkPolicy, required in k8s-prd. Signatures come from freshclam and the public mirrors where the site allows it, or from a site mirror or a mounted signature set for a site without internet, with a staleness alarm and a go-live record. How signatures reach a site without internet: To confirm (the owner or the site chooses).
