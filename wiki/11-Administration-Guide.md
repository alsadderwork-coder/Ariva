# Administration guide

For each deployment's System administrator and for the duty managers who own operational configuration. It covers users and roles, permissions, TOTP, integration clients and outbound endpoints, devices, zone profiles, alert rules, displays, the audit log and data retention.

Status: administration screens arrive with Phase 1 (epics Authentication, roles and audit; Zone editor; Alerting) and v1 (contracts). Everything below is the target behaviour, taken from the design, the security controls and the prototype. In Phase 0, zones come from a configuration file; user, role and audit administration exist as an API (ARV-011, section 2) without screens yet.

## 1. Principles

- Default deny. Every endpoint requires a permission (users), a scope (integration clients) or device authentication (sensors); anything else fails the build's endpoint inventory test.
- Permission policies, not role strings. Permission codes have the form `Area.Entity.Action` (for example `Ops.Zones.View`, `Admin.Zones.Edit`) and are declared in `Ariva.Core/Global.cs`.
- Site scope on every query and command: a user of one site never reads another site's data.
- The data boundary is enforced by field-level projection per role: a Terminal duty manager never receives per-desk border data, and nobody receives officer identity.
- Critical functions require step-up MFA: a TOTP check within the last 15 minutes.
- Everything that changes configuration, decides an SLA question or exports data is audited.

Critical functions (step-up MFA required):

| Function | Who |
|---|---|
| Publish or activate a zone profile | Site administrator or the duty manager who owns the zones |
| Sign a handler contract (v1) | Terminal duty manager |
| Create, change or rotate an integration client | System administrator |
| Create or change an outbound endpoint | System administrator |
| Grant or revoke roles, create users, reset a password or TOTP | System administrator (a second approving administrator for System administrator grants is a Phase 1 candidate) |
| Close a validation campaign (ARV-104a) | Border shift supervisor, Terminal duty manager or System administrator of the site |
| Recompute a closed validation campaign's results (ARV-104g) | Border shift supervisor, Terminal duty manager or System administrator of the site |

## 2. Users and roles

| Field | Rule |
|---|---|
| Display name | Free text |
| Organisation | Border authority, airport operator, a handler (for example Handler B), or a security contractor |
| Role | Only roles valid for that organisation and deployment: Border shift supervisor in a border deployment; Terminal duty manager and Handler station manager in an airport deployment; System administrator in either; Validation observer in either, for the people who count during a validation campaign (section 2c) |
| Deployment | Derived and enforced: a border deployment user cannot hold an airport role, and the reverse |
| Sign-in method | Ariva's own sign-in, the only one built: PBKDF2 password hashing, TOTP for every account and step-up for critical actions (ADR-0026, security guide section 3). Sign-in through the customer's identity provider (OIDC, D5's option) is not built: it is ARV-134a (Target procedure), and the owner decided on 2026-10-11 that sign-in does not change until that work (docs/product/decisions.md). No host registers an OpenID Connect handler or calls an identity provider, Keycloak or any other; `ISvcAuthenticator` only names the boundary where such federation would plug in |
| Expiry | Optional end date for temporary accounts |

Role grant rules:

- Grants only through the role assignment service: the granter's own role must rank at least as high as the role (System administrator above the three operational roles and the validation observer), nobody changes their own roles, and the last active System administrator keeps the role.
- Every grant and revoke needs step-up MFA and is audited; a revoke ends the user's sessions.
- Role codes (`BorderShiftSupervisor`, `TerminalDutyManager`, `HandlerStationManager`, `SystemAdministrator`, `ValidationObserver`) never change once shipped.
- Until handler organisations exist (ARV-213), a Handler station manager account sees every handler's queue zones at its sites, border lanes and security included ([security guide](13-Security-Guide.md) section 4). Grant it only where every handler at the site may see the others' queues.
- A validation observer (ARV-104a) holds one permission, `Validation.Capture`: it records manual counts for the running validation campaigns of its sites and corrects its own counts, and nothing else (no operational screen, topology, report or campaign management). Give the account the campaign's site only: Ariva refuses every site for an account whose only role is Validation observer, when you create it, change its sites, grant the role or revoke its other role (400). An account that also holds another role follows that role. The person who plans or starts a campaign never counts for it, even with the observer role as well (403). Observers may be border officers seconded to the campaign: Ariva stores only their account id with each count, and the account itself holds the name you give it, so use a neutral user name and display name (for example `obs.amm.07`) where the data boundary requires it.

What each role sees and creates is in [Product overview](01-Product-Overview.md) (Roles). The authorisation matrix (`security/permission-matrix.json`, role by endpoint by expected status) is the reference; it drives the authorisation tests.

Phase 0 API (ARV-011), under `api/v1/admin`: `users` (search with text, role and disabled filters and an allowlisted sort; view; create; update display name and email; `reset-password`; `reset-totp`; `roles/{role}` PUT to grant and DELETE to revoke; `unlock`; `disable`; `enable`), `roles` (the five roles, their rank and permissions) and `audit-entries` (search and view). Sites (ARV-012): `api/v1/admin/sites` creates and renames sites (codes never change, sites are never deleted) and `users/{id}/sites` sets a user's access to every site or a list (critical, only within your own sites; narrowing ends the user's sessions). Everyone reads only their sites through `api/v1/sites`. An administrator limited to some sites manages only accounts inside them and cannot create sites; the break-glass account and the administrators that existed before site scoping reach every site. A new account and a password reset get a temporary password of four groups of five characters, shown once; the user must change it at the next sign-in. Accounts are disabled, never deleted. The break-glass account does not appear here.

Sessions: access tokens last 15 minutes; a new session id is minted at every sign-in; refresh tokens rotate on every use, are stored hashed, and reuse of an old refresh token revokes the whole family. The refresh cookie is HttpOnly, Secure, SameSite Strict.

## 2a. Site topology

In Ariva.Web, Topology (ARV-052) shows the tree as five columns, airports to desks: pick the site, then an airport, terminal, level and checkpoint; the details of the item last picked show below. An administrator adds items with Add on each column (Add a range for desks), edits names, floors, sizes, lane categories and in service in the details, deletes with a confirmation on the page, and maps a desk's AMAN or AODB code in the desk's details. Airports are added or changed only by an administrator of all sites. Every other role sees its sites read only; terminal duty managers also see the desk codes, border shift supervisors and handler station managers do not. The screen calls the API below, which checks every change.

ARV-014 adds `api/v1/admin/airports`, `terminals`, `levels`, `checkpoints` and `desks`, each with search (text, parent, site, an allowlisted sort, pages of at most 500), view, create, update and delete.

| Entity | Rules |
|---|---|
| Airport | IATA code (three letters, never changed), optional ICAO code, name, IANA time zone (picked from the list, grouped by region with the current UTC offset; the server checks it). Deployment-wide: only an administrator with every site creates, changes or deletes airports; every topology reader can read them |
| Terminal | Code unique in the airport; belongs to one site, fixed at creation, which every level, checkpoint and desk under it inherits |
| Level | Code and floor number unique in the terminal; width and depth in metres (up to 2,000) define the floor coordinate system for zones |
| Checkpoint | Kind `CheckIn`, `Security`, `Emigration` or `Immigration`, fixed at creation |
| Desk | Kind by checkpoint: `Counter` at check-in, `SecurityLane` at security, `Desk` and `EGate` at emigration and immigration; border desks serve at least one lane category and e-gates include `EG`; can be taken out of service |

`POST desks/range` creates a numbered range in one go (for example prefix `D`, 1 to 22, width 2 gives D01 to D22): at most 200, every code valid and free, otherwise nothing is created. `desk-code-mappings` (or a CSV file, section 2e) maps another system's code to a desk: AMAN desk and e-gate codes to border desks and e-gates, AODB counter codes to check-in counters; a code is unique per system and site, a desk has one code per system, and the feeds resolve codes through these mappings and park what they cannot resolve. Whether AODB also sends security lane codes is To confirm per airport.

Each level can carry one floor plan (ARV-018) at `api/v1/admin/levels/{levelId}/floor-plan`: upload a PNG, JPEG or SVG of at most 20 MB as multipart field `file` with `metresPerPixel`, `originX` and `originY` (the floor coordinates, in metres, of the image's top left corner). The file name may be at most 200 characters, each accent or other combining mark counting as one (a longer name is refused, never cut). The file type is read from its content, so a renamed file is typed by what it is; raster images may be at most 16,384 pixels a side and 128 megapixels (an A0 sheet at 250 dpi fits). SVG drawings keep shapes, paths, text, gradients, patterns, clip paths, masks and markers with inline presentation styles; scripts, links, style sheets, embedded HTML or images, filters and anything pointing outside the file are removed before storing, so export plans as plain vector drawings (at most 200,000 elements). A host takes one upload at a time; a busy host answers 429 and the upload can be retried. A new upload replaces the previous plan, and a level cannot be deleted while it has a plan. `PUT .../calibration` changes the scale and origin, `GET .../content` returns the image, `DELETE` removes the plan. Uploads and deletes need an administrator; every topology reader can view plans of their sites. What Ariva checks, keeps and serves of a plan, and what happens to a malicious file: [File handling](13a-File-Handling.md), section 3.1.

Every file you upload (floor plans, SSIM schedules, CSV imports, site configuration bundles, advertisements) is scanned for malware first (ARV-092b): a file the scanner recognises is refused with 400, "The file was refused: the malware scanner found a known threat in it.", and recorded in the audit trail as `Upload.MalwareRefused`; while the scanner does not answer, uploads are refused with 503, "Uploads are paused: the malware scanner did not answer. Try again in a few minutes." ([File handling guide](13a-File-Handling.md) section 4; [Operations runbook](10-Operations-Runbook.md) section 4.18).

Development and demo deployments start with the fictional Demo International Airport (ARV-019, site `DMO`, terminal `T1`, IANA zone Asia/Dubai): level `ARR` (arrivals, floor 0) with arrival immigration `IMM` (desks AR-01 to AR-22: AR-01 crew, AR-02 to AR-04 citizens, AR-05 to AR-07 residents, AR-08 to AR-22 visitors; e-gates AG-1 to AG-6), and level `DEP` (departures, floor 1) with check-in `CI` (islands A to D, counters A01 to D12), security `SEC-N` and `SEC-S` (lanes N1 to N5 and S1 to S5) and departure immigration `EMI` (DP-01 to DP-22 by the same lanes, e-gates DG-1 to DG-4). Both levels are 100 by 60 metres. Zone profile version 12, published by `demo-seed`, has the prototype's 16 queues and 7 overflow bands with their entry, exit and overflow entry lines. The seed only adds what is missing: it never changes or deletes a record, leaves a draft someone started alone (and then skips v12), stops without writing if existing DMO records belong to another site or have another kind, and creates no users or site grants; give people access to `DMO` like any site. Turn it on with `Seed:DemoTopology` (vm-local) or the Helm value `demoSeed` (demo); production refuses it.

The same deployments also get a second, illustrative site after DMO (ARV-139a, [docs/demo/auh-terminal-a.md](../docs/demo/auh-terminal-a.md)): `AUH-TA`, the arrivals immigration hall of Zayed International Airport (AUH) Terminal A, modelled from public information only. Airport `AUH`, terminal `A`, level `ARR` (lower arrivals level, 200 by 150 metres, an assumption) with arrival immigration `IMM`: counters IC-01 to IC-38 and smart gates SG-01 to SG-34 (both counts reported, unverified), queue zones `A-CRW`, `A-DIP`, `A-CIT`, `A-RES`, `A-GCC`, `A-VIS`, `A-TRF` and `A-EG` by lane, overflow bands `A-VIS-OV` and `A-EG-OV`, a staff and a service zone per counter (`IC-01 staff`, `IC-01 service`, linked to the desk, so the counters' states come from sensors alone, ARV-116), 84 sensors in Commissioning without credentials, an illustrative floor plan and zone profile version 1, published by `demo-seed`. Everything but the cited facts is an assumption. The site is flagged "Illustrative, not surveyed": every screen of the site and its passenger displays show a banner in English and Arabic. Only the seed sets the flag; the sites API ignores it in a body and the runtime database role cannot change it. The seed never writes into a site `AUH-TA` without the flag, so a real deployment of that code is never touched. Replace the illustrative plan with a real one by uploading it on the Zones screen; a real plan is never committed. Give people access to `AUH-TA` like any site.

Names (of sites, airports, terminals, levels, checkpoints, desks, zone profiles, zones and lines) are 1 to 200 characters of visible text (ARV-159): any script and its marks, digits, punctuation and emoji (the England, Scotland and Wales flags included, each only whole, ARV-169), but no control character, line break or invisible format character (a right-to-left override, a zero-width space or joiner, any other tag character); such a name is refused with 400 and the text "A name holds no control characters, invisible format characters or broken characters." (for a site: "The site name is at most 200 characters, without control, invisible or broken characters."). A name saved before ARV-159 is kept, but its record cannot be edited until it is renamed; Operations Runbook 4.2b lists such names. Codes are 1 to 16 upper case letters or digits with single inner hyphens. Deletes are soft (history and zone profiles keep their references), refused while live records exist underneath, and free the code for reuse. Everyone sees only the records of their sites; another site's record answers like one that does not exist. Every change is audited.

## 2b. Site operating calendar (ARV-118)

The operating calendar decides which minutes count in the pilot's availability criterion (99 percent of operating hours; [KPI definitions](15-KPI-and-SLA-Definitions.md) section 8). There is no screen yet (deferred); administrators use the API `api/v1/admin/sites/{siteCode}/calendar`. Every role reads the calendar of its sites (`GET`, the site's view permission); only administrators of the site change it (the site's edit permission). Every change is in the audit log (`SiteCalendar.*`). Times are the site's local time: the IANA zone of the site's airport (UTC for a site without one); the answer names the zone and today's local date.

| Entry | Request | Rules |
|---|---|---|
| Weekly hours | `PUT .../calendar/weeks` with `effectiveFrom` (a local date `yyyy-MM-dd` after today, at most 366 days ahead) and `hours`, a list of `{ "day": "Monday", "opens": "06:00", "closes": "22:00" }` | Up to 4 intervals a day, none overlapping (Sunday's overnight interval runs into Monday). A closing time before the opening time is on the next day (`18:00` to `02:00`), and a closing time equal to the opening time is refused; `00:00` to `24:00` is the whole day; a day without intervals is closed. The version is in force from its day until a later version's day. Setting the same day again replaces the version; `DELETE .../weeks/{id}` removes it |
| Dated exception | `POST .../calendar/exceptions` with `date`, `closed` (true with no hours, or false with 1 to 4 intervals) and a `reason` (1 to 200 characters) | Replaces the intervals that open on that local day (the overnight part of the previous day still counts). One exception per day; `DELETE .../exceptions/{id}` removes it |
| Maintenance window | `POST .../calendar/maintenance-windows` with `startsUtc`, `endsUtc` (UTC, whole minutes, ISO 8601 ending in Z) and a `reason` | Starts after now, at most 7 days long and 366 days ahead. Operating minutes inside it count in neither side of the ratio. `DELETE .../maintenance-windows/{id}` cancels it |

Record entries before they take effect: a week or an exception before its local day starts, a maintenance window before it starts (server time). An entry that has taken effect can no longer be changed or removed (409): it is part of the record. Two administrators recording the same day's exception, or a new weekly version of the same day, at the same moment: one succeeds and the other gets 409 (read the calendar and try again). A removed entry disappears from the calendar and stays in the database as deleted, with a `SiteCalendar.WeekRemoved`, `ExceptionRemoved` or `MaintenanceCancelled` audit entry holding what it was. A maintenance window that has already started cannot be recorded, so an unplanned outage stays in the figures; this is the Proposed rule (TC-83). A site without any weekly version in force is open around the clock: every minute counts. A site administrator of one site gets 404 for another site, and an entry of another site through its own site's route answers 404 too.

Example (Dubai, open 06:00 to 22:00 every day from next Monday):

```
PUT /api/v1/admin/sites/DMO/calendar/weeks
{ "effectiveFrom": "2026-10-12", "hours": [ { "day": "Monday", "opens": "06:00", "closes": "22:00" }, ... ] }
```

## 2c. Validation campaigns (ARV-104a, ARV-104b, ARV-104g)

A validation campaign proves a site's numbers before anyone relies on them ([Commissioning and calibration](07-Commissioning-and-Calibration.md) section 8; formulas F18). There is no screen yet: the observer tablet is ARV-104c and ARV-104d, the campaign and report screens ARV-104h. Until then use the API under `api/v1/sites/{siteCode}/validation`.

| Who | Permission | Roles holding it |
|---|---|---|
| Reads campaigns, every observer's counts and tracer runs | `Validation.View` | Border shift supervisor, Terminal duty manager, System administrator |
| Reads the border desks of a campaign and every observer's desk states (border data) | `Validation.View` and `BorderDesks.View` | Border shift supervisor, System administrator |
| Plans, starts and closes campaigns (closing needs a second factor within 15 minutes); puts border desks in scope only with `BorderDesks.View` | `Validation.Manage` | Border shift supervisor, Terminal duty manager, System administrator |
| Records and corrects their own counts and desk states, records tracer runs | `Validation.Capture` | Validation observer only |
| Logs, corrects and reads back desk states, and sees the desks to log (border data) | `Validation.Capture`, and either `BorderDesks.View` or no role but Validation observer | Validation observer alone, or with Border shift supervisor or System administrator |

Managers and administrators do not capture (separation of duties, decided by the owner on 2026-10-08): the ground truth stays independent of whoever configures the system or runs the campaign. If a manager or an administrator must count (a paper sheet, for instance), give that account the Validation observer role as well; it still never counts for a campaign it planned or started (403). Handler station managers hold none of the three.

Desk states are border data (first security review of ARV-104b, 2026-10-08): an account that holds an airport role (Terminal duty manager or Handler station manager) and the Validation observer role counts lines and times tracers, but sees no desk in the capture list and is refused (403) on desk logs, desk corrections and its own desk reads. Desk logs come from a Validation observer account with no other role (the border's own observer) or from a border shift supervisor or administrator who also holds the Validation observer role. Do not name people in a correction's reason: it is kept beside a desk and a minute.

| Step | Request | Rules |
|---|---|---|
| Plan | `POST .../validation/campaigns` with `name` (1 to 200 characters), `profileVersion` (the site's published zone profile version you reviewed), `zoneIds` (1 to 50 queue zones of that version), `lineIds` (up to 200 lines of those zones or of their overflow bands), `days` (1 to 31 local dates `yyyy-MM-dd` in the site's time zone, from 31 days back to 366 ahead), optional `targetBinsPerLine` (1 to 2,976) and `targetTracerRuns` (0 to 1,000), and optional `deskIds` (up to 100 staffed immigration or emigration desks of the site, in service; e-gates and airport counters are refused; a terminal duty manager naming desks gets 403) | A newer published version answers 409 (read the profile again). A target left empty takes its placeholder (20 bins per line, 30 tracer runs) until the pilot's KPI annex answers TC-04; the campaign shows `placeholder: true`. A count line standing alone (on no zone) is counted by no queue zone and cannot be in scope |
| Start | `POST .../campaigns/{id}/start` | Planned only, and only while its profile version is still the published one (409 otherwise) |
| Capture | `POST .../validation/capture/campaigns/{id}/counts` with `lineId`, `binStartUtc` (UTC on the quarter hour, ending in Z), `crossingsIn` and `crossingsOut` (0 to 10,000); optional `Idempotency-Key` header | The campaign runs, the line is in scope, the bin starts on a planned local day, has ended (a minute of clock tolerance) and ended before the profile version was retired. One count per line, bin and observer (a second is 409; two observers may count the same line and bin). Resending with the same key returns the stored count (200); the same key with another count is 409. A key belongs to the observer who sent it: another observer's identical key makes that observer's own count (201). The account that planned or started the campaign is refused (403) |
| Correct | `POST .../capture/campaigns/{id}/counts/{countId}/corrections` with the crossings and a `reason` (1 to 200 characters) | Only your own latest revision (409 for an older one, 404 for another observer's); it becomes the next revision, the corrected one stays. Audited (`ManualCount.Corrected`) |
| Read | `GET .../campaigns` (text, status, an allowlisted sort, pages of at most 500), `GET .../campaigns/{id}` (scope, targets, the version's state, bins captured per line), `GET .../campaigns/{id}/counts` (current revisions, or `currentOnly=false` for every revision; by line, observer and bin range); observers `GET .../capture/campaigns` (the running campaigns with their lines and the site's time zone) and `GET .../capture/campaigns/{id}/counts` (their own) | A site you cannot see, a campaign of another site and another observer's count answer 404 |
| Tracer runs | `POST .../capture/campaigns/{id}/tracer-runs` with `deviceClockUtc` (the tablet's own clock when it sends, read again at every retry) and 1 to 20 `runs`, each with `zoneId` (a queue zone in scope), `tracerCode` (`T-` and 2 or 3 digits, never a name), `joinedUtc` and `exitedUtc` (the tablet's times, UTC ending in Z) and `abandoned`; `Idempotency-Key` header required | Ariva measures the tablet's offset (its clock minus Ariva's at receipt) and stores the tablet's times, the offset and the corrected times; more than 5 minutes off is 400 (set the tablet's time automatically). Each run lasts at most 3 hours, joined on a planned local day, exited not in the future beyond a minute (400 otherwise, the value never repeated). Resending with the same key returns the stored batch (200); the same key with other runs is 409; a run already sent in another batch is 409, and so is a batch past 500 runs of yours in the campaign. Tablet times more than 32 days before or more than a minute after the tablet's own clock reading are refused (400) before any correction. Read with `GET .../campaigns/{id}/tracer-runs` (by zone, observer, tracer code, join range) and `GET .../capture/campaigns/{id}/tracer-runs` (your own) |
| Desk logs | `POST .../capture/campaigns/{id}/desk-observations` with `binStartUtc` (UTC on the quarter hour) and 1 to 20 `desks`, each a `deskId` in scope and exactly 15 `states` (`Closed`, `Idle`, `Serving`, `Paused`, or null for a minute not observed); `Idempotency-Key` header required | Only minutes that have ended (a minute of tolerance), on a planned local day; one state per desk, minute and observer (a minute already sent is 409; resending with the same key returns the stored batch). Correct with `POST .../capture/campaigns/{id}/desk-observations/{observationId}/corrections` (`state` and a `reason`; your own latest only; audited `DeskObservation.Corrected`). Read with `GET .../campaigns/{id}/desk-observations` (border roles only: a duty manager gets an empty page with `desksIncluded` false) and `GET .../capture/campaigns/{id}/desk-observations` (your own). An account with an airport role gets 403 on these three observer calls and `desksIncluded` false with no desk in `GET .../capture/campaigns`, even with the Validation observer role |
| Close | `POST .../campaigns/{id}/close` | Critical (a second factor within 15 minutes, otherwise 401 `mfa_required`); from Planned or Running; nothing is captured or corrected afterwards (409). Audited with plan and start (`ValidationCampaign.*`) |
| Results | `GET .../campaigns/{id}/results` (Validation.View), optional `?revision=n` (1 to 1,000) | The results as JSON (ARV-104g): each criterion against its target and the comparison behind it, availability, calibration records, profile version and geometry hash. Computed when asked while the campaign is not closed; frozen at the close as revision 1 with `revision.contentSha256`, the SHA-256 of the stored document. Your roles decide the sections: the `desks` section only for roles that see border desks; `audience` says what you got. 404 for another site's campaign or a revision that does not exist; 409 for a campaign over 400 zone-days; 429 and 503 carry Retry-After |
| Recompute | `POST .../campaigns/{id}/results/revisions` with a `reason` (1 to 500 characters) | Critical (a second factor within 15 minutes) and audited; only a closed campaign whose results are frozen (409 otherwise). Adds the next revision with your reason and keeps every earlier one; the answer is the new revision. Every Validation.View holder of the site reads the reason on the campaign's Results tab: say what changed, never name a person |

A campaign, its scope, its counts, tracer runs and desk logs are evidence: nothing is deleted, a closed campaign never changes, and the database refuses an edited count, run or desk state, or one in a campaign that is not running, even from a hand-written statement. Desk logs are border desk data: they stay in the border deployment and only border roles read them. If a new zone profile version is published during a campaign, counts of bins that ended before it stay valid and later bins are refused; plan a new campaign over the new version (re-validate after any layout change, F18).

## 2d. Moving or rebuilding a site's configuration (ARV-122a, ARV-122b)

A configured site can be carried to another environment (a staging site to the pilot's production) or rebuilt after a loss as one bundle. API only for now; a screen can follow if field engineers need one. Both actions need `SiteConfiguration.Transfer` (system administrators only) and a second factor in the last 15 minutes (otherwise 401 `mfa_required`), work only at sites the caller holds (another site answers 404) and are audited with the bundle hash, the counts and the outcome, never a name or a part. The bundle's limits and checks as an upload: [File handling](13a-File-Handling.md), section 3.4.

| Action | Call | What happens |
|---|---|---|
| Export | `GET api/v1/admin/sites/{siteCode}/configuration` | The answer holds `bundle` (the document to keep), `bundleSha256`, the counts, and the published zone profile's two hashes: `geometryHash` (F22 v1, the version's own) and `portableGeometryHash` (the same geometry on the same codes at any site). The bundle carries the topology (terminals with their airport's IATA code, levels, checkpoints, desks), the desk code mappings, the published zone profile (a site without one is exported without it, and the answer says so), each level's floor plan file, the devices (not retired), the alert rules and the displays. Never users, roles, integration clients, endpoints, secrets, audit, time series, validation data or report schedules; never a device's credential, calibrations, state or access settings (source networks, certificate pin; only whether it had any), an alert rule's escalation contact (only whether it had one), state or alerts, or a display's pairing credential. |
| Import | `POST api/v1/admin/sites/{siteCode}/configuration`, body: the export's `bundle` (at most 20 MB); optional `?airportCode=XXX` | Into an empty site only (no topology, mapping, plan, device, alert rule, display or zone profile of any status; 409 otherwise): everything is created anew in one transaction, all or nothing. A record created at the site by hand while an import runs waits for the import and is made after it; an import started while such a create is under way waits for it and then answers 409 (ARV-154). The answer holds the same `bundleSha256` as the export, the bundle's `sourceSite` (what the bundle claims, not authenticated), the counts, the draft profile's id and portable hash, `deviceCredentials` (each imported device's code and its new credential, shown this once), `devicesNeedingAccessSettings` (the codes of the devices whose source networks or certificate pin were left behind) and `rulesNeedingEscalationContact` (the codes of the rules whose escalation contact was left behind). |

How to move a site:

1. On the source, export the site and keep the `bundle` and the `bundleSha256` of the answer.
2. On the target, create the site (Users and access, or `POST api/v1/admin/sites`) and the airport the bundle names if it is not there yet: an import never creates an airport. To place the terminals at another existing airport (a copy within one deployment, where the source's terminal codes are taken at its own airport), add `?airportCode=` with that airport's IATA code.
3. Import the bundle and compare the answer's `bundleSha256` with the export's, out of band (read both aloud, or compare them in the change ticket). Equal hashes mean nothing in the bundle changed on the way. They do not prove who made the bundle: anyone can recompute SHA-256, which is why only an administrator with a fresh second factor may import, and why every part is checked again as if typed in (codes, names, kinds, limits, geometry, and every floor plan file typed by its bytes and an SVG sanitised again).
4. The zone profile arrives as a draft. Review it in Zones and publish it with your second factor as usual; the new version's `geometryHash` differs from the source's (it names levels and desks by their new ids), while its `portableGeometryHash` (export the target to read it) equals the source's when nothing changed.
5. Devices arrive in Commissioning, each with a new credential in the answer's `deviceCredentials`: install each on its device at once (the answer is the only place it is shown; the source's credentials never work at the target), set the source networks and certificate pin again for each device listed in `devicesNeedingAccessSettings` (the device's access settings; the bundle never says what they were, so take them from the site's commissioning as-built pack: the network or IP plan for each device's source networks and the certificate register for its pin, the same pack whose device list the CSV import loads, wiki 07 section 2; owner decision 2026-10-13), and calibrate every device (wiki 07). A device the registration would refuse (a zone not under its footprint, an unsupported transport) refuses the whole import.
6. Alert rules keep their codes (an import takes codes up to `R-100000`, so the target keeps room for new rules); type the escalation contact again for each rule listed in `rulesNeedingEscalationContact` (contacts never travel). Displays arrive unpaired: issue each player's credential with the display's new credential action (`POST api/v1/admin/displays/{id}/credential`, with your second factor). Rules and displays act once the draft is published (step 4), since they name its zones.
7. Grant users the new site.

A display code is unique among the live displays of the whole deployment, so copying a site within one deployment answers 409 while the source's displays exist: delete them first, or move the site to another deployment.

Export and import share one queue per host with floor plan and SSIM uploads: one runs at a time and two wait, so at a busy moment a call answers 429 with `Retry-After` (10 seconds); wait that long and send it again. The audit records every import past the site check: imported, refused (with the fixed reason) or failed (including an import rolled back after it was written, for example when the commit fails), each with the bundle hash when the manifest checked out and the bundle's claimed source site.

An export answers 409 with a fixed text naming the kind of record, never a value, when a stored value would be refused by the import (ARV-162): a terminal, level, checkpoint or desk name, a published zone profile with a name or a zone outline the rules now refuse, a floor plan file name with a path or a control or invisible character (stored before ARV-153), or a device model, alert rule name or display text with a control or invisible character; rename or change it (for the profile, publish a corrected version; for a plan, upload it again under a clean name) and export again. A bundle is refused with 400 and a fixed text when a part is missing, extra or unknown, a hash does not match, the format version is not 1, a row leaves out a member or adds one, an alert rule code is above `R-100000`, or a part breaks a rule; with 413 when the body passes 20 MB or a part its own bound (8 MB for a configuration part); with 409 when the site is not empty, a terminal code is taken at its airport or a display code is taken by a live display. A bundle exported before ARV-122b (without the devices, alert rules and displays parts) is refused: export the site again. An alert rule must watch queue zones or overflow bands of the bundle's profile (a health check queue zones only) and a display must show queue zones, otherwise the bundle is refused. An export is refused with 409 when the site has more records of a kind than a bundle holds (50 terminals, 200 levels, 1,000 checkpoints, 5,000 desks, 10,000 desk code mappings, one plan per level, the profile's 500 zones and 1,000 lines, 2,000 devices, 500 alert rules, 200 displays), when its bundle would pass 20 MB (smaller plan images help), when the published profile still names a removed level or desk, when a device hangs on a removed level, when a device, alert rule or display names a zone the published profile does not have (or the site has no published profile), when an alert rule's code is above `R-100000` (an import would refuse it), or when two of its terminals share a code at different airports.

An import checks in this order, so the first problem found is the one answered: the `airportCode` shape (400); the bundle's envelope, manifest, sizes and hashes (400 or 413); the malware scan of every decoded part (400 for a detection, 503 while the scanner does not answer; ARV-092b); the strict reading of each part (400); the request rules (400); the airports (400); whether the site is empty (409); the plan: a terminal code taken at its airport (409), then the topology, mappings, profile, alert rules and displays by their own rules and the rules' and displays' zones (400); the alert rules' roles (400); the floor plan files (400); the display codes (409); then everything is written and, last, each device goes through the registration, whose own rules (transport, mapping, zone and reach) answer 400. A bundle with a taken display code and a device the registration would refuse therefore answers 409 first. Decisions behind these rules: docs/product/decisions.md, ARV-122a and ARV-122b.

## 2e. Importing devices and desk code mappings from CSV (ARV-123a, ARV-123b)

Two CSV imports load a site from the as-built pack, on the Devices screen and in the Topology screen's desk code panel (ARV-123b, below) or through the API (ARV-123a). Each is a preview, then a commit of the same file; the commit applies the whole file in one transaction, or nothing. Both work only at sites you hold (another site answers 404) and are audited with the file's SHA-256, the counts and the outcome, never a cell or a credential. The files' limits and checks beside every other upload: [File handling](13a-File-Handling.md), section 3.3.

| Import | Calls | Columns (header row of exact names, any order) |
|---|---|---|
| Devices | `POST api/v1/admin/sites/{siteCode}/device-imports/preview`, then `/commit`. The device registration's permission (`CreateDevice`) and a second factor in the last 15 minutes for both steps, as for registering one device | `code, family, model, transport, dialect, clockSource, terminal, level, x, y, mountingHeightMetres, orientationDegrees, queueZone`; optional `mappingName, footprintLengthMetres, footprintWidthMetres, footprintRadiusMetres` |
| Desk code mappings | `POST api/v1/admin/sites/{siteCode}/desk-code-mapping-imports/preview`, then `/commit`. The mapping permission (`CreateDeskCodeMapping`); no second factor, like the single mapping (an owner question in docs/product/decisions.md) | `externalSystem` (`Aman` or `Aodb`), `externalCode`, `checkpoint`, `desk` |

How to import:

1. Send the file as multipart field `file` to `preview`. Each row is checked as the registration (or the mapping service) checks what you type, by running it and rolling it back, so the preview refuses what the commit would: a zone the device's footprint does not reach, a code already used, an AMAN code for a check-in counter. The answer lists the rows that pass and each refused cell as a row (the header is row 1), a column (from 1, in the file's order) and a fixed text, at most 100 of them with the total; it never repeats a cell.
2. Fix the refused rows and preview again until nothing is refused: only then does the answer carry `previewToken`, good for 15 minutes, for you, this site and this exact file.
3. Send the same file with `previewToken` to `commit`. A token from another user, another site, another file or the other import, or older than 15 minutes, answers 409. The commit checks every row again: if anything changed since the preview (a device registered meanwhile with the same code), nothing is imported and the answer names the row.
4. Devices arrive in `Commissioning`; the commit's answer lists each device's new credential once: install it on the device at once and calibrate the device (wiki 07). The answer is the only place a credential is shown.

In Ariva.Web (ARV-123b):

- **Devices screen, Import devices** (beside Register a device; only for holders of the registration's permission, `Device.Create`): a dialog for the site chosen at the top of the screen. Choose the `.csv` file: a file that is not a `.csv` file, is empty or is over 1 MB is refused in the browser before anything is sent (the server checks again). **Check the file** sends the preview; if your last authenticator code is older than 15 minutes, the same step-up dialog as for registering one device asks for a fresh one, and the preview is sent once it is given. The dialog then shows how many rows the file has, how many pass and how many cells are refused, and the file's SHA-256 (as in the audit entry); each refusal by row (the header is row 1), column (its number and its spreadsheet letter, such as `12 (L)`, or Whole row) and reason, in your language where the screen has words for the server's fixed text (otherwise as the server wrote it), with "The first 100 of N are listed" beyond 100; and the rows that pass (row, code, family, model, terminal, level, queue zone; at most 500 listed). **Register N devices** is enabled only when nothing is refused, until the time shown (the preview's 15 minutes); it sends the same file again. A commit refused by the server (a row taken meanwhile, a preview older than 15 minutes) is shown in the dialog and the file must be checked again.
- **The new credentials, once.** After the commit the dialog lists each device's code and credential with a Copy action, and Copy all as CSV (`code,credential` lines), under a warning that they will not be shown again. The dialog closes only once **I have copied every credential** is ticked: Escape and the close button show a reminder instead. The credentials exist only in the open dialog: closing it drops them, as does leaving the page; they are never written to the browser's storage, the address or the console, and the devices list never shows them. A credential lost before it was installed is replaced with Issue a new credential in the device's panel (section 6). The devices list refreshes with the new devices in `Commissioning`.
- **Topology screen, desk code panel, Import mappings** (on a selected desk's "Codes in other systems" panel; only for holders of `DeskCodeMapping.Create`, administrators): the same dialog for the desk's site, for any desk of the site, not only the one selected. No authenticator code is asked for. **Create N mappings** commits, the dialog closes and the panel lists the desk's codes again.

Rows, models and zone names from the file are shown as text, never as markup (CWE-79). Hiding the import actions from those without the permission is a convenience, not the control: the server refuses everyone else (403), out-of-reach sites answer 404, and the device import asks for a second factor whatever the screen shows. Copy all leaves the credentials on the system clipboard: once they are installed, clear the clipboard or copy something else over it. Decisions behind the screens: docs/product/decisions.md, ARV-123b.

The file: UTF-8 (a byte order mark is optional), comma separated, a quoted cell may hold commas and quotes (doubled), lines end with CRLF or LF; at most 1 MB (413 beyond), 500 device rows or 10,000 mapping rows, 200 characters a cell. A text cell may not start with `=`, `+`, `-`, `@`, a tab or a carriage return (a spreadsheet would run it as a formula), and no cell holds a line break or another control character. A number is digits with an optional leading minus and decimal point, such as `-0.5` or `12`: the minus is read only as the sign, and the column's range applies (x and y from -1 to 2001 m, the mounting height 0 to 100 m and 2 to 20 m to register, the orientation 0 to 360 degrees, footprints 0 to 1000 m), so `-1` is a position but never an orientation; `+`, `=`, `@`, exponents and spaces are never part of a number. A device code is any code of the topology pattern (TC-40). One import runs at a time per host; a busy host answers 429 with `Retry-After`. Decisions behind these rules: docs/product/decisions.md, ARV-123a.

## 3. TOTP enrolment and reset

Ariva's own sign-in is the only one built (section 2, Sign-in method); everything below is what it does today, except the steps marked Proposed. Tests named here are in `Platform/Backplane/Ariva.UnitTests` (unit), `Platform/Backplane/Ariva.IntegrationTests` (integration) and `Platform/Testing/Ariva.E2E/tests` (E2E).

### 3.1 Enrolment

1. Every account enrols an authenticator at its first sign-in, before any other action: until it confirms one, the account holds only the pending scope, which carries no permission (`User.IsPending`, `StoredPermissionResolver`; integration `TotpTests.Enrolment_Should_KeepThePendingScopeUntilAValidFirstCode_When_TotpIsRequired`). `Auth:TotpRequired` is on in every committed configuration file, and outside vm-local a host refuses to start with it off (`AccountExtensions.LocalOnlyProblem`; unit `AuthSettingsTests.AddArivaAccounts_Should_RefuseSignInWithoutTotp_When_AnyHostRunsOutsideVmLocal`). So, as built, every role uses MFA. D5 requires it for administrators; whether a site wants it for the other roles is To confirm per site (TC-06).
2. The first sign-in screen (`/setup` in Ariva.Web) shows a QR code and the key once; the user scans it into an authenticator app and confirms with a current code (`SvcAuthenticator.EnrolTotpAsync` and `ConfirmTotpAsync`). Ariva then shows 10 recovery codes once, with a copy action (ARV-051). Account security (`/account`) changes the password (given the current one) and replaces the recovery codes (given a current authenticator code); it does not enrol another authenticator. An enrolled account cannot start a new enrolment (`User.BeginTotpEnrolment`), so a new or lost phone always goes through the reset in section 3.2.
3. TOTP follows RFC 6238 with a replay guard: a code cannot be used twice.
4. A recovery code stands in for the authenticator at sign-in and at step-up, each code once (integration `TotpTests.Login_Should_AcceptEachRecoveryCodeOnce_When_TheAuthenticatorIsLost`). A user who has lost the phone but holds unused codes can keep working until the reset, and should ask for the reset at once.

### 3.2 Lost or replaced authenticator (ASVS V6.4.4)

What Ariva does (ARV-011):

- **Who resets.** A holder of `User.Edit` (System administrators) on Users and access (Reset authenticator) or `POST api/v1/admin/users/{id}/reset-totp`, for accounts inside the administrator's own sites; another site's account and the break-glass account answer 404 (`SvcUsers.VisibleAsync`).
- **Never the caller's own account.** `SvcUsers.ResetTotpAsync` refuses it with 403 "You cannot change your own roles, password or authenticator here." (`AdministrationErrors.OwnAccount`), and the screen disables the action on your own account. This is a control, but it compares accounts, not people: Ariva cannot tell that two accounts belong to one person. Tests: integration `AdministrationTests.Resets_Should_EndSessionsClearTotpAndAudit_When_AdministratorResets`; E2E `api/administration.spec.ts` "privilege escalation attempts return 403", `functional/users.spec.ts` "an administrator cannot change its own account on the screen, and the API refuses it however it is asked" and "a site administrator sees and grants only its own site; the API refuses wider access".
- **Step-up first.** The reset is a critical action (`[RequiresRecentMfa]`, listed in `security/critical-actions.json`): it needs an authenticator or recovery code confirmed in the last 15 minutes, otherwise it answers 401 `mfa_required` and the screen asks for a fresh code (unit `CriticalActionsTests.Endpoints_Should_MatchTheCriticalList_When_EveryHostIsBooted` and `CriticalEndpoint_Should_Return401WithMaxAge_When_SecondFactorIsOld`).
- **What the reset changes**, in one transaction (`SvcUsers.ResetTotpAsync`): it clears the authenticator (`User.ResetTotp`: the enrolled flag, the protected secret and the last accepted step), marks every unused recovery code as used, and ends every active session of the user (`AccountSessions.RevokeAllAsync`, reason `totp-reset`). The ended sessions' refresh tokens stop working, and each session's cached copy is dropped after the commit, so every host refuses the old access tokens within about 5 seconds (`Auth:Sessions:CacheSeconds`, 4). The reset does not evict the user's cached role grants (it does not call `AccountSessions.EvictPermissionsAfterCommit`; the roles do not change): a new sign-in before the user enrols again is in the pending scope, which holds no permission. Integration `AdministrationTests.Resets_Should_EndSessionsClearTotpAndAudit_When_AdministratorResets` checks the ended session, the cleared secret and that no unused recovery code is left.
- **What is recorded.** The audit entry `User.TotpReset`, written in the same transaction (`AuditTrail.RecordAsync`): the time, the administrator's id and user name, the caller's address, the trace id, the target `User` with the account's id and user name, and the account's summary before and after (user name, display name, email, roles, sites, disabled, `totp=True` before and `totp=False` after, `mustChangePassword`), never the secret or a code. The log event `SecurityEvent.TotpReset` (9122) carries the account id, the administrator id and the number of sessions ended. Tests: integration `AdministrationTests.Resets_Should_EndSessionsClearTotpAndAudit_When_AdministratorResets` (actions, actor and address); E2E `api/administration.spec.ts` "grants, revokes and resets work for a stepped-up administrator and are audited".
- **How the user enrols again.** The user signs in with the password alone (Ariva asks no code of an account without an authenticator, `SvcAuthenticator.LoginAsync`), lands on the first sign-in screen in the pending scope, scans the new QR code, confirms a code and receives 10 new recovery codes (section 3.1). The enrolment writes the log event `SecurityEvent.TotpEnrolled` (9109) with the account id; it writes no audit entry of its own, so the reset's audit entry and these log events are Ariva's whole record.

Until the user enrols again, the password alone opens the enrolment: whoever knows the password could enrol their own phone. The procedure below closes that window by replacing the password in the same visit.

**Identity proofing procedure (Proposed).** Each site confirms this default or replaces it with its own in its go-live record (TC-05, docs/product/pilot-to-confirm.md). A replacement must be at least as strong as enrolment (ASVS 5.0 V6.4.4). In Ariva an account is enrolled by the person who receives the temporary password an administrator created for a named person (section 2); this procedure rebuilds that chain: the person is proven, receives a new temporary password over a channel tied to the proof, and enrols at once.

1. **Request.** The user asks through their line manager or the duty manager, who passes the request to a System administrator of the user's site. A request that arrives another way (an email or chat message from the user alone, a call from an unknown number) starts the procedure but is never acted on by itself.
2. **Prove the person**, by one of:
   - in person: the user shows the staff identity card the site issues, and the administrator compares the photo and the name with the person and with the account's display name;
   - call back: the administrator calls the user on the number in the site's staff directory, never a number the caller gives, and the user confirms the request on that call.
3. **Line manager confirms.** The administrator reaches the user's line manager in person or on the manager's directory number, and the manager confirms that this person needs the reset. Without that confirmation, nothing is reset.
4. **Separate the roles.** The administrator who resets is not the person reset; Ariva enforces this for the same account (403, above). The administrator is also not the line manager who confirmed, and never resets an account of their own held under another name: these two are rules of the procedure, which Ariva does not check.
5. **Step up.** Confirm a fresh authenticator code when Ariva asks.
6. **Reset the password, then the authenticator**, before the user signs in (Users and access: Reset password, then Reset authenticator). In that order the old password stops working while the old authenticator is still required, so at no moment does a password someone else may know open the enrolment. Give the temporary password only to the proven person: in person, or read out on the call-back call; never by email, chat or text message, and never through the line manager.
7. **Enrol at once.** The user signs in with the temporary password while the administrator is still with them or on the call, chooses a new password, enrols the new authenticator and keeps the 10 recovery codes. The administrator checks that the account shows an authenticator again on Users and access.
8. **Record.** In the site's ticket or log book: the date, the account's user name, who asked, the proof used (in person with the staff card, or call back), the line manager who confirmed and the administrator. Never a copy, photograph or number of the identity card or of any other proof document, and never the temporary password. Ariva's own record is the audit entries `User.TotpReset` and `User.PasswordReset` and the log events above.
9. **If the proof or the confirmation fails**, reset nothing and tell the site's security contact. If the account may be in someone else's hands, disable it (Users and access, Disable): its sessions end at once.

### 3.3 Lost or forgotten password

What Ariva does (ARV-011):

- There is no self-service recovery: Ariva.Web and the API have no "forgot password" route. A user who knows the password changes it on Account security (`SvcAuthenticator.ChangePasswordAsync`); a lost password is reset by an administrator.
- The reset (`POST api/v1/admin/users/{id}/reset-password`, `User.Edit`, a critical action with the same step-up; Users and access, Reset password) refuses the caller's own account with 403, like the authenticator reset. `SvcUsers.ResetPasswordAsync` creates a temporary password (`TemporaryPasswords.New`: 20 random characters from an alphabet without look-alikes, in four groups of five, drawn again until it passes the password policy for that user name), stores only its PBKDF2 hash and marks the account to change it, clears the failure count and any lock, ends every session (reason `password-reset`), writes the audit entry `User.PasswordReset` (the same fields as in section 3.2; the summary shows `mustChangePassword=True`, never the password) and logs `SecurityEvent.PasswordReset` (9121). The answer carries `Cache-Control: no-store` and shows the temporary password once.
- The authenticator stays: the user signs in with the temporary password and an authenticator code, or a recovery code (`SvcAuthenticator.LoginAsync`), so a password reset alone never bypasses the second factor. The session stays in the pending scope until the user chooses a new password: 12 to 128 characters, not on the breached password list, containing neither the user name, the product name nor a site context word, and different from the temporary one (`PasswordPolicy.Validate`, `SvcAuthenticator.ChangePasswordAsync`); the user's other sessions end.
- Tests: integration `AdministrationTests.Resets_Should_EndSessionsClearTotpAndAudit_When_AdministratorResets` (the old password stops working; the temporary one gives the pending scope), `AuthenticatorTests.ChangePassword_Should_RefuseWeakReusedOrUnverifiedPasswords_When_Asked`; unit `AdministrationTests.TemporaryPasswords_Should_PassThePolicyAndNeverRepeat_When_Generated`; E2E `api/administration.spec.ts` "grants, revokes and resets work for a stepped-up administrator and are audited" (the old temporary password answers 401, the new one 200, and no password reaches the audit) and `functional/users.spec.ts` "an administrator creates an account after a step-up, gives it a site and roles, resets and disables it, and reads the audit".

Procedure (Proposed, with TC-05): steps 1 to 5, 8 and 9 of section 3.2 apply unchanged. Hand over the temporary password as in step 6, and the user signs in with it and their authenticator at once. If the authenticator is lost as well, follow section 3.2, which resets both.

### 3.4 Every administrator has lost a factor

What Ariva does (ARV-010c): each deployment has one break-glass account, a System administrator with every site, created only by the installer command (`--create-break-glass`, [Deployment guide](04-Deployment-Guide.md) section 6.2; `BreakGlassAccounts.IssueAsync`). It signs in with its user name, its password and one unused recovery code each time (10 are printed with the credential), and step-up takes another recovery code. It is never locked out (`SvcAuthenticator.RecordFailureAsync`), every sign-in is the critical log event `SecurityEvent.BreakGlassSignIn` (9110) with the address and the recovery codes left, and the users API never shows it (integration `TotpTests.BreakGlass_Should_SignInWithARecoveryCodeNeverLockAndStayOutOfTheApi_When_Issued`).

Procedure:

1. The site's custodians open the sealed break-glass credential (two-person custody is recommended, Deployment guide section 6.2).
2. Prove the administrator to be reset as in section 3.2, steps 1 to 4; the administrator's own line manager confirms.
3. Sign in as break-glass, reset the administrator's password and then authenticator, hand over the temporary password as in section 3.2 step 6, and sign out. The administrator enrols at once; regular administrators handle every later reset.
4. Proposed: rotate the break-glass credential after every use (`--rotate-break-glass`, from a shell in a running api-main pod, Deployment guide section 6.2) and seal the new one, since a recovery code was spent and the credential was handled. Rotating needs a cluster operator with access to the namespace, under the customer's change control; so does creating the account where it was never created.
5. Review the audit trail: every change made under break-glass names its user name as the actor.

When the only regular administrator is compromised rather than locked out, follow the Deployment guide, section 6.2: create a replacement administrator with every site, then disable or revoke the compromised one.

## 4. Integration clients

Created for each AODB, immigration system, sensor gateway or consumer of the wait-times API.

| Field | Notes |
|---|---|
| Name | The external system |
| Kind | `Aodb`, `Immigration`, `SensorGateway`, `Other` |
| Scopes | `flights:write`, `allocations:write`, `immigration:write`, `sensing:write`, `queues:read`, `displays:read`; grant the minimum |
| Bound site codes | A client bound to one site cannot write another |
| Allowed source CIDRs | Calls from elsewhere fail |
| Per-request TOTP policy | Requires `X-TOTP-Code` on every call; on by default for immigration clients |
| Status | Active or Disabled |

On creation Ariva shows the client secret and the TOTP provisioning URI once. Hand them over out of band by two separate channels.

API (ARV-042), under `api/v1/admin/integration-clients`, System administrator only: list (optionally `?siteCode=`), view, create, `PUT` to change name, scopes, sites, networks and the per-request policy, `secret` to rotate the secret, `totp` to reset the seed (each shown once), `disable`, `enable` and `unlock`. Every change needs a second factor in the last 15 minutes and is audited without secrets. You can bind a client only to sites you hold, and you see only clients whose sites are all yours. Every client needs at least one allowed source network (CIDR, at most 16, no `/0`, no host bits): token exchanges from anywhere else are refused and not counted. Any change stops the client's current tokens on their next call. A client locked after 10 failed token exchanges unlocks by itself after 15 minutes or when you unlock it; find the cause first (Operations runbook, integration client locked out). A lock stops new tokens only; tokens the client already holds run until they expire, so to stop a client at once, disable it. Enabling a disabled client does not clear a lock: unlock it separately. Clients are never deleted: disable them, so their recorded calls stay attributable.

SSIM schedules (ARV-046), under `api/v1/admin/sites/{siteCode}/flight-schedules` (permission `CreateFlightSchedule`, System administrator, your own sites): `preview` reads a file and shows what it would do without changing anything; `import` applies exactly what was previewed (send the same file and horizon with the preview's `previewToken`, yourself, within two hours). Use it when a site has no live AODB feed yet, or to give a new season's baseline; a schedule creates legs and never changes one a live feed has reported. Every import is audited with its outcome and counts, even one that fails part way.

Outbound endpoints (ARV-045), under `api/v1/admin/outbound-endpoints`, with the same integration permissions (System administrator): list (optionally `?siteCode=`), view, register (`POST` with `code`, `name`, `purpose` `Generic`, `AcrisFlights` or `AmanFeed`, `siteCodes`, `connection` and `secret`), `PUT` to change the name, sites and connection, `PUT {id}/secret` to replace the secret, `disable` and `enable`. Every change needs a second factor in the last 15 minutes and is audited without secrets; the secret is never shown again. You can bind an endpoint only to your own sites and you see only endpoints whose sites are all yours. An ACRIS or AMAN endpoint feeds exactly one site. An `AmanFeed` endpoint (ARV-050) pulls AMAN's feed from AMAN's Integration API where AMAN's Kafka is not shared: `TotpClientCredentials` only (AMAN's client id, secret and TOTP seed, with per-request TOTP: an AMAN pull always sends `X-TOTP-Code`), `pullPath` the feed path ending in a slash (for example `/feed/`, the contract names follow it), and a poll interval of 30 to 3,600 s; its status shows the records pulled, applied, unchanged (already received over another transport), refused and unreadable. The authentication kind of an endpoint never changes: register a new endpoint and disable the old one. Changing the base URL, networks, pinned CA or token path needs the secret again in the same request (the partner gives you the secret for the new place); a rename or a change of timeouts does not. Give the networks the partner's service is really in, never a broad range: Ariva refuses any address outside them, and never calls this host, link-local or cloud metadata addresses whatever they say. Endpoints are never deleted.

Operations:

| Task | How |
|---|---|
| Rotate the secret or the TOTP seed | Generate new values (shown once); coordinate the switch time with the integrator. Whether old and new can overlap is To confirm |
| Suspend | Set status to suspended; tokens already issued expire within 15 minutes |
| Unlock after lockout | Ten consecutive failures lock a client for 15 minutes and alert administrators. Find the cause (wrong clock, wrong secret, attack) before the integrator retries |
| Review | Every call is audited with client, scope, endpoint, site, result and payload hash |

Details for integrators: [Integration guide](08-Integration-Guide.md).

## 5. Outbound endpoints

Every system Ariva calls is an `OutboundEndpoint` record:

| Field | Notes |
|---|---|
| Base URL | HTTPS only (HTTP only for allowlisted lab hosts). Request paths are relative to it |
| Allowed CIDRs | The resolved IP must be inside them at call time (blocks DNS rebinding) |
| TLS | Optional client certificate, optional pinned CA |

At most 500 rules per site, and codes stop at R-999999. Every create, change and delete is in the audit log with the rule's values before and after as JSON (fixed fields first, then the zones' count and SHA-256, then the zone list). Reading, changing or deleting a rule of another site answers 404, like one that does not exist; creating one in a site you do not hold answers 400, like an unknown site. `DesksBelowPlan` rules are border data (ARV-181b2, lead decisions of 2026-10-15), and so are `PredictedNowcast` rules since ARV-187 (owner decision of 2026-10-16: a lane queue is stepped with its share of the arrival wave, so a predicted value carries the lane split): only a caller holding `ArrivalWaveLanes.View` (the Border shift supervisor and the administrator) creates one, changes a rule to one, backtests or previews one, or imports or exports one. Anyone else is answered 403 with the text "Open desks below recommendation and predicted nowcast are border data: only a caller with ArrivalWaveLanes.View creates, changes, imports or backtests a rule on them." once the site check has passed (another site's code still answers 400, like an unknown site); a site configuration import holding such a rule answers 400 (`InvalidAlertRules`), and an export by a caller without the permission answers 400 with the same text. Such a caller never finds such a rule (the list leaves it out; reading, changing and deleting it answer 404), so a duty manager can neither read nor delete a border rule, its own predicted rules from before ARV-187 included. The alert rules screen offers the two metrics ("Open desks below recommendation", "Predicted nowcast") only to holders of `ArrivalWaveLanes.View`, and for them offers the border roles alone as owner (no "Every role of the site" choice) and as escalation role, with a one-line hint that the metric is border data reaching border roles only; for open desks below recommendation also `GreaterThan` and `GreaterOrEqual` only and queue zones only (a predicted nowcast keeps all four comparators and may watch an overflow band); this is a convenience, the API enforces every one of these rules and the screen shows its refusals (400 with the first problem, 403 `BorderOnly`) as it shows any other. A stored rule on either metric whose owner or escalation role is not a border role, or for open desks below recommendation that fires below its threshold (one from before ARV-181b2 or ARV-187, or changed in the database), is never evaluated: its open alerts are resolved as `RuleWithdrawn` and its targets' states dropped, and one warning naming the site and the rule code is logged per rule and values version in the Stream host (again when the rule's values change, and once after a restart; ARV-187 replaced the warning per tick). The alert rules screen marks such an enabled rule with the badge "Not evaluated: fix its border settings" (administrators and border roles see it), which goes away once the rule is saved with border roles. Repairing one: an administrator gives it a border owner (and a border escalation role or none); a supervisor may delete it, but cannot take it from the duty manager (`RoleNotHeld`), and disabling it is refused until it has a border owner. While a site holds such a rule, its configuration export answers 409 ("An alert rule of the site fails the checks an import applies ...", `RulesNotImportable`), since the import would refuse it. Release notes (wiki 18) list the SQL that finds them. The database repeats the checks above and keeps a rule's site and code. The demo seed (ARV-019) adds R-001 to R-005 above to the demo airport once, each audited, and only when the published profile has the zones they watch; a site where they were deleted does not get them back. Alerts move from Raised to Acknowledged, Escalated and Resolved (User guide, Live operations, ARV-039); a rule with `notifyByEmail` emails the people of its owner role (every operational role when it has none) when an alert is raised and the people of its escalation role when it is escalated (ARV-040): only enabled accounts that hold the role and the alert's site and have an email address, never the break-glass account. A user's email must be one plain address (no display name, comma, spaces or line breaks), or the users API answers 400. Emails name the escalation role, never the rule's free-text escalation contact. One alert email per alert, kind and address; past the hourly limit per address the next ones are held back and recorded as such; an alert still Raised after the rule's escalation minutes is escalated by the evaluation to the escalation role or contact and audited. Duplication and suppression windows are not built yet.

Evaluation (ARV-038). Ariva.Api.Stream evaluates every enabled rule once a minute (`Alerts:Evaluation`) on what the stream stored, one target at a time: each queue zone in scope, or each commissioned device of those zones for `SensorOffline`. A minute without a value (no row yet, or the queue length degraded by a sensor outage) is skipped: it neither counts towards nor breaks a run. The condition must hold for the sustain minutes in a row to raise an alert; while it is open no second alert is raised for that rule and target; it resolves by itself when the clear condition (beyond the clear threshold, or the condition no longer holding) has held for the clear minutes. A new target (a new or re-enabled rule, a zone added, a device commissioned) starts at the present: earlier minutes are for the backtest, so no stale alerts are raised. Editing a rule restarts its counts (an open alert stays and clears under the new values, unless the metric changed, which resolves it as `RuleChanged`); a target that leaves the rule has its open alert resolved as `TargetWithdrawn`; disabling or deleting a rule resolves its open alerts as `RuleWithdrawn`. Each rule is evaluated in its own transaction, so one that fails is logged and retried without holding up the others. An alert keeps what the rule said when it was raised. The backtest is the same evaluation over the same stored minutes from the range's start, so it shows exactly the alerts the live evaluation raised over a range it evaluated from that start (proved on the reference evening: R-001 at 18:05). A value beyond a billion is recorded on the alert at that bound. What each metric reads:

| Metric | Value per minute |
|---|---|
| `Nowcast` | The minute's nowcast; skipped while the queue length is degraded. A nowcast flagged only because its throughput comes from exits (the desk state of ARV-049 is not yet joined to the nowcast) is judged |
| `QueueLength` | People in the queue zone and its overflow bands |
| `BinP90` | The largest P90 among the zone's 15-minute bins that ended in the last 150 minutes (their latest revision, so a backtest after bins became final can differ from what was judged live) |
| `SensorOffline` | 1 while the device is in an outage the stream recorded, or offline in the registry since it was last heard; otherwise 0 |
| `PredictedNowcast` | The highest nowcast projected within the lead time: the queue now, stepped a minute at a time with the arrival-wave projection and what the desks clear at the current throughput. The projection (ARV-047, formulas F14) gives a queue zone the arrivals of the lane categories its desks serve (through the service zones linked to desks in the published profile, counting only desks of an Immigration checkpoint on the queue zone's level, ARV-191), shared among the queue zones serving the same lane; desks of an emigration checkpoint or of another level link no queue to a lane, so a departures queue standing only at such desks has no projection however their lane categories are set, and a zone serving no lane has nothing to judge, and a backtest finds none (projections are not stored). Border data since ARV-187: the projection is the lane split of the arrival wave, so the rule belongs to a border role and its alerts (with the predicted value and minute) reach the Border shift supervisor and the administrator only, on every channel, as for `DesksBelowPlan`; the terminal duty manager keeps `Nowcast` (live-wait) alerts |
| `OverflowOccupied` | Since ARV-115: 1 for a minute in which an overflow band held anyone (its highest reading above zero), 0 when the bands that reported held no one; a minute without a band reading is skipped. A band whose sensor is silent beyond 2 minutes is Unknown (neither occupied nor empty) and counts in neither until it reports again, so a rule whose only band is Unknown neither raises nor clears. A queue zone watches all its bands; an overflow zone in scope watches that band only. The demo seed's R-002 raises after 3 occupied minutes and clears after 3 empty ones |
| `DesksBelowPlan` | Since ARV-181b2, "Open desks below recommendation" (formulas F16): for each minute the staffing job computed (once a minute, `lane_staffing`), the desks the current quarter hour's indicative recommendation asks for minus the desks open now by desk state, at least 0. A minute has no value when the job missed it, its row fails the staffing API's read-back check or is not that minute's current interval, the interval has no recommendation (its reason), or the open count is unknown or degraded. The live evaluation takes each lane up to its latest computed minute and a backtest reads the same stored rows, so both give the same alerts. Typical rule: 1 or more desks short (`GreaterOrEqual` 1) for 3 minutes, cleared after 3. Its alerts reach the Border shift supervisor and the administrator only, on every channel: the alerts list and actions, the live screens, email (when written and again when sent), the daily report with its CSV and scheduled deliveries, and the weekly summary, whatever the alert's owner and escalation roles say |
| `ConservationResidual` | Since ARV-114b (formulas F18 and F20): the size of the conservation residual of the zone's 15-minute bin that ended last by the end of the minute, in people: the people counted in or out that the queue's occupancy does not show, whichever the sign. Judged once both boundaries of the bin were measured; a bin with a boundary unmeasured has no value |
| `TrackCompletion` | Since ARV-114b: the track completion of that bin in percent (tracks that exited over tracks that entered), judged once the bin is final (every track resolved; while people are still queuing their tracks are not lost). A zone whose sensors do not track people has no value. Typical rule: below 90 with a clear threshold of 95. The same rate marks the final bin `Degraded` below 90 percent (formulas F11, Proposed) |
| `OccupancyOutOfRange` | Since ARV-114b: the minutes of that bin with a reading above a zone's physical capacity (zone profile, queue zones and overflow bands), judged once the bin has ended; a zone without a capacity has no value |

The three health checks (ARV-114b) are judged on the bins the stream stored (`zone_health_bin`, their latest revision) and hold a bin's value for its 15 minutes after it ends. The live evaluation waits for each bin to be settled before it takes its minutes (for `TrackCompletion` until the bin is final, at most about 2 hours after its end; after 3 hours a bin still unsettled no longer holds it back and its minutes count as without a value), so it raises exactly what the backtest finds over the same stored bins, later by that wait. A recomputation that adds a revision of a bin after its minutes were judged can make a later backtest differ from what was raised live, as for `BinP90`.

### Advertising policy (ARV-145)

Many border authorities do not allow commercial advertising in arrivals and immigration halls, so advertising is off for every site until a system administrator allows it. The policy is a panel on the Passenger displays screen and `api/v1/admin/sites/{siteCode}/advertising-policy`:

| Field | Notes |
|---|---|
| Allowed | Whether the site's split displays may show advertising in their second region. Off for a site that never had a policy |
| Excluded zones | Up to 20 published queue zones of the site (for example the immigration hall's) where advertising stays off even when the site allows it: a display showing any of them shows instructions |
| Reason | Required for every change, 10 to 500 characters on one line: who authorised it (the border authority or the airport operator) and their reference, for example "Border authority letter BA-2026-17" |

Who may do what: terminal duty managers and border shift supervisors see the policy (`AdvertisingPolicy.View`, with their display permissions); only system administrators change it (`AdvertisingPolicy.Edit`), and changing it is a critical action that asks for a second factor in the last 15 minutes (owner decision 2026-10-16: no second sign-off by a border role). Every change is audited as `AdvertisingPolicy.Changed` with the administrator, the time and the whole policy before and after, reason included; a change whose excluded zones and reason would not fit one audit entry whole is refused. The runtime database role cannot delete a policy: turning advertising off is a change like any other.

What it does:

- A display can be set to Advertising (or keep it while its zones change) only while the policy allows it for every zone it shows; the display service and the database (script 0057) both refuse otherwise. A site configuration import refuses displays set to Advertising: a new site starts with advertising off, and the policy never travels in a bundle.
- A display set to Advertising before the policy was turned off, or before one of its zones was excluded, keeps the setting but its board shows instructions from the next poll (within about 10 seconds). The panel lists these displays under "showing instructions because of this policy", and the displays list marks them. To edit such a display, set its second region back to Instructions.
- A change of the policy is judged against the site's published zone profile: the form shows which version the excluded zones are being confirmed against and offers that version's queue zones (read with it), and a save that allows advertising is refused (409, "Another zone profile has been published since you reviewed this policy") when another version was published while the administrator was reviewing; the panel then shows the new version to review. Duty managers and supervisors can publish new profiles, in which zones can be renamed, moved, dropped or added (an excluded name could even be given to another zone), so once another profile is published no display of the site shows advertising (each falls back to instructions at its next poll) until a system administrator saves the policy again, after checking the excluded zones against the new profile. The panel says so, and lists any excluded zone that is no longer a published queue zone.
- Advertising endpoints (the media library of ARV-142a and the playlists, schedules and timeline of ARV-143a) live in `Controllers/AdminArea/Advertising` and carry `[AdvertisingAllowed]`: they answer 403 for a site whose policy does not allow advertising, and 404 for a site outside the caller's sites or one that does not exist (the same answer). A unit test boots every host and fails the build when an endpoint whose route names advertising, or whose controller lives in an Advertising namespace, lacks it; the one exception is the display fetch below, which is display-authenticated and must stay so (the same test checks it). Since ARV-143b a display allowed to advertise plays the playlist scheduled for it (see Advertising playback on displays below).

### Advertisement library (ARV-142a, ARV-142b)

While a site's policy allows advertising, the Passenger displays screen shows its advertisement library under the policy panel (`api/v1/admin/sites/{siteCode}/advertising/media`). An item is an image or a video (ARV-142b) with its advertiser, campaign and the first and last day it may play (the site's local days, at most 731 days apart):

| Step | Who | Notes |
|---|---|---|
| See | `Advertising.View` or `Advertising.Manage` (terminal duty managers, system administrators) | The library with each item's preview, details, state and who uploaded and approved it. Images preview at once (the newest 40); a video shows its length (for example "2 seconds", to a tenth) and loads only when someone presses Load the video |
| Upload | `Advertising.Manage` (the same roles) | At most 30 upload attempts per person in 10 minutes, images and videos together, refused files included (429 beyond). The type is read from the bytes, never the name or the declared type: a file that starts with an MP4 `ftyp` box or a WebM (EBML) header is checked as a video (see Videos below), anything else as an image. Images: PNG, JPEG or WebP, at most 10 MB, at most 3,840 pixels a side and 8,294,400 pixels in all (3,840 by 2,160), read from the header before anything is decoded; SVG, HTML, PDF, GIF, animated images and anything else are refused. The image is decoded and written anew (turned upright from its EXIF orientation, converted to sRGB), so no metadata, comment, text chunk or data after the image's end survives and a polyglot's page or script is gone. Each file, image or video, is served with its own type and headers that stop a browser from treating it as anything else. It is stored under a generated key; the file name is kept only for people to recognise it, and one with a path or a hidden character is refused. It starts as a Draft |
| Approve | `Advertising.Approve` (the same roles) with a second factor in the last 15 minutes | Only a person other than the uploader and the last person who changed the item (two people); 403 otherwise. The approval names the item as the approver was shown it (its review token: the file, the details, the state and the last changer); when someone changed the item meanwhile it is refused (409, "This item has changed since you reviewed it") and the screen shows it again. An approved item plays within its days |
| Change | `Advertising.Manage` | The advertiser, campaign or days. An approved item goes back to Draft and stops playing until another person approves it |
| Retire | `Advertising.Manage` | A draft or an approved item; it never plays again and is kept with its history. A retired item cannot be changed or approved |

A file the malware scan refuses (section 2a) counts as an upload attempt like any refused file. Every upload, change, approval and retirement is audited (`AdvertisingMedia.Uploaded`, `.Changed`, `.Approved`, `.Retired`) with who did it and the item before and after (a video's length as `durationMilliseconds`). The database (script 0058) holds the same rules for any writer: a new item is a draft its uploader last changed, no approver is ever the uploader or the last changer, an approved item's details and approval are kept while it stays approved, an approval or a retirement changes nothing else in the same write, the file, the uploader and the creation stamps never change, a retired item is final, and nothing is deleted. Script 0059 (ARV-142b) adds the video types (`video/mp4`, `video/webm`, stored with the extension `mp4` or `webm`, which must match the type), at most 10 MB for an image and 100 MB for a video, and a video's length (1 to 120,000 milliseconds, none for an image), which like its file never changes after upload. Border shift supervisors hold neither permission: content in a hall where the system administrator allowed advertising is still the airport's. A site's library lists at most 500 items, retired ones included. Images and videos beside every other upload, and what happens to a malicious file: [File handling](13a-File-Handling.md), sections 3.5 and 3.6.

A display fetches an item through `api/v1/display/advertising/{id}` with its own code and credential (as it fetches its board; a user's token answers 401), never a public URL: only an approved item of the display's own site within its days, while the display is a split display set to advertising and the site's policy allows it for every zone the display shows, read on every fetch; anything else answers 404 (a full display, or one set to instructions, included). The preview on the screen and the display fetch send the image or video with its own type, `nosniff`, a sandboxing content security policy, `Cross-Origin-Resource-Policy: same-origin`, `no-store` and, since ARV-092, `Content-Disposition: inline` under a name the server builds (`advertisement-{id}` and the extension of the type read at upload, never the uploaded name). The review token, the two-person approval, the states, the permissions and the audit are the same for videos. Since ARV-143b the display player fetches the advertisements of its plan this way and shows each from an object URL, which the web app's content security policy allows (`img-src` and `media-src 'self' blob:`); see Advertising playback on displays below.

#### Videos (ARV-142b)

| Container | Picture | Sound |
|---|---|---|
| MP4 (brands isom, iso2, iso4, iso5, iso6, mp41, mp42, avc1 or M4V) | H.264 (`avc1` or `avc3`) | AAC, or none |
| WebM | VP8, VP9 or AV1 | Opus or Vorbis, or none |

A video has one picture track of at most 3,840 pixels a side and 8,294,400 pixels in all (as its container states it, the same limits as images), at most one sound track, a length stated in its header and nothing after its last box or element. No track or media header of an MP4 may state more than a second beyond the movie's length, and every WebM cluster opens with its start, none past the stated length, and a WebM is timed in milliseconds (the timestamp scale WebM writers use, so a block can reach at most 32.8 seconds past its cluster's start). The size and length are what the container states: the picture data itself is not decoded on the server, so the size limit and the second person's look at the preview bound what a crafted file holds, and the display player ends each item at its slot's end (ARV-143b). Refused besides: QuickTime files (brand `qt  `), fragmented MP4 and live WebM recordings (their length is not stated up front), encrypted or compressed WebM tracks, other tracks (text, subtitles, timecode, metadata), truncated files, and any other codec (HEVC, for example). Ariva never decodes a video: managed code reads its container only (`AdvertisingVideos.Check`: every box or element within its parent and the file, at most 12 deep and at most 4,096 read, the media data never walked), so a video plays only in the browsers that show it (the library preview and, since ARV-143b, the display players), each in its own sandbox.

Before a video is stored its metadata is removed without moving the media, so it still plays:

- MP4: the user data (`udta`), `meta` and `uuid` boxes become zeroed `free` boxes of the same size, free space (`free`, `skip`, `wide`) is zeroed, and so are the handler names, the H.264 compressor name and the creation and change times of the movie, its tracks and their media.
- WebM: tags, attachments, chapters, the recording's title and date, track names and the `CRC-32` of each element the check walks (the header, the segment, its information and tracks) become `Void` elements of the same length with zeroed data.
- Kept on purpose: WebM's `MuxingApp` and `WritingApp` (the muxer's name, for example "Lavf60.16.100", which Matroska requires) and the media data itself (an H.264 encoder's settings message inside the picture, for example). Markup hidden in free space or metadata is zeroed; markup after the end is refused. The compressed media can still hold bytes the uploader chose, so the serving headers above stay the control against content sniffing.

Limits are settings, validated at start-up; set them for Ariva.Api.Main, which takes the uploads:

| Setting (`Advertising:Videos`) | Default | Bounds | Environment variable |
|---|---|---|---|
| `MaxMegabytes` | 20 | 1 to 100 | `Advertising__Videos__MaxMegabytes` |
| `MaxSeconds` | 30 | 1 to 120 | `Advertising__Videos__MaxSeconds` |

100 MB and 120 seconds are ceilings every installation keeps (`AdvertisingMedia.MaxVideoBytes` and `AdvertisingMedia.MaxVideoSeconds`; script 0059 holds both in the database too). A larger video answers 413 "The file is larger than 20 MB." and a longer one 400 "The video is longer than 30 seconds." (the numbers are the settings); any other refused video answers 400 with one text that lists what is taken ([Troubleshooting](17-Troubleshooting-and-FAQ.md), Displays). The upload endpoint declares the ceiling (100 MB plus 64 KB of framing), and a filter (`AdvertisingUploadLimitAttribute`) lowers the body limit before the form is read to what the installation takes: the larger of 10 MB and `MaxMegabytes`, plus 64 KB. A body declared larger answers 413 "The file is larger than 20 MB." at once (the number is the larger of 10 and the setting), and one sent without a length that grows past the limit while it is read is cut off there with the same answer, so nothing larger than the installation takes is buffered. An upload arriving slower than 32 KB a second (after 10 seconds' grace) is cut off as well with 408 (over HTTP/1.x, which the ingress forwards), so a slow sender cannot hold the one upload a host takes at a time. The service then holds the file to the larger of 10 MB and the setting on its declared length and again while reading it. A video is read into memory whole (at most its size) and stripped in place, one upload at a time per host under the `upload` concurrency policy (two waiting).

The chart's api-main and web-api ingresses accept bodies of 21m (`nginx.ingress.kubernetes.io/proxy-body-size` in every values file), which fits the 20 MB default with its framing. An installation that raises `MaxMegabytes` above 20 must raise both ingresses' body size to match (for example 101m for 100 MB); otherwise the ingress refuses a larger upload with its own 413 before Ariva sees it.

### Advertising playlists and schedules (ARV-143a)

A site's advertising plan is a set of playlists (what plays, in which order) and schedules (where and when each playlist plays). Plans are kept on the Advertising screen (`/advertising`, sidebar item Advertising under Operations; [User guide](12-User-Guide.md), Advertising) and through these endpoints of Ariva.Api.Main:

| Endpoint (under `api/v1/admin/sites/{siteCode}/advertising`) | Methods |
|---|---|
| `playlists` | GET (list), GET `{id}`, POST, PUT `{id}`, POST `{id}/retire`, POST `{id}/restore` |
| `schedules` | The same set |
| `timeline?display=<code>` | GET: one display's week |

Who may do what: `Advertising.View` or `Advertising.Manage` reads the plans and the timeline; `Advertising.Manage` creates, changes, retires and restores them. Terminal duty managers and system administrators hold both, as for the library; border shift supervisors and handler station managers hold neither. A plan needs no second person: what plays is approved item by item in the library. Every endpoint carries `[SiteScoped]` and `[AdvertisingAllowed]`: a site outside the caller's sites answers 404, and so does another site's playlist or schedule named by id under this site's route (the same answer as one that does not exist); while the site's advertising policy does not allow advertising every endpoint answers 403, and the plans are kept for when it is allowed again.

A playlist:

| Field | Notes |
|---|---|
| Name | 1 to 120 characters, on one line |
| Items | 1 to 40, in playing order, each named once: an advertisement of the site's library that is not retired, or an active instruction slide of the site. Drafts and advertisements outside their dates may be planned; only approved items within their dates play, and the screen marks the others as not playable now |
| Seconds on screen | An image or a slide: 5 to 60. A video: its own length rounded up to the second, at most the installation's video length (`Advertising:Videos:MaxSeconds`, 30 by default), whatever was asked |
| Weight | 1 to 10, 1 by default: how many times the item plays in one cycle of the playlist on the displays (ARV-143b), so its airtime is its weight times its seconds on screen |

The playlist shows the length of one pass (its items' seconds added up, each once); a cycle on the displays adds each item's seconds as often as its weight. An advertisement or a slide retired after the playlist was saved leaves the playlist as it was: it can still be renamed or retired, and changing its items needs every item to be valid again.

A schedule:

| Field | Notes |
|---|---|
| Playlist | An active playlist of the site |
| Shown on | Site: every display of the site. Zone: the displays that show any of the named queue zones of the published profile. Display: the named live displays of the site. 1 to 20 zones or displays. These are the instruction slides' targets; they stand in for display groups, which Ariva does not have |
| Days | 1 to 7 days of the week |
| Window | One window in the site's local time, "HH:MM" to "HH:MM". A closing time before the opening runs past midnight into the next day (Friday 22:00 to 02:00 still applies at 01:00 on Saturday), and one equal to the opening is refused; 24:00 closes at midnight (on the screen, the box "Until the end of the day (24:00)"). Two windows on one day are two schedules |

Limits: 40 items in a playlist, 100 playlists and 200 schedules in a site, retired ones included (so retiring frees no place). Beyond them a creation answers 409 ("The site has 100 playlists, retired ones included; this one is not added.", or the same for 200 schedules). The site's advisory locks hold the limits, so two creations at the same moment cannot pass them.

Which schedule applies to a display at an instant:

1. A schedule naming the display comes before one naming a queue zone it shows, and that before one for the whole site.
2. Among alike targets, the window that opened last wins, so a peak window inside an all-day one plays while it is open.
3. Then the newest schedule (then its id, so the answer is the same every time).

When none applies, the display shows its instructions. A retired playlist stops its schedules applying: they stay active and show "Playlist retired: not applied", and restoring the playlist brings them back. Windows keep their local hours across daylight saving: on the day the clocks go forward the skipped times never occur (a window in them is shorter or never opens), and on the day they go back the repeated hour is covered twice. Schedules do not check the policy's excluded zones: a display showing an excluded zone cannot be set to advertising, so a zone schedule naming one affects no advertising display.

The timeline shows one live display of the site over 7 days from the site's local midnight today, as stretches, each with the playlist that applies or none (instructions), in the site's time zone. It names the display's second region: a display set to Instructions shows instructions whatever the plan says, and the screen says so.

Every change is audited (`AdvertisingPlaylist.Created`, `.Updated`, `.Retired`, `.Restored`, and the same for `AdvertisingSchedule`) with who made it and the plan before and after; a playlist's entry records every item. Nothing is deleted: plans are retired and restored. Script 0060 adds the tables `advertising_playlist` and `advertising_schedule`; its checks and triggers hold the rules for every writer (a playlist's items, their kinds, ids, slots and weights, the same site, advertisements not retired and slides active, whenever the items change; a schedule's targets a list of 0 to 20 different names, and none for the whole site; a row's id and site never change), and the runtime database role cannot delete or truncate either table.

The readings behind these rules (the slides' targets in place of display groups, one window per schedule, the precedence, a retired playlist stopping its schedules, the limits, no second person for a plan) are Proposed, pending the owner (`docs/product/decisions.md`, 2026-10-18 ARV-143a).

Since ARV-143b the display board plays these plans, as described next; the timeline shows which playlist applies, while the board also leaves out items that may not play and gives way to instructions under the wait rule.

### Advertising playback on displays (ARV-143b)

A split display set to Advertising, at a site whose advertising policy allows it for every queue zone the display shows, plays the playlist that applies to it in its second region. The board (`GET api/v1/display/board`, with the display's credential only) carries the plan as `advertising`, worked out again on every board (every 10 seconds); the policy is read each time, so a plan is never itself permission to advertise.

| Board field (`advertising`) | Notes |
|---|---|
| `playlistId` | The playlist that applies now, by the precedence above |
| `items` | The items that may play now, in the playlist's order: advertisements approved and within their dates on the site's local day, and active slides with words in the display's languages. Each carries its kind, its slot in seconds, and an advertisement's id and type or a slide's icon and words. A draft, a retired item, an advertisement outside its dates and a slide in none of the display's languages never play. A slide in a playlist plays wherever its schedule applies, whatever the slide's own targets: the schedule decides where |
| `order` | One cycle of the playlist: each item as often as its weight, the repeats spread through the cycle by smooth weighted round robin (weights of 2 and 1 play A, B, A). An item's airtime in a cycle is its weight times its slot. Every player of the plan plays the same order |
| `untilUtc` | When the plan next changes (a window opens or closes, so that another schedule wins or none applies), looked for no further ahead than the display's stale threshold, at most 30 minutes, and never past the site's next local midnight, when advertisements' dates turn |
| `pauseMinutes` | The display's wait rule, or none |

The board names the playlist and the advertisements by their ids, gives each item's type and slot, and carries the slides' words; it never carries the playlist's name, an advertiser's or campaign's name, a file name or a person's name. `advertising` is null, and the second region shows instructions, when no schedule applies, the playlist is retired, nothing in it may play now, or the policy does not allow advertising for every zone the display shows; the board of a display set to Instructions, or of a full display, never carries one.

The player (Ariva.Web `/display`):

- Plays the cycle's order in the second region, and starts again at its first place when the plan changes. An image shows in an image element and a video plays muted, without controls and without looping, each from an object URL of the bytes it fetched with the display's credential (`api/v1/display/advertising/{id}`, above); a slide shows as instruction slides do. It fetches the next item while the current one plays, so it starts on time.
- Ends each item at its slot's end, whatever the media holds: a video longer than its slot is cut, and a shorter one holds its last frame until the slot ends.
- Shows instructions for the slot of an item that fails to load or play (a fetch refused or cut off, bytes of another type than the board named, a video the browser will not play); the next item plays on time, and the failed one is tried again at its next turn.
- Applies the wait rule on each board, as it holds its bands: advertising gives way to instructions when the nowcast of any queue zone the display shows, with fresh data (no older than the display's stale threshold), reaches the display's minutes, and plays again only when every zone with fresh data is below them by the display's hysteresis. With no fresh data the state holds as it was. A display without the rule never pauses.
- Keeps the advertisements it fetched in memory only, never in web storage: at most 40 items and 150 MB, the least recently used out first. It releases items that leave the plan, everything when advertising stops, and everything with the page. An item larger than that plays from its own object URL without being kept, and is fetched again at its next turn. Besides the cache it may hold the next item, fetched ahead, when that does not fit beside the one on screen, so at its peak a player holds 150 MB and one item (at most the installation's video size). While an item's bytes are on their way, the region shows the instructions rather than nothing.
- Stops the plan at `untilUtc` when no newer board has come, measured by the server's clock (the board's `serverUtc` plus the time since it came), not the screen's. Through a network loss it keeps playing the items it holds until then, at the latest when its board goes stale; then the second region shows instructions, which stay loaded and need no request. An item it does not hold shows instructions for its slot meanwhile.
- When advertising is turned off (the policy, an excluded zone, the display set to Instructions or Full), shows instructions from the next board and releases its cache.
- Reports what it played (ARV-144). Each advertisement it showed (never a slide) is a play from the moment its image has loaded or its video plays in its slot (not while its bytes are on their way, when the instructions show) until the slot's end or until it is cut short (interrupted: the wait rule, a stale board, the plan's end or change, advertising turned off, the item failing after it showed, the page going); it is completed only when it lasted to the slot's end and was on screen for the slot within 2 seconds, so an advertisement whose bytes came late in its slot is reported as cut short (the server would refuse it as completed). An item that fails before it shows, or is on screen for less than a second, is no play. The start is by the server's clock as the player keeps it, to the millisecond, and the length is the time on screen, at most 125 seconds. Plays wait in memory only, never in web storage, at most 500 (the oldest out first), and go to `POST api/v1/display/plays` with the display's credential in batches of at most 100, one request at a time, every minute (sooner when 100 wait, but never within 12 seconds of the last). A 200 lets the batch go (accepted, duplicates and refused alike); a 400 drops it; no answer, a 429 or a 5xx keeps it for the next turn; a 401 drops it and stops the reports until a good board comes back. Nothing is sent while the board is refused. As the page goes it tries once more with fetch keepalive, which may not arrive.

Set the wait rule on the display form (Passenger displays), in the field "Advertising gives way to instructions at a wait of" (minutes, empty for never), shown for a split display set to Advertising; the displays list shows each such display's rule ("Advertising gives way to instructions at a wait of 20 minutes", or "Advertising plays whatever the wait"). Through `api/v1/admin/displays` the field is `advertisingPauseMinutes`: a value outside 1 to 240 answers 400 ("Advertising gives way to instructions at a wait of 1 to 240 minutes, or never."), and a request that leaves the field out clears the rule (the screen always sends it). Script 0061 adds the column `display.advertising_pause_minutes` with a check of 1 to 240 or none (`ck_display_advertising_pause`) for every writer. The rule is audited with the display's other settings and travels in a site configuration bundle; an import still refuses displays set to Advertising, so an imported display shows no advertising and keeps its rule for when it is set to Advertising again.

The display fetch serves a split display set to advertising any item of its site that may play now, not only the items of its current plan (the library is approved for the site's displays item by item, and tying the fetch to the plan would work the plan out on every fetch); it answers 404 for a full display, one set to Instructions, and an item that may not play now. The proof of play (below) refuses plays outside the display's plan.

Each board costs a bounded amount of work, however many schedules the site has: at most 200 schedules read, the look-ahead stepped a minute at a time for at most 30 steps, and a few queries for the site's active playlists, the playlist that applies, its advertisements and its slides. A fault while the plan is being worked out fails the whole board, not only the second region: the player keeps its last board, whose queue waits are not refreshed and go stale when no good board comes within the display's stale threshold (residual, security review of ARV-143b).

Proof of play (ARV-144). The player reports its plays to `POST api/v1/display/plays?code=<display code>` with the display's credential in `X-Ariva-Display-Key` only (a user token, another display's credential or a code that is not the display answers 401), a JSON body of at most 64 KB (413 beyond): `{"plays": [{"mediaId", "startedUtc", "durationMilliseconds", "completed"}]}`, 1 to 100 plays a batch (400 "A batch holds 1 to 100 plays."), at most 6 batches a minute per display, refused ones included (`Security:RateLimiting:DisplayPlays`; 429 beyond). The answer counts the plays taken (`accepted`), those the server already had (`duplicates`: a play is keyed by its display, advertisement and start, so a batch sent twice counts once) and those refused (`refused`), and is never cached. The server takes a play only when the display could have shown it, as its board would have:

| Rule | Refused when |
|---|---|
| The display plays advertising | It is not a split display set to Advertising, or the site's policy does not allow advertising for every zone it shows (every play of the batch is refused: a plan is never itself permission) |
| The play is possible | It names no advertisement, its start is not UTC (a time without `Z` or an offset), it started more than 24 hours ago, it lasts less than 1 or more than 125 seconds (less than a second on screen is no play, and the player does not report it), or it had not ended by the time it was reported (5 seconds are allowed for the player's timing, so none starts in the future) |
| It was scheduled | Its advertisement is not an item of the playlist that applied to that display when the play started, or a minute before (the board the player last read), by the plans as they are when it is reported; or the advertisement may not play on the site's local day it started (a draft, retired, outside its dates) |
| It kept its slot | It lasted more than its item's slot plus 2 seconds, or says it completed in less than its slot minus 2 seconds (an advertisement in a playlist twice may match either slot) |
| It overlaps nothing | It was on screen together with another play of the display, in the same batch or stored before, for more than a quarter of the shorter play or more than a second (a play that only touches the next is taken; one inside another never is). Batches of one display are decided one at a time (an advisory lock per display), so two sent at once cannot both claim the same airtime |

Refused plays are never stored, and a batch with refused plays is logged on Ariva.Api.Main as `SecurityEvent.DisplayPlaysRefused` (event 9126: the display, its site and the counts, never the body). The plays taken go to the hypertable `advertising_play` (script 0062: the start, the site, the display, the advertisement, the playlist it was scheduled from, the length, completed or not, and when the server took it), which the runtime role inserts into and reads, never updates, deletes or truncates, through the table or a chunk; its checks hold the same bounds for any writer. It is kept 400 days by default (`Database:Retention:AdvertisingPlayDays`, 30 to 3,650 days, set by the migration job; Helm `migration.retention.advertisingPlayDays`), one period for every site of the installation. A plan changed between a play and its report refuses the plays made under the old plan; a player whose estimate of the server's clock jumps by more than a second between two boards may lose a play to the overlap rule, so the figures may under-count, never over-claim.

The figures (`ISvcAdvertisingFigures`, no endpoint yet: the report, its permission and its CSV export are ARV-146) cover 1 to 31 local days of a site, none after the site's today, for a caller with `Advertising.View` on that site (anyone else is answered as if the site did not exist): per day, display and advertisement, the plays, those completed, their airtime and the airtime the plans scheduled, then the same by campaign, advertiser, display and day with the share of the scheduled airtime delivered. The scheduled airtime is worked out from the plans as they are when the figures are read, over the displays that play advertising now, each playable item taking its weight times its slot of every cycle (slides fill the cycle and are not counted), so past plan versions, periods with advertising off and the wait rule's pauses lower the share delivered.

The readings behind proof of play (advertisements only, the rules above, retention for the installation rather than per site, the figures from the current plans) are Proposed, pending the owner (`docs/product/decisions.md`, 2026-10-18 ARV-144).

The readings behind these rules (a weight as plays per cycle, the plan holding until its next change within the stale threshold and the site's local day, what may play, the wait rule as a display setting held with the hysteresis, a failed item's slot, the cache's size, the fetch serving any playable item of the site, no names on the board) are Proposed, pending the owner (`docs/product/decisions.md`, 2026-10-18 ARV-143b).

Each display is a kiosk URL on the display VLAN. A player set to advertising may hold up to 150 MB of advertisements in memory besides the page, and one more item fetched ahead (at most the installation's video size, 20 MB by default), so allow for it when choosing the kiosk's browser and memory. Boards never show a realised wait. Whether an existing signage estate (for example Samsung MagicInfo) can show web content is To confirm on site.

## 10. Audit log

Phase 0 (ARV-011) records every user administration action (create, update, grant, revoke, password and TOTP reset, unlock, disable, enable) with time, actor, address, trace id, action code and before and after summaries without credentials, in the same transaction as the change; the API can only read it and the database refuses updates and deletes from the application login. The target scope: recorded for every configuration change, sign, publish, calibration, acknowledgement, SLA decision, export, role change, integration call and administrator action: time, user or client, role, action, object id, summary and, for integration calls, the payload SHA-256. The audit log is kept indefinitely and is served from PostgreSQL (no OpenSearch in the MVP). Exports of the log are themselves audited.

A screen may check some of these rules first, as a convenience; the server is the authority. ### 13.8 Not checked by the server

Combinations a screen accepts that no server rule compares:

- **A smaller level.** The Topology screen accepts a smaller width or depth for a level (`SvcTopology.UpdateLevelAsync`, `Level.Update`) without comparing it with the devices placed on the level or the zones of its published profile. The zones are checked again when the next draft is validated or published (`ZoneProfile.Validate`); a device only when it is moved.
- **A floor plan's scale and origin.** The Zones screen's floor plan upload takes a scale and an origin (`FloorPlan.Calibrate`) that are not compared with the level's width and depth: a plan that covers part of the level, or reaches past it, is accepted.
- **The desk of a service or staff zone.** The Zones screen offers every desk of the site, and the server checks only that the desk belongs to the site (`SvcZoneProfiles.AddZoneAsync`): the desk's level, checkpoint and kind are not compared with the zone or its queue zone. The arrival-wave projection counts only desks of an Immigration checkpoint on the queue zone's level (ARV-191, section 8), so such a link is ignored there.
- **A queue zone's lane.** The Zones screen's lane is checked for its form only (`ZoneProfile.SetZoneLane`), not against the lane categories of the desks its service zones name.
- **Warning and critical thresholds.** A rule has one severity and one threshold, so there is no warning and critical pair to compare; two rules on the same zones and metric (a Warning above 10 minutes and a Critical above 8, for example) are not compared with each other (alert rules screen, `SvcAlertRules`).
- **A campaign's desks and zones.** The campaign form offers every staffed border desk of the site, and the server checks the desks against the site only (`ValidationCampaign.DeskScopeProblem`), not against the campaign's queue zones: desks of another hall can be in scope.
- **A schedule's zones and the excluded zones.** The Advertising screen's zone schedules are not compared with the policy's excluded zones (`SvcAdvertisingSchedules`); section 9 explains why this changes no display.
