# Security guide

For Dalil engineers, DevOps, and the customer's security reviewers. It summarises how Ariva is protected, what the customer's cluster must provide, and how security is checked on every change. The engineering reference is `../docs/security/cwe-controls.md`; it is checked on every story, pull request and release. `../docs/security/asvs-l2.md` maps every OWASP ASVS 5.0 Level 2 requirement to its control and test, or to the gap and the story that closes it (ARV-074), for tenders that cite ASVS.

## 1. Security model in brief

| Principle | How |
|---|---|
| No inbound internet | Users through the ingress on the site network; sensors on their own VLAN behind the gateway; displays on their own VLAN reading a read-only endpoint |
| Default deny | Every endpoint needs a user permission, an integration scope or device authentication; a test fails the build if one does not |
| Least data | No images, no biometrics, no officer or passenger identity; AMAN sends aggregates only; only lane-level aggregates leave a border deployment |
| Separate principals | Users and integration clients have separate signing keys and token audiences; devices have a scheme of their own (a per-device credential, never a token), accepted only on device endpoints and nowhere else |
| Integrity | Zone profiles and contracts are immutable versions; the runtime database role cannot change raw hypertables; evidence packs are sealed with SHA-256; a golden replay of the archive hash-chains its inputs and outputs and is recorded append-only in `replay_run` (time, login and a chain link set by the database), so a change to an exported replay is detected; the archive and that record are as trustworthy as the runtime database login (ARV-036); everything is audited |
| On premises, in country | Every deployment runs in the customer's environment; no telemetry leaves without consent. Library telemetry is off in code: MassTransit's usage report (versions, OS, time zone, topic names) is disabled where every host registers the bus, a host refuses to start if `MASSTRANSIT_USAGE_TELEMETRY` turns it back on, and the E2E log scan fails a run that reports it (ARV-097) |

## 2. Control summary (14 CWEs)

| CWE | Threat in Ariva | Main control |
|---|---|---|
| CWE-78 OS command injection | A device name, file name or AODB field reaches a shell | Ariva never starts processes; a test checks no Ariva assembly references `System.Diagnostics.Process` |
| CWE-77 Command injection | Kafka or Helm commands assembled from input | No runtime command assembly; topics only from a fixed list; Helm only in pipelines |
| CWE-94 Code injection | Rule expressions, templates or dynamic queries executing input | Alert rules are typed data; no scripting, dynamic LINQ or polymorphic JSON; report templates are embedded resources; CSP `script-src 'self'`; no prototype pollution in the web app: objects keyed by server data are Maps or built with `Object.fromEntries` and spreads, never written as `obj[key] = value`, and `__proto__` and `Object.assign` are not used (scan rules SEC-131 and SEC-132, ARV-089) |
| CWE-918 SSRF | Pull URLs pointed at internal services or cloud metadata | All outbound calls through registered endpoints: administrator-created with step-up MFA, HTTPS, allowed CIDRs checked at call time, no redirects, relative paths only; in production also the NetworkPolicies, which let api-integration reach only the outbound endpoints listed in the release's values and no other pod any (ARV-085, section 6a) |
| CWE-862 Missing authorisation | A new endpoint ships without a check | Default-deny fallback policy; endpoint inventory test boots every host and fails on any endpoint without authorisation metadata unless allowlisted |
| CWE-863 Incorrect authorisation | Cross-site reads; a duty manager seeing per-desk border data; one handler seeing another | Permission policies; site scope on every query; field-level projection per role; integration clients bound to scopes and sites; alerts visible and actionable only by the roles responsible for them, also on the live hub (ARV-039); border alert metrics (open desks below recommendation, ARV-181b2, and the predicted nowcast, ARV-187), whose values carry the lane split of the arrival wave, reach holders of `ArrivalWaveLanes.View` only on every channel; authorisation matrix tests and IDOR tests |
| CWE-306 Missing authentication for critical functions | Publishing a profile, signing a contract, creating clients, changing roles without fresh authentication | Authentication everywhere except the health probes, which no Ingress routes: every host answers `/health` and `/healthz` 404 at the ingress, so they answer only on the pods' own ports (ARV-085); step-up MFA (TOTP within 15 minutes) on critical functions |
| CWE-287 Improper authentication | Weak storage, TOTP replay, token confusion | PBKDF2-SHA256 with 600,000 iterations for passwords and client secrets; constant-time comparison; TOTP replay guard; lockout and rate limits; strict JWT validation (issuer, audience, lifetime, key, algorithm allowlist, 30 s skew); one generic error for every login failure |
| CWE-93 CRLF injection (email headers) | A rule name, zone or address adding a header or a recipient to an alert email | Recipients are one plain address, checked when an administrator sets them, again when an email is written and again when it is sent, with a database check; template values are made one line of printable text (control, line-break and format characters removed, clipped); the subject is one line; MimeKit encodes every header; one recipient per message (ARV-040) |
| CWE-501 Trust boundary violation | Unvalidated vendor, AODB or request data reaching the domain | Request models validated before mapping; entities never bound from requests; request JSON read strictly on every host (a member the request does not define, a member sent twice or a number sent as a string answers 400) and a query parameter sent more than once refused with 400, neither answer repeating what was sent (ARV-089; the sign-in, the other authentication endpoints and the integration token exchange keep their earlier parsing until ARV-089a, because of the owner's login freeze); vendor and AMAN payloads validated, size-limited and mapped at the adapter edge; display texts (alert rule, display, integration client, report schedule and user display names, device models, notes and display messages) refuse control and invisible format characters of every plane, judged per code point (ARV-158); the client address taken from `X-Forwarded-For` only when the connection comes from the ingress controller's pod network, which in production is a Helm value the hosts refuse to start without or too wide (ARV-085, section 6a) |
| CWE-269 Improper privilege management | Self-elevation, over-privileged services | Grants only by a higher-ranked granter, no self-grants, System administrator grants need a second administrator; non-root containers; separate database roles for runtime and migrations, and a third login of its own for the validation service, the only one that reads the shadow nowcast (ARV-104g1: every host refuses to start if its runtime login can read a value of it: the reader role or `pg_read_all_data` held in any way, a superuser, or a grant on a value column of the table or a chunk to it, a role it holds or PUBLIC); per-service Kafka ACLs; the GitHub dev release runs on `main` only, in the `k8s-dev` environment, with a namespace-scoped kubeconfig and read-only package access |
| CWE-384 Session fixation | A pre-login session surviving sign-in | Stateless 15-minute access tokens; new session id at every sign-in; rotating, hashed refresh tokens with family revocation; HttpOnly, Secure, SameSite Strict cookie on `/auth` |
| CWE-89 SQL injection | Filters, sort fields, Timescale queries built from strings | Parameterised queries only; binary COPY with typed writers; Timescale DDL only from versioned scripts; allowlisted sort and filter fields |
| CWE-120 Buffer overflow | Oversized or deeply nested payloads | Managed code only, unsafe blocks disabled; body limits (APIs 1 MB, sensor pushes 256 KB, file imports 20 MB streamed); JSON depth 32; bounds-checked binary parsing; Kafka messages up to 1 MB |
| CWE-79 Cross-site scripting | Names, notes, flight data or messages rendered as HTML | Svelte text interpolation only (`{@html}` banned); strict CSP; `X-Content-Type-Options: nosniff`; CSV exports neutralise formula prefixes |

## 3. Authentication and MFA

| Principal | Method | Token |
|---|---|---|
| Users | Ariva's own sign-in (ADR-0026): PBKDF2 password hashing, TOTP required for every account (an account without it gets only the pending scope until it enrols), step-up with a fresh TOTP code for critical actions, lockout and per-address limits. Sign-in through an external identity provider (OIDC, D5's option) is not built | Access token 15 minutes, in memory in the browser; rotating refresh cookie (`__Secure-ariva_rt`) |
| Integration clients | Client id, client secret and TOTP (AMAN-compatible flow, hardened) at `POST /api/v1/auth`; optional `X-TOTP-Code` on every call | JWT, audience `ariva-integration`, 15 minutes, no refresh token |
| Devices | Per-device credential over HTTPS (`Authorization: Bearer ardk_...`, `X-Ariva-Device-Key`, or Basic with the device code as user name), optionally limited to source networks and bound to a pinned client certificate; client certificate or username and key over MQTT with TLS | Device authentication on Ingest endpoints (ARV-022): 401 for a missing, wrong, revoked or out-of-network credential and for a user token; 403 for the zone of another device; limited per device |
| Display players | The display's code (query `code`) and its own credential in `X-Ariva-Display-Key` (ARV-058), compared as SHA-256 in constant time; only the board endpoint, the advertisement fetch (`api/v1/display/advertising/{id}`, ARV-142a, which the player uses since ARV-143b) and the proof of play (`api/v1/display/plays`, ARV-144) accept it | None; limited per credential |
| Cronz job dashboard | An operator key checked against `Cronz:Dashboard:KeySha256`; off unless enabled; its Ingress answers only the management network in its `sourceRanges` (403 to any other client), required in production (ARV-085, wiki 04 section 5). Not tied to a user or MFA (ASVS V6.3.3, story ARV-087) | None |
| Simulator operators (non-production only) | A simulation key checked against configured SHA-256 digests (`SimulationKeyHandler`, scheme `Ariva.SimulationKey`, in `Ariva.Simulation.Api/Security/SimulationKeyAuthentication.cs`); the simulator refuses to run in k8s-prd | None |
| Services | Database and Redis passwords, Kafka SASL/SCRAM over TLS in production (shared logins per deployment today). Database logins: the runtime login every host uses (DML only), the migration login the migration job uses (DDL), and the validation reader login (ARV-104g1), which only the validation service in api-main uses, to read the shadow nowcast and nothing else. In production the ingress authenticates every pod by its certificate from the cluster CA (ARV-082b, section 6), and NetworkPolicies allow only the firewall matrix's flows between the pods and their backends (ARV-085, section 6a). Mutual TLS and per-service identities are not built yet (ASVS V13.2, story ARV-083) | |

Ariva.Web (ARV-051, ADR-0026) keeps the access token in memory only, never in web storage or a readable cookie (CWE-384). A reload or a new tab gets a token from the refresh cookie (`__Secure-ariva_rt`: HttpOnly, Secure, SameSite=Strict, Path=/api/auth), which only Ariva.Api.Main on the web origin receives: the ingress routes `/api` and `/hubs` on the web host to Main, so the web app makes no cross-origin call and `connect-src 'self'` covers it. One tab refreshes at a time (Web Locks API) and shares the new token and sign-out with the other tabs over a BroadcastChannel; the server's refresh grace period covers a tab that refreshes with a token another tab has just rotated. A non-secret `ariva-signed-in` flag in local storage only spares a signed-out visit the refused refresh. A 401 `mfa_required` (RFC 9470) opens the step-up dialog and sends the action once more; a 401 `session_expired` returns to sign-in; the page to return to is a path on the web origin only (no scheme, no `//`, no backslash), so a crafted link cannot redirect off the site. The sidebar hides screens by the permissions of `GET /api/auth/me`; the server checks every call. Text from the server and the user is rendered by interpolation only, and the QR code is an SVG path built in the browser (no `{@html}`, no innerHTML). Floor plans (ARV-053) are fetched with the token and drawn by an SVG `<image>` from an object URL, so `img-src` adds `blob:`; an image never runs a plan's script, and the server strips scripts from SVG plans when they are uploaded. Advertisement videos (ARV-142b) are fetched the same way, with the token and only when someone asks, and played from an object URL, so the CSP gains `media-src 'self' blob:` and no other media source (asserted in `tests/functional/shell.spec.ts`). The passenger display player (ARV-143b) fetches the advertisements of its plan with the display's credential, never a user's token, naming each only by the GUID the board gives, takes the bytes only when they are of the type the board named, and shows them from object URLs through the same sources; it keeps them in memory only (at most 40 items and 150 MB, nothing in web storage) and revokes each URL when the item leaves the plan, when advertising stops and when the page goes.

Ariva's integration authentication follows AMAN's flow but adds hashed secrets, a TOTP replay guard, one generic error, rate limits with lockout, UTC-only time handling and separate keys per principal type.

## 4. Authorisation and the data boundary

- Permissions are declared as constants (`Area.Entity.Action`) and attached to every controller action with the `Permission` attribute; integration endpoints carry `[IntegrationScope]`; sensor endpoints carry device authentication; SignalR hubs check the permission on every group join.
- The live hub (`/hubs/live`, ARV-035) needs `LiveQueue.View` to connect and checks every `JoinZone` against the caller's stored permissions and sites, and the site's published zone profile, answering the same `forbidden` for another site's zone and an unknown one; a connection holds at most 64 zones and makes at most 120 joins a minute, a session at most 8 connections per replica, messages are limited to 8 KB and errors carry no detail. The access token may come as the `access_token` query value only on `/hubs`, only when no Authorization header is present, once and at most 4 KB; application logs redact it, and only the web host's `/hubs` Ingress serves the hub (`tokenInQuery` in the chart), writing no access log and only critical errors and exporting no OpenTelemetry spans (the chart pins `enable-opentelemetry` "false" there, and the controller's own OpenTelemetry stays off). Every other host, api-main's included, answers `/hubs` 404 at the ingress before any location, no Ariva Ingress writes a ModSecurity audit log, and the controller's access log writes no query string (ARV-091; the chart refuses an Ingress or annotation that would undo it, section 6b). Snapshots taken from Redis are size-limited and checked before they are sent.
- Every site-bound query and command goes through a site scope; organisation-level tenancy uses NHibernate filters with PostgreSQL row-level security on contract, SLA and alert tables as a second line.
- The data boundary is physical where it matters most: border and airport are separate deployments, and only lane-level aggregates cross, one way. Inside an airport deployment, a handler sees only its own desks, contracts and alerts.
- AMAN contracts carry no person, document or officer identifiers; a unit test fails the build if a contract property name looks like one.
- Advertising on passenger displays (ARV-145) is off for every site by default. Only a system administrator with a fresh second factor changes a site's advertising policy (`AdvertisingPolicy.Edit`, a critical action), with a reason naming who authorised it, audited before and after; the display service and a database trigger refuse a display set to advertising where the policy does not allow it, its board falls back to instructions at the next poll, and the policy is saved against the site's published zone profile: once another profile is published (zones renamed, moved, dropped or added by the roles that edit profiles) no display of the site shows advertising until an administrator saves the policy again, so a profile change never shifts an exclusion on its own. Advertising endpoints carry `[AdvertisingAllowed]` (403 for a site whose policy is off, 404 outside the caller's sites or for a site that does not exist, the same answer); a unit test boots every host and fails the build when an endpoint whose route names advertising, or whose controller lives in an Advertising namespace, lacks it. Advertisement images (ARV-142a) are typed by their bytes, refused above 10 MB or 3,840 pixels a side or 8,294,400 pixels before anything is decoded, their header read in managed code before the native decoder sees them, and decoded and written anew, so no metadata, comment or hidden page is carried over (the files are served with their own type and `nosniff`, the control against content sniffing); only Ariva.Api.Main carries the native image library (SkiaSharp), one decode at a time and 30 upload attempts per person in 10 minutes. Advertisement videos (ARV-142b: MP4 with H.264, WebM with VP8, VP9 or AV1) are typed by their container and never decoded on the server: managed code reads the container only (`AdvertisingVideos.Check`: every box or element within its parent and the file, at most 12 deep and 4,096 read, nothing allocated from a declared size, the media data never walked) and refuses truncated, fragmented, live, encrypted and QuickTime files, data after the last box or element, tracks other than one picture and one sound, and pictures above the image limits; metadata and free space become zeroed padding of the same size, so the media does not move and markup hidden there is gone, while markup after the end is refused. The compressed media is still the uploader's choice, so a video is served like an image (its own type, `nosniff`, a sandboxing CSP, `Cross-Origin-Resource-Policy: same-origin`), and its decoders run only in the browsers that play it, each in its own sandbox. Videos count towards the same 30 attempts and are held to 20 MB and 30 seconds by default, 100 MB and 120 seconds in any installation. An item plays only once a person other than its uploader and its last changer approved it with a second factor, naming the item as it was shown (refused once it changed), which script 0058 also holds for any database writer; another site's item answers 404; a display fetches an item only with its own credential, and only an approved item of its own site within its days while it is a split display set to advertising and the advertising rule allows it. The fetch serves any such item of the site, not only the items of the display's current plan (decision point 7 of ARV-143b); the proof of play of ARV-144 refuses plays outside the plan (below).
- Advertising playlists and schedules (ARV-143a, `api/v1/admin/sites/{siteCode}/advertising/playlists`, `.../schedules` and `.../timeline`) carry `[SiteScoped]` and `[AdvertisingAllowed]`: 404 outside the caller's sites, and for another site's playlist or schedule named under this site's route (a plan is looked up by its id and the route's site together, so it answers like one that does not exist); 403 while the site's policy is off, the plans kept. `Advertising.View` or `Advertising.Manage` reads and `Advertising.Manage` changes (terminal duty managers and system administrators; border roles neither); a plan needs no second person, since what plays is approved item by item. A playlist names only advertisements of its own site's library that are not retired and active slides of its own site, and a schedule an active playlist, published queue zones and live displays of its own site; script 0060's checks and triggers hold a playlist's items and a schedule's playlist to the same site for any database writer, and the runtime role cannot delete or truncate plans. Every change is audited and nothing is deleted (retire and restore). Caps bound what a site can hold and what the timeline resolves: 40 items in a playlist, 100 playlists and 200 schedules in a site, retired ones included (409), held under the site's advisory locks so that creations at the same moment cannot pass them; the timeline is one display's 7 days. Names and labels are shown as text.
- Advertising playback (ARV-143b): the display board carries a plan only for a split display set to advertising at a site whose policy allows advertising for every zone the display shows, read on every board (every 10 seconds), so a plan is never itself permission and turning the policy off reaches the players at their next board. The board reads the schedules, playlists, advertisements and slides of the display's own site only, and plays only approved advertisements within their dates on the site's local day and active slides. It carries the playlist's and the advertisements' ids, the items' types and slots and the slides' words, never the playlist's name, an advertiser's or campaign's name, a file name or a person's name (a unit test pins the board's advertising fields to that list). The plan holds until `untilUtc`, no further than the display's stale threshold ahead (at most 30 minutes) and never past the site's next local midnight, judged by the server's clock, so a player cut off from the server stops advertising no later than its board goes stale. Each board's plan costs at most 200 schedules read, 30 minute steps of look-ahead and a few queries, however many schedules the site has; residual: a fault while the plan is worked out fails the whole board, so the player keeps its last board, whose queue waits go stale when no good board comes within the display's stale threshold. The wait rule is a number of minutes, 1 to 240 or none, held by the service and by script 0061's check.
- Proof of play (ARV-144, `POST api/v1/display/plays`): the display's own credential only, its prefix checked against the display at every batch, no user permission (a unit test pins it beside the display fetch as the two display endpoints exempt from `[AdvertisingAllowed]`, which apply the advertising rule to the display instead); 64 KB a body, 1 to 100 plays, 6 batches a minute per display, refused ones included. A play is taken only when the display could have shown it: a split display set to advertising whose site's policy allows it, an advertisement of the playlist that applied to that display when the play started and that may play that local day, at least a second long and within its item's slot, overlapping no other play of the display (two plays share no more than a quarter of the shorter and never more than a second, so a play inside another and stacked short plays are refused), started within the last day and ended by the time it is reported. The stored plays are read and the overlaps decided under the display's advisory lock in the write's own transaction, so batches sent at once cannot both claim the same airtime. So a display's credential can claim only airtime its own plans gave it, once, at most its wall-clock time plus a second at each change of play. Refused plays are not stored and the batch is logged as a security event (9126, the counts only, never the body). The table `advertising_play` (script 0062) holds ids, times, lengths and outcomes only, no passenger data and nothing about who was near a screen; the runtime role inserts and reads, never changes or removes a play (through the hypertable or a chunk), and its checks bound the length and times for any writer. The figures service checks the caller's sites and `Advertising.View` itself until ARV-146 gives it an endpoint, answering anyone else as if the site did not exist, and reads at most 31 local days of the site, none in the future.

## 4a. File handling (ARV-092)

Ariva.Api.Main takes six kinds of file: floor plans, SSIM schedules, the device and desk code mapping CSV imports, site configuration bundles, and advertisement images and videos. No other host takes a file. Each is typed by its bytes, never by its name or declared type; held to a size at the ingress, at the endpoint and in the read, and to bounds on what it unpacks to (pixels, SVG elements, lines and legs, rows, parts and records, container boxes); rebuilt or stripped where Ariva keeps it (SVG plans rebuilt through an allowlist, advertisement images decoded and written anew, videos' metadata zeroed; PNG and JPEG plans are kept as uploaded) or never kept at all (SSIM and CSV files, whose checked values are imported); stored only under keys Ariva generates, outside any web root; and served back only as data, with its own type, `nosniff`, a sandboxing content security policy and `Content-Disposition: inline` under a name Ariva builds from the record's id and the detected type, never the uploaded name. Every text answer of the API hosts and the web pod names UTF-8 (`SecurityHeadersMiddleware`, the web image's nginx configuration). One upload runs at a time per host. No upload is scanned for malware yet (ASVS V5.4.3): ARV-092b scans every upload in the hosts and ARV-092c runs the scanner in the chart, both Target procedures, not built yet. The [File handling guide](13a-File-Handling.md) gives, upload by upload, who may send it, the types, extensions and limits, what Ariva does to it, where it is stored, how it is served, the rate limit, the audit, and what happens to a malicious file today and after those stories.

## 5. Secrets management

| Secret | Where it lives |
|---|---|
| Database, Kafka, Redis, SMTP credentials | `appsettings.*.<env>.json` written into Kubernetes secrets by the release pipeline from a secret variable group (or by the customer's process); never in the repository |
| Validation reader login (ARV-104g1) | Its own Kubernetes secret, `ariva-validation-reader` (keys `username` and `password`), given only to api-main and the migration job as environment variables from the secret (never an appsettings file, which the base files would spread to every host); required in k8s-prd. The chart test fails if another workload gets it, a unit test if a committed appsettings file carries it, and outside vm-local any host but api-main refuses to start with it. The migration job sends PostgreSQL only a SCRAM-SHA-256 verifier of the password, never the password itself (the runtime login, older, is still set from its plain password: keep statement logging off on the database) ([Deployment guide](04-Deployment-Guide.md), sections 6.2 and 7.1) |
| Log pseudonym key (ARV-091, ARV-091a) | Its own Kubernetes Secret, `ariva-log-pseudonym-key` (key `pseudonym-key`; `logging.pseudonymKeySecret`), required in k8s-prd and given only to the five API hosts as `Logging__PseudonymKey` from the Secret, never to the Jobs, the web pod or the simulator. Never a chart value, an appsettings file or a ConfigMap: a host outside vm-local refuses it from a configuration file, and a k8s-prd host refuses to start without it. Readable by no one who reads the logs (section 6b, checklist item 21) |
| Log store sender credentials (ARV-091a, optional) | Only where the log store authenticates senders: Loki's user name and password (`logging.lokiCredentialsSecret`, as `Loki__Username` and `Loki__Password`) and the OTLP collector's headers (`otel.headersSecret`, as `OTEL_EXPORTER_OTLP_HEADERS`), each in a Secret the site creates and names, sent over https only; outside vm-local a host refuses them from a configuration file |
| Registry credentials | `dalilacr-secret`, rendered from pipeline variables |
| Integration client secrets | Stored only as PBKDF2 hashes |
| TOTP seeds, outbound endpoint secrets | Encrypted with the Data Protection key ring (AES-256-GCM for keys since ARV-080; the ring itself wrapped with RSA-OAEP-SHA256 and AES-256-GCM under an RSA 3072 certificate) and re-protected under the current key by the daily `SecretReprotection` job |
| Token signing keys | Separate keys for users and integration clients; devices use per-device credentials stored as hashes, not tokens |
| TLS keys and certificates | The ingress hosts' certificates in the Ingresses' `tlsSecretName` secrets (default `ariva-tls`), from a public CA or the customer's PKI by the rule in the [Deployment guide](04-Deployment-Guide.md), section 6.2 (ARV-084). In production also one certificate per pod (`ariva-api-main-tls` and the others), issued by the site's cluster CA, whose certificate the ingress trusts from `ariva-cluster-ca` (ARV-082b; [Deployment guide](04-Deployment-Guide.md), section 6.2) |

The key ring table (`data_protection_key`) admits only signed keys in Ariva's format (ARV-080), so a key planted there is ignored. A planted revocation is still possible for anyone who can write to the database: values under the revoked keys stop working (users re-enrol their authenticator, outbound secrets must be entered again, everyone signs in again). If that happens, delete the planted `revocation` row with the migration (administrator) login, since the runtime login cannot delete from that table, and restart the hosts, or restore the database from backup; and treat it as a database compromise.

At rest, secrets stay in Kubernetes secrets or a vault (D5). Enable encryption at rest for Kubernetes secrets on the customer's cluster. Backups (ARV-126, [Deployment guide](04-Deployment-Guide.md) section 10): the Data Protection key ring lives in the database, wrapped under the certificate, so it travels in the database backup and no backup holds a key unwrapped; every backup file is encrypted with age and its manifest signed with an operator's SSH key, which a restore verifies against an allowed-signers file kept outside the backup store before it trusts any hash; the Data Protection certificate, the token signing keys, the backup identity and the backup signing key are never in a backup, each in a custody of its own.

## 6. TLS

TLS on every external hop: users, displays and integrators to the ingress; sensors to the gateway (HTTPS, MQTT over TLS with client certificates); outbound integrations (HTTPS, optional client certificate and pinned CA); the border-to-airport feed (mutual TLS, Proposed).

At the ingress (ARV-084), TLS ends at the site's ingress-nginx controller, whose protocols and suites apply to every host it serves: Ariva ships the controller values the site applies (`Platform/Cloud/Ariva.K8s/Helm/ingress-nginx-values.yaml`): TLS 1.2 and 1.3 only, the Mozilla intermediate TLS 1.2 suites (ECDHE-ECDSA and ECDHE-RSA with AES-128-GCM, AES-256-GCM or ChaCha20-Poly1305; no CBC, no static RSA key exchange, no DHE), no session tickets, X-Forwarded-* from clients not trusted. Each Ariva host leaves the suite order to the client, as Mozilla's intermediate profile does, every suite being AEAD with forward secrecy. TLS must end at that controller: a TCP (layer 4) load balancer in front is fine, but an L7 proxy that ends TLS before it makes every request look like plain HTTP (403 on the machine hosts, no HSTS). The chart adds to every response of every host, the ingress's own included: `Strict-Transport-Security: max-age=31536000; includeSubDomains` over HTTPS only (no preload), `X-Content-Type-Options: nosniff` and `Content-Security-Policy: frame-ancestors 'none'`; known gap: a 400 nginx answers for an invalid Host header over HTTPS has no HSTS. The machine hosts (api-main, api-ingest, api-integration) answer plain HTTP 403 and never redirect, so a client that sends a credential in clear is told instead of silently redirected; the web host and the Cronz dashboard redirect it to HTTPS. Residual: one mode applies per host, so the web host's `/api` and `/hubs` (Ariva.Api.Main on the web app's origin) redirect too, and a client that sends a token to `http://<web host>/api` or `/hubs?access_token=` sends it in clear before the 308; HSTS and the app's https origin make that unlikely for a browser. The controller logs neither token: the hub's Ingress keeps no access log, and no access log line holds a query string (ARV-091). The api-main host answers `/hubs` 404 in any scheme, so the hub is reached through the web host only. The affinity cookies are Secure, SameSite=Strict, Path=/, and the web app's sidebar cookie is `__Host-sidebar_state` (Secure, SameSite=Strict). Each host's certificate chains to a CA its clients trust: public, or the site's PKI where every client is a device the site manages ([Deployment guide](04-Deployment-Guide.md), section 6.2). The TLS check (`scripts/ops/tls-check.mjs`) proves the versions, suites, certificates, headers and plain HTTP behaviour on the live hosts after each release ([Operations runbook](10-Operations-Runbook.md), section 4.14).

Ingest's MQTT listener takes TLS 1.2 and 1.3 only and, on Linux, the pods' suites (TLS 1.3's three, and for TLS 1.2 ECDHE with AES-GCM or ChaCha20-Poly1305); before ARV-084 it took the operating system's defaults, because a listener with its own TLS options does not get the pods' policy.

Inside the cluster, production (k8s-prd) encrypts every backend connection or the host does not start: Kafka over SASL_SSL against its mounted CA (ARV-020), PostgreSQL over TLS verified against the internal CA in `Database:RootCertificate` (the TimescaleDB chart serves TLS and accepts TCP connections over TLS only), Redis with `ssl=true` verified against `Redis:CaCertificatePath` (the cache and the live hub's backplane), and the logs to Loki and the OTLP collector over https only (ARV-082a). The pinned CAs are the only trust: the image's system store is never consulted for PostgreSQL or Redis, and a certificate for another host name is refused. The ingress reaches every pod over TLS too (ARV-082b): each API host serves https only on 8443 and the web pod's nginx TLS only on 3443, from a certificate the site's cluster CA issued for the pod's Service, and every Ingress verifies it against that CA alone (`ariva-cluster-ca`) under the Service's in-cluster name, over TLS 1.2 or 1.3. There is nothing to fall back to: the pods have no plain listener, and a CA secret the controller cannot read gives 503, never plain HTTP. A k8s-prd host refuses to start when its configuration would serve plain HTTP, names no certificate file that exists, or allows TLS below 1.2; on the pods, as on the database, the TLS 1.2 suites are ECDHE with AES-GCM or ChaCha20-Poly1305 only. The API hosts take a renewed certificate without a restart; the web pods take theirs at their next restart (restart the web Deployment after a renewal until a follow-up story reloads it in place). No host calls another over HTTP today; a host that starts to must verify the other against the cluster CA. Dev and demo keep plain connections. Details per hop in [Network and ports](05-Network-and-Ports.md).

## 6a. Network isolation, trusted proxies and private probes (ARV-085)

In production (k8s-prd) every Ariva pod is isolated: a default-deny NetworkPolicy selects the five API hosts, the web pod and the migration and topics jobs, and the chart allows exactly the firewall matrix's flows ([Network and ports](05-Network-and-Ports.md), section Network policies). In: the ingress controller's pods to each pod an Ingress routes to, on its serving port only, and the sensor networks to Ingest's MQTT port; api-stream and the jobs take nothing. Out: DNS, the database, Kafka, Redis, the OTLP collector and Loki for the pods that use them; the SMTP relay for api-integration and api-cronz (alert email and the scheduled reports); the listed outbound endpoints for api-integration only; nothing for the web pod. The chart refuses the policies off in k8s-prd, and so does the prd environment of both Helmfiles. Every peer is a value: kube-dns, the database, Kafka and Redis have defaults to check against the cluster, while the OTLP collector, Loki, the relay and the outbound endpoints ship without peers and stay closed until the site gives them. That is the SSRF control working as intended: an outbound endpoint an administrator registers at run time is reachable only after its CIDRs are added to the values and released, so both the endpoint's own CIDRs and the network allow a destination. In production the chart refuses a peer wider than /8 (IPv4) or /16 (IPv6) and a namespace selector that selects every namespace without a pod selector. Dev, demo and localk8s render no policy by default.

The policies need a network plugin (CNI) that enforces NetworkPolicy; on one that does not, they are accepted and silently do nothing (checklist item 4). The kubelet's probes need no rule, since a NetworkPolicy cannot block a pod's own node; where the CNI filters node traffic anyway (a host firewall), the site adds a NetworkPolicy of its own for the nodes' addresses to the probe ports.

Trusted proxies: a host takes the client's address from `X-Forwarded-For` (and the scheme from `X-Forwarded-Proto`; never `X-Forwarded-Host`) only on a connection from the ingress controller's pod network, the last entry only. In production that network is the Helm value `ingressController.podNetworks`, which `values-k8s-prd.yaml` ships as `10.244.0.0/16` for the site to replace with its own pod CIDR; the committed production settings file lists none (it trusted every private range before). A production host refuses to start when nothing is trusted, a network is 0.0.0.0/0 or ::/0, wider than an IPv4 /14 or an IPv6 /48, has address bits after its prefix, or would trust IPv4 clients through the dual-stack mapped form wider than a /14, and the chart refuses the same values before anything is deployed ([Deployment guide](04-Deployment-Guide.md), section 5). The controller trusts no `X-Forwarded-*` header from clients, and the pod network holds every pod, so the NetworkPolicies, which let only the controller reach the routed pods, are what keep another pod from naming its own client address, and they do so only where the cluster's CNI enforces them (checklist item 4). A site that can give the controller nodes' pod ranges in place of the whole pod CIDR narrows the trust further.

Private probes: every Ingress answers `/health`, `/healthz` and anything under them, in any case, 404 at its host's server level, before nginx picks a location, so no Ingress can route them; the 404 is judged on the request's own path before any rewrite, so the chart refuses, in every environment, the annotations `rewrite-target` and `use-regex` and any annotation value that writes an nginx `rewrite` directive (no Ariva Ingress rewrites a path). The probes answer only on the pods' own ports. The TLS check fails a host whose `/health/readiness` answers anything but 404 (or 403) through the ingress.

The Cronz dashboard answers only the networks in its Ingress's `sourceRanges`, required in production; `values-k8s-prd.yaml` ships a documentation network no client has, so it answers 403 to everyone until the site names its management network.

Client addresses: the source range and the trusted proxies need each client's own address at the controller (`externalTrafficPolicy: Local` on its Service, or the PROXY protocol). Behind SNAT every client arrives as a node or load balancer address: the dashboard then refuses everyone, or lets everyone in once someone adds those ranges, and per-address limits and device source networks see that one address. Never put node or load balancer ranges in `sourceRanges`.

## 6b. Security events and log protection (ARV-091)

Security events: every API host logs, at Warning, each refusal of the authorization middleware (a 403 as `SecurityEvent.AuthorizationForbidden`, 9114, with the missing permission or scope; a 401 as `AuthorizationChallenged`, 9115), each rate limiting 429 (9116, with the policy and the kind of partition, never its key), each refused input (9117 invalid model, 9118 strict JSON, 9119 repeated query parameter, 9127 NUL character) and each `[SiteScoped]` 404 (9128), beside the account and administration events of earlier stories (9101 to 9113, 9120 to 9126). Any other 401, 403 or 429, answered outside the authorization middleware and the rate limiter, is logged when its request ends as `SecurityEvent.RequestRefused` (9129, with the status and a fixed reason): an ended or revoked session, a pending account, a service's own 403 such as `BorderOnly`, the Integration API's per-client limit, the upload limit, and the sign-in's and the refresh's refusals. Each of these request-level events names who (the caller's id, or `anonymous`), from where (the client address after the trusted forwarded headers), where (the method and the endpoint's route pattern), why (a fixed reason) and the trace id, and never the refused input: no path, query string, header, body or value. Their category is held at Warning in code, and writing one never changes an answer. A throttle per kind and host process (60 a second, 3 from one source: the caller, else the client address, IPv6 by its /64) keeps a flood from filling the log store or hiding another source's event; what it leaves out is written as a summary every 10 seconds (9130) and counted by the metric `ariva.security.events`. Residual: 20 or more distinct sources in one second on one pod can still fill a kind's lines, and the summary and the metric then count the rest without naming their sources. The [log inventory](../docs/security/log-inventory.md), section 10, is the catalogue, with each event's fields and a proposed alert; [Operations runbook](10-Operations-Runbook.md) section 4.16 says how to find them. Not logged yet as events of their own: the sign-in success and failure with the account and the factors, the logout and the refresh, which are in the authentication code under the owner's login freeze (ARV-091b); meanwhile their 401 and 403 answers are 9129 events.

Who and where on every line: each line a request writes names the client address and the caller by id in the `Caller` fields (a user's account and session ids, an integration client's id, a device's or a display's id), never a name, an email address or a credential, beside the trace id. The enricher owns those fields, so a line about another account (an administrator's action) keeps that account apart from the administrator who acted. These are personal data of the site's staff in every log store; their readers and retention belong in the go-live record (checklist item 15; Proposed: 30 days, the operations team only, TC-65).

Protection levels, applied by the name of each logged value in every host before any sink sees it:

| Level | Data | Written as |
|---|---|---|
| Omit | Credentials and keys: passwords, tokens, cookies, TOTP and recovery codes, client secrets, device and display keys, the pseudonym key | `[REDACTED]` |
| Hash | Sensor track ids and desk codes (border-only data) | `#` and 12 hex characters of an HMAC-SHA256 under a key per UTC day, derived from `Logging:PseudonymKey` |
| Mask | Staff email addresses, also inside message text | `a***@example.com` |

A dictionary's keys take the dictionary's level too (keys that protect alike are kept as `<protected key>~<n>`, never in clear). The enricher fails closed: a property it cannot protect is written as `[REDACTED]`, the rest of the event is still protected, and the failure is counted (`ariva.security.log_protection_failures`). A pseudonym links lines within one UTC day and never across days. The master key, `Logging:PseudonymKey`, makes one day's pseudonyms equal across the pods and their restarts; outside k8s-prd, without it, each pod uses a random key of its own. It is a secret (checklist item 21): outside vm-local a host takes it only from the environment, as `Logging__PseudonymKey` from a Kubernetes Secret, and refuses to start when it comes from a configuration file or is malformed. Since ARV-091a the chart passes it from `logging.pseudonymKeySecret` to the five API hosts only, k8s-prd requires it (the chart, both Helmfiles' prd and every host there refuse to go without it), and at install the chart refuses a Secret that is missing or holds a key the hosts would refuse. Whoever holds it can recompute any day's pseudonym of every desk code, so it stays in the secret store, away from the log store's readers. Residual: exception text is not rewritten, so a library's message (an SMTP relay refusing a recipient) can carry a whole address.

Where logs go: the hosts log to the console, Loki and the OTLP collector only, fixed in code. Only `Serilog:MinimumLevel` is read from configuration, and a host refuses to start in every environment when the `Serilog` section holds any other key, so no setting can add a sink, such as a file in a pod or Loki over plain HTTP past the production TLS guard. The JSON file sink is for vm-local (the E2E run), and a host elsewhere refuses to start with `LogFile:Path` set. At the ingress (Ariva's controller values and chart): no Ariva Ingress writes a ModSecurity audit log (`SecAuditEngine Off` on each, `enable-modsecurity` "false" for the whole controller), the access log writes the request line without its query string, and only the web host serves `/hubs`. The chart refuses a site annotation that would turn the audit log back on, write a ModSecurity debug log, copy request values into a rule's message or write a log directive ([Deployment guide](04-Deployment-Guide.md), section 5, `ingresses`), and the controller values keep the error log at `notice` or above, nginx's log escaping on and the controller's OpenTelemetry off (checklist item 5). Residuals: the controller's error log still writes nginx's request line with its query string on upstream errors and ModSecurity denies (a search's text can appear there), and the access log keeps the referrer and `$remote_user` (a device's code).

Shipping (ARV-091a): in production the logs leave every pod for a logically separate store. A k8s-prd host ships its logs over TLS to Loki or to the OTLP collector, besides the console, or it does not start; the chart's `logging.collector` (`loki` as shipped, or `otlp`) is required there by the chart and by both Helmfiles' prd. Optional sender credentials, for a store that authenticates senders, come from Secrets only and go over https only: outside vm-local a host refuses Loki's pair or an OTLP header variable from a configuration file or with a plain http address. The store's readers, its protection against change and its retention are the site's, recorded at go-live (checklist item 15, with the [log inventory](../docs/security/log-inventory.md) section 8.1, which says for Loki, the OTLP collector and a customer SIEM how the store controls each). Residuals: the chart cannot check that Loki's peers hold the Loki of `Loki:Uri`, so the go-live record proves that a startup line arrives; the hosts trust the public CAs only for these stores, so a store whose certificate chains only to the site's PKI cannot be reached until ARV-200.

An entry whose approver starts with `PENDING` stays visible as a warning in every report; only a human approver replaces it. Today one exception is pending: the anonymous health probes (`SEC-052`), which return only a status word and are excluded from OpenAPI.

Current state (1 October 2026): the analyzers (layer 2), the repository scan (layer 3), the layering and data-boundary tests (part of layer 4) and the dependency audits (layer 6) run through `node scripts/verify.mjs security` and `dotnet test`. The PR validation pipeline (`Analyze-solution.yaml`) runs the build, the unit and integration test projects and the web checks, but not yet the repository scan or the audits; adding them is a Target procedure, implemented in Phase 0 epic Skeleton and platform. The behaviour test project, the nightly pipeline and the ZAP pipeline are planned. Update (5 October 2026): the dynamic scan (layer 7) runs in `security-zap.yml` and through `node scripts/verify.mjs zap` (ARV-063); a High risk alert fails it unless a person approved an entry in `security/zap-triage.json`, and lower risks are triaged in `backlog/progress.md`.

## 10. Penetration testing

An external penetration test runs before the pilot goes live and once per major release, with a client-approved scope. The test is a release gate. Security accreditation with the client is part of the pilot's critical path (2 to 8 weeks in the roadmap assumption).
