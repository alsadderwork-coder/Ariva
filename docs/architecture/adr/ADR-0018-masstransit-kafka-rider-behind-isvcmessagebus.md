# ADR-0018: MassTransit 8 with the Kafka Rider behind ISvcMessageBus; raw Confluent consumer for stateful stream processing

- Status: Accepted
- Date: 2026-10-01
- Source: Product owner decision, 2026-10-01 ("MassTransit 8"), replacing the earlier Proposed Confluent.Kafka option

## Context

Kafka is the event backbone (D5). AMAN runs MassTransit 8.4 with the Kafka Rider, and the product owner wants Ariva to stay on the same bus for team familiarity and shared patterns.

A read of AMAN's code on 2026-10-01 (HEAD b72d69c) found that the bus is wired but several protections described in AMAN's docs are not active:

| AMAN today | Effect |
|---|---|
| `IdempotencyFilter` and `MessageTrackingFilter` exist in `Aman.Infra/Messaging` but no `UseConsumeFilter` registers them | No duplicate suppression after a crash or rebalance |
| `OutboxMessage` rows are written only when a publish throws; the `OutboxProcessor` job's `[TickerFunction]` is commented out | Not a transactional outbox; failed publishes are never resent |
| No retry, no dead-letter handling (`Kafka:RetryCount` is bound but unused); v8 topic endpoints discard faulted messages | A consumer exception silently drops the message |
| Producers are registered without keys; topics created with one partition and replication factor 1 | No ordering per entity, no parallelism, no broker redundancy |
| One consumer group (`aman-group`) for every service | A deploy of one service rebalances all of them |

MassTransit facts that shape the design (v8 source and docs, checked 2026-10-01):

- v9 is commercial. v8 stays Apache 2.0; the official transition table ends v8 maintenance after 2026. Latest v8 is 8.5.11 (2026-09-30), which requires Confluent.Kafka 2.15.1 or later.
- The v8 bus outbox exists for EF Core and MongoDB only and does not cover rider producers (`ITopicProducer`); rider outbox support arrives in v9.1. There is no NHibernate outbox.
- v8 topic endpoints have no partition assigned or revoked callbacks, and no built-in error topic (`EnableErrorTopic` is v9).
- Offsets are checkpointed per partition after messages complete in order (at-least-once; a crash replays up to one checkpoint window). Messages are spread over `ConcurrentMessageLimit` lanes by key, so order holds per key; `ConcurrentDeliveryLimit` above 1 breaks ordering. With more than one lane a stop can commit past records it never handled (ARV-253, note of 2026-10-25 below), so Ariva runs one lane per Kafka consumer and several consumers per endpoint (`ConcurrentConsumerLimit`) instead.

## Decision

1. **Integration and domain events** (queue intervals, nowcasts, alerts, topology changes, AMAN feed, AODB and immigration events) use **MassTransit 8.5.11 with the Kafka Rider** behind AMAN's `ISvcMessageBus` abstraction, hosted on an in-memory bus as in AMAN. Pinned: `MassTransit` 8.5.11, `MassTransit.Kafka` 8.5.11, `Confluent.Kafka` 2.15.1.
2. **Stateful stream processing** in Ariva.Api.Stream (per-zone track state, snapshots, replay) uses the **Confluent.Kafka consumer directly**, through an Ariva.Infra abstraction that exposes partitions, offsets and rebalance callbacks. The rider cannot tell a consumer when it loses a partition, and Stream keeps state per partition.
3. Ariva builds the protections AMAN lacks, as part of ARV-020:
   - **Transactional outbox on NHibernate:** domain events are written to `outbox_message` in the same transaction as the aggregate change. A relay (`BackgroundService`, single leader through a PostgreSQL advisory lock) claims rows with `FOR UPDATE SKIP LOCKED`, produces them in id order through keyed `ITopicProducer<string, T>`, and stops for a key on failure so order holds.
   - **Inbox (idempotency) filter:** `INSERT INTO processed_event(consumer, event_id) ON CONFLICT DO NOTHING` inside the consumer's NHibernate transaction; zero rows inserted means a duplicate, which is acknowledged and skipped. Unlike AMAN's Redis claim, a crash cannot mark an unprocessed event as done.
   - **Dead-letter filter:** outermost consume filter. After bounded in-process retries it produces the original key, body, headers, topic, partition, offset and error to `<topic>.dlq.v1`, then returns so the offset commits. Replay from the DLQ is an admin operation (`/replay` command, audited).
   - **Keys always set** (zone id, desk id, gate id, device id, site id); topics provisioned at startup from `KafkaTopics` with configured partitions and replication; **one consumer group per service and endpoint** (`ariva-<service>.<purpose>`).
   - Endpoint defaults: `AutoOffsetReset` earliest, `ConcurrentDeliveryLimit` 1, `ConcurrentMessageLimit` 1 (one lane per Kafka consumer, ARV-253; a host refuses any other value), `ConcurrentConsumerLimit` from `Kafka:Consumers:ConsumersPerEndpoint` (1 to 6 consumers in the endpoint's group, parallel across partitions), `CheckpointInterval` 5 s, `CheckpointMessageCount` 500 (bounds replay), short exponential retry.
   - Telemetry: `AddSource("MassTransit")` and `AddMeter("MassTransit")`; MassTransit's bus health check is part of readiness.

## Consequences

- Parity with AMAN's bus, with the gaps above closed in Ariva and reported to AMAN (see `docs/security/cwe-controls.md`).
- **Licence and maintenance risk:** v8 maintenance ends after 2026. Mitigations: MassTransit stays behind `ISvcMessageBus` and inside Ariva.Infra (no MassTransit types in Ariva.Core, enforced by an architecture test); the outbox, inbox and DLQ are Ariva code, not MassTransit features, so a swap to the raw Confluent client or to a v9 licence is a single-project change. Decide before go-live (tracked in `docs/product/decisions.md`). Community forks (OpenTransit, PublicTransit) are watched but not relied on.
- Two Kafka consumption styles in one codebase; the kafka-streaming skill says which to use where.
- Confluent.Kafka moves from AMAN's 2.8.0 to 2.15.1; Testcontainers.Kafka integration tests cover the at-least-once, duplicate and DLQ paths.
- A second outbox writer (ARV-115): Ariva.Api.Stream's `StreamStore` writes `OverflowDetected` rows to `outbox_message` itself, in the same raw Npgsql checkpoint transaction as the band minutes, zone snapshots and offsets that decided them (not through an NHibernate unit of work); the relay alone publishes them, after the commit. Both writers check a row against the table first (`OutboxLimits`: a message key of at most 200 characters), the stream dropping such an event with a warning and the NHibernate outbox failing the commit with the reason, so neither stalls on a database error.
- Filter order, verified in ARV-020 with MassTransit's pipe probe on an endpoint built by the same `ConsumePipeline.Configure` the rider uses: MassTransit places `UseMessageRetry` first in the message pipe whatever the configuration order, so a dead-letter filter cannot wrap the retry. The dead-letter filter therefore sits inside the retry and acts only on the final attempt (`GetRetryAttempt()` equal to the retry limit); the observable behaviour is the one decided above (retries first, then one dead letter, offset committed). The inbox and unit of work run inside both, with a fresh scope per attempt.

## Alternatives considered

- Confluent.Kafka for everything (the earlier proposal). No licence exposure, but diverges from AMAN and reimplements serialisation, consumer hosting and telemetry. Remains the fallback if v8 support becomes a problem.
- MassTransit 9 with a commercial licence. Adds the rider outbox and error topics; cost and licence-key operations for every deployment. Revisit at go-live.
- Rebus. Not used ([ADR-0004](ADR-0004-kafka-for-facts-workflows-without-second-broker.md)).

## Implementation notes (ARV-020)

- Dead-letter topics are `<topic>.dlq.v1`; for a topic outside the `ariva.` prefix (AMAN's feed) the prefix is added in front (`ariva.aman.feed.desk-session-changed.v1.dlq.v1`), so every dead letter stays under Ariva's ACLs.
- A dead letter the broker refuses is retried until accepted (it holds the partition), because the v8 rider discards a message whose fault escapes the pipe.
- One event type per topic: the rider keeps one producer per topic name, so `EventCatalog` refuses a second type on a topic; a new shape gets a new versioned topic (ADR-0019).
- Values are plain JSON (camelCase, `System.Text.Json`), not MassTransit envelopes, so the raw Confluent consumer and the Python worker read them directly. Headers carry `ariva-event-type`, `ariva-event-version`, `ariva-correlation-id` and `ariva-causation-id`.
- Topic provisioning runs in the background and retries every 10 seconds, so a broker that is not reachable yet does not stop a host; the relay waits for the bus to be healthy, ends a pass on a broker failure (a 30 second produce timeout), and only rows that cannot be read hold back their key.
- Readiness runs the health checks tagged `ready`, which includes MassTransit's bus and rider check. A host without consumers stays ready while Kafka is down and keeps its events in the outbox.
- Note of 2026-10-12 (ARV-156), correcting the point above without changing the decision: a host with consumers stays ready during a broker outage too. MassTransit reports a started bus whose Kafka endpoint is faulted as Degraded, not Unhealthy (Unhealthy only until the bus has started), and `/health/readiness` answers 503 only for Unhealthy, so it keeps answering 200 (its body says "Healthy") while the outage shows as the bus check's Warning in the log. Whether a Degraded bus should fail readiness or raise an alert is an open decision (`docs/product/decisions.md`).
- Offline verification in this environment compiled against MassTransit 8.4.0 and Confluent.Kafka 2.8.0 (the versions available without NuGet); the pinned 8.5.11 and 2.15.1 build in CI. The Testcontainers.Kafka tests (poison to DLQ, redelivery skipped by the inbox, plain JSON on the wire) run in CI only.
- Hardening from the ARV-020 security review: production requires SASL over TLS (`SaslSsl`, with the cluster CA from `Kafka:SslCaLocation`) or the host does not start; a dead letter's body is cut at 512 KB (flagged) so the letter always fits 1 MB; a consumer's own cancellation is retried and dead-lettered like any failure (no `Ignore<OperationCanceledException>`); an event over 1 MB fails its commit instead of blocking its key in the outbox; an unknown event type holds its key without counting attempts; the relay producer does not linger; inbox entries are kept 35 days, longer than any deleting topic's retention.
- The raw stream consumer commits manually: offsets are stored after each record and committed only after the handler checkpoints its state (periodically and before a clean revoke); after a handler failure or a lost partition the state is dropped and nothing is committed, so the records since the last checkpoint are replayed.
- Note of 2026-10-13 (ARV-166), adding to the decision without changing it; the owner's decision of the same day follows. A produce queued behind a message in flight when the broker connection drops could wait for ever, and with it a device push, an outbox relay pass (its transaction and leader lock) or a dead letter. The cause is in the rider, not in librdkafka (read in the decompiled 8.5.11 assemblies; evidence in backlog/progress.md): `PipeContextSupervisor<ProducerContext>.Send` treats any exception from a send, a cancellation of the caller's token included, as a fault of the topic's cached producer and disposes it (`ActivePipeContext<T>.Faulted`); `KafkaProducerContext.Dispose` skips its flush once librdkafka has reported a local error on that producer (a broker going down is one), and a disposed producer serves no more delivery reports, so the sends still outstanding on it never complete. A device that dropped its request therefore stranded every other push outstanding on its topic. Ariva contains the effect inside the rider: `KafkaProduce` ends every produce Ariva awaits within 45 seconds (`SendTimeout`: librdkafka's 30 second message timeout, its reporting delay of up to its 10 second reconnect backoff, and 5 seconds) with `KafkaProduceTimeoutException`, giving the produce a token of its own that cancels then (which also releases a stranded produce) and ending the wait then whatever the client does; the caller's token never reaches the rider, so a caller that gives up (a device dropping its request, a relay pass ending, a stopping host) stops waiting at once while its produce runs on to its report or its bound; the relay's pass holds its transaction, leader lock and claimed rows for at most `Kafka:Outbox:PassSeconds` (60) seconds of producing; the dead-letter retry loops end when their receive endpoint begins to stop (`EndpointStopping`, the endpoint's own Stopping event: a signal any earlier, the host's ApplicationStopping or the bus's PreStop, let a Kafka endpoint whose consumer had ended on a broker error report Completed, so MassTransit's stop skipped it and its transport started a new consumer in the stopped host), as a cancellation of the message's own token, which MassTransit neither retries nor rescues, so the message is left unacknowledged and delivered again after restart; and delivery reports keep no copy of the message (`dotnet.producer.delivery.report.fields` none), so a stranded report handler pins a few hundred bytes, not the message. Still true after it: a failed send, or Ariva's own cancellation at 45 seconds on a producer that has not reported by then, disposes its topic's producer and strands the sends outstanding on it, which now fail at their bound and are sent again by the relay or the device (at-least-once; consumers behind the inbox drop the copies by event id and the sensing archive by batch id; the queue engine does not yet drop a repeated interval-count batch, ARV-168); and, made reachable by this change (before it, a stop whose dead letter Kafka refused hung until the pod was killed, so nothing was committed past the record and it came back after a restart; the bounded stop now ends cleanly), MassTransit's checkpointer can commit past a record left unacknowledged at a stop once a later record of its partition completes and is checkpointed before the endpoint stops, so such a record can be skipped (accepted by the owner on 2026-10-13 for ARV-166, closed before the pilot by ARV-171, which writes a refused dead letter durably first) (the stop warning names its topic, partition and offset for a replay).
- Owner decision of 2026-10-13 (ARV-166, ARV-167): ship the bounded mitigation of the note above now; ARV-167 then gives Ariva its own Confluent producer per host for sends, behind `ISvcMessageBus`, keeping MassTransit's rider for consuming, which removes the cause (a failed or cancelled send no longer disposes a producer that other sends share). ARV-167 writes the amendment to decision 1 of this ADR and the matching changes to CLAUDE.md and the kafka-streaming skill; until then decision 1 stands as written (`docs/product/decisions.md`).
- Note of 2026-10-13 (ARV-168), adding to the decision without changing it: the queue engine now drops a resent batch by device and batch id within its window (formulas F5), so the copies an abandoned or resent produce makes are dropped by the inbox (event id), the sensing archive (batch id) and the engine alike. A resend is deduplicated only when its body is byte-identical (docs/architecture/sensor-adapters.md).
- Note of 2026-10-13 (ARV-171), adding to the decision without changing it, and closing the skip that the ARV-166 note above left open: a dead letter that Kafka has not taken when its receive endpoint stops is first written as an `outbox_message` row for the dead-letter topic (`IDeadLetterStore`, `OutboxDeadLetterStore`: its own short transaction, at most 10 seconds, an id derived from the consumer group, topic, partition and offset so a record delivered again adds no second row), and only then does the record complete; the relay sends the row later like any other, with its per-key order, backoff and pass bound (message type `ariva.dead-letter`, sent only to `KafkaTopics.DeadLetter` of the letter's source topic, which must be a constant). Every host now registers the dead-letter producer of every topic, because any host can lead the relay. A dead letter is bounded as a whole (its JSON within 1 MB less 16 KB: the body gives way first, then the headers). ARV-166's unacknowledged path stays only where nothing durable can be written: the database away as well, or (until ARV-175) a NUL or lone surrogate in the record's key, headers or error text, which PostgreSQL refuses; there the checkpointer can still commit past the record, and the warning names it for a replay. A stop does not cancel a retry wait (MassTransit builds the endpoint's retry with no cancellation): the stop waits out the schedule and the final attempt keeps the letter, so a retry wait leaves no faulted record either.

- Amendment of 2026-10-13 (ARV-167) to decision 1, on the owner's decision of the same day (the ARV-166 note above): Ariva owns its Kafka sends. Every send Ariva makes, `ISvcMessageBus` publishes (Ingest's direct publish of sensing batches among them), the outbox relay's rows (events, and dead letters kept at a stop) and the dead letters of the consume filters and the stream consumers, goes through one Confluent producer per host that Ariva owns (`KafkaProduce`, an `IProducer<string, byte[]>` in Ariva.Infra), still behind `ISvcMessageBus`; MassTransit 8.5.11's rider stays for consuming only (topic endpoints, retry, and Ariva's inbox and dead-letter filters) and registers no producer. Decision 1 therefore reads: integration and domain events are consumed with MassTransit 8.5.11 and the Kafka Rider and produced with Ariva's own Confluent producer, both behind `ISvcMessageBus`; decision 3's relay produces through that producer rather than `ITopicProducer<string, T>`. The producer is built when the host starts (`KafkaProducerLifetime`, registered before the relay and the bus, so it starts before them and stops after them), flushed for at most 5 seconds at stop and disposed with the container, which first fails every send still waiting for its report; nothing else disposes or replaces it. A send is handed over with `Produce(topic, message, handler)`, which takes no cancellation token, so neither a caller who gives up nor a failed send can reach the client: the cause in the ARV-166 note is removed, not only bounded. ARV-166's bounds stay (an awaited send ends within 45 seconds, now a backstop since every send ends by its delivery report first; a caller's cancellation ends only its own wait; the relay's pass bound). The wire format is the rider's (read in its 8.5.11 code, captured before the change and contract-tested against a rider producer registered as before): topic from `KafkaTopics` (the producer refuses any other, AMAN's included, and the relay sends an event row only to its type's topic), key as UTF-8, value as the event's JSON (its runtime type), librdkafka's default partitioner, headers `ariva-event-type`, `ariva-event-version`, `ariva-correlation-id`, `ariva-causation-id`, `MT-Activity-Id` when traced (the send span's id from Ariva's `Ariva.Kafka` activity source, which MassTransit's consume side takes as its receive span's parent) and `MessageId`; the rider's `ConversationId`, `DestinationAddress` and `SourceAddress` are no longer written, since nothing in Ariva reads them. The producer's queue is bounded to fit the pods' memory limits (`queue.buffering.max.kbytes` 32768, `queue.buffering.max.messages` 10,000; reasons and arithmetic in `docs/architecture/overview.md`, Producing), and a full queue refuses at once, which Ingest answers 503 and the relay treats as a broker failure. A fatal producer error (an idempotence refusal; librdkafka's remedy is a new client) is the only thing that replaces the client: it is recreated in place, at most once per `Kafka:Producer:RecreateSeconds` (30) from the failed client's creation, sends failing at once in between, the replaced client retired off the send path within bounds (its own reports end their own waiters, the rest fail with `Local_Destroy` and their senders send again); each fatal error and recreation is logged Critical and counted on the `Ariva.Kafka` meter; readiness does not change. The relay now waits for the producer (started, and not in that gap) instead of MassTransit's bus health, which sending does not need. ARV-171's registration of every topic's dead-letter producer in every host is no longer needed and is gone. The implementation note "the rider keeps one producer per topic name" no longer gives the reason for one event type per topic; the rule stays because a topic endpoint reads one value type. The consequence on licence and maintenance narrows: producing no longer depends on MassTransit, and consuming remains a single-project swap.
- Note of 2026-10-14 (ARV-165), adding to the decision without changing it: a broker outage during a consumer's offset commit. MassTransit 8.5.11's Kafka consumer commits with the synchronous `Commit`, which waits for a group coordinator that a broker that is away never gives, and its agent completes only once that commit returns, so the endpoint stays Ready, the bus check Healthy and the bus's stop waiting meanwhile (45 seconds, librdkafka's session timeout, measured; for good in one ARV-156 run). Ariva does not depend on that state any more: readiness has a `kafka` check of its own (a metadata request through the producer's handle within 3 seconds, Degraded, so an outage raises the ARV-125 alert while readiness answers 200); every host's shutdown timeout is 50 seconds and every API pod's grace period 60, and the bus's stop wait is the shutdown timeout less 15 seconds (`MassTransitHostOptions.StopTimeout`, 35 seconds: a stop during a message's retries needs up to 25), so a host stops in time; a host refuses to start with settings that break that arithmetic; and the endpoints MassTransit's stop skips (it stops only started, ready or faulted endpoints, so one between restarts after a broker error kept restarting in a stopped host) are stopped after the bus by `KafkaEndpointsLifetime`. The relay no longer counts a broker or producer outage against a row: such a failure retries the row after `Kafka:Outbox:BrokerRetrySeconds` (5) without an attempt, so every key resumes within seconds of the broker's return; the producer's recreation catches every exception but running out of memory, and a sweep ends a delivery report more than 90 seconds late. Evidence and measurements: `CommitRaceTests`, backlog/progress.md.
- Note of 2026-10-14 (ARV-176), adding to the decision without changing it: topic endpoints are connected to the rider at run time instead of being configured with the bus. MassTransit 8.5.11 starts the configured endpoints as part of the bus's start and waits for them, so one endpoint whose topic was missing faulted the start and left the bus stopped for good, every consumer of the host with it (at Ariva.Api.Integration, one missing AMAN feed topic stopped all four AMAN consumers). The bus now starts with no topic endpoint, and `KafkaConsumerEndpoints` connects each consumer's endpoint (`IKafkaRider.ConnectTopicEndpoint`, the same group, settings and consume pipe) once its topic exists: it waits at start only for the consumed Ariva topics (AMAN creates its own; at most 60 seconds, then at most 30 seconds for readiness, both checked against the pod's startup allowance), logs and gauges a missing topic (`ariva.kafka.consumed_topic_missing`), and connects it when it appears, without a restart; its checks never hold the host's stop. Evidence: `MissingTopicTests`, `ConsumerEndpointsTests`, backlog/progress.md.
- Note of 2026-10-14 (ARV-125a), adding to the decision without changing it, on the note of 2026-10-12 (ARV-156): the readiness body now says "Degraded" (200) while a check is Degraded, instead of "Healthy", and names no check or detail; the owner's decision of 2026-10-13 (a degraded bus raises an alert, not a readiness failure) is built as the `ariva.health.status` gauge per check (0 Healthy, 1 Degraded, 2 Unhealthy, from the host's health check publisher), which the ARV-125b alert rules read.
- Note of 2026-10-15 (ARV-126), adding to the decision without changing it: the outbox keeps the state of the compacted topics. The relay's housekeeping still deletes sent rows after `Kafka:Outbox:KeepSentDays`, except the newest row of each key on a compacted topic (`TopicCatalog.CompactedTopics`), which stays however old (script 0052 adds the `(topic, message_key, seq)` index that finds a newer row). After a Kafka loss, `scripts/ops/ariva-db.sh after-kafka-loss` marks those rows unsent again and the relay sends them through its normal path with their original event ids, so the republish goes through the outbox like every other send; consumers drop what their inbox has already applied (wiki 04 section 10.5).
- Note of 2026-10-23 (ARV-175), adding to the decision without changing it, and closing two findings of the ARV-171 review: (1) a dead letter whose record carried a NUL character or a lone surrogate in its key, a header name or value, or the error message could not be kept (PostgreSQL text refuses NUL, jsonb refuses both), so the record ended on ARV-166's unacknowledged path; `DeadLetters.Create` now replaces each with U+FFFD after cutting (a cut can split a surrogate pair), names the parts in the `ariva-dead-letter-text-replaced` header (never the characters) and keeps the topic, partition, offset and consumer exact, and `OutboxKeyOf` keys such a letter by its key's digest. (2) A dead-letter row whose send failed with a broker error ended the relay pass, so a `.dlq.v1` topic whose leader was away held events behind it for up to the 45 second produce bound, again at each retry. A pass now claims up to a batch of event rows and then up to a batch of dead-letter rows, so a backlog of dead letters cannot crowd events out, and sends the events first (rows of different topics are independent, so no key's order changes); it spends at most 5 seconds on dead letters (`OutboxRelay.DeadLetterPassBound`: each dead-letter send is bounded by what is left of them, and the rest wait for the next pass); and a dead-letter row's failure that is not its own (the broker away, the dead letters' share, a refusal such as a missing ACL) holds back its topic for a minute (`DeadLetterTopicHold`): the hold is kept on the topic's unsent rows (each due no earlier than its end, one constant statement in the pass's transaction), so no relay claims them meanwhile, whichever leads, also after a restart, while the other dead-letter topics carry on. A send cut short by the pass's own time is not the topic's fault and holds nothing. So a dead-letter topic that cannot be reached delays the events written meanwhile by at most 5 seconds once a minute, and once more each time a letter for it is kept meanwhile at a host's stop (that try holds the topic again). An event row's broker failure still ends the pass. A record's own header named like a flag is kept under `record:`, so a record cannot set the letter's flags. Not done here: escalating a broker-unavailable streak (an Error and a metric) and skipping passes while the cached broker probe answers false, from the ARV-165 review.
- Note of 2026-10-25 (ARV-177), adding to the decision without changing it, and reopening the stop side of the ARV-166 residual: MassTransit 8.5.11's Kafka consumer passes records at a stop in two ways no Ariva filter can prevent while an endpoint has more than one lane. When the bus's stop wait ends with a record still in hand, `ConsumerAgent.ActiveAndActualAgentsCompleted` cancels it (`CancelPendingConsumers`), and `BatchCheckpointer` treats a cancelled confirmation as it treats a faulted one: it moves on and commits the next completed record of the partition. And a record waiting in its lane behind one in hand when the endpoint begins to stop is never handled (`KafkaMessageConsumer.Handle` returns at once for a stopping consumer), so its confirmation is cancelled when the consumer closes and passed the same way. Both were reproduced on a real broker (backlog/progress.md, 2026-10-25): a record queued behind a 4 second one on a clean stop was consumed by neither host and the group's committed offset was past it. So holding a record in hand at a stop (ARV-177's first design) does not keep it: its confirmation had already been cancelled when the hold began (the committed offset, read 3 seconds later, was past it), and the dead letter the last attempt keeps after a host's disposal is the record's only trace, so it stays. ARV-253 takes the fix (with one lane per endpoint, records complete in fetch order, so the checkpointer never meets a completed record after an unresolved one; the alternative is Ariva's own consumer loop on the Confluent client, as Ariva.Api.Stream has). The same story: no Ariva client asks a broker to create a topic (`allow.auto.create.topics` false in `KafkaClientConfig`), a send for a missing topic fails after about 5 seconds as its own failure (`topic.metadata.propagation.max.ms` 5 seconds; at librdkafka's 30 it failed as a message timeout, which read as the broker being away) and the relay holds that topic on its rows until the failed row's backoff ends, MassTransit's rider takes the same base (`KafkaClientConfig.Rider`), and the `kafka` readiness probe asks for DescribeCluster through the producer's handle, a request that names no topic.
- Note of 2026-10-25 (ARV-253), adding to the decision without changing it, and closing the stop's passed records of the ARV-177 note: every topic endpoint's Kafka consumer has one lane (`ConcurrentMessageLimit` 1, `ConcurrentDeliveryLimit` 1 as before), and a host refuses to start with any other `Kafka:Consumers:ConcurrentMessageLimit`. With one lane a consumer's records are handled by one task executor in the order they were fetched, so the completed records of each partition are always its first ones, and `BatchCheckpointer`, which commits the last completed record it reaches, never meets a completed record after an unresolved one: a record cancelled in hand at the stop wait's end, one never handled behind it, or one left unacknowledged by the dead-letter loop stays uncommitted, and the next host consumes it. Parallelism comes from `ConcurrentConsumerLimit` instead, set from `Kafka:Consumers:ConsumersPerEndpoint` (1 to 6, default 1): that many Kafka consumers join the endpoint's group, each with its own partitions, lane, checkpointers and prefetch, and the endpoint's librdkafka fetch queue (`queued.max.messages.kbytes`, 64 MiB, librdkafka's default for one consumer) is shared out among them. Measured: the integration tests on a real broker (`QueuedAtStopTests`: with eight lanes the one-partition case committed offset 4 past the queued record at 2 every run, with one lane nothing is passed and the next host consumes it; `InHandAtStopTests`: a 20 s attempt past an 11 s stop wait, neither it nor the record behind it passed; `DeadLetterKeptAtStopTests`: the stop commits just past the poison record), and the pilot load run of 2026-10-25 21:58Z with one consumer per endpoint on 6 partitions (wiki 05): every push 202, every crossing counted, the sensing archive's lag back 18 s after the D5 burst (peak 3,413 records) where the ARV-230 runs with eight lanes took 20 s and 26 s (peaks 3,813), 205 AMAN feed records produced and every desk interval stored and mapped, nothing left in the outbox. The cost is ordering's: a retrying or stalled message now holds every partition its consumer reads, not only its key's lane, for at most its attempts (`RetryCount` + 1, 4 by default), each cut at `HandlerTimeoutSeconds`, with the retry waits between them and its dead letter's send after them: about 5 minutes at the defaults (4 times 70 s and up to 15 s of waits) and about 8 at the largest handler timeout (120 s), growing with `RetryCount` (0 to 10 since ARV-254, a host refuses to start outside them), and then by its dead letter, which since ARV-254 is kept in the outbox once the broker has refused it for a minute, so that the message completes: at most `ConsumerSettings.LongestHold`, about 6 minutes 50 seconds at the defaults, longer only while the outbox refuses the letter too (the broker is then tried for another minute, and so on), while a handler ignores its cancellation (ARV-096e), or by the inbox's rollback after a cut attempt, which runs without the attempt's token and is bounded by the database client's own timeouts (the poll interval's extra minute takes it at the defaults); `ariva.kafka.consumer_hold_seconds` and the `consumerHeld` alert show a hold past it (note of 2026-10-26 below); raise `ConsumersPerEndpoint` for a host whose groups lag. Rejected for now: Ariva's own consume loop on the Confluent client with an ordered checkpoint, as Ariva.Api.Stream has (per-key parallelism within a partition, at the price of rebuilding the rider's retry, inbox and dead-letter pipe); it stays the route if a consumer ever needs more than one record of a partition at once. Then open, closed by ARV-177a (note below): the attempt cancelled in hand runs on while the host disposes its services, and its last attempt could keep a dead letter for the valid message, which the next host processed as well (a duplicate letter, not a loss).
- Note of 2026-10-25 (ARV-177a), adding to the decision without changing it: a failure the stop caused is not dead-lettered. `DeadLetterFilter` takes a failure for the stop's when the message's own token was cancelled (MassTransit cancels it, with the record's confirmation, when the bus's stop wait ends with the message still in hand) or when its endpoint is stopping and the failure's chain holds an `ObjectDisposedException` (a service of the host's container, a connection or a session disposed under the attempt; the chain is searched to a depth of 16 and at most 256 exceptions, past which the failure is dead-lettered, a copy rather than a loss). It then throws the message's own cancellation, which MassTransit's retry passes on without another attempt and its receive pipe does not rescue, so the record is left unacknowledged; with one lane per consumer (the ARV-253 note) nothing after it completes, so it is not committed and the next host processes it. Before, the last attempt of such a message kept a dead letter for a valid event (reproduced on a real broker: `InHandAtStopTests` with no retry, a 20 s attempt past an 11 s stop wait, one kept letter; none since), which the next host's relay sent while that host processed the record too. A failure of the message's own while its endpoint stops and before the stop wait ends is still dead-lettered and kept (ARV-171): it is the message's last attempt, not the stop's.
- Note of 2026-10-26 (ARV-254), adding to the decision without changing it, and closing three lows of the ARV-253 review. (1) MassTransit 8.5.11's consume loop (`KafkaMessageConsumer.Consume`, read in its decompiled source) polls a record, then waits for a slot of its prefetch (`PrefetchCount`, 1,000), then hands the record to its lane, so once the records fetched behind a held one fill the prefetch the loop stops polling until the hold ends. librdkafka's `max.poll.interval.ms` (300 s by default; the rider did not set it) was shorter than the longest hold the settings allowed, so a long hold took the consumer out of its group and, after the rebalance, the records it had not committed were handled again (duplicates the inbox drops, not a loss). Reproduced on a real broker (`HeldConsumerTests`: a prefetch of 2 and a 20 s hold; with a poll interval of 8 s the held record was handled twice, with 40 s once). Every rider consumer's poll interval is now `ConsumerSettings.MaxPollInterval`, the longest hold and a minute (470 s at the defaults). (2) `Kafka:Consumers:RetryCount` is bounded to 0 to 10 (a host refuses to start outside them), so the settings bound the longest hold (`ConsumerSettings.LongestHold`): the attempts at their handler timeout, the retry waits at their longest, and the dead letter, whose broker refusals now end after a one minute window (`DeadLetterRetry.SendWindow`; the wait before the window's last attempt is cut to what is left of it, so that attempt starts by the window's end) by keeping the letter in the outbox, as at a stop (ARV-171), so that the message completes; only when the outbox refuses it too is the broker tried for another window. 410 s at the defaults. (3) A receive filter on each topic endpoint (`KafkaConsumerHolds`) notes when each record's receive begins and ends, which spans its attempts, the retry waits and its dead letter, and the gauge `ariva.kafka.consumer_hold_seconds` (by topic and group, never a value from the record) reports each endpoint's oldest record in hand; the chart's `consumerHeld` rule fires above `holdLimit` (420 s) for 2 minutes. The cost of the longer poll interval: librdkafka also sends it as the group's rebalance timeout, so in a rebalance (a rolling update, a scale out, a pod lost) a member held with its prefetch full delays its whole group for up to that long (470 s at the defaults where it was 300 s, about 26 minutes at ten retries of the largest handler timeout); a host refuses to start when the interval would pass a day, librdkafka's largest. Left open: while both the broker and the database refuse the letter the hold has no bound (the consumer leaves its group at the poll interval and its uncommitted records come again, duplicates and not losses), and the alert fires; a handler that ignores its cancellation (ARV-096e) and the inbox's rollback after a cut attempt, which runs without the attempt's token and is bounded by the database client's own timeouts, can also hold a little past the longest hold.
