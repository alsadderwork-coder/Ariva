# Test cadence

Owner decision 2026-10-08. Every story still passes its own gates before it is marked passing; the full suite runs at checkpoints instead of twice in every story. Measured on ARV-104b before the change: unit tests about 2 minutes plus the build, integration 8 minutes, full E2E about 11 minutes plus host start-up, Stryker about 35 minutes (an hour or more when the queue engine changed: about 12 mutants a minute on two cores, 2.5 hours for its 1,733 mutants at the 2026-10-09 checkpoint), and the full gates ran twice per story (before and after the security review's fixes).

## Per story: `node scripts/verify.mjs story`

```
node scripts/verify.mjs story --specs tests/api/validation.spec.ts,tests/functional/validation-observer.spec.ts --integration "FullyQualifiedName~Validation"
node scripts/verify.mjs story --plan     prints what it would run, runs nothing
```

The gate compares the working tree with `--base` (default `HEAD`, the uncommitted story) and decides:

| Step | When |
|---|---|
| Build, reference golden check, all unit tests (architecture, security, domain, golden replays), and the count guard that every listed case has its results (ARV-164a) and every theory listed once its rows from the project's `theory-rows.json` (ARV-251) | Always |
| Security: scanner self-test, full scan, base images, chart security, dependency audits, the E2E expect message check and the artifact check's self-test (ARV-152) | Always |
| Docs text rules | Always |
| Web: svelte-check, lint, build | When `Platform/Frontplane/Ariva.Web` changed |
| Integration, filtered by `--integration` (`FullyQualifiedName~A\|FullyQualifiedName~B`: methods whose fully qualified name holds A or B, run as the test executable's `--filter-method *A*`; ARV-164b), then the count guard over the same filter | When `Ariva.Infra` or `Ariva.IntegrationTests` changed |
| Integration, full, then the count guard (the test executable, not dotnet test, as the unit suite; ARV-164b) | When the change is wide, adds a Timescale script, or touches persistence without a filter |
| Visual regression (the `visual` project in the pinned Playwright image, ARV-188), before E2E | When `Platform/Frontplane/Ariva.Web`, the visual suite (`tests/visual`, its baselines included), the support code it imports (`tests/support`), its browser script (`scripts/visual-browser.mjs`), the E2E configuration that declares it (`playwright.config.ts`) or the Playwright pin the image must match (`package.json`, `package-lock.json`) changed |
| E2E: the story's `--specs`, the spec files it changed, and the smoke set | When backend, web, simulator or E2E code changed |
| E2E, full | When the change is wide |
| No secret in the E2E report, output and traces (ARV-152) | After every Playwright run |
| No secret in the unit and integration TRX files (ARV-252: a theory row's arguments are part of its display name) | After every unit and integration run |

The smoke set is `health`, `auth`, `security-baseline` and `permission-matrix` (API) and `shell` (functional). The permission matrix is always in because authorization is where cross-site and missing-permission defects show. The smoke set is not the release smoke suite (ARV-128, `tests/smoke`, wiki 04 section 8.1), which is the read-only check of a deployed environment; its specs are the `smoke` project of the full E2E run, and a story that changes them names them in `--specs` (`tests/smoke/<name>.spec.ts`) with `tests/api/smoke-guard.spec.ts`.

A change is wide when it reaches every host, every screen or the whole pipeline (the `WIDE` list in `scripts/verify.mjs`): `Ariva.Api.Common`, `Ariva.ServiceDefaults`, `Ariva.Di`, `Ariva.Api.Stream`; `Ariva.Core` `Security`, `Messaging`, `Queueing`, `Global.cs`, `RoleCodes.cs`, the shared domain components `Domain/Common`, `Domain/Components`, `Domain/Contracts`, `Domain/Constants`, `Domain/Criteria/BaseCriteria.cs` and `Domain/ViewModels/AdministrationViewModels.cs`, the service contracts `Services/Core`, and the project and lock file (ARV-160: the entity bases, value types such as `DisplayText`, the event base, the contracts, the shared constants, the criteria base and the paged result `PageViewModel`, `IUnitOfWork`, `ICurrentUser`, `IStorageProvider`, `ISvcMessageBus`; the per-feature entities, enums, criteria, inputs and view models stay scoped); `Ariva.Infra` `NHibernate`, `Messaging`, `Streaming`, `Security`, `DataProtection`, `Caching`, `Services/Foundation` (the service bases and the unit of work), `Settings` (the database, hosting, token and session settings, every Postgres connection, the certificate downloads), the `Timescale` classes (the schema checks and migrations every host runs at its start; a new script runs the full integration suite on its own, the table above), `Monitoring`, `Resilience` (the dependency outage answer) and the project and lock file; the simulator; the web app's `src/lib/core`, hooks and build configuration, and the shell every screen sits in (the root `+layout` and `+error.svelte`, the `(modules)` layout with the sign-in gate, the shell and `StepUpDialog`, the `(public)` layout and `PublicFrame`, `app.html`, `app.css`, the `layout` and `shared` components, the theme, `navigation.ts`, `utils.ts` and the i18n loader; the message files and page components stay scoped); the E2E configuration and `tests/support`; the solution and central package files. A renamed file counts at both its old and new paths (ARV-160), so moving a file out of a wide folder is wide too.

The security-reviewer still reviews every story. After its fixes, only the tests the fixes touch run again. A FAIL verdict is closed by a focused re-check of the fixes (the story's criteria need a PASS); a full second review runs only for a High finding or a fix that changes authorization.

The visual step (ARV-188, about 4 minutes) first makes sure the pinned Playwright image is on the machine (`node scripts/visual-browser.mjs ensure`): it reuses the image when Docker has it and pulls it otherwise (about 1.2 GB to download, 3.5 GB on disk), so no manual pull is needed; when Docker is not running or the pull is refused, the step fails with that reason and nothing renders in another browser. It runs before E2E, as at a checkpoint, because the baselines expect the demo seed: on services that earlier runs left data in, a screenshot can differ for reasons that are not the change's, so run it on fresh services. Added after ARV-181b1 (2026-10-16): the staffing panel passed its story gate and four immigration baselines then failed only in CI.

A full E2E run (a wide story or a checkpoint) needs fresh services: the suite assumes an empty database, and data left by earlier runs fails tests that create fixed names (seen 2026-10-08: seven failures, all "already exists" and duplicate rows, gone on fresh services). With `CI=true` set, a missing `helm` turns the chart security step into a failure; without it the step self-tests its rules and skips the render.

One heavy run at a time on a machine: `verify.mjs` scopes that start the hosts or Testcontainers (integration, e2e, visual, demo, rehearsal, pilot-load, zap, all, story, checkpoint) take a lock in the machine's temporary folder (`ariva-verify.lock`) and a second one refuses to start while the holder lives (a stale lock is taken over). Stryker has its own lock (`ariva-mutation.lock`, one mutation run per machine) and runs in its own worktree (see the checkpoint's step 4), so one mutation run and one heavy run may share the machine. It was added after two checkpoints started in one worktree shared the E2E ports and collided in Stryker. One integration suite at a time on a machine: the Testcontainers of two runs share the Docker host's memory and disk (seen 2026-10-08 on a 16 GB host: PostgreSQL in crash recovery, 39 failures with 57P03, and later a full disk, "No space left on device"). Before a checkpoint, check the free space; build output of old worktrees and unused images are the first to go.

## Checkpoint: `node scripts/verify.mjs checkpoint`

Runs on a committed tree (it refuses uncommitted changes) every 5 stories, at the end of each phase and before go-live (ARV-138):

1. Build, unit tests, the Release proof (the solution built in Release and NbjSiteScopeTests run there, `node scripts/verify.mjs release`, which GitHub's backend job ran on every pull request until ARV-295), security, docs, web.
2. Integration, full.
3. Visual regression (the pinned image reused or pulled, as in the story gate), then E2E in full, on fresh services (the visual baselines expect the demo seed).
4. Stryker, in a worktree of the checkpoint's commit in the machine's temporary folder (`ariva-mutation-tree`, removed afterwards; about 2 GB while it lives), after the checkpoint has released the machine lock: Stryker replaces `Ariva.Core.dll` in the unit tests' output while it runs, so in its own worktree it no longer blocks this checkout, and story gates may run meanwhile (owner decision 2026-10-09; before, a checkpoint with the queue engine changed held every story for over two hours). It uses one test session fewer than the machine's cores (at least two) and, outside Windows, runs at a lower CPU priority (`nice -n 10`), so a story gate beside it gets the CPU first (2026-10-10: an integration test timed out at 5 minutes with the load at about 20 while Stryker ran at normal priority). The first checkpoint in this form took 117 minutes for 7 engine files (94.54 percent), against 5.5 hours in the main checkout with telemetry on. Stryker mutates the engine files changed since the previous checkpoint (one `--mutate` per changed file, which replaces the configured list); in full when no checkpoint is recorded; skipped when no engine file changed. Stryker's own `--since` mode ended silently after its coverage capture with the MTP runner on 2026-10-08, so it is not used. The step fails when Stryker puts any method in safe mode, prints no final score or reports fewer tests found than the worktree's unit test build lists, even if Stryker exits zero (ARV-069a and ARV-164a, `scripts/mutation-run.mjs`; the rule that avoids safe mode is in wiki 16). Stryker 5.0's MTP runner captures coverage one test at a time and allows each test 1.5 times its initial run time plus `additional-timeout`, at least 30 seconds. When a test runs past that, the runner kills its test server, but keeps waiting for the dead server's coverage relay: every later test on that runner then waits 10 seconds and is marked Dubious, and with all its runners in that state a run takes days (2026-10-23: `QueueEnginePositionRunTests`' hall zone test, 5 seconds alone, ran past 30 seconds with the queue engine's coverage recorded; 7,051 tests went Dubious at about 1,025 an hour, with or without a gate beside it). `additional-timeout` is therefore 120 seconds in `stryker-config.json`: the same run captured all 7,070 tests in 23 minutes with none Dubious. It also lengthens the wait before a mutant that loops is counted as a timeout. A run whose log shows "Test run timed out while capturing per-test coverage" has hit this again: find the test (`Ariva.UnitTests --filter-uid <id> --output Detailed` names it) and make it lighter or raise the value.

While no checkpoint is recorded, `--mutation-base <commit>` names an earlier checkpoint run whose mutation step passed although another step failed: the rerun tests mutation only on engine code changed since that commit, and `checkpoint.json` records the base, so a fix to an unrelated step does not repeat a run of an hour or more.

When everything passes it writes `backlog/checkpoint.json` (commit, date, platform since ARV-295, stories since the previous checkpoint, per-step results), which is committed as "Checkpoint: full suite green". The story gate prints how many stories have passed since the last checkpoint and says when one is due; the next story does not start until it has run.

A checkpoint failure is fixed before the next story starts. Each story is its own commit, so the failing change is one of at most five.

## Live pipeline: `node scripts/verify.mjs demo`, `rehearsal` and `pilot-load`

Three scopes run in real time through the whole pipeline, Ariva.Api.Stream included, which the E2E suite does not start: two play the reference evening (seed 9303 at the demo airport DMO), the third puts the pilot hall under load. They run at the end of each phase and before go-live (ARV-138), on fresh services, never in a story gate or a checkpoint: the demo and the rehearsal take about two hours each, the pilot load run about 25 minutes, each holds the machine lock, and none has anything a story could shorten. Run `pilot-load` also after a change to the stream engine's state, the ingest path, the hub or a host's resources, and on the site's hardware before sizing a BOQ on it (wiki 05).

## Secrets in test reports and artifacts (ARV-152)

Playwright uses an expect's custom message as the step title even when the assertion passes, and the HTML report keeps every step title; the same goes for a `fill`, whose title is `Fill "<value>"`, and for a request context's call or a navigation, whose subtitle is the URL with its query. Before ARV-152, `expect(x.status(), await x.text())` in 60 spec and support files copied answers into the report: device and display credentials, integration client secrets, temporary passwords, TOTP seeds and the sign-ins' tokens; every functional spec wrote its account's password and TOTP codes there, and two probes put a JWT there through a query string. Four things keep the report and the test output clean:

1. `expectStatus(answer, status, message?)` and `expectStatusIn(answer, statuses, message?)` (`tests/support/expect-status.ts`) check a status and put the answer into the message only when the status is wrong, redacted by `redactSecrets` (`scripts/secret-shapes.mjs`, the shapes the artifact check looks for: secret JSON members, plain or JSON-escaped, string, array or object valued; `access_token=`, `password=`, `key=` and the like in a query, fragment or form body; `ardk_`, `ardp_`, `ics_`, JWTs, bearer values, otpauth seeds, temporary passwords, recovery codes), with at most 2,000 characters quoted. `{ soft: true }` makes either soft. A check that is not about a status keeps the answer out of the message and lets the matcher show it on failure (for example `expect(review, 'the profile is publishable').toEqual(expect.objectContaining({ publishable: true }))`). The support helpers that throw on a wrong status (`airports.ts`, `smoke-site.ts`) quote the answer through `redactSecrets` too.
2. `fillSecret(field, value)` (`tests/support/web-auth.ts`) types a password, a TOTP code, a recovery code or a key: it waits for the field to be visible and editable, then sets the value in the page and dispatches `input` and `change` (which Svelte 5's bindings listen to), so the step's title is "Evaluate". `fillSignIn` and every step-up, account and setup code field use it. It keeps the value out of step titles only: a failed page's error context (the ARIA snapshot Playwright writes next to the error) lists input values, password fields included, and a trace records the call's argument; for those the artifact check is the backstop.
3. A request that carries a token, a key or a password in its query goes through Node's fetch (`call` in `tests/support/accounts.ts`, which records no step), never a request context. A navigation may carry a display key only in the fragment (`#key=`) of an absolute address (`${webUrl}/display?...#key=...`): Playwright leaves the fragment out of the step only when the address parses on its own, and keeps a relative one (`/display?...#key=...`) whole. The report also keeps the lines around each step as its snippet, so a made-up token or key is built at run time (`['eyJ...', 'e30', 'c2ln'].join('.')`, `'sim-guess-'.padEnd(35, '0')`), never written out on a source line.
4. Two checks. `node Platform/Testing/Ariva.E2E/scripts/expect-messages.mjs` reads code only (comments and strings masked) and fails when an expect message, a step title, an annotation, an attachment or console output holds a `.text()`, `.json()` or `.body()` call, a `.body` property, a secret-named member or variable (`credential`, `clientSecret`, `totpSecret`, `temporaryPassword`, `password`, `secret`, `accessToken`, `refreshToken`, `recoveryCodes`, the credential keys, `jwt`, `token` and names ending in `Token`, and `process.env` keys, secrets, passwords, tokens and seeds), an answer's `.url()` (its query may carry a token; `whereOf` in `tests/support/api-assertions.ts` leaves it out, as `expectProblemDetails` and `expectApiSecurityHeaders` now do), or a variable whose latest binding holds an answer or a secret, one step removed included (a template or a `+` concatenation that carries one); when a value typed with `fill`, `type`, `pressSequentially` or `insertText` is such a secret (their step title is `Fill "<value>"`: use `fillSecret`); when a request context's call or a navigation puts a secret parameter (`access_token=`, `token=`, `key=`, `secret=`, `password=` and the like, whatever its value, a literal included) or a token, credential, secret or key into its address's query, or into the fragment of a relative address; and when a source line holds a secret's shape (`scripts/secret-shapes.mjs`). An address is read from the argument, the latest binding of the name it starts with, the body of the function that binding calls, and every definition of the member it ends with (in the file, else in the support files); a member or a call it cannot read at all is flagged. A field read from an answer (`(await r.json()).id`) is a value of its own. Since ARV-249 it also fails when an expect's subject or its matcher's argument is such a secret, or a call named for one (`response.refreshCookie()`, `totpCode(...)`), a variable bound to a `process.env` key, secret, password, token or seed, the text of an element that reveals one (`credential-value`, `credential-reveal`, `totp-secret`, `recovery-codes`), or a request's `authorization` or `cookie` header (a failing matcher prints both: `Expected substring: not "..."`, `Received string: "..."`), unless the matcher prints nothing of a secret subject (`toBeTruthy`, `toBeDefined`, `not.toBeNull`, `not.toBeUndefined`, `not.toBeFalsy`); a spec asserts a secret as a boolean, a count or a shape (`expect(text.includes(secret)).toBe(false)`, `expect(recoveryCodes.length).toBe(10)`, `expect(/^ics_/.test(secret)).toBe(true)`, `expect(a.refreshCookie() === b.refreshCookie()).toBe(true)`), and a page's address by its parts (`expect.poll(() => new URL(page.url()).hash.includes('key=')).toBe(false)`, since a failing `not.toHaveURL` prints the address and its key); a web-first text matcher (`toHaveText`, `toContainText`, `toHaveValue`) on the element that reveals a secret fails too, since it prints the element's text: assert on a child that holds none (its title). A secret's boolean comes before any other assertion on the same text, since the first failure is the one printed. Since ARV-224 an address (a request context's call, `goto`, `waitForURL`, `waitForRequest`, `waitForResponse`, `route`, `unroute`) is also read down to where it comes from: a name through its binding, every assignment of a variable included (`+=` read as a concatenation); a parameter through the call being read or every call of its function in the file (a list method's callback through the list's elements; a function passed on as a value, or any other anonymous callback, is not read); a member through the object literal it comes from; an element through its list (a list literal, `Object.values`, `entries` or `keys` of an object literal, `filter`, `slice`, `map`); a call through what its function returns (every function of that name in the file, or one a support module exports); and `??`, `||`, `&&` and `?:` through every branch. A name set by a destructuring assignment, or whose object or list the file changes (a member or element set, `push` and the other mutating methods, `Object.assign`), is not read, and a change made through another name is not seen. Its leading part must end in a literal, a regular expression, a predicate, a `new RegExp(...)` pattern or an origin: a name imported from a support module (`../support/<name>`), named as one (`webUrl`, `hosts`, `apiHosts`) and exported as a `const` the module never changes, or a member of one, a reviewed export (`REVIEWED_ORIGINS`: the smoke suite's `target.base`), or the `baseURL` fixture of a test's or a hook's callback; a name that only looks like an origin, or comes from another module, is not one. One that comes from anything else (a value read from the page or an answer, an unbound name, a callback's parameter) fails, since it could carry a server-issued credential such as a display's key: build the address from literals and an imported origin, as `playerUrl()` in `tests/functional/displays.spec.ts` does. The address is absolute when its leading part is an origin or `http(s):`; its later parts are inlined when they resolve and otherwise read for secrets only (a secret value anywhere; in the query or fragment also a quoted secret or a name that looks like one; the smoke suite's `credential(credentialVariables.displayCode)` reads a display's code, which is not a secret), which leaves a server-issued value under a neutral name there to review. Parameters are read across all the parts: a secret parameter (`key=`, `token=`, `access_token=`, `session=` and the like) fails in the query, and in the fragment unless the address is absolute and its step drops the fragment (`goto` and the request calls do; the waits and routes keep their argument whole). A request's options must be an object literal, or a name bound to one that nothing changes afterwards, with no spread or computed name, and its `params`, which Playwright joins to the query, may not name, hold, spread or compute a secret. In a file whose addresses name a secret parameter no matcher may take an address by value: `toHaveURL`, or any subject holding a `.url()` read (a page's, a frame's, a request's) or a `location` read in `page.evaluate`, however it is cut or wrapped (`split`, `slice`, `replace`, `decodeURIComponent`, a template, an object, a spread), a name in it that may hold one (through any number of bindings, a loop's list, or as a parameter the argument at each call of its function or a list callback's list; past 40 steps the check fails closed), or a call of the file's or a support module's function that returns one, unless its outermost operation (or that name's own use) gives a boolean or a number (`includes`, `startsWith`, `has`, `test`, a comparison, `length`; not `&&`, `||` or `??`, which give an operand) or reads the pathname, origin, host, hostname, protocol, port, the search parameters' names or a search parameter that is not a secret's; assert a boolean such as `new URL(page.url()).hash.includes('key=')`. In any file a matcher argument that names a secret parameter or a secret's prefix (`ardp_`, `ardk_`, `ics_`), or a matcher on `searchParams.get` of a secret parameter, fails. Not read: a navigation a support helper makes (the flag is per file), an address set inside `page.evaluate`, `newContext({ baseURL })`, `goto`'s `referer`, the parameters of a function passed on as a value or of an object's or a class's method, a helper of a module the check does not read; a binding is the latest one before its use whatever its scope, and a support module is found by its base name. Its `--self-test` proves it fires on 248 bad patterns and stays quiet on 112 good ones (support modules stood in by three samples), and finds 4 literal shapes on source lines while 4 values built at run time pass; the helper and the smoke suite's leak probe (which leaks a made-up password on purpose, ARV-128) are left out, and the source-line rule leaves out `global-teardown.ts`, which runs outside every test (no step's snippet shows it) and checks the log scan's own rule on a made-up code. `node Platform/Testing/Ariva.E2E/scripts/artifact-secrets.mjs` scans the report (with the zip it embeds), the test output (trace zips, error contexts, attachments) and, in CI, the run's log and the hosts' logs for device and display credentials, integration client secrets, JWTs, bearer and `access_token` values, TOTP seeds (otpauth URIs, `totpSecret` members), recovery codes and temporary passwords (as answers carry them and on their own shapes, as a dialog or an error context shows them: letters and digits mixed, so prose is not one, and any code in the sign-in or step-up recovery field (`textbox "Recovery code": ...`, English and Arabic labels)), TOTP codes where a TOTP label precedes them (a `code` JSON member, a fill of a code field, or a code field's value in an error context's ARIA snapshot, `textbox "Authenticator code": 493817`, by the web app's English and Arabic labels: the server issues no other six-digit code), and by exact value the run's E2E account passwords and TOTP seeds (derived from `ARIVA_E2E_ACCOUNT_SEED` as `accounts.ts` derives them), the run's other secrets (the simulator, mock AMAN, ACRIS and Cronz keys and the validation reader's password: `playwright.config.ts` keeps a value it is given, so `verify.mjs` and CI derive them from the same seed in the config's formats and give them to the run, and the check knows them), the seed, the database passwords and what the run wrote to `.e2e-keys`; it names the file and the kind, never the value, and a zip it cannot read is a finding. Values made of URL-safe characters are found through a set lookup over the text's runs of such characters, so hundreds of megabytes of host logs take seconds. Its `--self-test` puts each kind in a plain file, a report's embedded zip, a trace zip, a zip inside a zip and an error context, passes a clean set, refuses an unexpanded `$(NAME)` as a seed, and proves `redactSecrets` clears each secret sample and keeps plain text. `node scripts/security/secret-assertions.mjs` (ARV-249) holds the C# tests to the same rule: it reads each `.Should()` with its subject and the assertions chained after it, and fails on a secret subject asserted with anything but `NotBeNull`, `NotBeNullOrEmpty`, `NotBeNullOrWhiteSpace`, `NotBeEmpty`, `BeTrue`, `BeFalse` or a delegate's exception assertions, or on a secret among an assertion's arguments (an expected value, a because argument), since a failing FluentAssertions assertion prints both into the test log, the TRX file and CI's log; a secret is read from its name (one ending in Password, Secret, Credential, a compound Token such as AccessToken, Jwt, ApiKey, the key kinds, RecoveryCode, TotpCode, TotpSeed or TotpUri, a variable named `token`), an index, range or substring of one, a concatenation, interpolation, `??` or `?:` that carries one, a call that issues one, computes a TOTP code or reads a protected value back (`Unprotect`), and a read of a secret JSON member (`GetProperty("clientSecret")`), a secret header (`GetValues("X-TOTP-Code")`, `X-Api-Key`) or the Authorization header; it masks comments, preprocessor lines and every kind of string literal (verbatim, interpolated, raw), reads string literals and initializers as subjects, fails on an assertion whose subject it cannot read, and fails when it finds fewer than 100 files in the unit and integration test projects; its `--self-test` proves it fires on 61 bad patterns and stays quiet on 56 good ones. As a residual, a name, a JSON member, a header or an element read is the heuristic (the C# check follows no data flow), so a secret held under another name (a seed called `Seed`, a planted canary, a refresh token called `successor`), a container asserted by shape whose failure would print the secret it holds (an answer or a page that should not contain one, asserted with `not.toContain` on a plain value) and literal made-up values in the source (`"refresh-secret"`, `"correct horse"` in `RedactionEnricherTests`) are held by review, not by the checks. All three run in the security step of `verify.mjs`, in CI's security gate and in the Azure DevOps pipeline's security steps.

`verify.mjs` gives every Playwright run it starts (e2e, visual, demo, rehearsal, zap, and those of story and checkpoint) an account seed of its own, unless the caller set one, and runs the artifact check on the run's folders when it ends (for zap, `zap-reports` too); `node scripts/verify.mjs artifacts` runs it alone on what a run left. CI (`github_archived/workflows/ci.yml`) sets a seed for the e2e job, exports the run's derived secrets (`artifact-secrets.mjs --env github`) and masks the seed and every value derived from it (`--mask github`), so a failing assertion that prints a password shows `***` in the public log; it runs the check after the visual run and after the suite (the suite's check reads the hosts' logs as well), and uploads the visual differences, posts the failure comment and uploads the Playwright report only when it passed; a finding fails the job instead. CI's backend job (ARV-252) runs the unit and integration suites with their output, which carries the in-process hosts' console logs, written to `unit.log` and `integration.log` and not to the job log, each suite ended by coreutils `timeout` (14 and 27 minutes, with its process group) a minute before its step's own timeout, which would end only the step's shell and leave the suite writing on; the job's limit is 60 minutes. The test log check then copies both logs, the TRX files and the AMAN pact to `checked/` and checks that copy (no seed there: the shapes and the other values); every later step reads and uploads the copy alone, so nothing written after the check reaches them, and only once the check has passed are the logs printed (between `::stop-commands::` with a random token and its resume on a line of its own, so no log line is read as a workflow command), their last lines and failing tests quoted in the step summary and the pull request comments (backticks taken out, so a line cannot end the code block), and the TRX files and the pact uploaded; a finding fails the job and none of it is shown. The count guards run before the check and print case names only; a failed listing's output goes through `redactSecrets`. `backendLogWiring` in the same script holds that wiring step by step, comments left out: every suite step writes to its log alone under a timeout of its own and comes before the check, the check runs after a failed suite, cannot continue on an error and checks the copy, and every later step names the copy only, waits for the check's success and prints with commands stopped. Its `--self-test` plants a device credential in a host's JSON log line and in a TRX's output (found, named by file and kind, never printed; the hosts' usual lines pass) and fails on twenty-one miswirings (a suite teed, run again after the check, run through `dotnet test` or without a timeout; the check before a suite, skipped by a failed suite, continuing on an error (`set +e`, `set +o errexit`, `set +eu`, a shell of its own, since ARV-271) or reading the logs in place; a copy that keeps links (since ARV-271 the check copies with `cp -RL`); a log read in place, quoted unchecked, printed with commands live or resumed on a log line; a result uploaded unchecked or from outside the copy; a gate written in a comment or joined by `||`). Since ARV-271 the same self-test holds the mutation workflow (`mutationLogWiring`: Stryker's output written to its log file only, `ARIVA_MUTATION_QUIET`, not to the public job log; the log and the report copied to `checked/` with links followed, checked, and uploaded from the copy only once the check passed; no step reads them in place; thirteen miswirings refused) and the E2E job's failure comment (`e2eCommentQuotes`: every quoted log line loses its backticks). Since ARV-271a the workflow text these checks guard is pinned, whole jobs at a time, by a hash of its text in `PINS` (in `artifact-secrets.mjs`; its lines as they are, an action's commit SHA and an image's digest as placeholders so the bots' pin bumps pass): every job whose token can post where people read it (`pull-requests`, `issues`, `contents` or `discussions` write, `write-all`, or no permissions at all, the repository's default), which today are CI's backend and e2e jobs, `images.yml`'s build, `security-scan.yml`'s trivy, `base-images.yml`'s resolve and Claude's two; the mutation job; and the security gate that runs this self-test; with each, its workflow's text outside `jobs:` (`on`, `permissions`, `env`, `defaults`). Any edit of a pinned job or header, a step added to it included, fails the self-test (CI's security gate and `verify.mjs`) until its hash is changed with it, so the change shows in that file's diff for review (`--pins` prints the hashes as they are); a job that can write and is not pinned fails, a pinned job may use no local action (its file is not pinned), and a route to a pull request comment found in a job that is not pinned (`gh pr|issue comment`, `review`, `edit` or `create`, `gh api` on comments, reviews or GraphQL, GitHub's API by URL, a comment, script or Claude action, a local action) fails as well, a tripwire for a job posting with a token of its own. The workflows are read failing closed, since the reader is not a YAML parser: a plain `jobs:` key (a comment after it allowed), plain job keys at two spaces (an id may start with `_`), each job's own keys plain and at four spaces with a `steps:` block whose items start at six, permissions as `read-all`, `write-all`, `{}` or a block of `<scope>: read|write|none` lines (anything else, a flow mapping or a quote, counts as writing), no setting after `jobs:` (it would sit outside the pinned header), no job twice, no YAML anchor, alias or merge key, steps as a plain block and no reusable workflow; anything else fails. Left to review: the scripts the pinned jobs run (`artifact-secrets.mjs` itself, `mutation-run.mjs`, `test-count-guard.mjs`, `base-images.mjs`, `verify.mjs`), an action's commit SHA (the placeholder takes any SHA of the same action: Dependabot proposes them and review reads them), what other jobs of a workflow share with a pinned one (caches and artifacts), a token of a job's own posting by a route the tripwire does not know, and an edit made to pass the text checks below. The checks under the pins read the shell as text, so they are tripwires that an edit made to pass them can word around; review stays the control for such an edit. They read a run block's comments as the shell does (a `#` inside quotes is text, a quote over several lines included) and a step's gate only at its own level and exactly (none under `with:` or `env:`); require each check line to be its script's last line at its own level, in a script with no function, `exit`, `exec`, `return`, `trap`, `kill`, here-document, alias or the like, `PATH` change or job left in the background; and refuse a path through `checked/../` and a write into `checked/` after the check (a redirection by any path, tee, copy, move, link, unpack, in-place edit or `cd`). In the backend job they refuse the test results or a log named through a variable or a glob read before the check (the count guards' `--trx` aside), a checked log named outside a step's `LOGS_CHECKED` block (followed by its `if` and `fi` keywords, not its indentation), `LOGS_CHECKED` set in the step and a here-document there; in the mutation job they require the run to be its step's one command and the only step running the gate or Stryker, and refuse any other step naming `.verify` or `checked/`. The comment check (`commentQuotes`) splits a script into pipelines as the shell does (quotes, `$'...'` and escapes read; inline variables and the shell's keywords looked through) and reads every one that writes a comment's body file (its groups, subshells, ifs and loops redirected into it, and its single redirections, by any path): any command but `echo`, `printf`, a test, `grep -q`, an assignment, `set` with an option or a loop's head ends with `tr -d '\140'` and writes nothing before that filter, and `gh` reads nothing there. A step that posts is read whole: no function, alias or the like, `PATH` change, tee, `exec`, here-document or command substitution; exactly one `gh ... comment --body-file <file>` (no `--body`, `-F` or stdin); no copy or edit into the file; and only the token, the number, the repository check, the image and the check's outcome from the workflow in its environment (never a pull request's title). It holds both CI failure comments, the test counts comment (its Test counts step's lines into `test-summary.md`, its post step exactly that post, no other step naming the file) and every other workflow's comment step. The self-test refuses each edit the story names and both review rounds' variants (more than sixty cases): through the checks where they can read it, and through the pins any edit of a guarded job or header, a same-named copy of a step, a PATH, environment or workflow variable change, a step added between a check and what it guards, the self-test's own step removed, a job that can write and is not pinned (spelled in any of the ways the third round of review tried: a comment after a key, a quoted key or value, flow-style permissions, `contents: write`), a setting after `jobs:`, a job twice, an anchor, a reusable workflow, a blank after a line's `\`, a comment route outside the pinned jobs, a local action in one and a workflow whose jobs or steps are laid out otherwise than the checks read. ## What this trades

A regression outside a story's own area is found at the next checkpoint, up to four stories later, instead of at once. The wide list sends the changes most likely to cause that through the full suites at the story itself.
