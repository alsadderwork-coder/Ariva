# Test cadence

Owner decision 2026-10-08. Every story still passes its own gates before it is marked passing; the full suite runs at checkpoints instead of twice in every story. Measured on ARV-104b before the change: unit tests about 2 minutes plus the build, integration 8 minutes, full E2E about 11 minutes plus host start-up, Stryker about 35 minutes (an hour or more when the queue engine changed: about 12 mutants a minute on two cores, 2.5 hours for its 1,733 mutants at the 2026-10-09 checkpoint), and the full gates ran twice per story (before and after the security review's fixes).

## Per story: `node scripts/verify.mjs story`

```
node scripts/verify.mjs story --specs tests/api/validation.spec.ts,tests/functional/validation-observer.spec.ts --integration "FullyQualifiedName~Validation"
node scripts/verify.mjs story --plan     prints what it would run, runs nothing
```

The gate compares the working tree with `--base` (default `HEAD`, the uncommitted story) and decides:

| Step | When |
|---|---|
| Build, reference golden check, all unit tests (architecture, security, domain, golden replays) | Always |
| Security: scanner self-test, full scan, base images, chart security, dependency audits, the E2E expect message check and the artifact check's self-test (ARV-152) | Always |
| Docs text rules | Always |
| Web: svelte-check, lint, build | When `Platform/Frontplane/Ariva.Web` changed |
| Integration, filtered by `--integration` | When `Ariva.Infra` or `Ariva.IntegrationTests` changed |
| Integration, full | When the change is wide, adds a Timescale script, or touches persistence without a filter |
| E2E: the story's `--specs`, the spec files it changed, and the smoke set | When backend, web, simulator or E2E code changed |
| E2E, full | When the change is wide |
| No secret in the E2E report, output and traces (ARV-152) | After every Playwright run |

The smoke set is `health`, `auth`, `security-baseline` and `permission-matrix` (API) and `shell` (functional). The permission matrix is always in because authorization is where cross-site and missing-permission defects show. The smoke set is not the release smoke suite (ARV-128, `tests/smoke`, wiki 04 section 8.1), which is the read-only check of a deployed environment; its specs are the `smoke` project of the full E2E run, and a story that changes them names them in `--specs` (`tests/smoke/<name>.spec.ts`) with `tests/api/smoke-guard.spec.ts`.

A change is wide when it reaches every host, every screen or the whole pipeline (the `WIDE` list in `scripts/verify.mjs`): `Ariva.Api.Common`, `Ariva.ServiceDefaults`, `Ariva.Di`, `Ariva.Api.Stream`; `Ariva.Core` `Security`, `Messaging`, `Queueing`, `Global.cs`, `RoleCodes.cs`; `Ariva.Infra` `NHibernate`, `Messaging`, `Streaming`, `Security`, `DataProtection`, `Caching`; the simulator; the web app's `src/lib/core`, hooks and build configuration; the E2E configuration and `tests/support`; the solution and central package files.

The security-reviewer still reviews every story. After its fixes, only the tests the fixes touch run again. A FAIL verdict is closed by a focused re-check of the fixes (the story's criteria need a PASS); a full second review runs only for a High finding or a fix that changes authorization.

A full E2E run (a wide story or a checkpoint) needs fresh services: the suite assumes an empty database, and data left by earlier runs fails tests that create fixed names (seen 2026-10-08: seven failures, all "already exists" and duplicate rows, gone on fresh services). With `CI=true` set, a missing `helm` turns the chart security step into a failure; without it the step self-tests its rules and skips the render.

One heavy run at a time on a machine: `verify.mjs` scopes that start the hosts or Testcontainers (integration, e2e, visual, demo, rehearsal, pilot-load, zap, all, story, checkpoint) take a lock in the machine's temporary folder (`ariva-verify.lock`) and a second one refuses to start while the holder lives (a stale lock is taken over). Stryker has its own lock (`ariva-mutation.lock`, one mutation run per machine) and runs in its own worktree (see the checkpoint's step 4), so one mutation run and one heavy run may share the machine. It was added after two checkpoints started in one worktree shared the E2E ports and collided in Stryker. One integration suite at a time on a machine: the Testcontainers of two runs share the Docker host's memory and disk (seen 2026-10-08 on a 16 GB host: PostgreSQL in crash recovery, 39 failures with 57P03, and later a full disk, "No space left on device"). Before a checkpoint, check the free space; build output of old worktrees and unused images are the first to go.

## Checkpoint: `node scripts/verify.mjs checkpoint`

Runs on a committed tree (it refuses uncommitted changes) every 5 stories, at the end of each phase and before go-live (ARV-138):

1. Build, unit tests and security, docs, web.
2. Integration, full.
3. Visual regression, then E2E in full, on fresh services (the visual baselines expect the demo seed).
4. Stryker, in a worktree of the checkpoint's commit in the machine's temporary folder (`ariva-mutation-tree`, removed afterwards; about 2 GB while it lives), after the checkpoint has released the machine lock: Stryker replaces `Ariva.Core.dll` in the unit tests' output while it runs, so in its own worktree it no longer blocks this checkout, and story gates may run meanwhile (owner decision 2026-10-09; before, a checkpoint with the queue engine changed held every story for over two hours). It uses one test session fewer than the machine's cores (at least two) and, outside Windows, runs at a lower CPU priority (`nice -n 10`), so a story gate beside it gets the CPU first (2026-10-10: an integration test timed out at 5 minutes with the load at about 20 while Stryker ran at normal priority). The first checkpoint in this form took 117 minutes for 7 engine files (94.54 percent), against 5.5 hours in the main checkout with telemetry on. Stryker mutates the engine files changed since the previous checkpoint (one `--mutate` per changed file, which replaces the configured list); in full when no checkpoint is recorded; skipped when no engine file changed. Stryker's own `--since` mode ended silently after its coverage capture with the MTP runner on 2026-10-08, so it is not used. The step fails when Stryker puts any method in safe mode or prints no final score, even if Stryker exits zero (ARV-069a, `scripts/mutation-run.mjs`; the rule that avoids safe mode is in wiki 16). Stryker 5.0's MTP runner captures coverage one test at a time and allows each test 1.5 times its initial run time plus `additional-timeout`, at least 30 seconds. When a test runs past that, the runner kills its test server, but keeps waiting for the dead server's coverage relay: every later test on that runner then waits 10 seconds and is marked Dubious, and with all its runners in that state a run takes days (2026-10-23: `QueueEnginePositionRunTests`' hall zone test, 5 seconds alone, ran past 30 seconds with the queue engine's coverage recorded; 7,051 tests went Dubious at about 1,025 an hour, with or without a gate beside it). `additional-timeout` is therefore 120 seconds in `stryker-config.json`: the same run captured all 7,070 tests in 23 minutes with none Dubious. It also lengthens the wait before a mutant that loops is counted as a timeout. A run whose log shows "Test run timed out while capturing per-test coverage" has hit this again: find the test (`Ariva.UnitTests --filter-uid <id> --output Detailed` names it) and make it lighter or raise the value.

While no checkpoint is recorded, `--mutation-base <commit>` names an earlier checkpoint run whose mutation step passed although another step failed: the rerun tests mutation only on engine code changed since that commit, and `checkpoint.json` records the base, so a fix to an unrelated step does not repeat a run of an hour or more.

When everything passes it writes `backlog/checkpoint.json` (commit, date, stories since the previous checkpoint, per-step results), which is committed as "Checkpoint: full suite green". The story gate prints how many stories have passed since the last checkpoint and says when one is due; the next story does not start until it has run.

A checkpoint failure is fixed before the next story starts. Each story is its own commit, so the failing change is one of at most five.

## Live pipeline: `node scripts/verify.mjs demo`, `rehearsal` and `pilot-load`

Three scopes run in real time through the whole pipeline, Ariva.Api.Stream included, which the E2E suite does not start: two play the reference evening (seed 9303 at the demo airport DMO), the third puts the pilot hall under load. They run at the end of each phase and before go-live (ARV-138), on fresh services, never in a story gate or a checkpoint: the demo and the rehearsal take about two hours each, the pilot load run about 25 minutes, each holds the machine lock, and none has anything a story could shorten. Run `pilot-load` also after a change to the stream engine's state, the ingest path, the hub or a host's resources, and on the site's hardware before sizing a BOQ on it (wiki 05).

| Scope | What it proves | Default run |
|---|---|---|
| `demo` (ARV-064) | The three scripted events on the live screens, each for the role that owns it: R-001 at 18:05, S-17 offline at 18:20, R-004 at 19:10 | 17:40 to 19:40 with up to 14 minutes before it, about 2 hours 15 minutes |
| `rehearsal` (ARV-104j) | Ariva's own measurements against independent ground truth: the simulator's observers capture counts, tracer runs and desk states through the capture API, two campaigns (no error, 6 percent on `A-VIS entry`) are closed with step-up and their results frozen, and every criterion is judged from what Ingest, Stream and Cronz stored. The test writes nothing to the database | the window 18:00 to 19:30, played from 10 to 24 minutes before it to an hour past it, rehearsed 15 minutes after it: about 2 hours 15 minutes with the setup |
| `pilot-load` (ARV-124a) | The pilot hall under load through Ingest, Kafka, Stream, Integration (AMAN's feed) and Main: 30 T3 sensors, 20 desks and 6 e-gates on AMAN's feed, 50 screens and 10 boards for 5 minutes, the D5 burst (100 sensors, 15,000 positions a second) for a minute with a flooding device and bodies over 256 KB, then the recovery until Stream's lag is back; AUH-TA's seeded sensors play beside it. Two tests on one run: the first fails on any 5xx or transport error (a connection reset included, on the flooding device too: ARV-233 found and fixed their cause), a push without exactly one outcome, an accepted push with events Ingest refused, a limit that does not answer 413 with `Connection: close` or 429 with Retry-After, a measured device refused, a screen that cannot join or gets no snapshot of a zone from Stream, or a board that does not answer; the second is Stream's capacity (it runs throughout, its queue engine catches up after the burst, every zone's stored watermark passes the run's end within 5 minutes, and it counts at least 98 percent of the crossings Ingest accepted on every zone; the harness exits 2 when only capacity falls short), passing since ARV-230 (with ARV-232's connection bounds; ARV-124a closed with its run of 2026-10-22). Its report and measurements (stream state sizes, the desk feed state, the outbox, the archive, Redis, the staffing job's run durations) feed wiki 05's sizing notes | about 25 minutes with the provisioning (`ARIVA_LOAD_STEADY_SECONDS`, `ARIVA_LOAD_BURST_SECONDS` and `ARIVA_LOAD_RECOVERY_SECONDS` reshape it) |

`ARIVA_DEMO_START` and `ARIVA_DEMO_END` (demo minutes) shorten either run: for the demo the minutes it plays, for the rehearsal the window it rehearses (quarter hours, 30 to 240 minutes; a window without 18:15 leaves S-17's outage unchecked). The rehearsal writes `rehearsal-record.json` (both campaigns' content hashes, every criterion's value and verdict, the comparison behind them, the outages Stream recorded and the availability ledger's unavailable minutes) to its test output and attaches it to the report; its assertions on the criteria are soft, so one run lists every criterion that misses its target (a window over S-17's outage without it in the truth, and a read of the outages or the ledger that reaches its bound, stop the run at once). The rehearsal reads the outages, the ledger, the queue bins and the first live minute (`zone_outage`, `availability_minute`, `queue_bin`, `queue_minute`) in a read-only transaction with the hosts' runtime login (`Database__Username` and `Database__Password`, a member of `ariva_runtime` only), never the migration login: script 0001's default privileges let `ariva_runtime` select from every table the migration login creates, and scripts 0018, 0019 and 0042 take back only deletes, truncates and some updates, so the runtime login reads all four. It checks that before the evening plays (with `has_table_privilege`), so a missing grant fails the run in its first minute, not after two hours. It also reads both observer accounts through the admin users API, at the start and again right before the simulator receives them: each has the Validation observer role and no other, and DMO as its only site. The counts of both campaigns come from exactly those two accounts and never from the manager who planned, started and closed the campaign. Like every Playwright run of `verify.mjs`, either scope ends with the artifact check of the next section. A criterion that fails there is a finding about Ariva's engines or the harness, recorded and decided by the owner, never a threshold to loosen. The record of the reference run is [the validation rehearsal record](../product/validation-rehearsal-record.md).

## Secrets in test reports and artifacts (ARV-152)

Playwright uses an expect's custom message as the step title even when the assertion passes, and the HTML report keeps every step title; the same goes for a `fill`, whose title is `Fill "<value>"`, and for a request context's call or a navigation, whose subtitle is the URL with its query. Before ARV-152, `expect(x.status(), await x.text())` in 60 spec and support files copied answers into the report: device and display credentials, integration client secrets, temporary passwords, TOTP seeds and the sign-ins' tokens; every functional spec wrote its account's password and TOTP codes there, and two probes put a JWT there through a query string. Four things keep the report and the test output clean:

1. `expectStatus(answer, status, message?)` and `expectStatusIn(answer, statuses, message?)` (`tests/support/expect-status.ts`) check a status and put the answer into the message only when the status is wrong, redacted by `redactSecrets` (`scripts/secret-shapes.mjs`, the shapes the artifact check looks for: secret JSON members, plain or JSON-escaped, string, array or object valued; `access_token=`, `password=`, `key=` and the like in a query, fragment or form body; `ardk_`, `ardp_`, `ics_`, JWTs, bearer values, otpauth seeds, temporary passwords, recovery codes), with at most 2,000 characters quoted. `{ soft: true }` makes either soft. A check that is not about a status keeps the answer out of the message and lets the matcher show it on failure (for example `expect(review, 'the profile is publishable').toEqual(expect.objectContaining({ publishable: true }))`). The support helpers that throw on a wrong status (`airports.ts`, `smoke-site.ts`) quote the answer through `redactSecrets` too.
2. `fillSecret(field, value)` (`tests/support/web-auth.ts`) types a password, a TOTP code, a recovery code or a key: it waits for the field to be visible and editable, then sets the value in the page and dispatches `input` and `change` (which Svelte 5's bindings listen to), so the step's title is "Evaluate". `fillSignIn` and every step-up, account and setup code field use it. It keeps the value out of step titles only: a failed page's error context (the ARIA snapshot Playwright writes next to the error) lists input values, password fields included, and a trace records the call's argument; for those the artifact check is the backstop.
3. A request that carries a token, a key or a password in its query goes through Node's fetch (`call` in `tests/support/accounts.ts`, which records no step), never a request context. A navigation may carry a display key only in the fragment (`#key=`) of an absolute address (`${webUrl}/display?...#key=...`): Playwright leaves the fragment out of the step only when the address parses on its own, and keeps a relative one (`/display?...#key=...`) whole. The report also keeps the lines around each step as its snippet, so a made-up token or key is built at run time (`['eyJ...', 'e30', 'c2ln'].join('.')`, `'sim-guess-'.padEnd(35, '0')`), never written out on a source line.
4. Two checks. `node Platform/Testing/Ariva.E2E/scripts/expect-messages.mjs` reads code only (comments and strings masked) and fails when an expect message, a step title, an annotation, an attachment or console output holds a `.text()`, `.json()` or `.body()` call, a `.body` property, a secret-named member or variable (`credential`, `clientSecret`, `totpSecret`, `temporaryPassword`, `password`, `secret`, `accessToken`, `refreshToken`, `recoveryCodes`, the credential keys, `jwt`, `token` and names ending in `Token`, and `process.env` keys, secrets, passwords, tokens and seeds), an answer's `.url()` (its query may carry a token; `whereOf` in `tests/support/api-assertions.ts` leaves it out, as `expectProblemDetails` and `expectApiSecurityHeaders` now do), or a variable whose latest binding holds an answer or a secret, one step removed included (a template or a `+` concatenation that carries one); when a value typed with `fill`, `type`, `pressSequentially` or `insertText` is such a secret (their step title is `Fill "<value>"`: use `fillSecret`); when a request context's call or a navigation puts a secret parameter (`access_token=`, `token=`, `key=`, `secret=`, `password=` and the like, whatever its value, a literal included) or a token, credential, secret or key into its address's query, or into the fragment of a relative address; and when a source line holds a secret's shape (`scripts/secret-shapes.mjs`). An address is read from the argument, the latest binding of the name it starts with, the body of the function that binding calls, and every definition of the member it ends with (in the file, else in the support files); a member or a call it cannot read at all is flagged. A field read from an answer (`(await r.json()).id`) is a value of its own. Its `--self-test` proves it fires on 63 bad patterns and stays quiet on 40 good ones, and finds 4 literal shapes on source lines while 4 values built at run time pass; the helper and the smoke suite's leak probe (which leaks a made-up password on purpose, ARV-128) are left out, and the source-line rule leaves out `global-teardown.ts`, which runs outside every test (no step's snippet shows it) and checks the log scan's own rule on a made-up code. `node Platform/Testing/Ariva.E2E/scripts/artifact-secrets.mjs` scans the report (with the zip it embeds), the test output (trace zips, error contexts, attachments) and, in CI, the run's log and the hosts' logs for device and display credentials, integration client secrets, JWTs, bearer and `access_token` values, TOTP seeds (otpauth URIs, `totpSecret` members), recovery codes and temporary passwords (as answers carry them and on their own shapes, as a dialog or an error context shows them: letters and digits mixed, so prose is not one, and any code in the sign-in or step-up recovery field (`textbox "Recovery code": ...`, English and Arabic labels)), TOTP codes where a TOTP label precedes them (a `code` JSON member, a fill of a code field, or a code field's value in an error context's ARIA snapshot, `textbox "Authenticator code": 493817`, by the web app's English and Arabic labels: the server issues no other six-digit code), and by exact value the run's E2E account passwords and TOTP seeds (derived from `ARIVA_E2E_ACCOUNT_SEED` as `accounts.ts` derives them), the run's other secrets (the simulator, mock AMAN, ACRIS and Cronz keys and the validation reader's password: `playwright.config.ts` keeps a value it is given, so `verify.mjs` and CI derive them from the same seed in the config's formats and give them to the run, and the check knows them), the seed, the database passwords and what the run wrote to `.e2e-keys`; it names the file and the kind, never the value, and a zip it cannot read is a finding. Values made of URL-safe characters are found through a set lookup over the text's runs of such characters, so hundreds of megabytes of host logs take seconds. Its `--self-test` puts each kind in a plain file, a report's embedded zip, a trace zip, a zip inside a zip and an error context, passes a clean set, refuses an unexpanded `$(NAME)` as a seed, and proves `redactSecrets` clears each secret sample and keeps plain text. Both run in the security step of `verify.mjs`, in CI's security gate and in the Azure DevOps pipeline's security steps.

`verify.mjs` gives every Playwright run it starts (e2e, visual, demo, rehearsal, zap, and those of story and checkpoint) an account seed of its own, unless the caller set one, and runs the artifact check on the run's folders when it ends (for zap, `zap-reports` too); `node scripts/verify.mjs artifacts` runs it alone on what a run left. CI (`.github/workflows/ci.yml`) sets a seed for the e2e job, exports the run's derived secrets (`artifact-secrets.mjs --env github`) and masks the seed and every value derived from it (`--mask github`), so a failing assertion that prints a password shows `***` in the public log; it runs the check after the visual run and after the suite (the suite's check reads the hosts' logs as well), and uploads the visual differences, posts the failure comment and uploads the Playwright report only when it passed; a finding fails the job instead. The comment quotes the hosts' error lines only when every run's own log scan (`global-teardown.ts`) passed. `security-zap.yml` does the same for its run: a masked seed, then the check over `zap-reports`, the run's log and the Playwright folders before the reports are uploaded or their summary is shown, and the scan's copies of ZAP's reports and output are written through `redactSecrets`. The Azure DevOps pipeline (`Analyze-solution.yaml`) masks the derived values (`--mask azure`, `task.setsecret`), sets the derived secrets as variables the later steps receive (`--env azure`), runs the check and publishes the report only when the check's own output variable (`e2eArtifacts.clean`) says so. CI keeps no trace (`trace` is off with `CI` set, in the gate environment too): a trace records every header, body and typed value, so the check would refuse every failed run's report; the report keeps the errors and each failed page's error context. A local run without `CI` keeps a failed test's trace, which the check then reports: delete it before sharing anything from those folders.

## What this trades

A regression outside a story's own area is found at the next checkpoint, up to four stories later, instead of at once. The wide list sends the changes most likely to cause that through the full suites at the story itself.
