# Data classification

Ariva's own sensitive data, sorted into four protection levels; what each level requires in transit, at rest, in backups, in logs, for access, display, retention, deletion, export, caching and browser storage; and the control and test that provide each requirement. For a site's security officer, data protection officers preparing a DPIA, and engineers who change what Ariva stores, shows or sends.

Status: this page describes the code, the charts and the docs as of 2026-10-19 (ARV-094). Where a control is not built, it says Missing, To confirm or Proposed. Section 6 lists the controls that had no test (their tests are now written and pass) and the controls that are missing, each with the test that proves it or would prove it.

## 1. Purpose

This page serves three ASVS 5.0 rows of [asvs-l2](asvs-l2.md):
- V14.1.1, identify all sensitive data and classify it into protection levels: sections 2 and 3.
- V14.1.2, document the protection requirements (encryption, retention, logging, access) per level: section 4.
- V14.2.4, data protection controls implemented as documented per level: sections 5 and 6.

How it relates to the other pages:
- The [data inventory](../privacy/data-inventory.md) lists the objects: every table, hypertable, continuous aggregate and view, and the data outside the database, each with its category, personal data, retention and owner. This page gives each of its categories a level (section 3.6) and does not repeat the objects.
- The [data boundary](../domain/data-boundary.md) lists what never enters Ariva: officer, traveller and document identities, biometrics, images and exact AMAN event times. Ariva holds none of it, so none of it has a level here. Its principle 5 (desk-level data, tracks and desk events never reach the airport side) sets the border rules of level L3.
- The [log inventory](log-inventory.md) lists every place a log is written and, in its section 10.6, the protection levels the redaction enricher applies by name: Omit, Hash and Mask. Here they are requirements per level: L4 values are omitted, staff email addresses masked, track ids and desk codes hashed.
- Keys and certificates are listed in the [crypto inventory](crypto-inventory.md), and their owner, generation, custody, rotation, compromise response and destruction are in [key management](key-management.md). This page gives them their level (section 3.2) and does not repeat them.

## 2. Protection levels

| Level | Definition | Examples |
|---|---|---|
| L4 Secret | Credentials, keys and what is equivalent to them: anything that lets its holder act as a person, a device, a display, a calling system or a host, or open what another L4 value protects. Its exposure is a security incident whatever else it reveals | Password hashes and salts, temporary passwords, TOTP seeds, recovery codes, refresh tokens, access tokens (JWT), integration client secrets, device and display credentials, outbound endpoint secrets, the Cronz dashboard key, the log pseudonym key, the Data Protection keys and their certificate, the token signing keys, the sensing day keys, the backup identity, and every other key of the crypto inventory |
| L3 Restricted | Personal data of Ariva's own users (staff), border data that only border roles may read, security records, and free text that may name a person | User names, display names, email addresses, sign-in records with client addresses and user agents, account and session ids beside what they did; border per-desk data (a desk code with a minute, data boundary principle 5) and the lane split of the arrival wave; audit entries and Integration API call records; notes, reasons and escalation contacts; security logs |
| L2 Internal | Operational and configuration data of a deployment, and pseudonymous identifiers that name no one | Zones and topology, devices and their health, queue aggregates, forecasts, alerts, reports, flights, advertising plans, availability; sensor track ids and their daily pseudonyms |
| L1 Public | What may be shown to anyone in the terminal | What a passenger display board shows: the waits per queue zone, the instruction slides, the display's labels, and the advertisements a site has approved and scheduled |

Rules:
- A level belongs to a value. Each category of section 3.6 takes the level of its main content; a column that holds a value of another level is named in the category's row and takes that level's requirements.
- A copy keeps its level wherever it goes: a log line, a Kafka record, a backup, an export, a cache, the browser.
- A hashed or encrypted L4 value stays L4: a password hash can be attacked offline, and a protected seed opens with the key ring. A keyed pseudonym of an L2 identifier stays L2 (track ids, section 3.5).
- Values joined together take the level of what the join reveals: a desk code alone is configuration (L2), but a desk code with a minute is border per-desk data (L3), because it could be joined with AMAN's records to identify an officer (data boundary, code mapping).
- Free text is L3 wherever it is kept: Ariva cannot recognise a name in text, so the screens ask users not to type one (data inventory, how to read it).
- What the data boundary's table "What never crosses into Ariva" lists has no level: Ariva never receives it.

Where the code or the data boundary says otherwise than the starting levels of this story, the level is adjusted:
1. **Session ids are L3, not L4.** The access token's `sid` is the id of the session's `user_session` row. It authenticates nothing (every request also needs the signed token that carries it) and finds no token (refresh tokens are kept as hashes), so every log line a request writes carries it as it is (log inventory, section 10.1, `CallerSessionId`). It refers to one person's sign-in, which is L3. The session's credentials, the access token and the refresh token, are L4.
2. **Credential prefixes are L2.** A device or display credential is stored as a prefix and a SHA-256 (`DeviceCredentials`, `DisplayCredentials`). The prefix (`DeviceCredentials.PrefixLength`, 13 characters) finds the row and cannot authenticate; administrators see it, and the device refusal lines log it ("Device authentication refused for {CredentialPrefix} ..."). The credential and its hash are L4.
3. **Lane staffing and the border alerts are L3, although they are lane aggregates.** `lane_staffing` and the alerts on open desks below recommendation and on the predicted nowcast carry the lane split of the arrival wave, which the owner made border data (decisions of 2026-10-15 and 2026-10-16, ARV-187): only `ArrivalWaveLanes.View` holders read them (data boundary, retention table). Other lane aggregates stay L2.
4. **The public halves of keys are L2.** The token validation public keys, the CA certificates, the age recipient and the backup allowed-signers file are not secret. Their integrity matters, and key management covers it.

## 3. Classification

### 3.1 Credentials

|---|---|---|---|
| A user's password | `user.password_hash`, `user.password_salt` | PBKDF2-SHA256, 600,000 iterations, random salt (`Ariva.Infra/Security/PasswordHasher.cs`) | L4 |
| A temporary password | The administrator's one answer (`UserCreatedViewModel`, `TemporaryPasswordViewModel`), then as the password | As the password | L4 |
| A user's TOTP seed | `user.totp_secret_protected` | Data Protection, purpose `Totp.DataProtectionPurpose` (`Ariva.Infra/Security/Totp.cs`, used by `SvcAuthenticator`) | L4 |
| Recovery codes | `recovery_code.code_hash`; shown once (`TotpConfirmedViewModel`, `RecoveryCodesViewModel`) | SHA-256 | L4 |
| A refresh token | The `__Secure-ariva_rt` cookie; `refresh_token.token_hash` | 256 random bits, stored as SHA-256 (`RefreshTokens.Hash`); its successor during the grace window under Data Protection (`RefreshTokens.SuccessorPurpose`) | L4 |
| A user's access token | The browser's memory; the `Authorization` header (on the live hub, the `access_token` query of `/hubs`) | ES256 JWT, 15 minutes; no host stores it (section 3.4) | L4 |

| A display credential (`ardp_`) | `display.credential_hash`; shown once (`DisplayIssuedViewModel`); the player address's fragment, then the player tab's `sessionStorage` | SHA-256 (`DisplayCredentials.Matches`); the prefix is L2 | L4 |

| The TickerQ hub ticket | The `__Secure-ariva_jobs_hub` cookie (`JobsDashboardGuard.TicketCookie`) | An expiry and its HMAC under a key each Cronz process draws at random, never the operator key; HttpOnly, Secure, SameSite=Strict, the hub's path only, 30 minutes (`JobsDashboardGuard.TicketLifetime`) | L4 |
| The break-glass credential | Printed once to the operator's terminal or written to `--break-glass-output` (`Ariva.Di/BreakGlassCommand.cs`) | Then as an account's password and recovery codes | L4 |
| Service credentials: the database logins, Kafka SASL, SMTP, the Redis connection, Loki and the OTLP collector's sender headers | The appsettings secret and the Kubernetes Secrets of the site | As the site's secret store keeps them; never in a backup (section 5.3) | L4 |

### 3.2 Keys

Every key and certificate of the [crypto inventory](crypto-inventory.md) is L4, and its public half L2 (section 2, adjustment 4). Among them: the user and the integration token signing keys, the Data Protection keys (`data_protection_key`) and the `ariva-dataprotection` certificate that wraps them, the log pseudonym key (`Logging:PseudonymKey`), the sensing day keys (`sensing_day_key`), the TLS private keys of the ingress, the pods, the MQTT listener and the database, the backup identity (age) and the backup signing key. Who owns each one, how it is generated, kept, rotated and destroyed, and what to do when one is exposed: [key management](key-management.md).

### 3.3 Staff email addresses

An email address is L3. Ariva holds staff addresses only; it never receives a traveller's or an officer's (data boundary).

| Where | How it is protected |
|---|---|
| `user.email` | Read and changed only through the user administration, whose permissions only the System administrator holds (`RolePermissions.SystemAdministrator`) |
| `email_message`, an alert email's recipient | No screen or API reads it; deleted after `Database:Retention:AlertEmailDays` (180 days, Proposed, TC-67); sent over STARTTLS or TLS outside vm-local and k8s-dev |
| `audit_entry`, the summaries of account changes | Quoted with the user name (`AuditSummaryTests.Summary_Should_QuoteNameAndEmail_When_TheyLookLikeMoreFields`); read by system administrators only |
| Logs | Masked to the first character and the domain (`a***@example.com`): by name (`LogProtection.MaskedNames`) and inside any text (log inventory, section 10.6) |
| The access token, the site configuration bundle, the CSV reports | Never: no claim (section 3.4), no member of the bundle, no column of a report |

### 3.4 JWT claims

The user access token, issued only by Ariva.Api.Main (`AccessTokenIssuer.Issue`, claim names in `ArivaClaims`, `Ariva.Infra/Security/AccessTokenIssuer.cs`; ADR-0026). The token as a whole is L4. Its parts:

| Claim | Holds | Level |
|---|---|---|
| Header `alg`, `typ`, `kid` | `ES256`, `at+jwt`, the key id derived from the public key | L2 |
| `iss`, `aud`, `iat`, `nbf`, `exp` | `ariva`, `ariva-users`, the issue time and the 15-minute lifetime | L2 |
| `sub` | The account id, a GUID | L3 |
| `sid` | The session id (the `user_session` row) | L3 (section 2, adjustment 1) |
| `family` | The session's refresh token family | L3 |
| `auth_time`, `amr` | When and how the person signed in | L3 |
| `name` | The user name | L3 |
| `scope` | `pending` for an account that must still change its password or enrol TOTP; absent otherwise | L2 |

Never in the token: roles and permissions (every host resolves them from stored grants, `StoredPermissionResolver`), the email address, the display name and the sites. `AccessTokenTests.Issue_Should_WriteOnlyTheDocumentedHeaderAndClaimNames_When_Issued` asserts the exact header and claim names above, for a pending account and for one that is not, and that none of these appears (section 6, item 2); `AccessTokenTests.Issue_Should_WriteAnEs256AtJwtWithKidAndClaims_When_Called` asserts no `role` claim.

The integration access token, issued only by Ariva.Api.Integration (`IntegrationTokenIssuer.Issue`, claim names in `IntegrationClaims`, `Ariva.Infra/Integration/IntegrationTokens.cs`), audience `ariva-integration`. The token as a whole is L4. Its claims name a calling system, not a person, so all are L2: `sub` (the public client id, `ic_` and 26 characters), `sid` (a new session id per exchange), `ver` (the client's token version), `scope` (its scopes) and `site` (one per bound site code), with the same header and time claims. `IntegrationClientTests.Issue_Should_WriteOnlyTheDocumentedClaimNames_When_AClientExchangesItsCredentials` (unit) asserts exactly these names (section 6, item 3).

### 3.5 Track ids

A track id is the number a sensor gives one anonymous person while it follows them through its coverage (`TrackPosition`, `LineCrossing`; [sensor adapters](../architecture/sensor-adapters.md)); Ariva namespaces it by device (`<device code>/<id>`). It is linked to no identity, rotated at zone exit, and never persists past the operating day (D4; data boundary, retention). Level L2, pseudonymous. Whether anonymous tracks are personal data is To confirm per jurisdiction (TC-75). From a border deployment, track ids never reach an airport deployment (data boundary, principle 5).

| Where | Form | Kept |
|---|---|---|
| Ingest and the sensing topics | As the device sent it, namespaced by device | The topics keep three days (`SensingArchive.Window`) |
| The queue engine's checkpoint (`stream_zone_state`) | The open tracks of the moment with their ephemeral ids | Overwritten at every checkpoint |
| The raw archive (`sensing_event`) | `<device code>/~` and 22 characters: HMAC-SHA256 of the track id under the random key of its UTC day (`SensingArchive.Pseudonym`). The day key is deleted by the first archive write at least three days after its day ended (`SensingArchive.DayKeysAsync`), later on a quiet site or while Stream is stopped; after that no one can link that day's pseudonyms to a track id (`SensingArchiveTests.Archive_Should_KeepOnlyDailyPseudonymsOfTrackIds`) | `Database:Retention:RawSensingDays`, 90 days by default (TC-62) |
| Logs | `#` and 12 hex characters: HMAC-SHA256 under the log key of the UTC day (`LogProtection.HashedNames`; `LogProtectionTests.Enrich_Should_HashTheValue_When_ThePropertyIsATrackIdOrADeskCode`) | The log store's period (Proposed 30 days, TC-65) |
| API answers, exports, reports | Never: no member of `Ariva.Core/Domain/ViewModels` names a track id, and the site configuration bundle and the reports hold none | |

### 3.6 Data inventory categories

Every category of the [data inventory](../privacy/data-inventory.md) tables, as it writes it. The Level is that of the category's main content; the Why names the columns or rows at another level (section 2, rules). `DataInventoryTests` keeps this table complete (section 6, item 1).

| Category | Level | Why |
|---|---|---|
| Accounts | L3 | Staff account data: user name, display name, email address, roles and sites with who granted them, sign-in sessions with client address, user agent and methods (`user`, `user_role`, `user_site`, `user_session`). The credential columns are L4: `user.password_hash` and `password_salt`, `user.totp_secret_protected`, `refresh_token.token_hash`, `recovery_code.code_hash` |
| Security | L4 | `data_protection_key` is the Data Protection key ring, each key wrapped under the `ariva-dataprotection` certificate; it opens every value protected with Data Protection |
| Audit | L3 | Security records. `audit_entry` names the acting account, its client address and the target, and its summaries may hold a name or an email address; `integration_call` records each call of a calling system with its source address |
| Configuration | L2 | Sites, topology, zone profiles, devices, displays, slides, advertising, calendars, alert rules, report schedules, integration clients, outbound endpoints and retention periods. L4 columns: `integration_client.secret_hash` and `totp_secret_protected`, the `outbound_endpoint` secret, `device.credential_hash`, `display.credential_hash`. L3 values: free text that may name a person (the `alert_rule` escalation contact, the `advertising_policy` reason, the `advertising_media` advertiser, campaign and file names, the `operating_day_exception` and `maintenance_window` reasons), account references (the `report_schedule` owner, `report_schedule_recipient`, the approver of `advertising_media`, `zone_profile.published_by`) and the audit columns. Display content becomes L1 when a board shows it: a display's labels, its instruction slides, its approved advertisements |
| Platform | L2 | `schema_version`: the applied scripts with their checksums, times and logins; no personal data |
| Evidence | L2 | Device calibrations, zone outages and replay runs: evidence for disputes. L3 values: calibration notes (free text), who recorded a calibration, the replay operator's name |
| Operational state | L2 | Latest states and positions: heartbeats, zone health, stream checkpoints and offsets, rule states, feed freshness, cursors, idempotency keys, proof of play. `stream_zone_state` holds the open tracks' ephemeral ids (L2, section 3.5); `desk_feed_state` holds the desk engine's lane context and exists only in a border deployment |
| Raw sensing | L2 | Anonymous track coordinates and heights with a daily pseudonym of the track id, line crossings, counts and device health; no image and no identity (section 3.5). In a border deployment tracks never leave it |
| Key material | L4 | `sensing_day_key`: the key of each UTC day's track pseudonyms, kept as plain bytes. Only an archive write deletes it (`SensingArchive.DayKeysAsync`, `SensingArchive.Window`): the first one at least three days after its day ended, so later on a quiet site or while Stream is stopped (section 6, item 10) |
| Queue measurement | L2 | Aggregates per queue zone, line, overflow band and minute or bin, with no identity. The nowcast a passenger board shows is L1 once shown |
| Validation evidence | L3 | Border per-desk data (`validation_campaign_desk`, `desk_observation_batch`, `desk_observation`, the desk section of `validation_result_revision`), observers as account ids, correction reasons in free text, and the shadow nowcast that only the validation reader login reads (`queue_minute_shadow`). The zone and line rows (`validation_campaign_zone`, `validation_campaign_line`, the counts of `manual_count`, the times of `tracer_run`) hold L2 values |
| Border feed | L3 | AMAN feed records: desk sessions and desk and e-gate intervals are desk-level border data for border roles only (data boundary, principle 5). `inbound_lane_demand` is lane aggregates but AMAN feed content, which stays in the border deployment |
| Desk measurement | L3 | Desk and e-gate minutes, desk zone readings and sensor-only desk minutes: a desk code with a minute, border roles only |
| Staffing | L3 | `lane_staffing` is lane aggregates, which alone would be L2; adjusted because the lane split of the arrival wave is border data, read only by `ArrivalWaveLanes.View` holders (section 2, adjustment 3) |
| Flights | L2 | Flight identity, times, places, aircraft, seat and passenger counts; no passenger or crew data |
| Alerts | L2 | An alert's rule, zone, value and state. L3 values: the escalation contact copied from the rule (free text), the user names of who acknowledged, escalated or resolved it and their notes (free text). L3 rows: the border alerts (open desks below recommendation, predicted nowcast), which carry the lane split (section 2, adjustment 3) |
| Notifications | L3 | `email_message`: the recipient's staff email address with the subject and body; a border alert's email carries border data |
| Reports | L3 | `report_delivery`: one row per recipient account and local day, so each row is a record about a member of staff |
| Messaging | L2 | Domain events as sent (aggregates and configuration) and processed event ids. L3 values: the zone profile published event names the publishing user; in a border deployment, desk-level events are border data |
| Availability evidence | L2 | Per site and minute, whether Ariva was measuring and why not |

The rows of the data inventory's "Outside the database" table, with the secrets and the browser.

| Data | Level | Why |
|---|---|---|

| The browser | L4 and L2 | The access token in memory and the refresh cookie (L4); two open exceptions of section 5.11, both L4: a display player's credential in its tab's session storage, and the Cronz dashboard key in the operator's local storage, kept there by TickerQ's browser app; the TickerQ hub ticket cookie (L4, HttpOnly); the sign-in hint and the theme in local storage (L2) |

## 4. Requirement matrix

| Requirement | L1 Public | L2 Internal | L3 Restricted | L4 Secret |
|---|---|---|---|---|
| In transit | TLS 1.2 or 1.3 on every connection of a k8s-prd deployment, with no plain fallback | As L1 | As L1; border data never leaves the border deployment | As L1; never in a URL on an API route (headers or the refresh cookie), except the live hub's token on `/hubs` |
| At rest | Plain in the database or file storage | Plain in the database or file storage | Plain in the database, behind the database logins; the runtime login cannot delete accounts or sessions or change audit entries | Hashed (PBKDF2-SHA256 for passwords and integration secrets; SHA-256 for random credentials, refresh tokens and recovery codes) or encrypted with Data Protection (TOTP seeds, outbound secrets); Data Protection keys wrapped under the certificate; other keys only in the site's secret store. Exception: the sensing day keys, plain until the first archive write at least three days after their day |
| In backups | In the backup, each file encrypted with age | As L1 | As L1; kept no longer than the dispute window plus the backup cycle (Proposed, TC-34) | Hashed and protected values stay so in the dump; the certificate, the signing keys, the appsettings secrets and the backup identity are never in a backup |
| In logs | Allowed | Allowed; track ids hashed per UTC day | Email addresses masked; desk codes hashed per UTC day; account and session ids, user names and client addresses written; the log store read by the operations team only (Proposed, TC-65) | Omitted (`[REDACTED]`) by name; inside text only Bearer and Basic credentials, JWTs, token query parameters and `ardk_` and `ardp_` credentials are masked, so another secret inside an exception's text is written (item 21) |
| Access | Anyone in front of a display; the board API answers only the display's own credential | Roles that hold the endpoint's permission, within their sites | As L2, narrower: staff accounts and audit entries for system administrators only; border data for border roles only; sign-in records and alert emails through no screen | No reader: the hosts verify or decrypt, and no answer returns a stored value; a key mounted only where it is used, except the Data Protection certificate and its key, mounted in all five API pods (item 22) |
| Display | Shown publicly | Shown to the roles that may read it | Shown to the roles that may read it; never on a passenger display | Shown once, when issued, to its holder, and never again (a credential's prefix is shown) |
| Retention | As its source; a board is computed, not stored | Per the data inventory: raw sensing 90 days (TC-62), Integration API calls and advertising plays 400 days (Proposed), aggregates and configuration indefinite | Per the data inventory: accounts and audit indefinite; sessions indefinite (TC-65); alert emails 180 and report deliveries 400 days (Proposed); desk zone readings 7 days; other border data indefinite (To confirm); logs 30 days (Proposed, TC-65) | Access tokens 15 minutes; refresh tokens end with their session; sensing day keys until the first archive write at least three days after their day; Data Protection keys kept after retirement; the rest as the row or secret that holds them (key management) |
| Deletion | Retired, never deleted | TimescaleDB drops chunks past their period; configuration soft deleted | Accounts disabled and sessions revoked, never deleted; audit entries append-only; alert emails and report deliveries deleted by the Cronz retention job; no erasure on request (To confirm) | Revoked when retired or rotated; sensing day keys deleted by an archive write, at least three days after their day; key destruction per key management |
| Export | In the site configuration bundle (display settings and labels) | In the bundle (topology, desk code mappings, the published profile and floor plans, devices, alert rules, displays) and the daily CSV (lane hours, alerts, device uptime) | Never in the bundle (no user, audit entry, escalation contact or time series); the CSV has no note, contact or user name, and border alerts only for `ArrivalWaveLanes.View` holders | Never exported (credentials, hashes, prefixes, access settings, pairing secrets); an import's new device credentials answered once |
| Caching | `no-store` on the board's answer (it carries a credential) | Server caches allowed; `no-store` for every signed-in caller | `no-store`; Redis holds roles and session state by ids only; security decisions cached without fail-safe | `no-store` on every credentialed answer; a device credential hash cached in memory only, never in Redis |
| Browser storage | The player's advertisements in memory only | Nothing in web storage | Nothing in web storage | The access token in memory only; the refresh token and the TickerQ hub ticket in HttpOnly cookies; two open exceptions: the display player's credential in `sessionStorage` (ARV-093b) and the Cronz dashboard key in TickerQ's `localStorage` (ARV-087) |
