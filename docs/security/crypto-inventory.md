# Cryptographic inventory

Every cryptographic key, secret, certificate and algorithm an Ariva deployment uses, with its permitted use, what it protects, where it is made and kept, how it rotates, and the code that creates, reads or checks it (ASVS 5.0 V11.1.2). For a site's security officer, site IT, Dalil operations and security reviewers.

Related pages: how each key is owned, held, rotated, revoked and destroyed is the [key management policy](key-management.md) (V11.1.1). The protection levels L1 to L4 are those of the [data classification](data-classification.md), where L4 is credentials and keys. The ASVS rows are in [asvs-l2](asvs-l2.md), section V11. Creating the secrets is [wiki 04](../../wiki/04-Deployment-Guide.md) section 6.2; the security guide's summary is [wiki 13](../../wiki/13-Security-Guide.md) section 5.

Status: this page describes the code, the charts, the scripts and the workflows as of 2026-10-19 (ARV-094).

Keeping it complete: `CryptoInventoryTests` (Ariva.UnitTests, added in ARV-094) reads this page. Every C# file under `Platform/Backplane` (the test projects left out) and `Platform/Simulation` that uses a cryptographic API (System.Security.Cryptography, Microsoft.AspNetCore.DataProtection, OtpNet or Microsoft.IdentityModel.Tokens) or configures TLS (System.Net.Security, System.Security.Authentication, `SslProtocols`, Npgsql's `SslMode` or Confluent's `SecurityProtocol`) must be named, in backticks, in a row of one of this page's tables, that is on a line that starts with `|`: the Code column of the keys table (section 1) or the Where column of the algorithms table (section 2). A file named only in prose does not count. Every C# file this page names must exist and match exactly one file. So a story that adds cryptography or TLS configuration adds its row in the same change. Paths are relative to the repository root.

## How to read it

- **Rows** have ids (K1 and so on for keys, A1 and so on for algorithms) so the key management policy can point at them.
- **Kind** is one of: asymmetric key, symmetric key, secret, certificate, password-equivalent (a random bearer value that works like a password: whoever presents it is let in).
- **Protects** names the data or channel and its level. A channel carries data of every level that crosses it, L4 included.
- **Stored in** names the Kubernetes Secret and its key, the database column (and whether it holds a hash or an encrypted value), or "memory only" (never written).
- **Rotation** is what the code or a written procedure does today, or To confirm.
- **CSPRNG** means .NET's `RandomNumberGenerator` (or Node's `crypto.randomBytes` in the scripts). No Ariva code uses `System.Random` (analyzer CA5394 is an error in `.editorconfig`).

## 4. Outside the code

What the site provides:
- **Certificates.** The ingress host certificates (K27), from a public CA or the site's PKI by the rule of wiki 04 section 6.2, with the go-live record per host (wiki 13 checklist item 18). In k8s-prd also the cluster CA and the six pod certificates (K28, K29), the database server certificate and the internal CA (K31), the Redis CA (K32), the Kafka CA (K33) and, with MQTT, its server certificate (K30). Device client certificates (K15) come from the device, its vendor or the site's PKI.
- **The site PKI and its issuers** (cert-manager, the customer's PKI): Ariva only consumes their output. Which hosts use the site's PKI is the site's choice per Ingress (`tlsSecretName`).
- **The secret store.** Every Kubernetes Secret named in section 1 is created by the site's operators with the commands of wiki 04 section 6.2 and kept in the site's secret store (D5). Creating, rotating and destroying them through a vault or the External Secrets Operator is ARV-083c (needs the owner's choice of store). Encryption at rest for Kubernetes Secrets is the cluster's (wiki 13 checklist item 2).
- **Partner credentials.** Outbound endpoints' secrets, API keys, HMAC keys and client certificates (K17 to K20) are issued by the partners; Ariva holds them only under K4.
- **Service credentials.** Kafka, Redis, SMTP, the log store and the registry (K36 to K40) belong to whoever runs those services.
- **Time.** NTP on every node and device (wiki 13 checklist item 14): access tokens get 30 seconds of skew and TOTP one step.
- **The ingress controller.** External TLS versions and suites hold only where the site has applied Ariva's controller values (`Platform/Cloud/Ariva.K8s/Helm/ingress-nginx-values.yaml`); the TLS check proves it at each release.

What the release pipeline uses:
- **No long-lived signing key.** `images.yml` signs every pushed image with cosign keyless (`cosign sign --yes`) and attaches the CycloneDX SBOM as a signed attestation (`cosign attest`), with `id-token: write` so the run's GitHub OIDC token gets a short-lived Fulcio certificate naming the repository, the workflow, the ref and the commit; the signature is recorded in the public Rekor log; the workflow verifies both right after pushing. `offline-bundle.yml` signs `manifest.json` keyless (`cosign sign-blob --bundle`) in a job that runs no build and no package manager; `scripts/offline/verify.mjs` checks the identity, the ref and the commit (wiki 04 sections 6.5 and 12).
- **Trust rests on repository settings**: only release maintainers may create, move or delete `v*` tags, and `main` is protected (To confirm by the owner before the first signed release, TC-54; wiki 04 section 6.5).
- **Pipeline credentials**: the GitHub environment `k8s-dev` holds `KUBECONFIG_B64`, the appsettings secrets, the database passwords and a read-only GHCR pull token (wiki 04 section 6.6); the Azure DevOps release reads a secret variable group and passes the registry password to Helm with `--set imageCredentials.password` (`Platform/Cloud/Ariva.Cicd/AzureDevOps/K8s/Release-ariva-k8s-dev.yaml`).
- **Not signed**: the Azure DevOps image builds (`Build-k8s-<service>`); signing them needs a key and is a Target procedure (wiki 04 section 6.5). Copy the signed GitHub images with their referrers instead.
- **Not built**: the licence file's signature and its offline check (wiki 11 section 12, wiki 04 section 12.5). No licence key exists yet.

## 5. Gaps found

Found while making this inventory. None is fixed here; each has a story or is To confirm.

1. Recovery codes carry 50 bits and are stored as unsalted SHA-256 (K9, A5), within reach of an offline search by a database reader. ARV-088.
2. Temporary passwords never expire and carry about 115 bits (K7). ARV-088 (expiry); the entropy against ASVS V11.5.1: To confirm.
3. Per-request integration TOTP codes are checked without the replay guard (A4). ARV-088.
4. Credential hashes (refresh tokens, recovery codes, device and display credentials) carry no algorithm label (A5). ARV-080a.
5. The Cronz dashboard key and the simulator keys are chosen by the operator with no entropy check (K22, K44). ARV-088 documents 32 random bytes; ARV-087 puts the dashboard behind user sign-in.
6. The display player keeps its credential in `sessionStorage` (K16). ARV-093b.
7. Expired Data Protection keys are never deleted: script 0002 gives the runtime login no DELETE and no job or procedure removes them, so the table only grows and an old key unwraps its payloads for as long as a certificate that wraps it is kept. Proposed story: a key ring retention and destruction procedure (with the migration login), tied to the certificate and backup custody of wiki 04 section 10. To confirm. ARV-207.
8. No tool revokes the Data Protection key ring, or ends every session of a deployment, after a compromise; today revocation is only something a database writer can plant (wiki 13 section 5), and sessions end per user. Waits for the login freeze (it ends every session); noted on ARV-207.
9. Cryptoperiods are procedures, not controls: nothing records or alerts on the age of the token signing keys, the pseudonym key, the service passwords or the device and display credentials. Only the Data Protection and MQTT certificates are in `ariva.certificates.expires_in`. ARV-207.
10. The comment of `TokenKeys` says the previous public key is kept for 90 days after a rotation. The code accepts it for as long as `previous.pem` is mounted, and only access tokens (15 minutes) are signed with K1 or K2 (refresh tokens are opaque, decision 7 of ADR-0026), so wiki 04 section 6.2 is right: remove `previous.pem` once the access token lifetime has passed. The comment is stale; correcting it waits for the login freeze to lift (the file is authentication code).
11. Wiki 04 section 6.2 gives the rotation steps of the user ring only; the integration ring's (K2: its own Secrets, a restart of api-integration) are not written. Proposed wiki change; To confirm.
12. The sensing archive day keys (K26) are stored in clear in `sensing_day_key`, so every database backup taken while they are still in the table keeps them for as long as the backup is kept (Proposed 14 days, TC-34), beyond `SensingArchive.Window`; and the table itself keeps them past the window until the next archive write runs its DELETE (K26). To confirm: protect them under K4, leave the table out of the dump, or accept and record. ARV-208 (owner decision).
13. Device client certificates are trusted by their pin alone: their validity period and revocation are not checked (A16). To confirm whether expiry should be enforced. ARV-210 (login freeze).
14. Outbound calls take the platform's TLS versions and suites (`OutboundTransport` sets none; A15). ARV-205.
15. Nothing requires `Kafka:SslCaLocation` in k8s-prd (K33), so a site file without it would leave the brokers to librdkafka's default trust store. To confirm (with the owner question on ARV-083b).
16. Closed by ARV-200: Loki and the OTLP collector are verified against the public CAs or, when the site names one, against its CA alone (K47, A15).
17. Every API host mounts the Data Protection certificate with its private key (K3), api-ingest and api-stream included. To confirm whether those two protect or unprotect anything; if not, they need not hold it. Noted on ARV-083b (each pod mounts only its own credentials).
18. One Kafka principal, one Redis password and one base settings secret serve every host (K36, K37, K34), and every Secret is created by hand. ARV-083b and ARV-083c.
19. The Azure DevOps release gives the registry password to Helm as a value (`--set imageCredentials.password`), so it is kept in Helm's release record in the namespace, while the GitHub release writes the Secret itself (K40). To confirm. ARV-209.
20. The development Data Protection key file is written and only then made owner-only (`DataProtectionCertificates.WritePrivate`), while the development token key is created owner-only (`TokenKeys.DevelopmentKey`). vm-local only; Proposed: create it with `UnixCreateMode` as well. ARV-209.
21. The runtime database login is set from its plain password by the migration Job (K34, script 0001), which a server log with statement logging on would record (wiki 13 checklist item 9). Known and documented; the validation reader already uses a verifier (A3). To confirm whether the runtime login should move to a verifier too.
22. The Data Protection certificate's one RSA key pair (K3) has two purposes: it wraps each key ring element with RSA-OAEP and signs it with RSA-PSS (`OaepGcmXml.Encrypt` in `Platform/Backplane/Ariva.Infra/DataProtection/OaepGcmXmlEncryption.cs`). NIST SP 800-57 Part 1 section 5.2 asks for one purpose per key and names key transport with signature as a pairing to avoid: a key transport key must be kept for recovery, while a signing key should be retired. Here the old certificate is kept while a backup needs it (wiki 04 section 10.4, step 6), and while a previous certificate is configured under `DataProtection:Previous`, a key element signed with its private key is still admitted (`OaepGcmXml.Decrypt` takes any configured certificate). Recorded as a deviation. ARV-211 (A separate signing key for the Data Protection key ring).
