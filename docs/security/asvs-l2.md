# OWASP ASVS 5.0 Level 2 mapping

Every requirement of OWASP ASVS 5.0.0 at Level 1 and Level 2 (253 in all; Level 2 includes Level 1), mapped to the control and the test that meet it, or to the gap and the story that will close it (ARV-074, 2026-10-05). The 14 CWEs in `docs/security/cwe-controls.md` stay the floor that every story is reviewed against; this mapping is what a tender's security annex asks for. Requirement IDs and levels are ASVS 5.0.0's; the requirement column is a short paraphrase, so read the standard (https://github.com/OWASP/ASVS/tree/v5.0.0) for the wording.

Statuses: Met (a control exists, checked in the code, with the test that proves it where one exists); Partly (some of it is in place, the cell says what is missing); Gap (not in place); N/A (does not apply to Ariva, with the reason). Documentation requirements count as Met only where a repository document really defines what is asked. Every Partly and Gap row belongs to one story in `backlog/prd-asvs-gaps.json` (ARV-080 to ARV-096), listed at the end. Line numbers in the evidence drift as code changes; the file and symbol are what to follow.

How it is kept current: the security reviewer (`.claude/agents/security-reviewer.md`) checks the rows of the areas a story touches and the story updates their status and evidence; a story that closes a gap moves its rows to Met with the test that proves it.

Of the 203 requirements that apply, 125 are met (62 percent; ARV-080 closed V11.3.1, V11.3.2 and V11.3.3). The gaps that matter most before production: backend connections inside the cluster are not encrypted (V12.3, ARV-082); every host shares one database login, one Kafka principal and one settings secret (V13.2, V13.3, ARV-083); uploads are not scanned for malware (V5.4.3, ARV-092); HSTS is not set and machine endpoints are redirected from HTTP silently (V3.4.1, V4.1.2, ARV-084).

Found and fixed during the mapping: the session, role, site and live zone join caches could answer from a copy up to an hour old when the database was slow or down, so a revoked session or a removed role could pass (V16.5.3; fixed as ARV-081 with `SecurityCacheOptions`); the chart did not mount the integration token key ring that every cluster settings file of Ariva.Api.Integration reads, and four API pods (cronz, ingest, integration, stream) had no `fsGroup`, so their app user could not read the 0400 key files they mount and they could not start in a cluster (both fixed in the chart, with chart test rules); the security and administration guides still described OIDC sign-in through Keycloak, which is not built, and the CWE-89 row cited a test that does not exist (corrected).
