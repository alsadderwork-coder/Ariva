# OWASP ASVS 5.0 Level 2 mapping

Every requirement of OWASP ASVS 5.0.0 at Level 1 and Level 2 (253 in all; Level 2 includes Level 1), mapped to the control and the test that meet it, or to the gap and the story that will close it (ARV-074, 2026-10-05). The 14 CWEs in `docs/security/cwe-controls.md` stay the floor that every story is reviewed against; this mapping is what a tender's security annex asks for. Requirement IDs and levels are ASVS 5.0.0's; the requirement column is a short paraphrase, so read the standard (https://github.com/OWASP/ASVS/tree/v5.0.0) for the wording.

Statuses: Met (a control exists, checked in the code, with the test that proves it where one exists); Partly (some of it is in place, the cell says what is missing); Gap (not in place); N/A (does not apply to Ariva, with the reason). Documentation requirements count as Met only where a repository document really defines what is asked. Every Partly and Gap row belongs to one story in `backlog/prd-asvs-gaps.json` (ARV-080 to ARV-096), listed at the end. Line numbers in the evidence drift as code changes; the file and symbol are what to follow.

How it is kept current: the security reviewer (`.claude/agents/security-reviewer.md`) checks the rows of the areas a story touches and the story updates their status and evidence; a story that closes a gap moves its rows to Met with the test that proves it.

Of the 203 requirements that apply, 158 are met (78 percent; V16.3.4 went back to Partly with ARV-124a's finding and to Met again with ARV-231). Since ARV-082b every connection of a production deployment is encrypted, and ARV-084 closed V3.3.2, V3.4.1, V3.4.4 and V3.4.6 (V12.2.2 waits for each site's record of which CA each host chains to, wiki 13 checklist item 18): every host at the ingress sends HSTS of a year, nosniff and `frame-ancestors 'none'` on every response, the ingress's own included, the affinity cookies are Secure and SameSite=Strict, and the machine hosts refuse plain HTTP instead of redirecting it. That hardening is the chart's, but it holds only on an ingress-nginx controller that takes the chart's snippets and pins TLS 1.2 and 1.3 with Mozilla's intermediate suites: the site applies `Platform/Cloud/Ariva.K8s/Helm/ingress-nginx-values.yaml` to its controller, and the TLS check (`scripts/ops/tls-check.mjs`) proves the result on the live hosts after a release. ARV-085 closed V13.2.5, V4.1.3, V15.3.4 and V13.4.5 for production: in k8s-prd every Ariva pod denies all traffic in and out and gets only the firewall matrix's flows (NetworkPolicies, which the chart and both Helmfiles refuse off there), the API hosts trust X-Forwarded-For only from the ingress controller's pod network (a Helm value; a host refuses to start without one or with one too wide), no Ingress routes the health probes, and the Cronz dashboard answers only its source ranges. These hold only on a cluster whose network plugin (CNI) enforces NetworkPolicy, once the site has given the peers, its pod network and its management network, and with an ingress controller that sees each client's own address (wiki 13 checklist item 4); dev, demo and localk8s render no NetworkPolicy. ARV-089 closed V15.3.5 and V15.3.6: request JSON on every host refuses unknown and duplicate members and numbers sent as strings, Ariva.Web compiles with strict TypeScript, and the web app keys objects by server data only through Maps, `Object.fromEntries` and spreads, held by scan rules SEC-131 and SEC-132. V2.2.1 and V15.3.7 stay Partly: the owner's login freeze keeps the authentication endpoints on the lenient parsing until ARV-089a, and the repeated query parameter rule does not cover the minimal endpoints or upload forms. ARV-091 closed V16.1.1, V16.2.1, V16.2.3 and V16.3.2: the log inventory (`docs/security/log-inventory.md`) covers every layer and destination, a host refuses the JSON file sink outside vm-local, every line a request writes names its client address and its caller by id beside the trace id, every refusal of the authorization middleware and of `[SiteScoped]` is a security event with a stable EventId, and any other 401, 403 or 429 is one too (`SecurityEvent.RequestRefused`), all listed in the inventory's catalogue (section 10); only `Serilog:MinimumLevel` is read from configuration, so no setting adds a sink; at the ingress no Ariva Ingress writes a ModSecurity audit log, the access log holds no query string and only the web host serves `/hubs`. V16.2.5 stays Partly because the protection levels do not reach exception text, and V16.3.1 and V16.3.3 wait for the sign-in, logout and refresh events (ARV-091b, after the login freeze). ARV-091a closed V16.4.2 and V16.4.3: a k8s-prd host ships its logs over TLS to Loki or the OTLP collector, or does not start, and takes the log pseudonym key from the chart's Secret, which the chart and both Helmfiles require in production; the access, protection against change and retention of the shipped logs are a go-live record (`docs/security/log-inventory.md` section 8.1, wiki 13 checklist item 15), so V16.4.2 holds for a deployment once that record is complete. ARV-092 closed V5.1.1, V5.4.1 and V4.1.1: the file handling guide (`wiki/13a-File-Handling.md`) documents every upload, from who may send it and its types and limits to what happens to a malicious file; every stored upload is served back under a name the server builds (`inline; filename="{prefix}-{record id}.{extension}"`, never the uploaded name); and every text answer names UTF-8, on the API hosts (`SecurityHeadersMiddleware`) and in the web pod's nginx, whose configuration the web image no longer serves from its web root. ARV-096 closed V15.1.2: packages come only from nuget.org through package source mapping (`nuget.config`) and only as each project's committed `packages.lock.json` names them, in every CI restore and every image build, and the third-party images run outside the chart are pinned by digest and checked like the base images; it also gave the on-demand reports a concurrency policy and a request timeout and every Ariva.Api.Main endpoint a default request timeout, while V15.2.2 stays Partly for the bounds that remain (the forms the sign-in freeze keeps, until ARV-089a; ARV-230 bounded the queue engine's state at the pilot rate, ARV-232 the database connections, ARV-096b closed the request path, ARV-096c the forms read for actions that bind none, ARV-096d the data reads and database timeouts and ARV-096e the run timeouts of jobs, loops and Kafka handlers) and V15.2.1 for the remediation frames in CI (ARV-096a). The gaps that matter most before production: every host shares one database login, one Kafka principal and one settings secret (V13.2, V13.3, ARV-083);

Found and fixed during the mapping: the session, role, site and live zone join caches could answer from a copy up to an hour old when the database was slow or down, so a revoked session or a removed role could pass (V16.5.3; fixed as ARV-081 with `SecurityCacheOptions`); the chart did not mount the integration token key ring that every cluster settings file of Ariva.Api.Integration reads, and four API pods (cronz, ingest, integration, stream) had no `fsGroup`, so their app user could not read the 0400 key files they mount and they could not start in a cluster (both fixed in the chart, with chart test rules); the security and administration guides still described OIDC sign-in through Keycloak, which is not built, and the CWE-89 row cited a test that does not exist (corrected).
