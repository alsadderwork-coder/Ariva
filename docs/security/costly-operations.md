# Costly operations

One inventory of Ariva's resource-demanding operations: what makes each costly, the bounds that hold it, its timeouts, its rate limit or concurrency limit, where each is set and the test that proves it. For a site's operations team sizing a deployment, for reviewers of a change that adds a read, an upload, a job or a consumer, and for the availability defences of [asvs-l2](asvs-l2.md) V15.2.2.

Status: this page describes the code as of 2026-10-21 (ARV-095, updated by ARV-096, ARV-096b to ARV-096e). ARV-096 gave Ariva.Api.Main request timeouts (a default for every endpoint without its own policy, and policies for the on-demand reports, the file transfers and the validation results, the live hub exempt) and a concurrency policy on the on-demand report and CSV endpoints; the values are Proposed (docs/product/decisions.md, ARV-096). Its security review added the steady upload (section 7): every upload reads its body with the request's token and, over HTTP/1.x, at 32 KB a second or more, so a slow sender holds the one upload slot for minutes, not hours. ARV-096b gave the four other hosts the default request timeout (Ariva.Api.Cronz's TickerQ dashboard and, while the login freeze lasts, Ariva.Api.Integration's token exchange exempt), the live hub a total of connections per replica, a request that sends no credentials no slot of a user's concurrency policy, and every body under a concurrency policy a steady read. Section 15 lists the costly operations that still have no limit or no timeout.

## 1. Purpose and how to read it

This page serves ASVS 5.0 V15.1.3 (document resource-demanding functionality and its availability defences). It gathers what other pages give feature by feature: the file uploads in [wiki 13a](../../wiki/13a-File-Handling.md), the Integration API's batches and AIDX in [integration](../architecture/integration.md), floor plans in `security/README.md`, and the measured bounds in `docs/product/decisions.md` (ARV-104g, points 1 and 8; ARV-123a, point 5).

Columns:
- **Cost driver**: what grows with the input or the data (memory, rows read, CPU, time held).
- **Limit**: the bound on that driver. "Refused" means a request over the bound gets an error rather than a cut answer; "cut" means the answer is marked as truncated.
- **Timeout**: what ends the operation if it runs long. "None" means none was found in Ariva's code; the platform's defaults may still apply (section 14).
- **Rate limit or concurrency**: the policy of `Ariva.Api.Common/Extensions/RateLimitingExtensions.cs` (or another limiter) that applies on top of the global per-address limit of section 2.
- **Where set**: file and symbol, or the setting (`Section:Key`) with its default.
- Unit tests are in `Platform/Backplane/Ariva.UnitTests`, integration tests in `Platform/Backplane/Ariva.IntegrationTests`, end-to-end specs in `Platform/Testing/Ariva.E2E/tests`.

Every limiter rejection answers 429 with `Retry-After`: a window limiter's own time, or 10 seconds for a concurrency limiter, whose lease names none (`RateLimitingExtensions.ConcurrencyRetryAfterSeconds`). The rate limiting middleware runs before authentication, so floods are refused before any token work (`UseAppRateLimiting`). Since ARV-096b the user concurrency policies (`upload`, `backtest`, `validation-results`, `reports`) count every request that sends credentials, read as JWT authentication reads them (the Authorization header's values joined, empty ones dropped; `RateLimitingExtensions.PresentsCredentials`, `SessionConcurrency`): only a request that sends none goes to a partition with no limit, since authentication refuses it at once with 401, so it neither takes a slot nor waits for one; a forged token, a device key or Basic is counted for the moment its authentication takes (unit `SessionConcurrencyTests`; `ReportsLimitsTests.Get_Should_Answer401WithoutWaiting_When_TheReportsPolicyIsSaturatedAndTheRequestSendsNoCredentials`, and `Get_Should_Answer429_When_ASignedInCallerAddsAnEmptySecondAuthorizationValue` on the real JWT scheme, from the security review).

A request timeout (ARV-096 on Ariva.Api.Main, ARV-096b on every host) cancels `HttpContext.RequestAborted`, the token every action passes on: a read that takes it stops at the database (NHibernate hands it to Npgsql, which cancels the command), and a request whose answer has not started gets 503 with `Retry-After: 30` (the status code pages write the problem body). It runs after routing and authorization (on Ariva.Api.Integration after the session checks and just before the call audit, so it bounds the audit's read of a body while authentication stays as it was), so a request's wait for a concurrency permit is not counted. A response already streaming at the timeout (a file being sent) is cut off rather than answered 503, and work an endpoint runs without the token (an SSIM import's units after the first) goes on to its end. MVC reads a request body without the token too (its form reader and its JSON input formatter take none), so a timeout does not end a body that is still arriving: the uploads of section 7 read theirs themselves, with the token, before model binding (`SteadyUploadAttribute`), and since ARV-096b so does every endpoint under a concurrency policy that binds a body (the backtest and the validation results' recompute; the Integration API's batches and AIDX messages are read by its call audit, after `SteadyIntegrationBodies` asks them for the same rate); any other body is at most 1 MB (or the endpoint's smaller limit), holds no permit, and is cut only by Kestrel's own minimum rate (section 15, item 12). MVC's form value providers read a form sent to any action that has a parameter (a `CancellationToken` counts), whatever the action binds, without the request's token and before the action's 415: up to the endpoint's body limit (the global 1 MB unless it sets its own), file parts over 64 KB in the pod's `/tmp` until the request ends, under no concurrency policy, the anonymous endpoints included: Ariva.Api.Main's sign-in and refresh (only the `auth` limit, 10 a minute per address) and Ariva.Api.Integration's token exchange (`integration-auth`, 20 a minute per address; its pod's `/tmp` is 64Mi). The Integration API's client-scoped endpoints read the whole body into memory first instead (the call audit, `IntegrationAuthentication`), up to the endpoint's limit, 5 MB for AIDX under its concurrency policy. This is older than ARV-096; ARV-096c refuses such a form before model binding (section 15, item 13).

## 7. Imports and uploads (Ariva.Api.Main)

Every upload, and the site configuration export, shares the `upload` concurrency policy: 1 at a time per host and 2 waiting, oldest first (`RateLimitingExtensions.UploadPolicy`, fixed in code), and has the `transfer` request timeout instead of the default (ARV-096: 15 minutes, `Security:RequestTimeouts:TransferSeconds`, 60 to 3,600 s; `RequestTimeoutsTests.Endpoints_Should_GiveEveryUploadAndWholeFileTheTransferPolicy_When_MainMapsThem` keeps the two together). Why not the default: the SSIM import was measured at 12,800 legs in 48 s (about 3.75 ms a leg, Testcontainers PostgreSQL on the development container), so its 100,000-leg bound takes about 6 minutes, and an upload at the slowest rate it is allowed (32 KB a second) brings 20 MB in about 11 minutes. Details per upload: [wiki 13a](../../wiki/13a-File-Handling.md), section 3. A request that sends no credentials takes no upload slot and waits for none (ARV-096b): it ends 401 at authentication (section 1).

Every upload also arrives steadily or ends (ARV-096, from its security review: `SteadyUploadAttribute` in `Ariva.Api.Common/Filters`, a resource filter on each endpoint of the `upload` policy; the advertisement upload takes the same steps through `AdvertisingUploadLimitAttribute`, which also sets its installation's size; `SteadyUploadTests.Endpoints_Should_ReadEveryUploadSteadily_When_MainMapsThem` keeps the inventory). Without it a body trickling in just above Kestrel's own minimum rate (240 bytes a second) held the host's one upload slot, and so every other upload and the export, for about a day at 20 MB. Before model binding the filter sets the request's minimum body rate over HTTP/1.x to 32 KB a second once 10 seconds have passed (Kestrel takes no per-request rate on HTTP/2 or HTTP/3, whose connections keep the server's own), so the largest body, 20 MB and the form's framing, is in within about 11 minutes (642 s) and a 1 MB CSV within about 32 s; a slower one is cut off with 408 and frees the slot at once. It then reads the body itself with the request's token (MVC's form reader and JSON input formatter take none), so the `transfer` timeout ends a read still going at 15 minutes on any protocol: a form through `ReadFormAsync`, the site configuration's JSON buffered whole (in memory to 30 KB, then a temporary file under `/tmp`, removed with the request) for model binding to read again; a form is read whatever the action binds (MVC's form value providers would read it anyway, without the token), and any other body the action does not bind whole is never read here. The answers are fixed texts: 413 with the endpoint's own refusal of a file too large (declared, or growing past the limit while read), 408 for a body too slow and 400 for one cut short or malformed. ## 15. No limit or timeout found

Costly operations that lack a bound, a timeout or a concurrency limit in Ariva's code today. None is fixed by this page; items 1 to 3 say what ARV-096 closed and what stays open; items 2, 9, 10 and 12 were closed by ARV-096b, items 1, 4 and 5 by ARV-096d and items 6 to 8 by ARV-096e.

1. **On-demand daily report and its CSV** (`ReportsController.Daily`, `DailyCsv`). Closed by ARV-096: the `reports` concurrency policy (2 at once and 4 waiting per host, 429 beyond) and the `reports` request timeout (60 s, 503 with Retry-After), whose token every read passes to the database (section 4). Closed by ARV-096d: every read of the report is bounded (`DailyReportLimits`: 300,000 queue minutes, that is 200 queue zones for a 25-hour day, 2,000 zone names, 2,000 devices, 20,000 outages) and a day past a bound is refused, never cut short, measured at that bound and at the 500 zones a profile can hold (section 4). Left: a site of more than 200 queue zones gets no daily report until ARV-234 aggregates the read by the hour in the database (Phase 3).
2. **Request timeouts on the other hosts**. Closed by ARV-096b: Ariva.Api.Ingest, Integration, Stream and Cronz have the default (120 s) too. Exempt: Ariva.Api.Cronz's TickerQ dashboard and its hub, a branch of the pipeline before the timeouts; and, while the login freeze lasts, Ariva.Api.Integration's token exchange, kept as it was until ARV-089a. Ariva.Api.Ingest's pushes (256 KB at 1 KB a second at least) arrive well within it.
3. **Reads of section 3 without a concurrency policy**: arrival wave, desk states, immigration view, overflow bands, zone health, availability, device health, advertising timeline, staffing recommendation, searches. Since ARV-096 each is under Ariva.Api.Main's default request timeout (120 s), so none holds a thread past it; none has a concurrency limit beyond the global per-address limit. Open because each bounds its rows and answers in seconds; a concurrency policy for a read class is for the load harness (ARV-071) to show a need. The backtest (section 6) has its own concurrency policy and the default timeout, and was measured at its bound by ARV-096b: a 64-zone rule over a day (92,160 minutes; a sensor rule 1,000 devices over 1,441 minutes) took 3.1 s at the most, so it keeps the default (integration `BacktestBoundTests`, a 4-core development container with the database on the same host, Debug build; lab measurements).
4. **Search counts**: closed by ARV-096d for the two searches whose tables grow with time and need no date range: the audit and alert searches count at most 10,000 matches, say so, and page no further (section 3). The other paged searches count tables bounded by configuration (users, sites, devices, rules, displays).
5. **Database command timeout**: closed by ARV-096d (section 14): `Database:CommandTimeoutSeconds` on every host's connections and a `statement_timeout` on the runtime login. A timeout answers 500 on the request that hit it (Npgsql's cancellation, as before). With ARV-083a's per-host logins, each login gets the same server limit.
6. **TickerQ jobs and background loops**: closed by ARV-096e. Every job and every loop of the hosts ends each run at its run timeout, cancelling its statements and calls (section 12); the hosted services without one are named with their reasons in `RunTimeoutInventoryTests`, which also runs every loop and job against a database that never answers. A new connection the server never answers ends at `Database:ConnectTimeoutSeconds` (section 14).
7. **Secret re-protection round**: closed by ARV-096e in time: a run ends at 30 minutes, and a cut run rewrites nothing (one transaction). It still reads every protected secret of the deployment in one round, one statement each, bounded by the number of accounts, clients and endpoints (`SecretReprotectionRound`).
8. **Kafka consumer handlers**: closed by ARV-096e. Confirmed first: no handler timeout existed, so a stuck handler held one of its endpoint's 8 slots. Each attempt now ends at `Kafka:Consumers:HandlerTimeoutSeconds` (70 s) and is retried, then dead-lettered (section 10).
9. **Live hub connections per replica**. Closed by ARV-096b: at most `Security:Hubs:MaxConnections` per replica, every session together (1,000 Proposed, 10 to 20,000, refused at start beyond), beside the 8 a session may hold; a negotiate beyond is answered 429 with `Retry-After` (security event 9116, policy `hub-connections`), and a connection past the total, negotiated or not, is closed at its handshake (`hub_full`). The default is Proposed: about 70 MB of buffers at the most; the load harness (ARV-124a) measures it.
10. **Integration batches and AIDX** (Ariva.Api.Integration). Closed by ARV-096b: the default request timeout runs before the call audit, which reads the body with the request's token, so a batch whose body stops arriving is answered 503 at 120 s and frees its permit; over HTTP/1.x the bodies must arrive at 32 KB a second or more (`SteadyIntegrationBodies`), so a 1 MB batch is in within about 40 s. An AIDX message (up to 5 MB, so up to about 170 s at that rate) has the `transfer` timeout (15 minutes) instead. A batch holds at most 500 items.
11. **Not built**: the forecast job and SLA evaluation (Cronz), the Integration API's `queues:read` and `displays:read` endpoints, and the weekly summary and advertising figures endpoints (ARV-146). Their limits come with their stories.
12. **Slow request bodies outside the uploads**. Closed by ARV-096b for every body under a concurrency policy: the alert rule backtest and the validation results' recompute read theirs with the request's token and, over HTTP/1.x, at 32 KB a second or more (`SteadyUploadAttribute`, with their own 413 text), and the Integration API's batches and AIDX messages likewise (item 10); `SteadyUploadTests.Endpoints_Should_ReadEveryBodySteadily_When_AConcurrencyPolicyHoldsThem` and `Endpoints_Should_HaveTheirBodiesReadSteadily_When_AConcurrencyPolicyHoldsThemOnIntegration` hold every concurrency policy to it. A body under no concurrency policy (at most 1 MB) holds no permit and is still cut only by Kestrel's own minimum rate (240 bytes a second after 5 s), since MVC reads it without the token; over HTTP/2 a per-request rate is not available and the request timeout ends what the token reads. Ariva.Api.Ingest's pushes set their own rate (1 KB a second) over HTTP/1.x only since ARV-096b: Kestrel refuses a per-request rate on HTTP/2, so a push over HTTP/2 failed before.
13. **Forms sent to the endpoints the login freeze keeps as they are** (until ARV-089a). Since ARV-096c every other action that binds no form field or file answers a form 415 with a fixed text before anything reads it (`UnboundFormFilter`, a global resource filter before model binding; `UnboundFormTests`), and every action that binds one is under the `upload` policy and reads it steadily; what follows now holds for Ariva.Api.Main's `api/auth` controller and Ariva.Api.Integration's token exchange only. Before ARV-096c it held for every host's MVC endpoints: MVC's form value providers read a form sent to any action that has a parameter (a `CancellationToken` counts), whatever the action binds, without the request's token and before the action's 415: up to the endpoint's body limit (the global 1 MB unless it sets its own), file parts over 64 KB in the pod's `/tmp` until the request ends, under no concurrency policy, the anonymous endpoints included: Ariva.Api.Main's sign-in and refresh (only the `auth` limit, 10 a minute per address) and Ariva.Api.Integration's token exchange (`integration-auth`, 20 a minute per address; its pod's `/tmp` is 64Mi). The Integration API's client-scoped endpoints read the whole body into memory first instead (the call audit, `IntegrationAuthentication`), up to the endpoint's limit, 5 MB for AIDX under its concurrency policy. This is older than ARV-096. On api-main the 128Mi `/tmp` holds the one upload in progress and every such form at once, so enough held requests fill it and the pod is evicted (about 130 forms of 1 MB; about 64 on Ariva.Api.Integration). Behind ingress-nginx, which buffers a request body before passing it on, a form reaches the pod whole and is held only as long as its request runs: an answer read slowly holds it up to the `transfer` timeout (15 minutes) on the whole-file downloads and the default 120 s elsewhere. Where bodies are not buffered (a pod reached directly, or another ingress), a body sent quickly and then stalled before its closing boundary holds its form for about 73 minutes per MB, since Kestrel's minimum rate is an average and no request timeout ends MVC's read; the anonymous endpoints allow that too. The sign-in endpoints and the Integration token exchange join the filter when the owner lifts the login freeze (ARV-089a).
14. **Backtest and sensor reads at their bounds** (found by ARV-096b's measurement; ARV-228, Phase 3). Time is not the cost but memory: a backtest at the bound allocates 146 to 397 MB (NHibernate maps every row through `AliasToBean`, about 1.5 KB a `queue_minute` row and 3.6 KB a `lane_staffing` row), so the `backtest` policy's two running and two waiting may churn about 0.8 GB at once on one host. The `lane_staffing` read of a day touches the whole day's chunk (interval 0 sits among intervals 1 to 12), and the P90 read reaches back a day of bins where 15-minute bins need 150 minutes. `zone_outage` has no time index and no retention, so the sensor backtest's outage read, and the daily and weekly reports' (`ReportReader`, `WeeklySummaryReader`), grow with the table's history rather than with the range read (a synthetic year of 1.47 million outages turned a 3 ms read into a 65 ms full scan).
15. **The queue engine's reorder buffer and checkpoint** (found by ARV-124a's pilot load run; ARV-230, High, and ARV-231, Medium, both before the pilot). The engine holds every track position for its zone's lateness (90 s) though a position only updates an open entrant's last sighting, so a zone's state grows with its sensors' position rate: about 20 MB of JSON at 6 T3 sensors, written whole for every zone at every checkpoint (every 5 s). The bounds hold (100,000 buffered events, 64 MiB a saved state) but are too wide for the pod: with the heap .NET takes from the 1500Mi limit, Ariva.Api.Stream ran out of memory three minutes into the pilot hall's steady rate. Beyond the buffer bound (a zone with more than about 7 T3 sensors) the engine refuses events of every kind, crossings included; the refusals are counted in the step's rejections but never logged, measured or stored (wiki 05, sizing notes).
16. **Database connections** (found by ARV-124a; ARV-232, Medium, before the pilot). Every host and replica keeps Npgsql's default pool (up to 100), and nothing bounds the sum against PostgreSQL's `max_connections` (100 by default): one replica of each host held up to 94 at once at the pilot rate, and at the D5 burst a display board answered 503 (53300).
