# Security

## Exceptions

`allowlist.json` holds the only permitted exceptions to the security gate (`node scripts/security/scan.mjs`).

Each entry needs: `rule` (SEC-nnn), `path` (repository relative, forward slashes), optional `contains` (text that must appear on the flagged line), `reason`, `proposedBy`, `approvedBy` and `date`. Entries for SEC-052 (anonymous endpoints) also list the route patterns they cover in `routes`, for example `["/health/startup"]`; `EndpointInventoryTests` boots every host and fails when an anonymous endpoint's route is not listed by an entry for the file that maps it. `AllowlistTests` fails CI when any field is missing or malformed.

An entry whose `approvedBy` starts with `PENDING` downgrades the finding to a warning instead of hiding it, so unapproved exceptions stay visible in every report. Only a human approver replaces `PENDING`; agents may propose entries but never approve them (enforced by the `guard-paths` hook, which simulates each agent edit and refuses it if any approved entry in the result is new or differs from the current file).

## Baseline

Every Backplane host calls `AddAppSecurityBaseline` and the matching middlewares from `Ariva.Api.Common` (see `Extensions/SecurityBaselineExtensions.cs` for the order). Settings live in the `Security` section of `appsettings.base*.json`.

| Control | Where | Settings |
|---|---|---|
| Default deny (CWE-862, CWE-306): the `Ariva.Deny` placeholder scheme never authenticates and the fallback policy requires an authenticated user, so everything except the allowlisted probes answers 401. The authentication story replaces the placeholder with the JWT bearer schemes. | `Security/DenyAuthenticationHandler.cs`, `Extensions/SecurityExtensions.cs` | none |
| API security headers: `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `Cache-Control: no-store` when the request carries credentials, no `Server` header | `Middlewares/SecurityHeadersMiddleware.cs` | none |
| Input limits (CWE-120): Kestrel body (1 MB), request line, headers and header timeout; form limits; JSON `MaxDepth` 32 | `Extensions/RequestLimitsExtensions.cs` | `Security:Limits` |
| Rate limiting: global fixed window per client IP and the stricter `auth` policy for login endpoints | `Extensions/RateLimitingExtensions.cs` | `Security:RateLimiting` |
| Errors as ProblemDetails; exception details only in vm-local | `Extensions/ErrorHandlingExtensions.cs` | environment |
| Forwarded headers trusted only from the listed proxies and networks (none by default; the k8s files list the private ranges and should be narrowed to the cluster's pod network) | `Extensions/ForwardedHeadersExtensions.cs` | `Security:ForwardedHeaders` |

Ariva.Simulation.Api keeps its own small copy (default deny, no `Server` header, body limit, ProblemDetails, headers) because it references Ariva.Business.Contracts only, and it refuses to start in k8s-prd. Its scenario endpoints (ARV-027) need an operator key (`Ariva.SimulationKey` scheme in `Security/SimulationKeyAuthentication.cs`): the bearer key is hashed with SHA-256 and compared in constant time with the configured digests, scopes `read` and `control` map to two policies, re-runs are rate limited per key, and with no key configured nothing authenticates. Ariva.Web sends its CSP and headers from nginx and from `vite preview`, both generated from `Platform/Frontplane/Ariva.Web/csp.config.js`.

## Permissions (ARV-009)

- Controllers authorize with `[Permission(nameof(Global.Defaults.Permissions.ViewDesk))]` (several names mean any one of them). The attribute is an `AuthorizeAttribute` whose policy `PermissionPolicyProvider` builds on demand; an unknown name fails closed. Controllers never name roles.
- `Global.Defaults.Permissions` (Ariva.Core) catalogues every permission as `Entity.Action` with View, Create, Edit, Search and Delete per entity, plus special actions such as `ZoneProfile.Publish`. Codes never change once shipped.
- `RolePermissions` (Ariva.Core/Security) is the role seed for BorderShiftSupervisor, TerminalDutyManager, HandlerStationManager, SystemAdministrator and, since ARV-104a, ValidationObserver (`Validation.Capture` only, and the only role holding it: the administrators' "every permission" rule leaves it out, owner decision 2026-10-08). Audit entries are read-only for every role; only SystemAdministrator manages users, roles and integration clients; product version (`/api/v1/system/info`) is for SystemAdministrator only.
- `permission-matrix.json` lists every endpoint of every host with the status each caller gets (anonymous and each role). `PermissionMatrixTests` fails when a host maps an endpoint that is not listed, when a permission row disagrees with the seed, or when a host answers a row differently; the E2E suite reads the same file with real tokens for each role. Add the rows in the story that adds the endpoint. Routes are templates: `{id:guid}` is called with `routeValues.guid`, an id that never exists. A row's optional `body` is sent as JSON and must fail the same way with and without a database (unknown user, wrong current password, unknown id), because the in-process hosts have none.
- Permissions come from the user's stored role grants (`user_role`), looked up by the token's `sub` and cached for one minute under the tag `user:{id}`; tokens carry no roles. ARV-011 adds the administration of grants with this seed as the default.

## Accounts and tokens (ARV-010a, ADR-0026)

- Local accounts only. Passwords: PBKDF2-SHA256, 600,000 iterations, 16-byte salt, never trimmed; 12 to 128 code points; refused when on the bundled breached list (46,146 entries of 12 or more characters from SecLists, MIT) or when they contain the username, `ariva`, the site code or an `Auth:ContextWords` entry. Weaker stored hashes are upgraded at the next sign-in.
- Every sign-in failure (wrong password, unknown, malformed, disabled or locked account) is the same 401 body after one full PBKDF2 verification. 10 consecutive failures lock the account for 15 minutes; failures are counted in one SQL statement so parallel attempts cannot lose counts. The `auth` rate limit allows 10 sign-ins a minute per client address.
- Access tokens: ES256 only, header `typ` `at+jwt` and `kid` (first 16 bytes of the SHA-256 of the public key), issuer `ariva`, audience `ariva-users`, 15 minutes, 30 seconds of skew, read from the `Authorization` header only. Only Ariva.Api.Main holds the signing key; every host holds the public keys (current and, during a rotation, previous). Key handling: [wiki/04-Deployment-Guide.md](../wiki/04-Deployment-Guide.md).
- An account with a temporary password (and, from ARV-010c, without TOTP) gets a token with `scope` `pending`, which `PendingScopeMiddleware` confines to endpoints marked `[AllowPendingScope]` (change password, logout, later TOTP enrolment) and anonymous ones.
- Sessions (ARV-010b): every sign-in creates a `user_session` row (the token's `sid`) and a refresh family; a refresh cookie sent with the sign-in is revoked (CWE-384). Every host checks the session of every authenticated request (`SessionValidationMiddleware`, cached 4 seconds per node and evicted through the Redis backplane on revocation), so logout, a disabled account, a password change (other sessions) and refresh token reuse end access within 5 seconds (CWE-613); the answer is 401 with `error: session_expired`. Lifetimes: 12 hours absolute; idle 30 minutes for SystemAdministrator (and accounts without an operational role), 4 hours for operational roles, extended by refresh.
- Refresh tokens: 256 random bits, stored as SHA-256 hex, used once. The claim is one UPDATE whose row lock orders two tabs refreshing together; within 30 seconds a used token returns its successor once (kept Data Protection encrypted until then), any other reuse revokes the family and logs `SecurityEvent.RefreshTokenReused`. The token travels only in `__Secure-ariva_rt` (HttpOnly, Secure, SameSite=Strict, Path=/api/auth, Max-Age the remaining absolute lifetime); `/api/auth/refresh` also needs `X-Ariva-Csrf: 1` and an Origin from `Security:Cors:AllowedOrigins` (CWE-352).
- SignalR hubs opt in with `AddSignalR().AddArivaHubSessions()`: the session is checked on connect and on every invocation, and a sweeper closes the connections of ended sessions every second.
- TOTP (ARV-010c): RFC 6238 (HMAC-SHA1, 6 digits, 30 seconds, one step either side), 160-bit secrets Data Protection encrypted (purpose `Ariva.Totp.v1`) and shown once at enrolment; the enrolment counts only after a valid first code. The last accepted step is stored on the user row and a code for it or an earlier one is refused in one UPDATE (CWE-294). An enrolled account sends its code with the password; without one the answer is 401 `mfa_required` (only after a correct password), and wrong codes count towards the same lockout. Ten Crockford recovery codes per enrolment, shown once, SHA-256 at rest, single use, regenerated with a TOTP code and a recent second factor. `Auth:TotpRequired` is on everywhere; only the E2E run turns it off for its general accounts.
- Break-glass (ARV-010c): one account per deployment (unique index), created and rotated only by `Ariva.Api.Main --create-break-glass` / `--rotate-break-glass`, signs in with its password and a recovery code, is never locked out, logs `SecurityEvent.BreakGlassSignIn` at Critical, and cannot be re-enabled through any API. Procedure: [wiki/04-Deployment-Guide.md](../wiki/04-Deployment-Guide.md).
- Step-up (ARV-010d): a critical action carries `[RequiresRecentMfa]` (15 minutes) and is listed in [critical-actions.json](critical-actions.json); `CriticalActionsTests` fails when the two disagree, when an endpoint guarded by a permission in `criticalPermissions` lacks the attribute, or when an attribute allows longer. The check reads `amr` (`otp` or `rc`) and `auth_time` from the token. A caller who only lacks the recent second factor gets 401 with `WWW-Authenticate: Bearer error="insufficient_user_authentication", max_age=900` (RFC 9470) and a problem with `error: mfa_required`; a caller who also lacks the permission gets the ordinary 403, so step-up never reveals an action. `POST /api/auth/step-up` takes a TOTP or recovery code for the current session, shares the replay guard and the lockout, records the new `auth_time` on the session (so refreshed tokens keep it) and returns a new access token. The matrix callers have no recent second factor, so critical rows expect 401.
- Administration (ARV-011): `api/v1/admin/users` (search, view, create, update, reset password, reset TOTP, grant and revoke roles, unlock, disable, enable), `api/v1/admin/roles` and `api/v1/admin/audit-entries`. Creating a user, both resets and every grant or revoke are critical actions. The five roles are fixed and ranked (`RoleHierarchy`: SystemAdministrator above the three operational roles and the validation observer, ARV-104a); an administrator never changes its own roles, password or authenticator through these endpoints and never grants or revokes above its own rank, and the last active regular administrator keeps the role (the break-glass account does not count). An account whose only role is ValidationObserver is never given every site: creation, a site change, a grant or a revoke that would leave it so answers 400 (ARV-104a). New accounts and password resets get a 20-character temporary password shown once and the pending scope. A revoke, a password reset and a TOTP reset end every session of the user; a grant or revoke evicts the cached permissions after commit. The break-glass account is invisible to these endpoints (404).
- Audit (ARV-011): every administrative change writes an `audit_entry` in the same transaction (actor, address, trace id, action code from `AuditActions`, before and after summaries without credentials). The API only reads it (`AdministrationTests` checks there is no write endpoint and no role holds a write permission), and script 0006 revokes UPDATE, DELETE and TRUNCATE on the table from the runtime login, so even a bug cannot rewrite it.
- Site scoping (ARV-012): a site (`site`, upper case code such as `AMM` or `AUH-T1`) is the unit of data access. A user has every site (`all_sites`) or the sites in `user_site`; `ISiteScope` resolves them per request (cached a minute, evicted with the roles on every change). Lists return only the caller's sites, and another site answers 404 exactly like an unknown one. `PUT api/v1/admin/users/{id}/sites` is a critical action, never on one's own account and never beyond the granter's own sites; narrowing ends the user's sessions. An administrator acts only on accounts whose access its own covers (others answer 404, including in search and the audit trail), and only an all-sites administrator creates sites. Existing administrators and the break-glass account have every site (script 0007), so site access can always be bootstrapped. The last active administrator can be neither revoked nor disabled; the check runs under a transaction-scoped advisory lock so two administrators removing each other at once leave one. `[SiteScoped]` marks every action with a site, airport or terminal reference and `SiteScopeTests` fails the build otherwise.
- Floor plans (ARV-018): `api/v1/admin/levels/{levelId}/floor-plan` takes PNG, JPEG or SVG up to 20 MB (`[RequestSizeLimit]` plus a bounded read; 413 beyond), one upload at a time per host with two waiting (`upload` concurrency policy; 429 beyond) so concurrent bodies cannot exhaust memory or `/tmp` (CWE-400). The type comes from the bytes, never the name or declared type; HTML or anything else is 400. PNG needs IHDR first and JPEG a start-of-frame; either is refused above 16,384 pixels a side or 128 megapixels, so no viewer decodes a pixel bomb. SVG is streamed with DTDs prohibited (CWE-611), at most 200,000 elements and depth 64, through an allowlist: listed SVG-namespace drawing elements only (script, style, `foreignObject`, `image`, `a`, animation, filters and every other namespace dropped with their content), listed attributes only, `href` and `url()` only as `#id`, no CSS escapes, at-rules or image functions, `xml:base` dropped, CDATA written as escaped text (CWE-79). Files are stored through `IFileStorage` under a generated key (`<32 hex>.<png|jpg|svg>`, checked against one pattern and resolved under the root); the uploaded name is display text only and refused when it carries a path, `..`, a drive separator, control or format characters (right-to-left override) or a lone surrogate (CWE-22). The image is served with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox; frame-ancestors 'none'` and `nosniff`; `SecurityHeadersMiddleware` keeps an endpoint policy only when it starts with `default-src 'none'` and denies framing, and adds the API baseline otherwise. A replacement locks the level row, so concurrent uploads queue rather than race the one-live-plan index; a level with a live plan cannot be deleted.
- Zone profiles (ARV-017): publishing is a critical action ([RequiresRecentMfa], `critical-actions.json`); drafts and versions are limited to the caller's sites (404 outside); one draft and one published version per site and unique version numbers are enforced by unique indexes, and edits and publishing of a profile are serialised by a row lock on the profile taken before it is read (publishing also locks the site), so what is validated and hashed is what is stored. Publishing names the geometry hash the publisher reviewed and is refused (409) when the draft changed since. Zone and line changes are audited with their name, kind, level and a SHA-256 of the polygon or the line's ends; framework and driver exceptions never reach the response (CWE-209). A published or retired version never changes: the service answers 409 and triggers in script 0012 refuse any update of its geometry or any delete (SQLSTATE 23001), so SLA evidence cannot be edited after the fact. Every change is audited.
- Devices (ARV-021): registering a device, rotating its credential and retiring it are critical actions ([RequiresRecentMfa], `critical-actions.json`). The credential is `ardk_` plus 256 random bits (base64url), generated by the server, returned once with `Cache-Control: no-store` and never again; the database keeps only its first 13 characters (to find the device) and its SHA-256, and audit entries and registry events carry the prefix at most (CWE-287). Retiring or removing a device clears the hash, so it can never authenticate again (a check constraint in script 0013 holds even against a bug). Devices belong to the site of their level and are limited to the caller's sites (404 outside); retiring and removing need `DeleteDevice`, which only administrators hold (CWE-863). Kinds are parsed by name only (codes and ids are matched to the true end of the string, so a trailing line break is not a code), models and zone names refuse control, format (right-to-left override) and split surrogate characters, positions must lie in the level and the footprint must reach the owning queue zone (CWE-501). Calibrations are evidence: the pass verdict follows from the numbers (check constraint), and a trigger refuses any update or delete (SQLSTATE 23001); a device goes Online only after a pass for a zone in the published profile. A refused request rolls back explicitly, because the request's unit of work otherwise commits what it touched; registrations in a site are serialised by the site row and changes to a device by its row.
- Device authentication (ARV-022): a scheme of its own (`Ariva.Device`) used only by `[DeviceAuthenticated]` endpoints on Ingest, which accept nothing else (a user token is 401) while the device credential opens no user endpoint (CWE-287, CWE-306). The credential arrives as `Bearer ardk_...`, `X-Ariva-Device-Key` or Basic with the device code; it must be well formed, its prefix must find a live device, and its SHA-256 is compared in constant time (a miss hashes against a placeholder, so timing does not tell a known prefix from an unknown one). A device may be limited to CIDR source networks (after the trusted proxies) and bound to a pinned client certificate (forwarded by the ingress only when configured); changing either, like rotating, is a critical action. `[DeviceAuthenticated(ownZoneOnly: true)]` answers 403 when the route names a zone other than the device's own queue zone (CWE-863). The device lookup is cached for at most a minute under a tag every registry change evicts after commit, on every host through the backplane, so rotation and retirement take effect at once (within a minute without the backplane). Device endpoints are rate limited per presented credential prefix before any database work; failures are logged with the prefix and reason, never the credential.
- Validation campaigns (ARV-104a, script 0047): `api/v1/sites/{siteCode}/validation/...` with `Validation.View`, `Validation.Manage` (closing a campaign is a critical action, `critical-actions.json`) and `Validation.Capture` (the observer side; the ValidationObserver role holds nothing else and no other role holds it). The account that created or started a campaign never counts for it, also when it holds the observer role besides a manager role (403; script 0047's insert trigger refuses such a row from any statement). An Idempotency-Key belongs to the observer who sent it: the replay looks among the caller's own counts and the key is unique per observer, so another observer's identical key makes a count of its own (CWE-863). The site is checked first and a campaign of another site, or another observer's count, answers 404 like a missing one (CWE-863); request models only, every string bounded, bodies of at most 32 KB (a campaign) and 4 KB (a count) (CWE-501, CWE-120); search sorts and status filters come from allowlists and all SQL is parameterised (CWE-89). Counts name their observer by Ariva user id only and the schema has no person name or document column (`ValidationTests.Schema_Should_HoldNoNameOrDocumentColumnOfAPerson...`). Evidence is append-only: corrections are new revisions with a reason, the runtime role has no UPDATE on counts or scope and only the lifecycle columns of a campaign, nothing is deleted, and triggers refuse a count outside a running campaign (share lock against a concurrent close), a correction that skips a revision, a scope row outside the campaign's profile version, and any change to a closed campaign (CWE-269). Create, start, close and every correction are audited.
- Tracer runs and desk observer logs (ARV-104b, script 0048): `.../validation/campaigns/{id}/tracer-runs` and `.../desk-observations` (`Validation.View`), `.../validation/capture/campaigns/{id}/tracer-runs`, `.../desk-observations` and `.../desk-observations/{observationId}/corrections` (`Validation.Capture`), with the same site check, 404 rules, separation of duties (403 and the triggers) and close lock order as counts. A batch needs an Idempotency-Key that belongs to its observer (replay among the caller's own batches, unique per observer and key). A tracer batch carries the device's own clock reading; the server measures the offset (device minus receipt), refuses more than 5 minutes and stores the device times, the offset and the corrected times. Tracer codes are campaign labels (`T-` and 2 or 3 digits, checked in code and by a database CHECK), never names. Desk states are border data, decided by one rule (`BorderDeskAccess`): only a caller with `BorderDesks.View` puts desks in a campaign (403 otherwise) or reads their states (others get an empty page marked `desksIncluded` false); only a caller with `BorderDesks.View` or whose only role is Validation observer sees the desks to log and logs, corrects and reads back desk states, so an account that holds an airport role and the observer role gets no desk and 403 (first security review, 2026-10-08); the observer reads back only what it recorded. Times outside the planned days or in the future beyond a minute answer 400 with the rule, never the value, and a tablet time more than 32 days before or a minute after the tablet's own clock reading is refused before the clock correction (an absurd year used to overflow it, 500). At most 500 tracer runs per observer and campaign (409). 400 answers never repeat what was sent, on all hosts: model binding messages do not quote a value that failed to bind, JSON reader messages are the fixed "The input was not valid." (`AllowInputFormatterExceptionMessages` false) and JSON paths, which quote the member names sent, become the key `body`. Bodies of at most 16 KB (a batch) and 4 KB (a correction); at most 20 runs, 20 desks of 15 states, 100 desks per campaign (CWE-120). The runtime role inserts and reads only (no UPDATE, DELETE or TRUNCATE on any of the five tables; CWE-269); desk state corrections are audited (`DeskObservation.Corrected`).
- Validation results (ARV-104g, script 0050): `.../validation/campaigns/{id}/results` (`Validation.View`; `?revision=n`) and `.../results/revisions` (`Validation.Manage`, critical: a second factor within 15 minutes, audited `ValidationResults.Recomputed`), `[SiteScoped]` with 404 across sites, the `validation-results` concurrency policy (4 at once, 8 waiting, 429) and a 90 s request timeout (503 with Retry-After). One stored document per revision with its SHA-256 (checked by the database at insert and by the service at every read; a mismatch or another campaign's document is not served); the answer is projected per caller from its stored roles: the desk section only with `BorderDesks.View`, observer-level results with View or Manage, the shadow's figures with View (CWE-863). One computation at a time per host and at most 400 zone-days per campaign (memory, CWE-400). The runtime role inserts and reads only; a trigger refuses updates and deletes (CWE-269).
- Messaging (ARV-020, ADR-0018): topic names come only from `KafkaTopics` constants and an event names its topic by attribute, never from input (CWE-77); producers send keyed values of at most 1 MB with acks from all in-sync replicas and idempotence, and topics are created with `max.message.bytes` 1 MB (CWE-120); values are plain JSON read into typed contracts, and a value that cannot be read goes to the dead-letter topic instead of being half applied (CWE-501). The outbox writes events in the entity's transaction, the inbox records each applied event in the consumer's transaction (a failed consumer rolls its claim back), and dead letters carry the exception type and message only, no stack trace. In production the connection is SASL over TLS with the cluster CA, or the host refuses to start; SASL credentials come from the secret (`Kafka__SaslPassword`). A dead letter's body is cut at 512 KB so it always fits the 1 MB limit, and its headers are bounded (50, 1,000 characters each).
- `Auth:DevelopmentUsers` creates accounts at startup in vm-local only (developers, the E2E run and the local demo, with random passwords); `Auth:TotpRequired` false likewise. Every host and the break-glass command refuse to start with either (`AddArivaAccounts`, `LocalOnlyProblem`) unless both the host's own environment name and `Application:Environment` are vm-local, so neither an environment variable on a cluster nor a mounted settings file without `Application:Environment` can switch them on (ARV-064). The host environment is what `ArivaEnvironment.Resolve` gives the host (the command line, DOTNET_ENVIRONMENT, ASPNETCORE_ENVIRONMENT, then `environment.json`), never the configuration key an unprefixed ENVIRONMENT variable sets. Neither side has a vm-local default (ARV-098): `environment.json` is in developer build output only (images are published without it), a host with no environment or an unknown name refuses to start, and `Application:Environment` comes only from `appsettings.base.<environment>.json` and must equal the host environment or the host refuses to start (tests `SecuritySettingsTests`, `SimulationEnvironmentTests`, and the chart rule that every .NET workload sets `DOTNET_ENVIRONMENT`).
