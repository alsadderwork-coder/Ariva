# Operations tooling (ARV-126)

Backup, restore and recovery for an Ariva deployment, and the TLS check of its hosts (ARV-084). Nothing here runs inside an Ariva host; the procedure is in [wiki 04 section 10](../../wiki/04-Deployment-Guide.md), the recovery steps in [wiki 10 section 4.13](../../wiki/10-Operations-Runbook.md) and the TLS check with what each finding means in [wiki 10 section 4.14](../../wiki/10-Operations-Runbook.md).

| File | Runs where | What it does |
|---|---|---|
| `ariva-ops.mjs` | An operator's machine (Node 22, kubectl, age 1.1 or later, ssh-keygen from OpenSSH 8.1 or later) | `backup` (database and files, each encrypted with age while it streams; the manifest of SHA-256 values signed with the operator's SSH key), `restore` and `files-restore` (the manifest's signature verified against an allowed-signers file kept outside the backup store before its hash is used, or a SHA-256 the operator gives from their own log; then a private copy hashed and decrypted, never the file given; since ARV-183 the allowed-signers file read by one strict grammar, a principal pattern or a `cert-authority` line refused unless `--allow-signer-patterns`, the verifying key's fingerprint and the set's namespace, time and database printed first (`--plan` prints them and starts nothing), and another namespace's set refused unless `--force-namespace`; `--allow-extension`, `--allow-login` and `--allow-setting` pass what a DBA-provided server carries on purpose to the checks), `keyring` (the Data Protection keys against the certificates you hold), `check`, `after-kafka-loss`, `update-extensions` (TimescaleDB's extensions to the image's versions after a new database image; ARV-236). `--plan` prints the commands; `--self-test` checks validation, argument arrays and the signed path with stand-ins for kubectl and age (run by `node scripts/verify.mjs security`) |
| `tls-check.mjs` | An operator's machine, or the dev release workflow after its release (Node 22 only; ARV-084) | Checks a site's hosts from outside and changes nothing: TLS 1.0 and 1.1 and every TLS 1.2 suite other than ECDHE with AES-GCM or ChaCha20-Poly1305 refused, TLS 1.2 and 1.3 working, the certificate verified for the host (`--ca`, or else Node's bundled Mozilla roots) in every handshake, so a host whose certificate does not verify fails on that alone and is offered no weaker protocol, suite or HTTPS request; a TLS 1.0 or 1.1 answer, or a weak TLS 1.2 suite, that arrives with a certificate that does not verify (a certificate other than the host's main one) counts as accepted; HSTS of a year with includeSubDomains and no preload on `GET /` and on the ingress's own 413, `GET /health/readiness` answered 404 by the ingress with the same headers (the probes are not routed; ARV-085), plain HTTP refused on the machine hosts and redirected on the browser ones. Hosts from `--host <name>[=refuse\|redirect]` or `--ingresses` (`kubectl get ingress -o json`, the chart's `ariva.dalil.tech/plain-http` annotation); `--resolve` for split DNS; `--summary` appends a Markdown table. `.github/workflows/release-dev.yml` runs it after the release; `--self-test` proves every rule against throwaway local servers, 36 stand-in hosts among them one that answers a weak protocol with a second certificate (run by `node scripts/verify.mjs security` and the CI security gate) |
| `ariva-db.sh` | Inside the TimescaleDB pod (copied to `/tmp` by `ariva-ops.mjs`) | `pg_dump` and the checks as the migration login with the password the pod holds; the restore's TimescaleDB steps as the database superuser over the local socket, which TimescaleDB requires (accepted by the owner, 2026-10-15); the extensions' update after a new database image (`update-extensions`, ARV-236) as the same superuser, which only the extension's owner may run, proposed and pending the owner: unlike the restore it runs TimescaleDB's update scripts on the live database, whose extension schema the migration login can write, so it first refuses Ariva sessions and functions or operators planted under the system's or TimescaleDB's names (a residual remains, wiki 04 section 6.8); a table of contents check before and a check after the restore for what a forged dump could leave (defence in depth; the signed manifest is the gate; since ARV-183 also privileged roles and what reaches them, role settings, ALTER SYSTEM settings, which it reads as the superuser with the search path pinned and only when nothing is planted, rules, functions outside the extensions but Ariva's own with a body its scripts ship, objects added to plpgsql, system functions replaced in place, publications and subscriptions); the republish of the compacted topics' state from the outbox |

Rules kept by both (CWE-78, CWE-269, CWE-532): every value is checked against a strict pattern, every command is an argument array started without a shell, values reach SQL only as psql variables, no password is on a command line or passes through the operator's machine, nothing unencrypted is written outside the cluster, nothing is restored without a signed manifest or the operator's own hash, and the Data Protection certificate's private key is never read. `Ariva.UnitTests/Operations/OpsScriptTests` keeps the script in step with the code, and `Ariva.IntegrationTests/Operations/BackupRestoreTests` restores a backup into a fresh server and starts the hosts on it.
