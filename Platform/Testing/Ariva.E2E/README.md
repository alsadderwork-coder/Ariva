# Ariva.E2E

API end-to-end tests and Playwright functional tests for Ariva. They run against real processes: the .NET hosts started with `dotnet run` and the production build of Ariva.Web served by `vite preview` with the same security headers nginx sends. They are layer 5 (behaviour tests) of the security gates in [docs/security/cwe-controls.md](../../../docs/security/cwe-controls.md).

## Projects

| Playwright project | Folder | What it drives |
|---|---|---|
| `api` | `tests/api` | Playwright's `request` fixture against Ariva.Api.Main (51001), Ariva.Api.Ingest (51002), Ariva.Api.Integration (51005) and Ariva.Simulation.Api (51020). No browser. |
| `functional` | `tests/functional` | Chromium against Ariva.Web on the `vite preview` port (51011). |
| `smoke` | `tests/smoke` | The read-only release smoke suite (ARV-128) against this local stack: health, the web sign-in page, the Ingest device check, the display board and player, the smoke account's sign-in and account check, the live hub, the daily report's route (403 for its role), and a sign-in through the web app. Its credentials come from `ARIVA_SMOKE_*` only: the config sets the addresses and the account `e2e.smoke` (a Handler station manager at site `E2SM` only, with an authenticator), and global setup gives E2SM a published profile, a test device and a display. Traces, screenshots and videos are off. A deployed environment runs the same specs with `npm run test:smoke` (`playwright.smoke.config.ts`, wiki 04 section 8.1). |
| `zap` | `tests/zap` | Only with `ARIVA_E2E_ZAP=1` (ARV-063): OWASP ZAP in its pinned image. API scans of the Main, Ingest and Integration OpenAPI documents (the hosts serve them in this run only) as `e2e.zapadmin`, with the sign-in, session and hub operations left out; baseline scans of every host and of the web build under the web image's nginx configuration. Reports, logs and `summary.md` in `zap-reports/`; fails on a High risk alert not in `security/zap-triage.json` and when a scan lost its session. Run it on its own (`node scripts/verify.mjs zap`): it attacks the hosts and leaves junk records. |

`playwright.config.ts` starts everything the suites need through `webServer` entries, one after another, waiting for each health URL: the first entry runs `scripts/build-backend.mjs` (one `dotnet build` per host) and then each host runs with `dotnet run --no-build` on its launchSettings port; the last entry runs `npm run build && npm run preview` in `Platform/Frontplane/Ariva.Web`. Outside CI an already running host or preview server is reused (`reuseExistingServer`); when you reuse Ariva.Api.Main, build the other hosts yourself.

### Behaviour worth knowing

- Default deny answers before routing. An anonymous caller (no token or an invalid one) gets 401 (with a ProblemDetails body) for unknown routes, wrong methods and TRACE as well, so routes cannot be enumerated. The genuine 404, 405 and 500 bodies are covered in `Ariva.UnitTests` (`ErrorHandlingTests`) with an authenticated test scheme.
- A 2 MB body sent to a protected route is answered with 401 before Kestrel reads it: authorization runs before model binding, and a client that sends `Expect: 100-continue` never uploads the body. Kestrel's 1 MB limit (413) applies once an endpoint reads a body. Request lines over 8 KB get 414 and header blocks over 32 KB get 431 from Kestrel.
- The web CSP allows SvelteKit's inline bootstrap script by hash (`kit.csp` in hash mode) and SvelteKit's route announcer style attribute by hash (`style-src-attr 'unsafe-hashes'`); there is no `'unsafe-inline'`. See `Platform/Frontplane/Ariva.Web/csp.config.js`.

## Run locally

Prerequisites: .NET 10 SDK, Node 22, and `npm ci` in `Platform/Frontplane/Ariva.Web` (the verify script does it when `node_modules` is missing).

```
cd Platform/Testing/Ariva.E2E
npm ci
npx playwright install chromium
npm test                    # both projects
npm run test:api            # API end-to-end only
npm run test:functional     # browser tests only
npm run report              # open the HTML report
```

From the repository root, `node scripts/verify.mjs e2e` installs missing dependencies and runs both projects.

Environment variables:

| Variable | Default | Purpose |
|---|---|---|
| `ARIVA_E2E_CONFIGURATION` | `Debug` | Build configuration for `dotnet build` and `dotnet run`. |
| `ARIVA_E2E_CHROMIUM` | not set | Path to an installed Chromium to use instead of the build that matches this Playwright version, for machines that cannot run `npx playwright install`. |
| `ARIVA_E2E_MAIN_URL`, `ARIVA_E2E_INGEST_URL`, `ARIVA_E2E_INTEGRATION_URL`, `ARIVA_E2E_SIMULATION_URL`, `ARIVA_E2E_WEB_URL` | the local ports | Point the suites at other ports or loopback addresses of this machine; a non-local address is refused (ARV-128). |
| `ARIVA_E2E_SCHEMA_UPDATE` | not set | `true` when PostgreSQL is up (CI, or `npm run dev:up` locally): the hosts migrate it at startup and the sign-in suites run. Without it they are skipped; in CI its absence fails the run. The hosts read `Database__*` from the environment (CI sets a separate migration and runtime login). |
| `ARIVA_E2E_REDIS_URL` | not set | `redis://[:password@]host:port` of a Redis for the live hub (ARV-035): Ariva.Api.Main uses it as its cache, SignalR backplane and live snapshot store, and `live-hub.spec.ts` publishes a snapshot there as Ariva.Api.Stream would. Without it the snapshot test skips. CI starts `redis:8.2-alpine` on 6380. `ARIVA_E2E_REDIS_INSTANCE` overrides the key prefix (`ariva:`). |
| `ARIVA_E2E_KAFKA_BOOTSTRAP` | not set | `host:port` of a single Kafka broker. Ariva.Api.Ingest provisions its topics there (one partition, replication 1) and answers sensor pushes 202 only once their events are in Kafka, so the accepted-push tests of `device-push`, `device-health` and `sensor-emulator` need it and skip without it. CI starts `apache/kafka:4.1.0` on 19092 and fails the run without it. |
| `ARIVA_E2E_CLAMD` | not set | `host:port` of the run's clamd (ARV-092b): Ariva.Api.Main gets it as `MalwareScan__Host` and `MalwareScan__Port` and streams every upload a test makes there before it stores it, so the scan path runs in every test. Without it a local run takes the clamd of `appsettings.local.json` (`npm run dev:up`, port 13310); `scripts/e2e-apphost.mjs` sets it to the AppHost's own. CI starts `clamav/clamav:1.4.3` on 3310 with `Platform/Cloud/clamav/clamd.conf` (offline, about 20 seconds to answer PING and about 1 GiB of memory) and fails the run without it; a non-local address or one that is not `host:port` is refused. |
| `ARIVA_E2E_KEY_DIR` | `.e2e-keys/` (git-ignored) | Where the hosts keep this run's development token key; `auth.spec.ts` reads it to sign tampered tokens. |
| `ARIVA_E2E_VALIDATION_READER_PASSWORD` | a random value per run | The password of the validation reader login `ariva_validation` (ARV-104g1), the only login that reads the shadow nowcast. Only Ariva.Api.Main gets it (`Database__ValidationReader__*`, with a database), as the chart gives it to api-main alone; Main migrates at startup and creates or updates the login. Every host refuses to start when its runtime login (`Database__Username`) can read the shadow nowcast (it holds `ariva_validation_reader` or `pg_read_all_data`, may select a value column, owns the table, or is a superuser), so the run's runtime login must be a plain login (CI's `ariva_app` is). The password must be printable ASCII. |
| `CI` | not set | When set: no server reuse, `forbidOnly`, one retry, two workers, and no traces (a trace records every header, body and typed value; ARV-152). |
| `ARIVA_E2E_ACCOUNT_SEED` | a random value per run | The seed of the E2E account passwords and TOTP seeds (`tests/support/accounts.ts`). `scripts/verify.mjs` and CI set one per run so that the artifact check afterwards (`scripts/artifact-secrets.mjs`, ARV-152) can look for those passwords in the report and the test output; they also derive the run's simulator, mock AMAN, ACRIS and Cronz keys and the validation reader's password from it (`artifact-secrets.mjs --env`), which the config keeps when they are set, so the check knows them too. |
| `ARIVA_SMOKE_*` | set by the config and global setup | The smoke project's target and credentials (`tests/smoke/support/target.ts`; wiki 04 section 8.1 lists them). In this run the config overwrites the addresses and the account and global setup the zone, device and display values, so values left in the shell from a deployed run are never used here. |

The `ARIVA_E2E_*` addresses point the suites at another port or host of this machine only (ARV-128): the suites write, attack and load, so `playwright.config.ts` refuses to load when a host, the web app, Stream, smtp4dev, Redis, Kafka or the database is not `localhost`, `127.0.0.0/8` or `[::1]`, and names the refused target (never its address, which may hold a password). A deployed environment is checked with the read-only smoke suite: `npm run test:smoke` with the `ARIVA_SMOKE_*` variables (wiki 04 section 8.1). Never run the suites with a port-forward or tunnel open on the hosts' ports (51001 to 51005, 51011, 51020): a deployed host would answer on a local address. Global setup checks first, before it writes anything, that every host answers as a vm-local host of this run: a CORS preflight from `http://localhost:51011` (allowed by vm-local's settings only) for the API hosts and the web app's `/api` proxy, and this run's simulator read key for the simulator (`tests/support/local-hosts.ts`, tested in `tests/api/local-hosts.spec.ts`). Never point the database, Redis or Kafka of an E2E run (`Database__*`, `ARIVA_E2E_*` or the hosts' connection settings) at a tunnel or port-forward to a deployed store either: the hosts the run starts are genuinely vm-local, so the check above passes, and they run SchemaUpdate and seed the development accounts (known passwords) into whatever store they reach before any test starts. A lasting guard is in Phase 3 (ARV-180).

The E2E accounts (`e2e.admin`, `e2e.border`, `e2e.terminal`, `e2e.handler`, `e2e.pending`, `e2e.changer`, `e2e.lockout`, `e2e.unlock`) are created by Ariva.Api.Main from `Auth__DevelopmentUsers__*`, which `playwright.config.ts` derives from a random seed per run; no password is committed, and the log scan in `global-teardown.ts` fails the run if any of them reaches a host log. `tests/support/global-setup.ts` runs `Ariva.Api.Main --create-break-glass` (or `--rotate-break-glass` on a reused database) once the hosts are up and writes the credential to the git-ignored `.e2e-keys/break-glass.txt`. The hosts run with `Auth__TotpRequired=false`, because the general accounts sign in many times a minute in parallel and the TOTP replay guard would refuse that; `e2e.totp` (seeded with a known secret) and `e2e.enrol` test TOTP itself, `e2e.stepup` (also seeded) tests step-up, `e2e.secadmin` (a SystemAdministrator with TOTP) runs the administration tests, and `e2e.siteadmin` with `e2e.siteuser` run the site access tests. Accounts carry site bindings (`Auth__DevelopmentUsers__N__Sites__M`, `*` for every site): border E2E1, terminal E2E2, handler both, the administrators every site; the seed creates the sites. Sign-in, refresh and logout calls go through Node's `fetch` (`call()` in `tests/support/accounts.ts`) rather than Playwright's request context, whose cookie jar would keep the refresh cookie and send it with the next sign-in, which revokes that session. The hosts trust loopback as a proxy in this run only, so each test sets its own `X-Forwarded-For` and the per-address sign-in limit applies where a test means it to.

### Keeping secrets out of the report (ARV-152)

Playwright keeps an expect's message as the step title even when the assertion passes, and a `fill` step's title holds the typed value. Check a status with `expectStatus` or `expectStatusIn` (`tests/support/expect-status.ts`), which add the answer to the message only on a wrong status, redacted; never pass `await x.text()`, `await x.json()` or a variable holding an answer as an expect message (`node scripts/expect-messages.mjs` fails on it). Type passwords, TOTP codes, recovery codes and keys with `fillSecret` (`tests/support/web-auth.ts`); it keeps them out of step titles, while a failed page's error context still lists input values, which the artifact check catches. Keep secrets out of step titles, annotations, attachments and console output too, and send a token, key or password that belongs in a query through `call` (`tests/support/accounts.ts`, Node's fetch, no step), never a request context, whose step keeps the URL with its query; navigate to a display with its key in the fragment of an absolute address (`${webUrl}/display?...#key=...`), since a relative address is kept whole; and build a made-up token or key at run time, since the report keeps the source lines around each step (the same check fails on all of these). After a run, `node scripts/artifact-secrets.mjs` (or `node scripts/verify.mjs artifacts` from the repository root) names every file of the report or the test output that holds a credential, by kind, never the value; `verify.mjs` runs it after each Playwright run and CI before each upload.

## In CI

`Platform/Cloud/Ariva.Cicd/AzureDevOps/Common/Analyze-solution.yaml` runs, after the security gate, the .NET build, the unit tests and the web checks: `npm ci`, `npx playwright install --with-deps chromium` and `npx playwright test` in this folder with `CI=true` and `ARIVA_E2E_CONFIGURATION=Release`, against a PostgreSQL container (`timescale/timescaledb-ha:pg17-ts2.30`) started by the pipeline; `.github/workflows/ci.yml` does the same with a service container and posts the failing tests on the pull request. The Playwright HTML report (`playwright-report/`) and `.verify/security-report.md` are published as build artifacts, also when a step fails.
